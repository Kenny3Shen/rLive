# 视频下载

rLive 的 B 站视频下载：在播放页选画质后，把 DASH 的视频轨与音频轨下载到本机，再无转码合并成一个可直接播放的 MP4。下载任务由 Rust 后台队列管理，切走页面或最小化窗口都会继续；开关应用也不会丢任务，未完成的条目可在下次启动后继续。

桌面端与 Android 都支持。两端共用同一套 Rust 队列与断点续传，只有收尾合并不同：桌面端在进程内用 FFmpeg 做流复制，Android 没有链接 FFmpeg，改用 Kotlin 的 `MediaExtractor` + `MediaMuxer` 重封装。浏览器预览没有 Tauri IPC，不提供下载。

## 一、入口

- **播放页「更多操作」**：顶部 HUD 的磁贴菜单里有「下载」，点开后选择画质并确认；桌面与移动端都从这里进入。
- **桌面端底部控制栏**：播放页桌面布局的底栏也有一枚「下载」按钮，效果相同。
- **下载页签**：视频页头部「推荐 / 热门 / 番剧 / 影视 / 下载」的最后一个页签，地址是 `/video?tab=download`。这里不是内容页，而是下载任务管理表面，因此没有分区条，也不参与列表请求。

播放页只对可下载的 B 站稿件显示入口：普通 UGC 视频与番剧 / 影视单集都能下载，直播、IPTV 与短视频流不在范围内。一个任务对应**当前这一集 / 这一个 P**，不会自动把整季或整个合集都排进队列。

## 二、画质与开始下载

画质列表来自当前播放页的 `accept_quality`，默认选中播放器当前画质。当前账号不可用的档位会置灰，不能选择；匿名或非大会员身份能下载的最高档位，与在线播放能看到的上限一致，rLive 不会绕开账号权限去请求更高档位。

确认后任务立即进入队列：

1. 后端用当前 Cookie、代理与请求头解析一次 playurl，拿到视频轨、音频轨的完整分片表。
2. 按字节区间顺序下载 `video.m4s` 与 `audio.m4s`。两条轨本身就是完整 fMP4 文件，支持 HTTP Range 断点续传。
3. 两条轨都完整后进入「合并中」：桌面端在进程内用 FFmpeg 做流复制（不重新编码）；Android 通过 `RliveVideoMuxPlugin` 用 `MediaExtractor` 读两条轨、`MediaMuxer` 写 MP4，同样不解码、不转码。
4. 合并成功后改名为 `<标题>.mp4`，任务进入「已完成」。

同一稿件、同一 P 重复点击不会重复创建任务：未完成的条目会被复用，已完成或正在进行的条目直接返回原任务。失败或已暂停的条目再次发起下载时，如果换了画质，会丢弃旧画质的分片重新下载，避免把两条不同 profile 的分片拼进同一个文件。

## 三、下载页签

页面分成「下载任务」与「已完成」两组：

- **下载任务**：排队、下载中、已暂停、合并中、失败，以及应用退出时被中断的条目。
- **已完成**：合并完成的 MP4，可「播放」（交给系统播放器）或「文件夹」（在文件管理器中定位）。「文件夹」只在桌面端出现，Android 没有可浏览应用私有目录的文件管理器入口。
- **暂停 / 继续**：暂停在下一个数据块边界生效，已经写入的分片保留；继续时从断点续传。合并阶段不能暂停。
- **重试**：失败条目保留已下载的字节，重试会从断点继续；换画质则从头下载。
- **删除**：二次确认后删除该条目的整个目录与记录。正在下载的条目会先等后台写入停止，再删目录；Windows 上不会留下被占用的半成品文件。

队列**同一时刻只下载一个任务**，其余按创建顺序排队。暂停或失败不会阻塞后面的条目；当前任务结束后自动开始下一个。进度通过 Tauri 事件推送（约每 500ms 一次），页面在存在活动任务时还会低频轮询兜底，因此切回页面能立即看到最新状态。

## 四、输出与存储

下载根目录是应用数据根目录下的 `downloads/`（与录制库同级）。桌面端可在下载页点头部「打开下载目录」定位；Android 上这个按钮不显示，目录位于应用私有沙箱 `<dataDir>/rlive/downloads`，应用外不可直接浏览。每个任务一个自包含目录：

```
downloads/
  <任务 id>/
    entry.json          # 任务元数据与最终文件名
    video.m4s.part      # 视频轨临时文件
    audio.m4s.part      # 音频轨临时文件
    output.mp4.part     # 合并中的临时文件
    <标题>.mp4          # 完成后的成片
```

任务 id 由稿件身份生成：普通视频是 `<bvid>-<cid>`，番剧 / 影视是 `ep-<ep_id>-<cid>`，因此同一稿件换集不会互相覆盖。文件名取稿件标题，去掉跨平台非法字符与控制字符，并截断到 80 个字符；Windows 保留名会自动加后缀。

成片是标准 MP4 容器内的原始音视频流，没有二次编码，画质与下载到的 DASH 轨一致。文件名与`entry.json`是恢复队列的唯一依据：应用启动时会扫描 `downloads/`，把上次处于下载中 / 合并中的任务改为「已暂停」并提示可继续，排队中的任务则自动重新入队；已完成但文件被移动或删除的条目会标为失败。

Android 的下载目录在应用私有沙箱内，`file://` 不能直接交给外部应用。点「播放」时 Rust 通过 `RliveVideoMuxPlugin` 的 `openFile` 命令，由 `FileProvider` 把文件换成 `content://` 再发 `ACTION_VIEW`，只授予一次性读权限；没有能打开 MP4 的应用时返回错误提示。

## 五、限制

- Android 端依赖系统 `MediaMuxer`，只做容器重封装；B 站两条 DASH 轨都是完整 fMP4，实测路径与桌面一致，但不同厂商 ROM 的解复用器差异仍可能影响部分冷门编码。
- 一个任务只下载当前这一集 / 这一个 P，不提供整季批量下载，也不支持下载字幕与弹幕。
- 下载文件只交给系统播放器打开，不进入应用内的 VOD 播放页，也不支持在 rLive 中续播或加载弹幕。
- 画质上限受当前 B 站账号权限约束；版权或地区受限的番剧 / 影视，playurl 本身就会失败，任务会显示上游错误。
- 下载不占用播放器的代理会话，但会占用网络带宽；同时只跑一个任务，避免多任务争用连接。
- 应用退出时未完成的任务会保留在磁盘上，重新打开后需要手动「继续」或自动从排队态恢复；不会在后台守护进程中继续下载。
