# 性能优化

记录 rLive 播放链路的性能问题、根因、优化手段与**实机测试**前后对比。所有数值均基于
Windows 主窗口（WebView2 + CDP）真机采集，非模拟或估算。

## 测试环境与方法

- **设备**：Windows 主窗口 dev 会话（`bun run tauri dev`，WebView2 CDP 9223），经 `scripts/sync-to-windows.sh` 同步镜像 `D:\dev\rLive` 后构建运行。

> 弹幕链路（侧栏列表、渲染层密度、时间轴重建）的独立压测与前后对照见[弹幕性能实测](弹幕性能实测.md)。
- **接入**：`playwright-cli attach --cdp=http://127.0.0.1:9223`，在真实主窗口页面（`window.__TAURI_INTERNALS__` 存在）上直接 `invoke` 后端命令并计时。
- **采样**：每项指标多次运行取中位数；后端取流类指标先跑一次预热吃掉冷启动 DNS/TLS，再计入正式样本。
- **网络**：家用宽带直连 B 站 CDN，无系统代理；不同时段 CDN/服务端负载会带来抖动，因此关注**同一会话内可比**的量，而非绝对秒数。
- **测试稿件**：B 站推荐流首项（4K 与 1080P 均覆盖），`media_cache: true`。

> [!NOTE]
> 取流类指标（`video_get_play_info`）含 playurl 签名请求 + 双轨 sidx + 代理启动的网络往返，绝对值随 CDN 波动明显（同稿件单次 390–1006ms）。因此代理启动这类**本地开销**用隔离基准单独测量，避免被网络抖动淹没。

## 问题一：VOD / 短视频首次加载耗时长

### 根因

`video_get_play_info`（`src-tauri/src/commands/video.rs`）里 playurl + 双轨 sidx 已用 `tokio::join!` 并行，但随后**三条代理串行 `await` 启动**：`start(video)` → `start(audio)` → `start_text(mpd)`。video 与 audio 两条互不依赖（各绑一个回环端口 + 各建一个 native-tls 客户端），却被串成一条链；mpd 依赖前两者返回的本机 URL，必须最后。

### 优化

video/audio 两条代理改为 `tokio::join!` 并发启动，mpd 仍最后串行（`commands/video.rs`）。仅音频模式保持单条启动不变。

### 实机数据（本地 proxy start 隔离基准，8 次中位数）

| 场景 | 串行两次 | 并行两次 | 改善 |
| ---- | -------- | -------- | ---- |
| `stream_proxy_start` 本地开销 | 8.3 ms | 4.9 ms | **约 −41%（省 ~3.4 ms）** |

单次 `stream_proxy_start` 本地开销实测中位 3.7 ms（min 3.3 / max 4.4）。首屏取流路径上省掉的是一次串行的本地 bind + TLS 客户端构建往返；在网络往返占主导（数百 ms）时，这部分是稳定但较小的收益，且并行化不引入额外风险。

> 说明：`video_get_play_info` 端到端中位数受 CDN 抖动主导（4K 稿件 245–2270ms，1080P 稿件 390–1006ms），无法作为并行化收益的干净证据，故用本地隔离基准衡量该项。

## 问题二：短视频加载第二分片耗时长、甚至卡死失败

### 根因（最严重）

`stream_proxy` 的上游转发客户端 `build_stream_client`（`src-tauri/src/stream_proxy.rs`）此前**刻意不设任何读超时**，只有 `connect_timeout(10s)`。转发循环 `while let Some(chunk) = stream.next().await` 对每个 chunk 也没有逐块超时。

当 CDN 在传第二分片途中 stall（既不发字节也不关连接）时：
1. reqwest 永远不会报错，那条连接就此挂死；
2. 更糟的是 `pool_max_idle_per_host(2)` 会把这条**半死连接留在连接池**里；
3. dash.js 重取同一分片复用到这条池化连接，就再次挂死，表现为「第二分片卡死失败」。

### 优化

给 `build_stream_client` 加 `read_timeout(SEGMENT_READ_TIMEOUT = 15s)`（相邻两次读之间的最大间隔，不是总时长）。stall 的读在 15s 后报错，reqwest 随即把这条死连接丢出池外；dash.js/原生媒体元素的下一次重取拿到新建连接即可自愈。健康的直播/VOD 流字节持续到达，永远触及不到这个间隔上限，因此对正常播放零影响。

15s 的取值：远高于实测健康分片的块间到达延迟，避免误杀慢速 CDN；又足够短，让卡死能在用户放弃前自动恢复。

### 实机验证

- `stream_proxy` 单元测试全绿：`cargo test --lib stream_proxy` → **27 passed, 4 ignored**（含并发 Range、缓存命中、代理转发等回归）。
- E2E 转发验证（真机）：并行启动后 MPD 可用（含 video/audio 轨），init 段 Range `bytes=0-1000` 经代理返回 **206**，耗时 241ms，转发路径正常。

> 卡死属偶发的 CDN stall 触发，无法稳定复现计时；此项以「消除永久挂死、恢复自愈能力」为验收标准，而非耗时数字。修复前该连接永不恢复，修复后 15s 内必被丢弃重连。

### 后续：分片续传与 502

15s 读超时只保证死连接最终被丢弃，用户仍会看到约 15s 的转圈。2026-10-29 实机连刷短视频（约 80 次切换出现 2–3 次）对应的日志是 m4s 分片中途截断（WebView 侧 `ERR_CONTENT_LENGTH_MISMATCH`）或发送阶段失败（代理不写任何字节就断开，WebView 侧 `ERR_EMPTY_RESPONSE`）。现在代理自己补救：

- **分片续传**：仅对带单一 `Range`、上游回 206 且 `Content-Range` 与请求一致的非 HLS GET 生效。块间停顿超过 `SEGMENT_STALL_TIMEOUT`（4s）或读出错时，按 `Range: bytes={已转发位置}-{end}` 新开请求续传，最多 `SEGMENT_RESUME_ATTEMPTS`（2）次；续传响应必须是 206 且区间匹配，否则放弃并断开下游。首段带强 `ETag` 或 `Last-Modified` 时续传请求同时发 `If-Range`（弱 `ETag` 按 RFC 9110 不用于 `If-Range`），续传响应的验证器与首段不一致同样视为被拒，避免 URL 内容变化后把两段字节拼进同一分片。客户端看到的仍是同一个连续的 206 响应体，拼接完整的分片照常写入磁盘缓存。200 全量、FLV、HLS 清单与 `force_hls` 直播流不变。
- **发送重试与 502**：分片请求发送失败立即重试一次；任何请求最终发送失败都回 `502 Bad Gateway`（固定文本，不回显带签名的上游地址），不再出现空响应。图片代理 `image_proxy` 的发送或读取 body 失败同样回 502。
- **遥测**：`stream_proxy_telemetry` 新增 `upstream_resumes`（续传请求数，同时计入 `upstream_requests`）。

回归测试在 `src-tauri/src/stream_proxy/cache_tests.rs`：截断与停顿后从已转发位置续传并落缓存、上游忽略续传区间时放弃且不落缓存、上游不可达时重试一次后回 502。

## 问题三：VOD 刷新按钮耗时长

### 根因

发现页列表是 `useInfiniteQuery`。刷新按钮此前调用 `listQuery.refetch()`，而 TanStack 对 infinite query 的 `refetch()` 会把**当前已加载的每一页按顺序串行重取**。用户滚得越深，刷新越慢——重取页数与已加载页数成正比。

### 优化

刷新改为 `queryClient.resetQueries({ queryKey })`：把查询重置到 `initialPageParam` 并**只重取首页**，把刷新成本从 O(已加载页数) 降到 O(1)。同时用独立 `manualRefreshing` state 表达进行中状态（reset 后是 `isLoading` 而非 `isRefetching`）。语义上也更贴合「刷新」——把信息流从头重拉，旧的尾页本就该丢弃（`src/features/video/VideoPage.tsx`）。

### 实机数据（`video_get_recommend` 串行重取，真机）

| 已加载页数 | 优化前（串行重取全部页） | 优化后（只重取首页） | 改善 |
| ---------- | ------------------------ | -------------------- | ---- |
| 1 页 | 1846 ms | ~1736 ms | 基本持平 |
| 3 页 | 5219 ms | ~1736 ms | **约 −67%** |
| 5 页 | 8676 ms | ~1736 ms | **约 −80%** |

优化后刷新耗时不再随浏览深度增长，恒定为一次首页 IPC 往返（约 1.7s，其中大头是 B 站推荐接口本身的网络往返）。翻得越深收益越大：第 5 页时从 8.7s 降到 1.7s。

> 这里测得的「~1736 ms」当时已经包含三次串行取批（见问题四），优化后同一指标降到 ~800 ms。

## 问题四：推荐流刷新仍要 ~2s（APP 主 feed 串行取批）

### 根因

`video_get_recommend` 走 APP 主 feed（`app.bilibili.com/x/v2/feed/index`）。该接口无页码也无游标，每次只返回 9~11 条，凑够默认的 20 条必须多批。旧实现 `collect_app_feed` 最多**串行** `await` 三批（`MAX_BATCHES = 3`），因此固定付出三倍往返。

单批耗时本身不是网络问题，而是**上游的设备个性化路径**：同一请求带 `buvid` 头实测约 500ms，不带约 140ms（6 轮交错取中位）。Rust 侧实测拆解（临时 `eprintln` 计时，仅用于定位，未保留）：`AppAuth::new` 约 100ms（TV 凭据校验），`ensure_buvid` 0ms（进程内缓存命中），单次 `auth.feed` 约 440~640ms，三批合计约 1.8s。上游 `curl` 对照同样复现 500ms 档位，确认不在本机链路。

### 优化

把整波批次改为并发发起：`futures_util::future::join_all((0..FEED_BATCHES).map(|_| fetch()))`，再按批序解析、去重（`src-tauri/src/sites/bilibili/video/app_feed.rs`）。

- **批次可并发是主 feed 特有的**。它与 story feed 的关键差异：主 feed 的批次彼此独立，并发取回的是不同窗口；story 的轮换游标在**服务端按时间推进**，并发只会拿到同一窗口的重叠切片（实测 3 路并发 15 条只有 6~11 条唯一），所以 story 必须保持串行。
- **批次 4 而不是 3**：并发窗口仍有少量重叠，3 批的去重后唯一条数最低探到 18（低于默认目标 20）；4 批把最低唯一条数抬到 28，且请求数只多一个。
- 语义不变：首批失败仍直接报错、后续批失败仍返回部分结果并置 `has_more = true`；目标条数满足后仍提前停止处理后续批（请求已发出，但不再消耗结果）。

### 实机数据（真机主窗口，`video_get_recommend`，默认目标 20 条）

| 形状 | 单次中位 | 范围 | 去重后唯一条数 |
| ---- | -------- | ---- | -------------- |
| 串行 3 批（优化前） | **1950 ms** | 1872–2018 ms | 每轮恰好 20（受目标截断） |
| 并发 4 批（优化后） | **822 ms** | 770–880 ms | 中位 30，最低 28（40 轮全部返回满 20 条） |

并发形状 A/B（同一次会话内交错，各 15~20 轮）：并发 3 批约 780ms，并发 4 批约 820ms，并发 5 批约 850ms——时延不再随批数线性增长（同一波往返），4/5 批的额外成本只有并发连接的排队。

### 刷新链路端到端对照

原刷新性能夹具（现已移除，可从 Git 历史查阅）真实点击刷新按钮，取 5 轮中位；以下仅为当时版本的历史测量，不代表当前性能：

| 指标 | 优化前 | 优化后 | 变化 |
| ---- | ------ | ------ | ---- |
| `video_get_recommend` IPC | 2071–2152 ms | **811–880 ms** | 约 −60% |
| 卡片重填（clear → refill） | 约 2200–2300 ms | **885–982 ms** | 约 −57% |
| 封面图片（同轮 N 张） | 约 20 张 / 8.3s 合计 | 14–20 张 / 4.3s 合计 | 随上游轮换波动 |
| 长任务 | 1 次 / 123–142 ms | 1 次 / 94 ms 合计 | 量级不变 |

封面图每轮仍全部 `diskCache:false`：刷新拿到的是新稿件、封面 URL 也全新，重新下载是预期行为而不是缺陷。剩余约 800ms 中，约 500ms 是上游单批的设备个性化路径（见上），其余是解析与 IPC；刷新链路的**应用侧串行等待已消除**。

> 问题三把「一次首页 IPC 往返」当作不可再压缩的底座（当时约 1.7s），问题四说明这个底座本身还有一半是应用自己串行取批造成的。

## 问题五：本轮慢加载调查与实机验证

> [!IMPORTANT]
> 2026-11-17 已在 Windows Debug 真实主窗口完成修复后复测。并发、取消、重复请求和刷新回顶行为通过当前样本，未发现语义回归或媒体错误；但直播、VOD 和推荐页的端到端等待仍有数秒，不能因行为修复通过而宣称加载已全部正常。网络、代理、缓存和运行时长均未做固定 A/B，本文不计算纯性能改善率。完整脱敏数据见 [`loading-fix-2026-11-17.json`](../bench/loading-fix-2026-11-17.json)。

复测环境为 WebView2 `157.0.4341.46`、Vite dev / React development / StrictMode、窗口 `1280×720`、原代理与画质设置、未清缓存。Windows 镜像与冻结工作区的 917 个源码文件逐项比较，内容差异为 0；运行的后端在全部 Rust 改动写入后启动，前端由 Vite 应用最新改动。

### 直播首页深分页刷新

直播首页的推荐流和分区列表都使用无限查询。手动刷新直接调用 `refetch()` 时，TanStack Query 会按页顺序重取当前已加载的全部页面，因此用户浏览越深，等待越长。

修复前在同一 Windows Debug 主窗口暖缓存中加载哔哩哔哩推荐流到 3 页、共 173 张卡片，首次加载三次请求分别约 4159 ms、4055 ms、4710 ms。完成加载后执行深度 3 刷新，刷新按钮约 21 ms 进入忙碌态；刷新阶段的 page 1、page 2、page 3 请求分别约 8190 ms、4001 ms、2794 ms，合计 14985 ms，与约 15124 ms 的忙碌总时长相差 139 ms。刷新时 page 1 本身比刚才的首次加载慢，因此不能把总耗时和分页数机械相乘；这里的可靠证据是三个请求按顺序累积并覆盖了整个 busy 周期。

当前修复把手动刷新改为 `queryClient.infiniteQuery({ pages: 1 })`：

- 刷新前取消正在进行的补货，只请求新的第一页。
- 新首页成功前继续显示原有多页列表，避免刷新时清空内容。
- 成功后用新首页替换全部旧页，后续分页从新的第一页重新开始。
- Tauri IPC 不响应取消时，查询函数在结果返回后检查取消信号并丢弃迟到的旧页，防止旧 page 2 覆盖新首页。
- 刷新期间暂停无限加载哨兵，避免深滚动留下的旧 sentinel 取消首页刷新并重新取旧页。
- 成功后先在 `requestAnimationFrame` 中回到顶部，回顶完成才结束忙碌态并重新启用哨兵；之后是否补货由新首页长度和用户实际停留位置决定，不会主动串行取 page 2、page 3。
- 刷新失败时保留旧多页数据，Query 回到 `idle`，同时保留 `isRefetchError`；用户可直接再次刷新，失败不会永久占住并发刷新表。
- 忙碌状态按 query key 的 hash 分别记录，切换分类或账号版本后不会继承旧视图的刷新状态，旧请求结束也不会关闭新视图的 busy。
- 只有发起刷新的 query 仍由当前视图观察时才回顶；切换分类或账号后，旧请求结束不会滚动新视图。

最终样本在 page 1、2、3 共 138 张卡片、`scrollTop=2965` 时执行刷新。刷新按钮在 7 ms 内进入忙碌态，旧卡片继续显示；page 1 用时 **3366 ms**，忙碌总时长 **3451 ms**，期间只请求 page 1。回顶调用发生时按钮仍禁用，调用后 24 ms 才结束忙碌并重新启用哨兵。成功静置 8 秒后仍只有 page 1，没有自动串补；用户之后滚到新首页尾部时，page 2、page 3 分别用 588 ms、646 ms。

另在刷新进行中切换分类：推荐刷新约 44 ms 后路由切到“全部网游”，旧请求在 1299 ms 后完成，但没有触发旧视图回顶，也没有改写新分类的数据或滚动位置。该结果验证的是请求所有权与交互语义；由于只有一个网络窗口，不计算改善百分比。

### 视频推荐刷新

最终样本对视频推荐连续执行三次真实手动刷新，每次都只发出一个 page 1：

| 轮次 | page 1 / 忙碌时长 | 自动 page 2 | page 2 启动相对忙碌结束 |
| --- | --- | --- | --- |
| 1 | 1866 ms / 1921 ms | 2239 ms | +256 ms |
| 2 | 2399 ms / 2452 ms | 3227 ms | +264 ms |
| 3 | 2846 ms / 2898 ms | 2962 ms | +263 ms |

自动补货发生在手动忙碌结束之后，按钮已恢复可操作，因此没有把后续内容填充误计入刷新响应。可是从点击到当前视口所需内容补齐仍可能累计到 4–6 秒，仍属于可感知的秒级等待。开发态冷导航还观察到两次 page 1 请求（3622 ms、4657 ms），伴随 StrictMode／预取路径；三次手动刷新均为单请求，不能把冷导航重复直接当成生产行为。

### 哔哩哔哩重复授权校验

实机调查观察到一次重复 OAuth 校验耗时 5716.6 ms。该等待发生在同一份凭据被连续验证的路径上，不属于页面渲染长任务。

当前实现复用最近一次成功的 OAuth 校验结果 5 分钟：

- 缓存位于进程内，只保存最后一份成功结果。源凭据或解析后凭据、`mid`、`expires_at` 和代理路由必须继续匹配，且服务端权威期限未到时才可命中。
- 并发分页或刷新通过单飞 gate 合并，只执行一次远端校验或刷新；等待者复用同一完成结果，不各自排队发起慢请求。
- 失败、风控和网络错误不缓存。清除授权或请求明确返回 `auth_required` 时立即作废对应缓存，避免失效凭据继续被复用。
- 服务端返回的 `expires_in` 仍是权威期限，校验成功时会将其换算成本机绝对时间并同步到缓存和数据库快照；`renewed` 只在 token 或账号身份真实轮换时成立。

CDP 只能观察 WebView 发出的 IPC，看不到 Rust `reqwest` 随后发往 passport 的内部请求，因此最终实机样本无法把授权命中单独拆成耗时。后端回归已验证第二次同凭据授权会直接命中缓存；当前不能把 5716.6 ms 视为已经消除的端到端时长。

### 哔哩哔哩重复 WBI 密钥请求

每次 IPC 命令都会创建新的站点实例。实例级 WBI 密钥缓存无法跨命令复用，详情、清晰度和播放地址连续读取时会重复请求 `nav`；当前实机经代理的一次 `nav` 约需 2.1 秒。

当前实现增加进程级 30 分钟 WBI 密钥缓存：

- 作用域同时绑定代理路由和 Cookie 的 SHA-256 摘要，只保存摘要，不把 Cookie 原文放进静态缓存。
- 同一作用域并发创建多个站点时单飞执行 `nav`，其他请求等待并复用同一密钥。
- 只有成功解析出非空 `img_key` 与 `sub_key` 才写入缓存；HTTP 错误、风控、解析失败和空字段都不缓存。
- 密钥和摘要只驻留内存、不写入配置或磁盘；作用域变化或 30 分钟到期后重新获取。

实机中同一固定房间的详情冷、热两次 IPC 分别为 **3029 ms、1100 ms**。该差值是整个房间详情链路的方向性观察，包含上游和代理波动；CDP 不能证明差额全部来自 WBI 命中，因此不把它写成缓存收益。

### VOD 首片响应头与正文耗时分离

一轮 VOD 样本的首个媒体请求约 210 ms 取得响应头，但正文继续等待约 15.67 s，随后才完成。仅看响应头会把该请求误判为正常，实际用户等待发生在响应体传输或上游连接停滞阶段。

当前已验证 VOD 媒体分片的整片换源路径：

- 只对同一 representation 有合法备用地址、长度不超过 32 MiB 的闭区间 GET 启用。代理在向下游写响应头前读取完整候选分片。
- 候选必须返回 `206`、`Content-Range` 与请求精确一致；若带 `Content-Length` 也必须一致。正文必须读到干净 EOF 且总字节数精确，截断、超长、读取错误或协议矛盾都会丢弃整个候选。
- 正文连续 4 秒没有收到新字节时丢弃当前候选，并向备用地址重新请求原来的完整 Range；不把不同节点或不同版本已收到的前缀拼成一份响应。
- 响应头单次等待上限为 4 秒、所有候选累计等待上限为 8 秒；从首个候选请求到正文收齐的整轮总预算为 20 秒。候选集耗尽后明确返回 `502`，不重新进入流式路径反复试同一批坏节点。
- `stream_proxy_telemetry.last_vod_failure_cause` 记录最近一次被丢弃候选的稳定类别，包括 `body_stalled`、`body_incomplete`、`content_range_mismatch`、`content_length_mismatch` 和预算耗尽等；后续候选成功时仍保留该诊断。

修复后的固定 VOD 使用真实视频搜索结果卡片进入，页面画质为 1080P、`media_cache=true`，没有降低画质或清缓存：

| --- | ---: |
| 卡片 click → route | 13 ms |
| `video_get_play_info` | 2597 ms |
| click → 首个视频正文 Range 开始 | 4604.8 ms |
| 首个视频正文 Range 完整下载 | 2731.7 ms |

### VOD 开发态重复取流与无主 IPC

React 19 开发态 StrictMode 会快速卸载并重订阅 effect。TanStack Query 只有在 `queryFn` 首次读取取消信号后才把 observer 退订视为支持取消，而 Tauri IPC 本身不能中途撤销。若在 signal 等待期直接启动 IPC，真实离开页面或快速换内容会留下没有页面所有者的取流请求，多个入口还可能让同一首开内容重复进入后端。

当前取流查询通过 `VideoPlaybackSessions.acquireForQuery` 收口：

- `queryFn` 调用栈内先同步预留 owner 轮次并清理旧 pending，再延迟一个微任务读取 Query 的 signal。
- 微任务恢复后核验本轮 epoch 仍是最新、owner 没有被 `clear()` 或新内容替换、signal 尚未取消；全部成立才启动 Tauri IPC。
- StrictMode 对同一 owner 与同一 query 的重订阅复用原 `fetchPromise`，只发起一次初始取流；不同页面 owner 即使内容相同也不共享。
- 真实卸载若在 signal 等待期发生，返回 `AbortError`，不会在 clear 后另行启动无人拥有的 IPC。
- `onSettled` 包在最终 Promise 外层，成功、失败、取消和预留失效都会结算自动恢复令牌。播放器 UI、Video.js 媒体源和 StrictMode 开关均未改动。

最终固定 VOD 进入本轮页面时只有一次同参数 `video_get_play_info`，13 ms 内完成路由，后续 init 请求分别用 2 ms、3 ms 命中已预取字节。观看结束后返回搜索页，5 秒观察窗口内没有新增 `video_get_play_info`，代理由一次 1 ms 的 `video_stop_play` 停止。开发态重复请求与无主 IPC 在当前样本中未复现。

## 问题六：内容返回后封面加载慢（2026-11-18）

列表 IPC 返回的是图片地址。图片独立下载和解码，接口完成并不代表封面已经显示。本轮在 Windows Debug 主窗口检查了这段链路，确认原实现把各平台图片集中到同一个 HTTP/1.1 回环 origin；WebView2 的连接槽被占满后，后续图片等待前面的响应。B 站视频列表还直接使用原始封面，增加了每个连接槽占用的时间。

### 实现变化

- 图片代理固定启动四个随机回环端口，共享一个 `reqwest::Client` 和一个磁盘缓存。前端按规范化后的上游 URL 稳定选择 origin，增加可同时发送的请求数；`revision` 不参与分流，列表返回仍使用相同的浏览器缓存键。
- 继续缓冲完整图片并返回准确的 `Content-Length`，保留 Windows WebView 的响应兼容性。单纯增加 keep-alive 不能消除单 origin 的连接数限制，因此本轮采用多个 origin。
- B 站视频和番剧列表封面使用 `@480w.webp`，保持原图比例，已有图片变换和 query / fragment 保留。评论图片保持原图。公开热门接口同一样本原始 JPEG 为 1920×1080、323,000 B，480×270 WebP 为 15,660 B，体积减少约 95.2%；这是一张图的大小对照，不代表所有封面都有相同降幅。
- 直播与视频卡片使用 `decoding="async"`，保留 `loading="lazy"`。`decoding` 是浏览器提示，本轮不根据该属性直接判定解码线程，也不把网络改善归因于异步解码。
- 图片代理初始化失败后可再次显式预加载；代理设置保存或配置重载后刷新 origin，旧请求的迟到结果不能覆盖新配置。

环境为 WebView2 `157.0.4341.60`、Windows Debug、Vite dev / React development、1280×720。未修改代理设置，未清应用磁盘缓存。完整脱敏数据见 [`image-loading-2026-11-18.json`](../bench/image-loading-2026-11-18.json)。

## 附：其他已落地的小优化

- 封面 `<img>` 的 `decoding` 使用 `async`（当前位于 `src/shared/components/MediaCard.tsx` 和 `RoomCard.tsx`），提示浏览器异步解码，避免要求图片解码与下一次绘制同步。浏览器具体调度方式需由 trace 验证，不能根据属性推断解码线程。
- **APP 推荐不再补齐发布日期（2026-10）**：补齐接口（`x/v3/fav/resource/infos`）实测被风控连续返回 412，即使先加进程级日期缓存与 5 分钟/30 秒冷却也仍会反复失败。日期只是首页卡片上的一行相对时间，因此整条补齐链路已移除：推荐每页少一次可选请求，也不会再为它付出 2 秒超时或冷却状态。只有 APP 推荐流的卡片不再渲染发布日期（`showPubdate={false}`），热门、分区榜、Web 推荐、搜索、相关视频、UP 投稿抽屉等自带日期的列表不受影响。
- **自适应侧栏把高频工作收口到单帧**：旧实现拖动时逐帧修改 grid 行高，暂停态约 `35fps`、`p95 41.7ms`。首版 transform 又在进入/退出时切换 `grid→block`、`relative→absolute` 并依赖 `:has()`，两个切换各产生约 `150ms` long task。最终方案从挂载起固定 block + absolute 骨架；按下只预备 aside 高度与 composer 补偿，拖动和惯性只写 transform，并仅在手势期间把这几个节点提升为合成层；松手同一任务写回真实占比再清临时状态（见[播放器技术文档](播放器技术文档.md)第 9 节）。按下预备/进入/结算最大 RunTask 约 `10–11ms`，样式重算最多 `7` 个元素，松手落位误差 `<0.01px`。
- **播放页去掉逐帧 React 提交**：Video.js time feature 播放时每个 RAF 都写 `currentTime`，控制栏进度条与时间文本每秒提交 50–80 次。`throttledTimeFeature` 包装原生 feature，只把逐帧的单字段写入节流到约 10Hz，seek/暂停/结束/时长变化等多字段同步立即发布；弹幕、ASR、续播上报直接读 `video.currentTime`，不受影响。侧栏页签 state 从播放页下沉到 `VideoSidebar`（播放页只保留不触发渲染的页签记忆），评论、相关视频、弹幕列表与评论发送区加 `memo`，切页签不再重渲染整页。模拟器（Android 16 x86_64、WebView 133、4:3 VOD、120Hz）：播放静止从约 `81fps` 且有 `65ms` long task 变为 `113–119fps`、约 10 次提交/秒、无 long task；相关↔评论切换从 `62–84ms` long task 变为无 long task；暂停态拖动同会话 A/B 中，手势期合成层把中位 `58fps` / `p95 33.4ms` 提升到 `86fps` / `p95 20.8ms`。模拟器播放态基线在 `76–119fps` 间漂移，播放中拖动不给绝对结论；暂停态拖动 `p95` 仍超过 120Hz 单帧预算，不能表述为 120FPS 达标，真机仍需验证。

## 已知限制

- `video_get_play_info` 端到端耗时仍由 B 站 playurl + CDN sidx 的网络往返主导，本轮优化针对的是应用可控的本地开销与失败自愈，无法压缩上游网络时延。
- 推荐流剩余约 850ms 同样由上游主导：单批带 `buvid` 约 500ms（设备个性化路径），并发只把这笔成本从三份摊成一份，不能消除它。上游不给页码/游标、每批只回 9~11 条也是外部约束。
- 列表 `staleTime=Infinity` 仅进程内有效，无跨会话持久缓存，重启后首次进页仍付一轮 IPC（本轮未改动，属可选后续项）。
- 第二分片「卡死」修复以恢复自愈能力为准，因其偶发、依赖 CDN stall，未附稳定耗时对比。
- APP 推荐条目没有发布日期，推荐页签的卡片因此不显示这一行；上游为何对补齐接口返回 412 尚无充分证据，本项目没有改身份、出口或补签名去绕过限制，而是直接去掉这项非必要信息。
- 本轮修复后的 Home page 1 仍为 3366 ms，视频推荐手动刷新为 1866–2846 ms，固定 VOD 首帧为 7712 ms、直播卡片首帧为 4829 ms；上层网络和服务仍带来秒级等待，当前行为正确不等于加载已恢复正常。
