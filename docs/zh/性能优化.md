# 性能优化

记录 rLive 播放链路的性能问题、根因、优化手段与**实机测试**前后对比。所有数值均基于
Windows 主窗口（WebView2 + CDP）真机采集，非模拟或估算。

## 测试环境与方法

- **设备**：Windows 主窗口 dev 会话（`bun run tauri dev`，WebView2 CDP 9223），经 `scripts/sync-to-windows.sh` 同步镜像 `D:\dev\rLive` 后构建运行。
- **接入**：`playwright-cli attach --cdp=http://127.0.0.1:9223`，在真实主窗口页面（`window.__TAURI_INTERNALS__` 存在）上直接 `invoke` 后端命令并计时。
- **采样**：每项指标多次运行取中位数；后端取流类指标先跑一次预热吃掉冷启动 DNS/TLS，再计入正式样本。
- **网络**：家用宽带直连 B 站 CDN，无系统代理；不同时段 CDN/服务端负载会带来抖动，因此关注**同一会话内可比**的量，而非绝对秒数。
- **测试稿件**：B 站推荐流首项（4K 与 1080P 均覆盖），`media_cache: true`。

> [!NOTE]
> 取流类指标（`video_get_play_info`）含 playurl 签名请求 + 双轨 sidx + 代理启动的网络往返，绝对值随 CDN 波动明显（同稿件单次 390–1006ms）。因此代理启动这类**本地开销**用隔离基准单独测量，避免被网络抖动淹没。

## 问题一：VOD / 短视频首次加载耗时长

### 根因

`video_get_play_info`（`src-tauri/src/commands/video.rs`）里 playurl + 双轨 sidx 已用 `tokio::join!` 并行，但随后**三条代理串行 `await` 启动**：`start(video)` → `start(audio)` → `start_text(mpd)`。video 与 audio 两条互不依赖（各绑一个回环端口 + 各建一个 native-tls 客户端），却被串成一条链；mpd 依赖前两者返回的本机 URL，必须最后。

### 优化

video/audio 两条代理改为 `tokio::join!` 并发启动，mpd 仍最后串行（`commands/video.rs`）。仅音频模式保持单条启动不变。

### 实机数据（本地 proxy start 隔离基准，8 次中位数）

| 场景 | 串行两次 | 并行两次 | 改善 |
| ---- | -------- | -------- | ---- |
| `stream_proxy_start` 本地开销 | 8.3 ms | 4.9 ms | **约 −41%（省 ~3.4 ms）** |

单次 `stream_proxy_start` 本地开销实测中位 3.7 ms（min 3.3 / max 4.4）。首屏取流路径上省掉的是一次串行的本地 bind + TLS 客户端构建往返；在网络往返占主导（数百 ms）时，这部分是稳定但较小的收益，且并行化不引入额外风险。

> 说明：`video_get_play_info` 端到端中位数受 CDN 抖动主导（4K 稿件 245–2270ms，1080P 稿件 390–1006ms），无法作为并行化收益的干净证据，故用本地隔离基准衡量该项。

## 问题二：短视频加载第二分片耗时长、甚至卡死失败

### 根因（最严重）

`stream_proxy` 的上游转发客户端 `build_stream_client`（`src-tauri/src/stream_proxy.rs`）此前**刻意不设任何读超时**，只有 `connect_timeout(10s)`。转发循环 `while let Some(chunk) = stream.next().await` 对每个 chunk 也没有逐块超时。

当 CDN 在传第二分片途中 stall（既不发字节也不关连接）时：
1. reqwest 永远不会报错，那条连接就此挂死；
2. 更糟的是 `pool_max_idle_per_host(2)` 会把这条**半死连接留在连接池**里；
3. dash.js 重取同一分片复用到这条池化连接，就再次挂死，表现为「第二分片卡死失败」。

### 优化

给 `build_stream_client` 加 `read_timeout(SEGMENT_READ_TIMEOUT = 15s)`（相邻两次读之间的最大间隔，不是总时长）。stall 的读在 15s 后报错，reqwest 随即把这条死连接丢出池外；dash.js/原生媒体元素的下一次重取拿到新建连接即可自愈。健康的直播/VOD 流字节持续到达，永远触及不到这个间隔上限，因此对正常播放零影响。

15s 的取值：远高于实测健康分片的块间到达延迟，避免误杀慢速 CDN；又足够短，让卡死能在用户放弃前自动恢复。

### 实机验证

- `stream_proxy` 单元测试全绿：`cargo test --lib stream_proxy` → **27 passed, 4 ignored**（含并发 Range、缓存命中、代理转发等回归）。
- E2E 转发验证（真机）：并行启动后 MPD 可用（含 video/audio 轨），init 段 Range `bytes=0-1000` 经代理返回 **206**，耗时 241ms，转发路径正常。

> 卡死属偶发的 CDN stall 触发，无法稳定复现计时；此项以「消除永久挂死、恢复自愈能力」为验收标准，而非耗时数字。修复前该连接永不恢复，修复后 15s 内必被丢弃重连。

## 问题三：VOD 刷新按钮耗时长

### 根因

发现页列表是 `useInfiniteQuery`。刷新按钮此前调用 `listQuery.refetch()`，而 TanStack 对 infinite query 的 `refetch()` 会把**当前已加载的每一页按顺序串行重取**。用户滚得越深，刷新越慢——重取页数与已加载页数成正比。

### 优化

刷新改为 `queryClient.resetQueries({ queryKey })`：把查询重置到 `initialPageParam` 并**只重取首页**，把刷新成本从 O(已加载页数) 降到 O(1)。同时用独立 `manualRefreshing` state 表达进行中状态（reset 后是 `isLoading` 而非 `isRefetching`）。语义上也更贴合「刷新」——把信息流从头重拉，旧的尾页本就该丢弃（`src/features/video/VideoPage.tsx`）。

### 实机数据（`video_get_recommend` 串行重取，真机）

| 已加载页数 | 优化前（串行重取全部页） | 优化后（只重取首页） | 改善 |
| ---------- | ------------------------ | -------------------- | ---- |
| 1 页 | 1846 ms | ~1736 ms | 基本持平 |
| 3 页 | 5219 ms | ~1736 ms | **约 −67%** |
| 5 页 | 8676 ms | ~1736 ms | **约 −80%** |

优化后刷新耗时不再随浏览深度增长，恒定为一次首页 IPC 往返（约 1.7s，其中大头是 B 站推荐接口本身的网络往返）。翻得越深收益越大：第 5 页时从 8.7s 降到 1.7s。

> 这里测得的「~1736 ms」当时已经包含三次串行取批（见问题四），优化后同一指标降到 ~800 ms。

## 问题四：推荐流刷新仍要 ~2s（APP 主 feed 串行取批）

### 根因

`video_get_recommend` 走 APP 主 feed（`app.bilibili.com/x/v2/feed/index`）。该接口无页码也无游标，每次只返回 9~11 条，凑够默认的 20 条必须多批。旧实现 `collect_app_feed` 最多**串行** `await` 三批（`MAX_BATCHES = 3`），因此固定付出三倍往返。

单批耗时本身不是网络问题，而是**上游的设备个性化路径**：同一请求带 `buvid` 头实测约 500ms，不带约 140ms（6 轮交错取中位）。Rust 侧实测拆解（临时 `eprintln` 计时，仅用于定位，未保留）：`AppAuth::new` 约 100ms（TV 凭据校验），`ensure_buvid` 0ms（进程内缓存命中），单次 `auth.feed` 约 440~640ms，三批合计约 1.8s。上游 `curl` 对照同样复现 500ms 档位，确认不在本机链路。

### 优化

把整波批次改为并发发起：`futures_util::future::join_all((0..FEED_BATCHES).map(|_| fetch()))`，再按批序解析、去重（`src-tauri/src/sites/bilibili/video/app_feed.rs`）。

- **批次可并发是主 feed 特有的**。它与 story feed 的关键差异：主 feed 的批次彼此独立，并发取回的是不同窗口；story 的轮换游标在**服务端按时间推进**，并发只会拿到同一窗口的重叠切片（实测 3 路并发 15 条只有 6~11 条唯一），所以 story 必须保持串行。
- **批次 4 而不是 3**：并发窗口仍有少量重叠，3 批的去重后唯一条数最低探到 18（低于默认目标 20）；4 批把最低唯一条数抬到 28，且请求数只多一个。
- 语义不变：首批失败仍直接报错、后续批失败仍返回部分结果并置 `has_more = true`；目标条数满足后仍提前停止处理后续批（请求已发出，但不再消耗结果）。

### 实机数据（真机主窗口，`video_get_recommend`，默认目标 20 条）

| 形状 | 单次中位 | 范围 | 去重后唯一条数 |
| ---- | -------- | ---- | -------------- |
| 串行 3 批（优化前） | **1950 ms** | 1872–2018 ms | 每轮恰好 20（受目标截断） |
| 并发 4 批（优化后） | **822 ms** | 770–880 ms | 中位 30，最低 28（40 轮全部返回满 20 条） |

并发形状 A/B（同一次会话内交错，各 15~20 轮）：并发 3 批约 780ms，并发 4 批约 820ms，并发 5 批约 850ms——时延不再随批数线性增长（同一波往返），4/5 批的额外成本只有并发连接的排队。

### 刷新链路端到端对照

`tests/vod-refresh-performance.browser.js`（真实点击刷新按钮，5 轮中位）：

| 指标 | 优化前 | 优化后 | 变化 |
| ---- | ------ | ------ | ---- |
| `video_get_recommend` IPC | 2071–2152 ms | **811–880 ms** | 约 −60% |
| 卡片重填（clear → refill） | 约 2200–2300 ms | **885–982 ms** | 约 −57% |
| 封面图片（同轮 N 张） | 约 20 张 / 8.3s 合计 | 14–20 张 / 4.3s 合计 | 随上游轮换波动 |
| 长任务 | 1 次 / 123–142 ms | 1 次 / 94 ms 合计 | 量级不变 |

封面图每轮仍全部 `diskCache:false`：刷新拿到的是新稿件、封面 URL 也全新，重新下载是预期行为而不是缺陷。剩余约 800ms 中，约 500ms 是上游单批的设备个性化路径（见上），其余是解析与 IPC；刷新链路的**应用侧串行等待已消除**。

> 问题三把「一次首页 IPC 往返」当作不可再压缩的底座（当时约 1.7s），问题四说明这个底座本身还有一半是应用自己串行取批造成的。

## 附：其他已落地的小优化

- 封面 `<img>` 的 `decoding` 由 `sync` 改回 `async`（`src/features/video/VideoCard.tsx`）：`sync` 会在主线程同步解码，冷启动时 N 张封面叠加同步解码阻塞首屏；`async` 交给浏览器异步解码，与项目内其他列表（history/iptv/recording）一致。

## 已知限制

- `video_get_play_info` 端到端耗时仍由 B 站 playurl + CDN sidx 的网络往返主导，本轮优化针对的是应用可控的本地开销与失败自愈，无法压缩上游网络时延。
- 推荐流剩余约 850ms 同样由上游主导：单批带 `buvid` 约 500ms（设备个性化路径），并发只把这笔成本从三份摊成一份，不能消除它。上游不给页码/游标、每批只回 9~11 条也是外部约束。
- 列表 `staleTime=Infinity` 仅进程内有效，无跨会话持久缓存，重启后首次进页仍付一轮 IPC（本轮未改动，属可选后续项）。
- 第二分片「卡死」修复以恢复自愈能力为准，因其偶发、依赖 CDN stall，未附稳定耗时对比。
