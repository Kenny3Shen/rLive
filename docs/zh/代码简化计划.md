# rLive 代码简化计划

> 状态：提案  
> 基线日期：2026-08-19  
> 源码版本：`2.0.0`

## 1. 目标

这里的“简化”不是压缩行数，也不是把大文件机械拆成小文件。目标是在不改变现有产品行为的前提下，减少一次修改需要同时理解和同步的状态、契约与生命周期数量。

计划优先解决以下问题：

1. 前后端 IPC、设置默认值和缓存 key 由多处手工维护，容易产生静默漂移。
2. 播放、录制、站点和弹幕的核心生命周期集中在少数编排文件中，修改影响面过大。
3. 一些跨功能能力仍归属于具体 feature，导致依赖方向与实际复用关系不一致。
4. 测试数量充足，但缺少少量能直接约束架构边界和跨语言契约的检查。

计划不以“所有文件必须小于某个行数”为目标。协议解析器、状态机和带大量 fixture 的测试文件可能天然较长；只有在一个文件同时拥有多种变化原因时才拆分。

### 2.2 已有优势

简化工作应保留以下已经形成的正确边界：

- `LiveSite` 把站点差异限制在 Rust，前端不复制平台签名和解析逻辑。
- TanStack Query 管理 IPC / 服务端数据，Zustand 管理设置和轻量会话状态，职责方向正确。
- 播放恢复会话与媒体生命周期会话已经在[架构说明](架构说明.md#21-会话所有权边界)中明确区分，不能重新合并。
- `xgplayer`、HLS、FLV / MPEG-TS、proxy session 和播放源模型已经统一，不能为 IPTV、录制或多画面再建平行内核。
- 录制 bundle 自包含、metadata 原子替换、后台弹幕和崩溃恢复均有较强测试保护。
- 平台不可靠能力、Cookie、弹幕发送和本地字幕的安全边界已有明确文档。

## 3. 核心结论

| 优先级 | 编号 | 问题 | 证据 | 简化目标 |
| --- | --- | --- | --- | --- |
| P0 | C1 | IPC 契约分散 | 前端约 115 次 `invokeCmd`，至少 68 个静态命令名散布在 36 个文件 | command 字符串、参数和返回类型只存在于领域 API 层 |
| P0 | C2 | 设置 schema 重复 | `AppSettings`、默认值、范围、归一化和 profile 字段分别出现在 Rust model、Rust settings、TS type、Zustand store 和 UI | Rust 保持持久化权威，前端只保留 UI 必需约束，并用契约测试防漂移 |
| P0 | C3 | 缓存 key 与更新规则分散 | `room_detail`、`history`、`recordings`、`follows` 等 key 在页面与组件中直接拼装 | 每个领域拥有 query key factory、query options 和缓存更新函数 |
| P1 | C4 | 播放核心归属错误 | IPTV、多画面和录制直接依赖 `features/room/player` 或 `features/room/danmaku` | 把真正跨功能的播放器 runtime 移入 `shared/player`，保留业务 adapter |
| P1 | C5 | 录制后端变化原因过多 | `recording.rs` 同时负责 manager、文件事务、HTTP、恢复和 1,700 多行测试 | 以不变量为边界拆为领域子模块，`mod.rs` 只暴露稳定 facade |
| P1 | C6 | 页面编排过载 | `PlayerPane`、`SettingsPage`、`FollowPage` 同时处理数据、状态和视图 | 页面保留路由级编排，交互状态和领域操作下沉到同域 hook / controller |
| P2 | C7 | 平台模块难以局部修改 | 单个平台文件同时包含 transport、parser、auth、send、fixture tests | 只在单个平台内部按协议阶段拆分，不建立虚假的跨平台通用层 |
| P2 | C8 | 依赖方向可被绕过 | `shared/components/RoomCard.tsx` 反向依赖 `follow` 和 `multi-room` | `shared` 不依赖 `features`；业务动作由调用方组合 |

## 4. 简化原则

### 4.1 行为先固定，结构后移动

每个工作包先补足当前行为的特征测试，再移动代码。一个 PR 不同时做目录迁移、重试参数调整和 UI 改版。结构 PR 的验收标准是可观察行为不变。

### 4.2 以所有权拆分，不以 helper 数量拆分

新模块必须拥有一种清晰的不变量或生命周期，例如“录制 metadata 原子提交”或“一个 proxy session 的创建和销毁”。只被调用一次、没有独立规则的三五行函数不需要单独文件。

### 4.3 领域接口优于全局工具箱

允许 `recording/storage.rs` 拥有录制路径规则，不把它抽成无边界的 `utils/fs.rs`。允许各平台保留不同的 Cookie 和协议验证，不为了减少重复把安全策略合并成一个宽松 helper。

### 4.4 后端负责可信边界

Rust 继续负责设置持久化归一化、URL / 路径验证、Cookie 使用范围、录制并发和磁盘保护。前端校验用于即时反馈，不能成为唯一校验。

### 4.5 依赖方向单向

目标方向为：

```text
app -> features -> shared -> components/ui
                 -> shared/api -> Tauri IPC

commands -> domain managers -> storage / protocol / site adapters
```

`app` 可以组合多个 feature；一个 feature 只有在真实业务流程需要时才能依赖另一个 feature。`shared` 不得反向依赖 `features`。

## 5. 目标结构

结构名称是建议，实施时可以随现有命名微调，但所有权不能退回原状。

### 5.1 前端

```text
src/
├── app/                         # 路由、Shell、跨 feature 组合
├── components/ui/               # Base UI / shadcn-style 基础组件
├── features/
│   ├── room/                    # 房间业务、恢复策略、房间侧栏
│   ├── recording/               # 录制业务 API、列表和回放 adapter
│   ├── iptv/                    # IPTV 发现与播放 adapter
│   ├── multi-room/              # 多实例编排
│   └── settings/
│       ├── pages/               # 分类页面
│       ├── account/             # 账号 / QR 登录视图状态
│       └── data/                # profile 与 LAN sync 入口
└── shared/
    ├── api/
    │   ├── commands/            # 按领域封装 invokeCmd
    │   ├── contracts/           # IPC 类型与事件 payload
    │   └── queryKeys/           # 稳定 key factory
    ├── player/
    │   ├── runtime/             # proxy + xgplayer + media 生命周期
    │   ├── fullscreen/          # Web / native / Android 兼容
    │   ├── controls/            # 控制层基础能力
    │   └── profiles/            # live / IPTV / recording 参数
    └── danmaku/                 # 真正被直播、录制、多画面共用的纯逻辑
```

`RoomCard` 应拆成无业务副作用的展示组件和 feature-owned action 容器。首页、分类和搜索可以复用展示组件；关注、预取和多画面操作由调用方传入，不允许展示组件直接导入相关 store 或 query key。

### 5.2 Rust 录制

```text
src-tauri/src/recording/
├── mod.rs                # RecordingManager facade 与公开 re-export
├── model.rs              # IPC model、StoredRecording、状态枚举
├── manager.rs            # start / stop / delete / shutdown 编排
├── session.rs            # ActiveSession、分段和 worker 最终化
├── storage.rs            # 根目录、当前录制目录切换、空间检查、manager lock
├── metadata.rs           # 原子写入、sidecar 恢复、索引扫描
├── danmaku.rs            # JSONL writer、计数和后台连接所有权
├── playback_server.rs    # token、Range、本地文件服务
├── ffmpeg.rs             # 现有 recording_ffmpeg 内容
├── ass.rs                # 现有 recording_ass 内容
└── tests/                # 跨模块生命周期与回归测试
```

`RecordingManager` 的公开 command surface 保持不变。拆分过程中不改变 bundle 命名、metadata 字段、`.part` / `.tmp` / `.bak` 事务、并发上限、512 MB 磁盘保护或 15 秒关闭期限。

### 5.3 Rust 流代理

```text
src-tauri/src/stream_proxy/
├── mod.rs                # StreamProxy facade
├── session.rs            # generation、预留、停止和监听器所有权
├── relay.rs              # 受限 HTTP relay
├── hls.rs                # manifest 识别、URI registry 与重写
├── twitch.rs             # token 刷新和广告清单恢复
├── probe.rs              # 源探测和容器校验
└── telemetry.rs          # 原子计数与脱敏 snapshot
```

录制回放、流代理、图片代理和 LAN sync 都包含小型 localhost HTTP 服务，但暂不直接引入 Axum / Hyper 统一重写。先只提取已经完全一致的请求头读取、响应写入和 shutdown primitive；URL 白名单、token、Range、缓存和内容类型策略仍由各服务拥有。

## 6. 工作包

### CS-0：建立防回归护栏

目标：让后续移动代码时可以证明行为未变。

任务：

- 保存本文件中的规模、调用点和依赖方向基线，新增可重复执行的统计脚本时只输出稳定指标。
- 为 `recording.rs`、`stream_proxy.rs` 和 `useWebPlayer.ts` 列出公开接口与关键不变量。
- 增加依赖边界检查：`src/shared/**` 不得导入 `src/features/**`。
- 增加 command 使用检查：完成 CS-1 后，业务文件不得出现裸 `invokeCmd("...")`。
- 把现有 live smoke test 继续标记为显式 opt-in，不能让外网波动成为普通 CI 失败。

验收：

- CI 能阻止新的反向依赖和裸 command 字符串。
- 新检查不要求网络、Cookie、直播中的房间或本地模型。

### CS-1：收敛 IPC、设置与 query 契约

目标：先降低最常发生的多点同步成本。

#### 1. 领域 API

按 `site`、`account`、`danmaku`、`follow`、`history`、`recording`、`settings`、`iptv`、`asr`、`profile` 和 `lanSync` 建立 API 模块。每个模块同时拥有：

- command 常量；
- 参数类型；
- 返回类型；
- event 名称和 payload 类型；
- 必要的 payload 运行时校验；
- 与 command 直接对应的 query options / mutation helper。

`invokeCmd` 仍作为底层错误归一化函数，但 feature 不直接调用它。第一阶段不急于引入 codegen；先消除散落字符串并建立跨语言 fixture。只有当手写契约仍持续漂移时，再评估 `specta`、`ts-rs` 或 JSON Schema 生成。

#### 2. 设置

- Rust `settings::normalize` 继续是持久化权威。
- `AppSettings::default` 与 normalization 常量收敛到同一 Rust 模块，避免 default 与 clamp 分离。
- 前端把 schema 镜像、UI 范围、Zustand state 和 persistence adapter 分开，不再由一个 800 行 store 同时承担。
- 前端启动所需的最小默认值可以保留，但必须用 Rust 输出的默认设置 fixture 做一致性测试。
- profile 的“可移植字段”和“设备本地敏感字段”继续使用显式 allowlist；安全字段不能为了自动推导而意外扩大。测试负责确认 allowlist 与 `AppSettings` 的差异是有意的。

当前 `danmaku_font_stroke` 的 TypeScript 注释仍写成 `0.5..=2.5`，而 store、Rust normalization 和架构文档实际为 `0..=1.5`。这类差异应由契约测试直接发现，不依赖人工查注释。

#### 3. Query key

使用稳定 factory，例如：

```ts
roomKeys.detail(siteId, roomId)
roomKeys.playUrls(siteId, roomId, quality)
historyKeys.all()
recordingKeys.list()
iptvFavoriteKeys.bySource(sourceId)
```

缓存更新规则与 key 放在同一领域模块。页面不再直接了解“更新全量缓存后还要更新按来源缓存”等细节。

验收：

- `invokeCmd` 只出现在 `shared/api` 或领域 API adapter 中。
- command 参数和返回类型不在 JSX 文件内临时声明。
- `AppSettings` 默认值、字段集合和关键范围有 Rust/TS fixture 对照。
- 同一 query 不再由多个页面用不同字面量拼 key。

### CS-2：简化播放器生命周期

目标：让直播、IPTV、多画面和录制回放共享稳定 runtime，但保留不同业务策略。

实施顺序：

1. 从 `useWebPlayer.ts` 提取无 React 依赖的 PiP、Fullscreen、音频归一化、播放源 fingerprint 和 profile。
2. 将 proxy + xgplayer 创建 / 销毁封装为独立 media session，显式接收 generation 和 transport fact callback。
3. `useWebPlayer` 缩为 React adapter，只负责创建 session、订阅 snapshot 和清理。
4. 将 runtime 从 `features/room/player` 移到 `shared/player/runtime`，直播、IPTV 和多画面改用各自 adapter。
5. 录制回放只复用 xgplayer runtime 与控制基础层，继续拥有时间轴、seek 和倍速语义。
6. 最后拆 `PlayerPane`：手势 controller、stage、overlay、side panel 各自拥有状态，页面只组合。

必须保持：
- 播放恢复会话选择 `PlayUrl`，media session 只报告 transport facts。
- 每个播放器实例拥有独立 generation、重试预算、proxy session 和媒体状态。
- IPTV 的两次重连、直播站点恢复规则、软切换和音量语义不变。
- Android 原生音量 / 亮度 / 方向、桌面 native fullscreen 和 Web fallback 继续分层。

验收：

- `features/iptv`、`features/multi-room` 和 `features/recording` 不再导入 `features/room/player` 内部文件。
- `useWebPlayer` 不直接包含业务恢复决策。
- 现有 `media-lifecycle`、`playback-recovery-session`、fullscreen、PiP 和多画面测试全部保持通过。

### CS-3：拆分录制后端

目标：降低录制改动的审查半径，不改变磁盘格式。

建议按以下顺序提取：

1. `model.rs` 和纯格式化 / 校验函数。
2. `playback_server.rs`，连同路径穿越和 Range 测试。
3. `metadata.rs` 与 `storage.rs`，连同原子替换、恢复、迁移和磁盘测试。
4. `danmaku.rs`，保持 `user_id` 永不序列化的测试。
5. `session.rs`，迁移分段、finalizing fence、shutdown 和 salvage 测试。
6. 最后收缩 `manager.rs` 和 `mod.rs`，保留 command-facing facade。

每一步只移动一个所有权边界。禁止在同一 PR 内顺便更改 bundle schema 或 FFmpeg timestamp 算法。

验收：

- `recording/mod.rs` 只暴露 manager、IPC model 和 ASS options。
- metadata、storage、playback server 和 session 各有本模块测试。
- 当前 v2 录制回放、旧 bundle 跳过、自动分段、后台弹幕、重复 start / stop、异常恢复和存储目录切换测试保持通过。
- 当前 `metadata.json` 必须显式包含 schema 版本；旧格式不进入 rLive 运行时回放路径。

### CS-4：拆分站点与弹幕协议

目标：让一次上游 API 变化只触及一个平台的一段协议。

建议边界：

- 站点：`client/session`、`browse`、`room`、`playback`、`parser`、`tests/fixtures`。
- 弹幕：`connect/reconnect`、`frame`、`parser`、`identity`、`send`、`tests`。
- 斗鱼发送的网页登录协商、WSS 代理和 `chatres` 状态机保留独立模块，不与收包 parser 混合。
- 抖音 SSR、reflow、`a_bogus` 和 MSSDK 弹幕签名保持独立，不合并为一个“签名工具”。
- Twitch GraphQL 分片浏览、HLS variant 解析和播放 token 分离；广告恢复仍由 stream proxy 侧持有运行时状态。

只在语义和安全策略完全一致时抽共享函数。`json_str` 这类几行解析 helper 的重复成本低于错误统一的风险，不应作为优先目标。Douyu 与 Douyin 当前几乎相同的 Cookie merge 可以先补共同 fixture，再决定是否提取。

验收：

- 每个平台的外网请求、纯 parser 和发送能力可分别测试。
- fixture 不包含真实 Cookie、token、用户 ID 或可复用签名。
- 新平台接入不需要修改已有平台 parser。

### CS-5：收缩页面与 feature 边界

目标：让 JSX 主要描述结构，让数据操作和复杂交互有明确 owner。

任务：

- `SettingsPage` 按分类拆页面；账号 QR 状态、profile 导入导出和 proxy 表单分别进入同域 controller。
- `settingsStore` 抽出 settings codec、persistence queue 和 ASR restart transaction，避免多个 setter 重复“乐观更新 -> 保存 -> 重启 -> 回滚”。
- `FollowPage` 把查询 / mutation、DND、分组视图和 Card 分开；直播关注与 IPTV 关注继续保持两个业务模型。
- `HistoryPage` 把观看历史与弹幕发送历史的 query / mutation 分开，页面只处理筛选和布局。
- `RoomCard` 变为无副作用展示组件；预取、关注分组和多画面动作由 feature adapter 注入。

验收：

- `src/shared/**` 到 `src/features/**` 的 import 数为 0。
- category 页面文件只负责一个设置分类或一个明确的页面编排。
- mutation 的乐观更新和 rollback 在领域 hook 中测试，不在多个 Card / Dialog 中复制。

### CS-6：补齐质量门槛

目标：用少量高信号检查保护简化成果。

建议增加：

- `bun run format:check` 进入 CI；当前 `bun run check` 实际只运行 lint 和 TypeScript。
- Rust CI 增加 `cargo fmt --check` 与聚焦的 `cargo clippy --locked --all-targets -- -D warnings`，若平台依赖产生噪声则先建立明确 allowlist。
- IPC contract fixture、设置默认 fixture、profile 字段策略测试。
- 依赖方向、裸 command、重复 query key 的静态检查。
- 至少一组不依赖直播外网的 Playwright 路由 smoke：设置、IPTV 发现页不创建播放器、录制库空状态和移动端导航。
- 浏览器自动化只覆盖关键工作流，不追求截图数量或任意覆盖率百分比。

验收：

- 普通 CI 不需要私密凭据或运行中的直播间。
- 架构规则失败时输出具体文件与违规 import / command。
- Windows / Tauri 真机构建仍按发布流程单独执行，不混入每个文档或纯逻辑 PR。

## 8. 度量与完成标准

### 8.1 结构指标

- 裸 `invokeCmd("...")` 的业务调用点从约 115 降为 0。
- `src/shared/**` 反向导入 `src/features/**` 从当前 4 个 import 降为 0。
- query key 字面量只存在于对应 key factory 或测试。
- `recording.rs` 和 `stream_proxy.rs` 变为目录 facade；测试随所有权迁移。
- 跨功能播放代码不再以 `room` feature 作为公共命名空间。

这些指标用于发现边界回退，不作为代码质量的唯一评价。一个 700 行的纯协议 parser 可能比七个互相跳转的 100 行文件更简单。

### 8.2 行为指标

- `bun run check`、`bun test tests/`、`bun run build` 和 Rust library tests 通过。
- 播放恢复参数、线路记忆、proxy generation、全屏和音量行为不变。
- 录制 bundle、metadata schema、回放 URL、自动分段和崩溃恢复行为不变。
- Cookie、token、弹幕文本和本机路径的日志 / profile 安全边界不变。
- `/iptv` 继续只做发现，不创建播放器或自动播放。

### 8.3 维护效率指标

实施前后各记录三类真实改动的触达文件数：新增设置字段、修改一个 command response、修复一个播放生命周期问题。目标是每类改动都只触达权威领域模块、adapter 和对应测试，不再需要全仓搜索来确认同步点。

## 9. 风险控制

| 风险 | 控制方式 |
| --- | --- |
| 目录迁移造成隐式行为变化 | 先复制测试和公开接口，再移动实现；每个 PR 只迁移一个 owner |
| 播放 cleanup 顺序变化 | 用 generation、session ID 和串行队列测试资源创建 / 销毁顺序 |
| 录制格式被无意修改 | 对 metadata、bundle 名称和恢复 fixture 做 snapshot / roundtrip |
| 设置字段在 profile 中泄漏 | profile 继续显式 allowlist，并增加敏感字段排除测试 |
| 抽象过度 | 需要第二个真实调用方或明确消除状态重复，才增加通用 abstraction |
| 新依赖扩大包体和构建风险 | codegen、HTTP framework 和状态机库先做 spike，对比收益后再决定 |

## 10. 明确不做

- 不在简化 PR 中改变平台能力、发送规则或绕过策略。
- 不删除 B 站 legacy endpoint、抖音 SSR、Twitch 清单恢复、WebKit Fullscreen 或 AudioWorklet fallback。
- 不把 Rust 业务逻辑搬到前端，也不为每个平台创建前端 adapter。
- 不把所有 Zustand state 合并成一个全局 store。
- 不以更换 React、Tauri、播放器或 UI 框架作为简化手段。
- 不为了减少文件数重新制造 3,000 行 facade。
- 不为旧 FLV / HLS 或旧 metadata 增加运行时迁移、补索引或回放兼容；旧数据由用户在升级前自行导出或备份。
