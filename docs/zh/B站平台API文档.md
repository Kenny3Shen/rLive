# 哔哩哔哩平台 API 文档

面向要修改 B 站适配器的开发者，说明 rLive 接入了哪些能力、走哪条上游通道、账号与发送有哪些硬性前提。
当前状态：浏览、播放、弹幕接收、SC 展示、扫码/Cookie 登录、普通弹幕发送与会话级自动发送均已支持。

## 能力总览

| 能力 | 状态 | rLive 行为 |
| --- | --- | --- |
| 分类、推荐、分区房间、搜索 | 已支持 | 使用网页公开可访问的直播与搜索数据；列表可按上游返回继续加载。 |
| 房间详情 | 已支持 | 解析真实房间号、主播、封面、热度、开播状态与公告。 |
| 播放与清晰度 | 已支持 | 获取可用协议、格式、编码与清晰度，并经本机 `stream_proxy` 交给网页播放器。 |
| 实时弹幕与 SC | 已支持 | 连接房间 WebSocket，展示普通消息、图片表情与醒目留言。 |
| 账号 | 已支持 | 可扫码登录或手动保存 Cookie；Cookie 仅保存在本机。 |
| 普通弹幕发送与会话级自动发送 | 已支持 | 均需本机发送开关和有效登录态；自动发送只属于当前房间会话。 |

## rLive 接入接口

所有站点适配器都实现统一的读取接口：`get_categories`、`get_recommend_rooms`、`get_category_rooms`、`search_rooms`、`get_room_detail`、`get_play_qualities` 与 `get_play_urls`。前端通过 `site_*` Tauri command 调用这些能力，不直接持有上游 Cookie、短时 token 或播放签名。

哔哩哔哩专用的实时能力：

- `danmaku_connect`：使用房间弹幕信息建立接收连接；断线时会轮换网关并刷新短时凭据。
- `bilibili_danmaku_send_status` / `bilibili_danmaku_send`：发送一个普通文本片段的窄接口；手动发送和会话级自动发送均复用它。
- SC 只用于展示；rLive 不提供支付、送礼或付费留言写入。

## 上游数据与播放

分类、房间列表、搜索、房间详情、弹幕连接信息和播放信息来自网页使用的直播接口。部分读取请求需要网页环境字段或 WBI 签名，属于适配器内部实现细节，不是稳定的第三方应用契约。

- 房间详情会解析真实 `room_id`，因此短号、展示号和发送所需的真实房间号不会混用。
- 播放地址与短时签名不进入前端持久化缓存；刷新房间或切换清晰度时重新获取。
- 可用清晰度与线路以上游下发为准，会随直播状态、账号、地区和平台策略变化。

## 账号与弹幕发送

接收普通弹幕通常可匿名工作；扫码或手动 Cookie 登录可改善网页登录态兼容性。图片表情只加载经过来源校验的 B 站 CDN 图片，SC 仅展示平台下发的事件。

发送使用登录后的网页写入接口：

```text
POST https://api.live.bilibili.com/msg/send
```

发送前必须同时满足：

1. 「设置 → 账号」中的 `danmaku_send_enabled` 已开启；该开关默认关闭、只保存在当前设备，也不随配置导入导出。
2. 本机 Cookie 含 `SESSDATA` 与 `bili_jct`；后者作为 CSRF 值使用。
3. 真实数字房间号、非空单行文本和当前保守的长度/冷却校验均通过。

会话级自动发送入口在房间标题栏右侧、移动端「更多房间操作」和全屏「更多操作」，默认关闭且不持久化，需共用本机授权、当前 Cookie/可发送状态和文本校验都有效才可开启。开启时立即发送首段，把换行与连续空白压缩为一个空格，再按 grapheme 拆成每段最多 20 个用户可见字符且不超过 B 站 UTF-16 上限的片段，顺序发送、末段后回到首段循环。请求不重叠，后续发送起始至少相隔当前会话设置的发送间隔。

结果语义：写入 command 返回不生成本地假弹幕，只有正常房间连接收到平台真实回显后消息才进入列表与飘屏。

## 已知限制

- 编辑文本、切换房间、离开页面、关闭应用或任意发送失败都会停用自动发送；失败不自动重试。
- 单个 grapheme 无法容纳在平台 UTF-16 上限内时显示校验错误。
- 不提供批量发送、自动回复、礼物、支付或对未知结果的自动重试。
- Cookie、CSRF、消息正文、短时 token 和上游原始错误不写入日志、不导出、不返回前端。发送 HTTP 客户端禁止跟随重定向，以免把登录态交给重定向目标。
