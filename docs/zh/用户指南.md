# rLive 用户指南

## 1. 简介

rLive 是跨平台直播客户端，桌面端与 Android 客户端可在同一应用内浏览、搜索、观看多平台直播，并接收弹幕。

当前站点状态：

| 站点 | 列表 / 搜索 | 播放 | 弹幕 |
|------|-------------|------|------|
| 哔哩哔哩 | ✓ | ✓ | ✓（单条发送需启用本机统一发送开关及有效 Cookie） |
| 虎牙 | ✓ | ✓ | ✓（单条发送需启用本机统一发送开关及有效 Cookie） |
| 斗鱼 | ✓ | ✓ | ✓（个人直播间已成功发送；单条发送仍需本机统一发送开关、完整 Cookie，并按 `chatres` 与真实回显处理） |
| 抖音 | 推荐 / 分类可分页（本地签名）；搜索需登录 Cookie | ✓ | ✓（本地签名直连） |
| Twitch | 桌面端尝试直播列表 / 分类 / 搜索分页；移动端首屏 | HLS（自动尝试恢复广告占位播放列表） | ✓（匿名 IRC） |

抖音推荐和分类使用本地 `a_bogus` 签名请求网页端分页接口，支持「加载更多」；签名接口首屏失败时回退到 SSR 首屏，后续页没有 SSR 回退。保存完整登录 Cookie 后可使用抖音直播搜索，但二维码登录、搜索等网页接口仍可能要求浏览器访问验证。

抖音实时弹幕使用公开 WSS 帧协议，连接地址由短时 MSSDK 签名保护。rLive 在本机计算签名并直连官方 WSS，无需配置外部签名服务。匿名 `ttwid` 会话或完整登录 Cookie 可提高连接可用性。接入边界详见[抖音平台 API 文档](抖音平台API文档.md)。

Twitch 支持直播列表、分类、搜索、房间、HLS 播放与匿名 IRC 弹幕。桌面端首屏返回有效 cursor 时会显示「加载更多」；首次翻页会在隐藏的临时 WebView 中加载 Twitch 页面，由 Twitch 官方 JavaScript 完成浏览器完整性验证，并在同一浏览器上下文中请求后续页。此过程不使用账号 Cookie、OAuth 密钥或第三方挑战实现，也不保存完整性令牌。Twitch 仍可能按设备指纹、网络或地区拒绝挑战，应用自动刷新一次上下文后会显示可重试错误；Android 和 iOS 继续只显示首屏。播放中检测到服务端插播的广告播放列表时，应用会自动尝试 Twitch 的备用播放档位，并优先选择能保留完整清晰度的档位；必要时会降到清晰度受限的档位以换取无广告画面。全部档位仍不可用时画面会短暂停顿，等待正常直播分片恢复。

## 2. 安装与启动

### Windows（推荐）

1. 从 GitHub Release 下载 `rLive_<版本>_windows-x64.exe`，或下载便携 ZIP 并解压。
2. 将 EXE 放在当前用户可写的独立文件夹中，不要直接放入 `Program Files`；双击即可运行，无需额外安装播放器。
3. EXE 和 ZIP 默认不内置 ASR 运行库。首次启用本地语音字幕时，应用会下载约 `212 MiB` 运行库及所选模型。

Windows 使用 EXE 所在文件夹作为完整应用目录：`rlive.db` 保存配置、Cookie、关注和历史，`logs/` 保存诊断日志，`models/` 保存字幕模型，`asr-runtime/` 保存按需下载的字幕运行库，`webview/` 保存 WebView 的 localStorage 和缓存。升级时将新 EXE 放回原文件夹即可沿用数据；移动整个文件夹可一起迁移应用和数据。首次运行新版本时，应用会从旧 `%APPDATA%\rlive` 和 WebView2 系统目录复制尚不存在的数据，旧目录保留为备份。

### 从源码开发

见仓库根目录 `README.md`：`bun install` → `bun run tauri dev`。

### 在浏览器中打开

rLive 客户端可以把自己的界面提供给普通浏览器，详见[9.2 浏览器访问](#92-浏览器访问)。这需要本机 rLive 保持运行，浏览器访问的是同一台机器上的数据。

## 3. 界面结构

| 区域 | 说明 |
|------|------|
| 左侧栏 | 主导航为首页、关注、分类、IPTV，桌面端另有「多画面」；底部依次为亮 / 暗模式、历史和设置，历史按钮位于设置按钮正上方。移动端全部可见入口平分底栏宽度，不再缩小历史与设置的点击区域 |
| 顶栏 | 首页显示站点切换与搜索（主播 / 房间号 / 标题）；切换平台时内容区会用短暂渐入过渡。关注页只显示「直播关注 / IPTV 频道」一级页签；移动端平台入口及历史页的「观看历史 / 弹幕历史」会平分可用宽度并保持居中；历史页右侧可清空当前时间线，不再按平台分类；IPTV 发现页保留频道源切换栏 |
| 房间页 | 左侧纯图标返回、直播间标题、播放器、右侧主播信息，以及「弹幕 / 关注 / 设置」标签 |

### 3.1 历史记录

历史页将所有已启用直播平台的记录合并为按日期排列的时间线，顶部可在「观看历史」与「弹幕历史」之间切换。页面内支持按平台、关键词以及今天、昨天、近 7 天、近 30 天或指定日期组合筛选，筛选状态会保留在当前页面地址中；顶部右侧的清空按钮只清空当前显示的整条时间线，不受平台筛选影响，并在执行前要求确认。观看历史在本机最多保留最近 2,000 个不同直播间，超过上限后自动淘汰最早记录，避免数据库随长期使用持续膨胀。

观看历史显示进入直播间时保存的直播间封面；旧版本已有记录或平台未提供封面时回退为平台图标。B 站、斗鱼和虎牙成功发送的弹幕会记录发送时的直播间标题、主播名称和房间号，这些字段都可参与搜索，也可从记录重新进入房间；旧版本记录缺少房间信息时仍按已有字段回退显示。

## 4. 观看直播

1. 首次启动默认打开哔哩哔哩；之后可在顶栏选择站点。
2. 从「分类」点击分区会打开独立直播列表页；搜索页可切换「全部 / 主播 / 房间号 / 标题」。
3. 房间顶栏左侧提供纯图标返回，内部打开的房间会回到来源页，直接打开房间链接则回到首页；右侧栏顶部显示主播头像、用户名、平台图标、房间号和当前热度。
4. 播放器控制条透明叠放在视频底部。播放期间闲置一段时间会自动隐藏；移动、点击或键盘操作即可再次显示。展开音量、清晰度或线路选项时，控制条会保持显示；焦点位于画面时，可用 `Space` / `K` 播放或暂停、`M` 静音、`F` 全屏。
   全屏会遮住应用顶栏，因此画面顶部会额外出现一层 HUD：左上角显示直播间标题、主播头像与名称、平台房间号和当前热度，右上角是「更多房间操作」。它与底部控制条同时淡入淡出，闲置后一起隐藏。菜单里可复制房间链接和播放直链、关注或取消关注、加入多画面；关注与多画面需要应用界面，选择后会先退出全屏再继续。
5. 刷新位于暂停左侧，会重新获取流元数据并重建播放会话；控制栏只保留一个音量入口，点击后展开竖向滑杆，静音按钮位于滑杆底部。「仅播声音」位于同一组控制中，开启后保持音频播放，隐藏视频、飘屏弹幕、SC 和字幕画面，并释放屏幕常亮；再次点击会恢复画面。音视频复用的直播地址仍需传输原始媒体流，因此该模式不保证减少网络流量。
   移动端画面支持纵向连续手势：左半边调节亮度，右半边调节音量；拖动时中央 HUD 实时显示图标、百分比和连续进度。Android 亮度写入当前 Activity 的窗口亮度，离开房间、直接切换房间或应用进入后台时会恢复；音量通过原生桥写入系统媒体音量，与硬件音量键共享设备档位，离开直播间或 IPTV 播放页后不会自动恢复。iOS/移动浏览器的亮度使用只影响画面的遮罩回退，音量仍只修改当前 `<video>`。
6. 清晰度和线路位于控制条右侧的播放设置中。线路只显示平台提供的名称或「线路 N」，不显示 FLV/HLS 协议文字。手动选择线路后，应用会在本机记住该平台直播间的选择；下次进入同一房间时优先匹配稳定的 `source_id`，平台没有返回相同来源时再回退到上次的线路序号。卡顿事件只用于本地播放遥测，不会自动切换线路或重载播放器。
7. 飘屏弹幕使用固定位置的图标按钮：文本气泡表示开启，关闭气泡表示关闭，不使用滑动或高亮色。右侧栏与全屏继续使用图标开关；收起右栏后再次打开，聊天列表仍会保留。点击一条普通弹幕可选择带图标的「复制」或「+1」操作：复制会写入剪贴板；在发送条件已就绪的 B 站、斗鱼或虎牙房间，「+1」会提交完全相同的一条文本，不会附加“+1”。本机提交不等于送达，列表和飘屏只以平台真实回显为准。

   画面上正在飘动的弹幕也可以直接操作，操作项与右侧列表一致。桌面端把鼠标移到一条弹幕上，这条会加上居中边框并原地停住，上方弹出操作菜单，其余弹幕照常飘动；指针离开弹幕和菜单后自动恢复。全屏时菜单会自动放大，便于在大屏上瞄准。移动端改为轻点一条弹幕选中，选中状态会保留直到轻点画面空白处，或再次轻点这条弹幕；菜单按钮始终使用放大尺寸，按钮之间留有间隔以防误触。轻点弹幕不会同时暂停播放，滑动和长按仍属于翻页与亮度/音量手势。
8. 默认清晰度和「软切换」可在「设置 → 播放」中调整。软切换默认开启，HLS、MPEG-TS 和 FLV 同协议换源时保留 xgplayer 与媒体元素；FLV 会替换内部 `mpegts.js` core，不要求跨 CDN 时间戳无缝连续。切换失败或跨协议时自动完整重建。
9. 抖音可匿名查看推荐/分类并通过「加载更多」继续浏览；列表请求使用本地 `a_bogus` 签名，首屏签名失败时回退 SSR，后续页无 SSR 回退。搜索需要先在「设置 → 账号」通过扫码登录或手动输入保存完整网页 Cookie。房间会优先由 SSR 取得内部房间号，再通过公开 reflow 数据解析播放信息。实时弹幕会在本机签名后直连，并解析普通聊天、表情聊天、礼物、点赞、进场与常见社交提示。Twitch 支持直播列表、分类、搜索、房间、HLS 播放与匿名 IRC 弹幕；桌面端通过隐藏临时 WebView 执行 Twitch 官方完整性挑战并尝试真实 cursor 分页，挑战被拒时可重试，移动端仅提供首屏。
10. 侧栏「IPTV」先打开频道发现首页，不会在进入时默认打开或播放第一个流。可加载 IPTV-org 官方日更的中文、中国大陆、东亚或综合公开频道分表；如需自定义源，请在「设置 → 网络」保存你有权使用的 HTTP(S) M3U 地址，随后首页会显示「自定义源」。同一分类下的「直链播放」可输入你有权使用的 HTTP(S) 媒体地址，直接进入共享播放器；rLive 会按地址识别 HLS、FLV、MPEG-TS 或原生媒体，并通过本机 `stream_proxy` 转发。频道卡片右上角和播放页顶栏均可关注或取消关注；发现页的「关注」筛选只显示当前来源的关注频道。关注页的「IPTV 频道」页签汇总各来源的关注，频道源选择移到关注页左侧栏顶部，移动端显示在分组条上方；桌面端左侧分组栏和移动端横向分组条负责自定义分组。两端都可从管理入口新建、重命名和删除分组，并从频道卡片调整归属。手机与桌面使用相同的来源、关注、更新、搜索、分类和可用状态流程；手机使用紧凑来源菜单与双列频道，桌面使用分段来源切换与多列频道。「更新源」重新下载当前 M3U；「检测可用性」按 URL 去重检测当前搜索/分类结果的前 120 个频道，并逐批显示进度、响应耗时和失败状态。两项网络操作均遵循应用代理。检测结果仅属于当前页面会话，更新或切换来源后会清除；绿色“可用”只说明本次请求取得了媒体数据（HLS 同时通过清单头校验），不保证后续分片、解码、地区授权或持续稳定。点击频道后才进入独立的沉浸式 `/iptv/play` 播放页，并使用 HLS、MPEG-TS 或 FLV 路径；返回会回到进入播放前的 IPTV、关注或设置页面。内置公开源关注与 IPTV 自定义分组包含在配置导入导出中；自定义地址及其频道关注只保存在当前设备，不写入路由、历史或配置包。

播放技术说明：应用通过本机 HTTP 代理转发直播流，前端由 `xgplayer` 管理媒体元素，使用 `xgplayer-mpegts.js` 处理 FLV / 裸 MPEG-TS，使用 `xgplayer-hls.js` 处理 HLS。底层仍分别使用 `mpegts.js` 与 `hls.js`。斗鱼上游 FLV 结束时会自动刷新房间签名和播放地址并重建播放器。播放遥测只在内存中保留有界的首帧、卡顿、缓冲、丢帧和代理聚合指标，不上传、不落盘，也不记录播放地址、Cookie 或 Referer。实现与隐私边界见[播放器技术文档](播放器技术文档.md)。

### 4.1 桌面多画面

多画面仅支持桌面端，最多同时打开 6 个直播间。可从左侧栏直接进入，也可在首页、分类、搜索、关注或历史的直播卡片右键菜单中选择「加入多画面」；单房间顶栏也提供「加入并打开多画面」。添加弹窗支持选择关注、历史记录，或输入平台和房间号。

多画面顶栏可选择 4 画面或 6 画面布局，选择会保存在当前设备。4 画面提供两种排列：默认的「主画面靠左」让主画面占据左侧 3×2 区域，3 个副画面沿右侧纵向排列；「四画面均分」将 4 个画面排成尺寸相同的 2×2 网格，左上角仍承担主画面的音频、弹幕和全屏角色。6 画面模式中，主画面占据左下方 2×2 区域，5 个副画面槽沿上方和右侧分布。已有直播间超过 4 路时，需要先移除多余直播间才能切换到 4 画面，避免仍在播放的直播间被隐藏。每个画面都是无独立窗口边框的播放区域。拖动画面左上角把手可交换两个已占用槽，也可把副画面移动到任意空槽；双击副画面或点击「设为主画面」会与当前主画面切换，并保留各直播间最近使用的副画面槽位。连续切换时，离开主画面的直播间会回到自己的记忆槽位，暂时被挤出的副路转到被提升直播间的原槽位，因此直播间不会因交换链路发生无规律的位置漂移。主画面被拖到空槽时，应用会自动提升另一副路，保证主画面区域不为空。

每路都有独立的播放/暂停、刷新、移除、静音和音量控制。首个直播间默认音量为 80%；随后加入的副路默认静音且音量为 0%，避免多路同时出声。切换主副画面会解除新主的静音（若其音量为 0% 则恢复为 80%），并将全部副画面静音；各路音量数值仍会保留。弹幕、SC 叠加层、本地字幕和弹幕发送只挂在主画面一路；副画面专注于并行观看，仅保留播放、静音和音量控制，也不挂载房间侧栏。

主画面控制栏的「全屏」只针对当前主画面：进入后主画面铺满屏幕，副画面和应用外壳不再显示，而不是把整个 3×3 导播矩阵一起放大。按 Esc 退出全屏；若在全屏时把当前主画面降级、拖到别的槽位或移除，应用会先退出全屏再完成切换。

多画面的容量与排列选择、槽位、位置记忆、房间元数据与各路音量保存在当前设备的 `rlive-multi-room` localStorage 中，关闭页面后仍可恢复；这些数据不进入 SQLite，也不包含在配置导入导出中。移动端不会显示入口，直接访问 `/multi-room` 时会提示继续使用单直播间播放。

## 5. 弹幕

### 5.1 连接

进入哔哩哔哩、虎牙、斗鱼、抖音或 Twitch 直播间后，应用会自动连接该站点的弹幕服务。右侧列表显示连接状态与消息；画面上方可显示飘屏弹幕。

- **哔哩哔哩**：在「设置 → 账号 → 哔哩哔哩」选择「扫码登录」或「手动输入」保存 Cookie，否则可能无法拿到弹幕 token。扫码使用手机端确认后只会将 Cookie 保存到本机。连接意外中断后会自动轮换服务器、刷新 token 并重连；系统消息会显示重连进度。
- **虎牙 / 斗鱼**：接收弹幕一般无需 Cookie。单条发送还需在「设置 → 账号」最上方启用「启用发送功能」并保存对应本机 Cookie。斗鱼与虎牙均支持扫码或手动输入；斗鱼当前网页对齐的发送实现已在个人直播间成功验证，每次运行仍以 `chatres(res=0)` 判断平台接收，并以正常收弹幕连接的真实回显决定展示，详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。斗鱼弹幕使用系统 TLS（Windows 为 SChannel），以兼容其 RSA 加密套件。
- **抖音**：在「设置 → 账号 → 抖音」可扫码登录或手动输入保存 Cookie；完整 Cookie 可用于登录态搜索，并改善弹幕会话可用性，但不绕过网页访问验证。推荐和分类通过本地签名接口分页，首屏签名失败时回退 SSR。若二维码返回验证页，请检查应用代理后重试，或在官方网页完成验证后复制完整 Cookie。实时弹幕在本机完成 MSSDK 签名后直连官方 WSS，断线重进会重新签名。
- **Twitch**：弹幕通过匿名 IRC WebSocket 连接。

### 5.2 发送 B站、斗鱼与虎牙弹幕

这是默认关闭的本机授权，以避免误发。在「设置 → 账号」最上方的「弹幕发送」中启用「启用发送功能」后，才会同时允许 B 站、斗鱼和虎牙的手动单条发送与房间右侧自动发送控制；授权开关只保存在当前设备，不会随配置导出或导入，但自动发送的开关、文本与发送间隔仅属于当前房间会话且绝不保存。它不是登录状态：每个平台仍须保存自己的有效 Cookie，并分别通过房间、文本、冷却和平台服务端校验；条件不完整时，该平台房间的发送框与自动发送控制均保持禁用。斗鱼旧协议已替换为当前网页认证与结果确认状态机，并已在个人直播间成功验证；每一条消息仍只在平台确认和真实回显后显示。

播放器功能栏中间的输入框仍是每次只提交一条普通文字弹幕的手动操作。点击发送、按 Enter 或对一条弹幕使用「+1」都会直接提交同一条文本；不提供批量发送、自动回复、礼物/支付或对不确定写入的自动重试。本机提交或平台 `chatres` 都不替代房间真实回显。

在房间右侧「设置」的「自动发送弹幕」仅适用于 B 站、斗鱼和虎牙。共用本机授权、Cookie/可发送状态和文本校验均就绪后，开启时会立即发送首段。文本会将换行和连续空白压缩为一个空格，再按 grapheme 拆分：每段最多 20 个用户可见字符，且不超过当前平台的 UTF-16 上限；片段按顺序发送，末段后从首段继续。发送请求不会重叠，后续发送起始至少相隔发送间隔；该会话参数默认 20 秒，可在 10–3600 秒间调整，修改会重排下一次发送。单个 grapheme 无法容纳在平台上限内时会显示校验错误。编辑文本、切换房间（同时清空该会话文本）、离开页面、关闭应用或任意发送失败都会立即停用本会话自动发送并显示原因；失败片段不会自动重试。

- **哔哩哔哩**：需要包含 `SESSDATA` 与 `bili_jct` 的有效 Cookie。只支持普通滚动、白色文本；后端会校验 Cookie、房间号、控制字符、当前网页端默认的 20 个 UTF-16 码元上限，并按房间施加 3 秒冷却。官方网页会按账号/服务端下发该上限；rLive 暂以调研到的默认值执行。发送请求不会携带 Cookie 跟随重定向。
- **斗鱼**：在「设置 → 账号 → 斗鱼」中可扫码登录或手动保存完整 Cookie。发送会校验数字房间号、非空单行文本与保守的按房间 3 秒冷却；当前实现使用当前网页的登录后加密协商、稳定设备身份、统一代理和 `chatres` / `error` 解析，且已在个人直播间成功验证。完整 Cookie 还需包含账号、设备和弹幕会话字段；缺失时会明确拒绝，而不会伪造设备 ID 或借用普通 JWT。仅在收到 `chatres(res=0)` 并看到真实回显后视为成功，详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。
- **虎牙**：在「设置 → 账号 → 虎牙」中可扫码登录，或手动保存包含数字账号 ID（`yyuid` 或 `udb_uid`）及登录凭据（`udb_n` / `udb_cred` / 扫码产生的 `udb_biztoken`）的 Cookie。发送前会校验解析出的房间、非空、单行且不超过 30 个 UTF-16 单元的文本，并施加短暂的本机冷却。

这三项发送能力只使用当前设备保存的 Cookie。Cookie 不会被记录到日志、导出或上传给其他服务。列表与飘屏仅在收到真实回显后显示；斗鱼还将 `chatres` 作为平台接收信号，与本机提交和房间展示分开报告。

### 5.3 平台真实回显

发送 command 在本机成功返回不会生成本地列表项或飘屏。右侧弹幕栏与飘屏只显示通过正常房间连接收到的平台真实回显，并保留平台原有样式；超时或发送失败仍应以平台直播间的实际状态为准。斗鱼将本地提交、`chatres(res=0)` 和真实回显区分为不同阶段，未知状态不会自动重试。

### 5.4 弹幕设置

路径：进入任意直播间后，使用右侧「弹幕 / 关注 / **设置**」中的 **设置** 标签。显示设置保存在本机，对后续房间同样有效；自动发送是例外，只属于当前房间会话。

| 项 | 说明 |
|----|------|
| 显示区域 | 飘屏可使用的视频高度（10%–100%） |
| 显示行数 | 自动安排轨道，或固定为 1–20 行 |
| 不透明度 | 飘屏文字透明度，拖动实时预览，松手保存 |
| 字号 / 字重 | 影响飘屏与右侧列表基础字号；字重提高亮画面可读性 |
| 速度 | 飘屏滚动速度（逻辑 1–10） |
| 相同内容合并 | 仅飘屏：在合并窗口内合并所有用户发送的相同普通聊天，并显示次数，例如「加油 ×100」；窗口默认 10 秒，可调为 5–30 秒；右侧列表逐条显示 |
| 礼物信息过滤 | 默认开启；隐藏各平台礼物通知及抖音「点赞 × 数量」等互动通知，不影响 SC |
| 屏蔽词 | 每行一词，输入即过滤；聊天、SC 与飘屏共用，并会自动保存 |
| 显示 SC 卡片（B 站） | 默认开启；在播放器左下角显示醒目留言卡片，关闭后立即停止显示 |
| 自动发送弹幕（B 站 / 斗鱼 / 虎牙） | 默认关闭的当前会话开关、文本与发送间隔；间隔默认 20 秒，可设为 10–3600 秒；满足发送条件后立即发送首个经过校验的片段，修改间隔会重排下一次发送 |

所有显示参数在房间内即时生效：滑块拖动时立即预览，松开后保存；开关与字重即时保存。

高弹幕量房间会按动画帧合并列表与 SC 更新，并限制等待队列大小；聊天页签保留有界队列，SC 叠加层最多同时显示 3 张卡片。Canvas 在没有活跃飘屏时停止请求动画帧，收到新消息、调整设置或改变尺寸时自动恢复，以降低 CPU 占用；轨道从顶部依次向下分配。斗鱼的高频进场包与伪装成聊天的“xxx 进入直播间”文本都会在 Rust 层丢弃；所有站点的进场事件也会在前端统一隐藏。

### 5.6 醒目留言（SC）

哔哩哔哩的 `super_chat` 消息会以紧凑卡片叠放在播放器左下角，最多同时显示 3 张，并按平台给出的置顶时长倒计时退出。发送者头像与名称位于身份区，金额保持醒目；经安全校验的 B 站金额档位主色与底色构成正文带，正文最多显示 3 行。头像缺失、被拦截或加载失败时显示名称首字母；应用不请求用户资料接口。屏蔽词同样作用于 SC。在房间右侧「设置 → 醒目留言」可关闭或重新开启卡片，默认开启；未接入 SC 的平台不显示该设置。

## 6. 本地语音字幕

Tauri 桌面客户端使用 sherpa-onnx streaming Zipformer 在本机生成中英双语直播字幕；Android 和 iOS 暂不支持，也不会显示相关设置或播放器入口。进入「设置 → 播放 → 语音字幕」，开启流式字幕；VAD（静音端点检测）和自动标点默认开启，可独立关闭。模型本身在关闭自动标点时约 `488 MiB`，默认约 `550 MiB`；Windows 首次启用还会按需下载约 `212 MiB` 字幕运行库，因此对应总下载量约 `700 MiB` 或 `762 MiB`。可选「本地热词」用于主播名、游戏名等专有名词，配置后会使用本地 hotwords 文件增强识别。可选「说话人区分」默认关闭，首次开启会再下载约 `27 MiB` 的 CAMPPlus 声纹模型。字幕更新间隔可在 `0.2–1.0 秒`内按 `0.1 秒`步长调整（默认 `0.2 秒`），字号可在 `12–48 px` 内调整（默认 `20 px`）。等待模型就绪后，进入直播间并点击播放器控制栏的字幕图标即可显示或关闭字幕。鼠标悬停或键盘聚焦字幕图标可在「字幕设置」浮层中直接切换「说话人区分」、配置原文和译文语言；两侧语言均支持自动选择。字幕翻译默认关闭，开启后仅将 final 文字批量发送到 Google 翻译，实时 partial 不会发送，并会继承「设置 → 网络」中的应用代理。

Windows 和 Linux x86_64 桌面端可在「推理后端」中选择「自动 / CUDA / CPU」。自动模式优先使用 NVIDIA CUDA，CUDA 运行库或驱动不可用时自动回退 CPU；设置页会显示实际 provider 和回退原因。选择 CUDA 时也会在不可用时回退 CPU。Linux 非 x86_64、macOS 桌面端固定使用 CPU。CUDA provider 会传递给 Zipformer、标点和声纹模型；当前 VAD 是 CPU endpoint 规则，不是独立模型。CPU provider 下 Zipformer 最多 8 个线程，标点与声纹模型最多 2 个线程。配置热词时会切换 modified beam search，未配置时使用 greedy search。关闭总开关会停止采集并释放常驻识别、标点和声纹会话，但不会删除模型文件。

直播音频只在当前设备的 WebView 与 Rust 进程之间传递，不上传到 rLive 服务，也不会保存音频或字幕历史。同一个长生命周期 Zipformer stream 持续接收无重叠 PCM 分块并返回当前 partial；VAD 开启时按静音端点结束语句，关闭时仍按最长 20 秒切分；自动标点开启时 final 和 partial 会恢复中英文标点，关闭时保留原始文本。final 与 partial 自动分行，长文本按播放器宽度自然换行。启用说话人区分后，只有 final 会添加“说话人 N”匿名编号，短句和临界相似度会沿用最近稳定标签，partial 不标注；编号在同一播放会话内保持，切房或切换媒体源时重置。短句、背景音乐、重叠讲话或强噪声可能无标签或不准确，编号不是姓名识别。设备速度低于实时速度时只保留最新待处理分块，以优先保证直播播放和界面响应。构建方式、输入格式、性能参数和已知边界见[本地语音字幕](本地语音字幕.md)。

## 7. IPTV

从左侧栏进入「IPTV」后会到达 `/iptv` 频道发现首页：默认提供 IPTV-org 官方日更的中文语言、中国大陆、东亚和综合公开频道分表。自定义 HTTP(S) M3U 地址只能在「设置 → 网络」保存；配置完成后首页会将其显示为「自定义源」，不再提供自由填写地址的入口。该地址只保存在当前设备，不写入路由、历史或配置包。首页只展示来源、分类、搜索、关注、可用状态与频道列表，进入时不会挂载播放器或默认播放第一个流。内置源不再使用超过应用安全上限的全球总表；支持多关键词按频道名/分组筛选，精确与前缀匹配优先展示，常用分组可一键选择，长列表按需展开。手机端使用紧凑来源菜单和双列频道，桌面端使用分段来源切换和多列频道，但操作名称与状态反馈保持一致。

频道卡片右上角与播放页顶栏使用同一关注状态，可随时关注或取消关注；发现页顶栏的「关注」筛选只显示当前来源的关注频道，并可继续叠加分类、关键词和可用状态。关注记录以来源和频道 URL 区分，保存名称、分组、台标、协议与必要请求头快照；源更新后暂时移除的已关注频道仍会显示，并可直接使用快照播放。不同自定义 M3U 使用互相隔离的本地标识，不会把私有列表地址写入关注表。内置公开源的关注可随配置档案导入导出；自定义源关注可能包含私有流地址或请求头，因此仅保留在当前设备。

「更新源」会按照当前应用代理重新下载 M3U，并在成功后更新频道数与时间；触屏设备也可下拉更新。「检测可用性」对当前搜索和分类结果按频道 URL 去重，最多检测前 120 个；前端以每批 24 个提交，原生端进一步限制并发与单项超时，等待媒体首字节并拒绝 HTTP 错误、空响应和伪装成频道的 HTML 页面，HLS 还必须包含 `#EXTM3U` 清单头。完成后可筛选「可用 / 不可用 / 未检测」，失败频道保留原因提示。检测不会启动播放器或占用播放代理，结果不持久化，更新或切换来源后自动清除。“可用”不等于完整播放保证：后续分片、编解码器、地区限制和上游持续稳定仍可能使播放失败。

点击频道后才会进入独立、沉浸式的 `/iptv/play` 播放页，通过本机代理加载 HLS、MPEG-TS 或 FLV 流，以处理嵌套 HLS 清单、分片和常见跨域限制。播放页使用与直播房间相同的透明 React 控制栏，提供重连、播放/暂停、静音/音量、仅播声音、画中画和全屏；播放时控制栏会自动隐藏，移动指针、触摸画面或按键后重新显示。「仅播声音」保持当前频道音频，隐藏视频并释放屏幕常亮，再次点击恢复画面。焦点位于画面时可使用 `Space` / `K` 播放或暂停、`M` 静音、`F` 全屏。使用返回会回到保留来源、分类与搜索条件的频道列表。

节目内容与可用性由上游 M3U 来源决定；应用仅解析并播放配置的流地址。

## 8. 关注与历史

- **关注**：关注页 Shell 顶栏只保留「直播关注 / IPTV 频道」一级页签，并显示对应关注数量；页签切换带有跟手横滑，桌面点击仍保留淡入平移动效。直播关注桌面端左侧栏顶部提供平台和直播状态两个选择框，移动端把它们放在分组条上方；筛选平台会写入 `platform` 查询参数，状态筛选只保留在当前页面。直播关注桌面端使用「直播分组」侧栏，移动端使用横向分组条；分组管理支持新建、重命名和删除，删除后其中的主播会移至「未分组」。在直播间或直播卡片菜单中首次关注主播时，可选择「未分组」、已有分组，或当场新建分组；拖动整张关注卡片并明确进入目标分组即可归组，也可在右键菜单中选择「移至分组」。IPTV 关注使用另一套自定义分组，频道源选择位于左侧栏顶部，移动端位于分组条上方。管理按钮可新建、重命名和删除分组，频道卡片可通过整卡拖拽或右键菜单改变归属。删除分组后其中的频道进入「未分组」，M3U 自带分类仍作为频道元数据保留。分组切换时频道内容按方向平移；频道可直接进入播放页或取消关注。分组和关注归属保存在本机 SQLite，主播关注、内置公开源 IPTV 关注及 IPTV 自定义分组包含在配置导入导出中。房间右侧「关注」会把直播中的主播排在前面，并在平台名称后通过时钟图标显示已开播时长；点击卡片可直接切换房间，无需先退出。移动端在页面或房间内关注列表下拉即可刷新开播状态，桌面端保留右下角刷新按钮。
- **历史**：进入过的房间会记入历史，可从历史快速再进。

| 线路记忆 | 手动选择后按平台和直播间保存在当前设备，最多保留最近 100 个房间；优先按 `source_id` 恢复，缺失时按线路序号回退 |
| 软切换 | 默认开启；HLS、MPEG-TS、FLV 同协议换源保留播放器，FLV 替换内部流内核，任何失败自动完整重建 |
| 多画面布局 | 仅桌面端；槽位、房间元数据和各路音量保存在设备 localStorage，不进入配置导入导出 |
| 本地语音字幕 | 仅 Tauri 桌面端；sherpa-onnx Zipformer、VAD/自动标点独立开关、本地热词、按需下载约 `488–550 MiB` 识别与标点模型、Windows 另下载约 `212 MiB` 运行库、可选约 `27 MiB` CAMPPlus 匿名说话人区分、Google 双语翻译字幕、`0.2–1.0 秒`更新间隔和 `12–48 px` 字号 |
| 网络代理 | 可选 HTTP(S) 代理，如 `http://127.0.0.1:7890` |
| 本地诊断日志 | Windows 发布版写入 EXE 同级 `logs\rlive.log`，单文件超过 2 MiB 会保留上一份；日志只记录脱敏失败信息，不写入成功过程、Cookie、令牌或弹幕正文 |
| IPTV 自定义 M3U | 仅在「设置 → 网络」保存有权使用的 HTTP(S) 地址；IPTV 首页仅显示已配置的「自定义源」，地址与该源的频道关注不写入路由、历史或配置包 |
| 哔哩哔哩 Cookie | 可扫码登录或手动输入；用于只读 API / 接收弹幕，发送功能另需 `SESSDATA` 与 `bili_jct` |
| 弹幕发送 | 位于「账号」页最上方；默认关闭的本机统一开关，同时控制 B 站、斗鱼和虎牙的单条普通文本发送；各平台仍须各自满足 Cookie、房间、文本和冷却校验 |
| 斗鱼 Cookie | 可扫码登录或手动输入；发送需完整的账号、设备和弹幕会话字段。当前网页对齐的发送状态机已在个人直播间验证；运行时仍以 `chatres` 和真实回显判定结果，不能仅凭输入框可用确认送达 |
| 虎牙 Cookie | 支持扫码或手动输入；发送普通弹幕需要 `yyuid` 或 `udb_uid`，以及 `udb_n` / `udb_cred` / `udb_biztoken` |
| 抖音 Cookie | 可扫码登录或手动输入；匿名浏览会自动建立临时 `ttwid` 会话；完整登录 Cookie 可用于直播搜索和弹幕连接，但不绕过网页访问验证 |
| 关于 | 提供项目 GitHub 主页跳转 |
| 弹幕设置（房间内） | 见上文；不再放在全局设置页 |

| 浏览器访问 | 仅客户端可开关；默认只监听 `127.0.0.1`，可选局域网暴露并生成访问令牌，把同一套界面提供给浏览器 |

### 9.1 局域网同步

在「设置 → 数据管理 → 局域网同步」中，发送设备先创建同步会话，接收设备再输入发送端显示的地址和 6 位配对码。rLive 只在发送设备当前的私有 IPv4 网卡上临时监听；接收端只连接私网或回环 IP 字面量，不使用系统代理，也不会跟随重定向。会话有效期为 5 分钟，成功下载一次后立即关闭；连续 5 次输入错误配对码会锁定当前会话，需要发送端重新创建。同步数据通过临时 HTTP 会话直接传输，请仅在可信局域网中使用。

同步使用与配置档案相同的事务合并逻辑，包含主播关注、标签、内置公开源 IPTV 关注、IPTV 自定义分组、历史和可移植设置。Cookie、自定义 M3U 地址及其频道关注、多画面槽位与音量、本机统一弹幕发送授权、ASR 启用状态、模型后端、VAD/标点/说话人开关、热词、更新间隔和字幕翻译设置不会离开当前设备。同步是合并而非远程镜像或持续同步，不会删除接收设备独有的关注和历史。

两台设备必须连接到允许设备间互访的同一 Wi-Fi 或有线局域网。无法连接时，请确认发送端会话仍在倒计时内、地址与配对码输入无误，并允许系统防火墙中的 rLive 入站连接；访客 Wi-Fi、AP 隔离或客户端隔离会阻止设备互访，此时应切换到普通局域网后重试。

Cookie、自定义 M3U 地址、本机统一弹幕发送授权、ASR 启用状态、VAD/标点/说话人开关、热词、更新间隔和字幕翻译授权/语言都只保存在本机 SQLite。导入配置不会覆盖这些设备私有项。请勿提交 Cookie、私有节目源地址或热词配置到 Git 或分享。

### 9.2 浏览器访问

在「设置 → 数据管理 → 浏览器访问」中开启后，rLive 会在本机启动一个小型 HTTP 服务，把客户端里的同一套界面提供给浏览器。默认地址是 `http://127.0.0.1:17650`，端口被占用时自动改用其他可用端口。用浏览器打开界面显示的链接即可浏览、播放、看弹幕和管理关注，页面执行的是客户端里完全相同的后端逻辑，不存在第二套账号或数据。

开关只出现在 rLive 客户端中。浏览器标签页可以看到服务状态，但不能开启局域网访问，也不能关闭自己正在使用的服务。

**默认只有本机可以访问。** 需要用手机或平板访问时，打开「允许局域网访问」，rLive 会生成一个访问令牌并把它附加在分享链接中。此时把链接里的 `127.0.0.1` 换成本机在局域网中的 IP 即可（界面中有提示）。持有该链接的设备可以完全操作本机 rLive 的数据和已登录账号，因此请只在受信任的网络中开启，用完及时关闭；关闭客户端也会一并停止服务。令牌在每次开启时重新生成，浏览器标签页关闭后即失效。

以下能力需要本机文件或设备权限，在浏览器中不可用，对应入口会隐藏：

| 能力 | 原因 |
|------|------|
| 配置导入导出 | 需要读写本机文件；可改用局域网同步 |
| 本地语音字幕 | 需要本机模型文件与麦克风/音频 IPC |
| Android 播放器控制 | 需要 Android 原生桥 |
| 开关浏览器访问本身 | 这项决定留在客户端一侧 |

**当前限制：局域网设备暂不能播放。** 直播流由本机 `stream_proxy` 代理，它只监听 `127.0.0.1`，播放地址也是 `127.0.0.1`。因此在本机浏览器中播放正常，而局域网设备打开的页面会把该地址解析到自己身上，浏览、搜索、关注、历史和弹幕可用，点击播放则会失败。需要在其他设备上观看时，请使用 rLive 客户端。

若打开链接后提示未连接本地服务，请确认客户端仍在运行、服务未被关闭，以及局域网访问时链接中的令牌完整。

## 10. 常见问题

**Q: 语音字幕支持 GPU 吗？**

A: Windows 和 Linux x86_64 桌面端支持 NVIDIA CUDA。请在设置中选择「自动」或「CUDA」；自动模式检测不到兼容 GPU、NVIDIA 驱动、CUDA provider 或其依赖时会回退 CPU，并显示实际 provider。Windows 构建默认包含 `sherpa-onnx-v1.13.4-win-x64-cuda.tar.bz2`，Linux 构建默认包含 `sherpa-onnx-v1.13.4-linux-x64-gpu.tar.bz2`，两者都需要 Compute Capability 6.1 及以上、CUDA 11.x 和 x86-64 cuDNN 8.x。Linux CUDA 路径尚未完成完整测试；macOS、Linux 非 x86_64 和移动端暂不支持 CUDA 字幕。详见[本地语音字幕](本地语音字幕.md)。

**Q: 语音字幕延迟较高或偶尔跳过内容？**

A: 将「字幕更新间隔」调到 `0.2 秒`可获得最快刷新；`0.3–0.5 秒`可减少 IPC 调用。Zipformer 的识别上下文保存在同一个 stream 中，不会因分块变短而重置。慢设备只保留最新待处理分块，不会无限排队。启用自动标点后，endpoint final 会恢复标点并与当前 partial 分行；配置热词会增加 modified beam search 开销，性能不足时可减少热词数量。编译期默认参数见[本地语音字幕](本地语音字幕.md)。

**Q: 说话人编号为什么变化或没有显示？**

A: 这是每个播放会话内的匿名声纹聚类，不是姓名识别；切房、换媒体源或关闭字幕会从“说话人 1”重新编号。过短语句可能无法提取声纹，音乐、噪声和多人同时说话也会降低准确率，此时字幕可能不显示编号。

**Q: 字幕字号会影响 ASR 推理性能吗？**

A: 不会。字号只在播放器叠加层渲染时生效，范围为 `12–48 px`，不会改变音频采集、模型或解码参数。

**Q: 斗鱼弹幕提示 HandshakeFailure？**  
A: 请使用包含 `native-tls` 修复后的版本；旧版 rustls 无法与斗鱼弹幕服握手。

**Q: 哔哩哔哩无弹幕？**  
A: 检查 Cookie 是否有效、是否含 `SESSDATA` 等；匿名时部分房间仍可能受限。

**Q: B 站二维码过期或扫后未登录？**
A: 点击「刷新二维码」后重新扫描，并在手机端确认登录；网络异常时可切换到「手动输入」粘贴浏览器 Cookie。

**Q: 虎牙进房闪退？**  
A: 请使用已修复 UTF-8 解析的版本；旧版在中文房间页可能 panic。

**Q: 抖音搜索提示需要登录？**  
A: 在「设置 → 账号 → 抖音」扫码登录，或粘贴完整网页端登录 Cookie 后重试。分类、推荐和房间播放不要求手动登录；推荐和分类支持加载更多，首屏签名失败时回退 SSR。若扫码返回浏览器访问验证页，请检查应用代理后重试，或在已完成验证的网页端复制完整 Cookie。

**Q: 抖音弹幕无法连接？**
A: 先确认房间仍在直播，并尝试重新进入房间以刷新签名与网页会话。若已登录，可在「设置 → 账号 → 抖音」检查 Cookie 是否有效。网络代理异常、地区限制或平台风控仍可能导致连接失败。

**Q: B站发送框为什么不可用？**
A: 先在「设置 → 账号」最上方启用「启用发送功能」，再保存包含 `SESSDATA` 和 `bili_jct` 的 Cookie；发送框只会在 B 站房间显示。

**Q: 斗鱼发送框为什么不可用，或点击后没有弹幕？**
A: 先检查「启用发送功能」和完整本机登录态；斗鱼发送还需要账号、稳定设备和弹幕会话字段。当前实现会分别报告本地提交、平台拒绝和未确认；只有 `chatres(res=0)` 加正常收弹幕连接的真实回显才算成功。请勿对未知状态重复发送，详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。

**Q: 斗鱼发送失败后如何收集诊断信息？**
A: Windows 查看 `rlive.exe` 同级 `logs\rlive.log` 中脱敏的失败阶段与错误码，并以平台真实回显为准；不要分享 Cookie、令牌、签名或弹幕正文。协议、限制与验证记录见[斗鱼平台 API 文档](斗鱼平台API文档.md)。

**Q: 虎牙发送框为什么不可用？**
A: 先在「设置 → 账号」最上方启用「启用发送功能」，再在「虎牙」中扫码登录或手动保存同时包含 `yyuid` 或 `udb_uid`，以及 `udb_n` / `udb_cred` / `udb_biztoken` 的有效 Cookie 后重新进入房间。

**Q: 黑屏无声？**  
A: 尝试换线路/清晰度；确认代理设置未阻断 CDN；退出再进同一房间时应用会刷新播放地址。
