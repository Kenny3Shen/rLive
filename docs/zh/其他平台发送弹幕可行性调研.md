# 其他平台发送弹幕可行性调研

更新时间：2026-07-26。本文讨论的是“观众以自己的已授权账号，在直播间主动发送一条普通文字弹幕”，不包括礼物、付费、自动回复、批量/定时发送或主播运营工具。

## 结论总览

| 平台 | 现阶段结论 | rLive 决策 |
|------|------------|------------|
| 哔哩哔哩 | **已实现，待受控账号验收** | 唯一已完成端到端代码实现与本地 HTTP 契约测试的直连发送链路；发布前仍需在获许可房间完成受控账号回显验收。 |
| 斗鱼 | **需要官方授权** | 现有公开能力可用于接收弹幕，不将未公开的网页/长连接报文当作发送接口；获得明确的“观众普通聊天发送”权限、文档和测试环境后再接入。 |
| 虎牙 | **需要官方授权** | 当前接收连接是匿名订阅链路。公开可见资料以合作 SDK 为主，未确认可供桌面客户端直接调用的普通文字发送契约。 |
| 抖音 | **需要官方授权** | 已有签名服务仅用于接收实时消息，不能推导出发送权限。应以官方直播 SDK / 明确的互动授权能力为前提，并先确认桌面端适配。 |
| 快手 | **不建议** | rLive 目前尚无快手实时弹幕接收链路；在没有官方双向互动契约前，先做“只发送”没有可验证的产品和技术基础。若获得官方能力，应先重新评估为“需要官方授权”。 |

这里的 **已实现，待受控账号验收** 表示 rLive 已完成代码与本地 HTTP 契约验证，但尚需在获许可房间完成真实服务回显验收；**需要官方授权** 表示只有获得平台书面/控制台授予的对应写入范围后才可排期；**不建议** 是当前项目的实现决策，不等同于宣称该能力在任何条件下都不可能实现。

所有平台还有一条共同结论：**通过复刻网页私有接口、重放 WebSocket 报文、伪造指纹或绕过签名来发送，均为“不建议”**。这类方式没有稳定契约，容易触发账号风控，也不应成为 rLive 的实现承诺。

## 逐平台依据与可行路径

### 哔哩哔哩：已实现，待受控账号验收

rLive 已有真实房间号、Cookie 存储、后端发送校验和普通聊天回显链路，并以本地 HTTP 服务验证表单、Cookie/CSRF 请求头、成功和限流映射。该链路的接口形态、登录前提及安全边界见 [B 站发送弹幕调研](B站发送弹幕调研.md)。发布前仍需使用受控账号和获许可房间确认真实服务端回显。

该实现不扩大为自动化能力：仍应只允许用户主动发起的普通文本，保持服务端校验、速率限制、失败不盲目重试，以及不处理礼物和支付。

### 斗鱼：需要官方授权

斗鱼开放平台公开 API 目录将“房间弹幕”列为“拉取弹幕”和“接入弹幕”，并以应用权限方式管理“获取指定直播间弹幕信息”。在本次查阅范围内，目录没有列出面向普通观众的直播间文字发送接口。

- 依据：[斗鱼开放平台 API 接口目录](https://open.douyu.com/source/)；目录中的详细接口内容可能要求开发者登录。
- 现有 rLive 实现：`src-tauri/src/danmaku/douyu.rs` 仅完成登录房间、加入群组、心跳与接收 `chatmsg` 等消息，没有可用的已授权发言身份或发送能力。
- 可行前提：平台提供明确的写入 scope、OAuth/应用凭据流程、限频与错误码文档，以及可供受控测试的房间或测试账号。

在这些前提之前，不应把接收协议中出现的消息类型或历史社区报文视为可写接口。

### 虎牙：需要官方授权

rLive 连接的是用于接收推送的匿名 TARS/WebSocket 链路；它没有携带可审计的用户授权身份，也没有暴露可用于普通文字聊天的产品契约。

- 依据：[虎牙开放平台](https://open.huya.com/) 与 [虎牙游戏联运 SDK 文档](https://dev.huya.com/docs/live-sdk/)。公开资料展示的是合作接入、账号/支付/观看/开播等 SDK 能力，且文档入口含 Android 接入材料；本次未确认可由 Tauri 桌面客户端直接使用的普通弹幕写入 API。
- 现有 rLive 实现：`src-tauri/src/danmaku/huya.rs` 只构造进房、心跳和接收消息。
- 可行前提：取得虎牙确认的桌面适用 SDK 或 API、账号授权方式、发送范围、审核/限频要求与上线许可。

即使合作 SDK 能够呈现原生互动，也不代表 rLive 可以把它替换为自定义的 HTTP 或 WebSocket 发送框。

### 抖音：需要官方授权

当前抖音实时弹幕链路先取得短时签名 WSS 地址，再接收推送。该签名只证明“可以建立接收连接”，不授予以某一用户身份写入聊天室的能力。

- 依据：[抖音 SDK 直播能力方案](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/solution)。官方资料说明第三方 App 在用户授权后可获得完整直播互动体验；这是一套受授权 SDK 产品能力，不是可从当前接收连接推导出的独立桌面发送 API。
- 现有 rLive 实现：`src-tauri/src/danmaku/douyin.rs` 仅请求受信任签名服务、建立 WSS、心跳、确认帧和解码入站消息。签名服务说明见 [抖音弹幕签名服务接入](抖音弹幕签名服务.md)。
- 可行前提：抖音确认适用于桌面产品的接入形态，授予对应应用和用户的互动写入权限，并提供审核、风控、限频与错误处理要求。

不应将 `Cookie`、短时签名 URL 或网页端行为参数视为可移植的“发送凭据”。

### 快手：不建议

rLive 的快手接入目前使用公开推荐、分类和房间初始状态数据；实时弹幕接收尚未实现。因此无法在本项目中验证“发出后由实时流回显”的基本闭环。

- 依据：`src-tauri/src/sites/kuaishou.rs` 与 [用户指南的当前能力表](用户指南.md)均明确快手“暂不支持实时弹幕”。[快手开放平台](https://open.kuaishou.cn/)提供开发者入口，但本次公开材料查阅未确认无合作授权即可使用的普通直播间文字发送契约。
- 当前决策：不为发送功能逆向网页请求、登录态或消息签名；不在尚无接收能力时新增仅发送的 UI。
- 重新评估条件：先取得官方实时互动/写入能力和桌面适用授权，再完成接收、身份状态、发送、回显、限频和错误恢复的闭环。

## 统一接入门槛

任何平台从“需要官方授权”升级到“已实现，待受控账号验收”前，至少要同时满足以下条件：

1. 平台以书面协议、开发者控制台权限或正式文档明确允许应用代用户发送**普通直播间聊天**；不是只允许读消息、送礼、私信、主播工具或嵌入原生页面。
2. 使用平台认可的 OAuth、SDK 或应用凭据；不能要求用户复制 Cookie、令牌、指纹参数或把凭据交给未知第三方服务。
3. 后端拥有可测试的身份状态、房间身份、文本校验、去重/冷却、限频、可读错误码与撤销授权流程。
4. UI 仅在权限就绪时出现发送框；每次发送必须由用户操作触发，不提供批量、循环、定时、自动回复、自动重试、礼物或支付。
5. 在可控账号和测试/获许可的房间完成发送、回显、拒绝、过期授权、断网和限频验证；日志和错误提示不得泄漏 Cookie、签名、消息内容或原始上游响应。
6. 产品、法务与平台条款审查通过，并有能力在授权撤销、接口下线或风控变化时立即关闭该平台的发送入口。

## 调研边界

公开文档会变更，且部分平台资料仅向已入驻合作方开放。本页记录的是 2026-07-26 可公开访问资料与 rLive 现有接入的交叉结论：未在公开目录中找到接口，不证明平台绝对不存在该能力；它只意味着 rLive 不应据此承诺或实现未授权的发送功能。获得新的官方合同、权限页或 SDK 文档后，应更新本页并重新做受控验证。
