# 其他平台发送弹幕可行性调研

更新时间：2026-07-27。本文讨论的是“观众以自己的账号，在直播间主动发送一条普通文字弹幕”，不包括礼物、付费、自动回复、批量/定时发送或主播运营工具。

## 结论总览

| 平台 | 现阶段结论 | rLive 决策 |
|------|------------|------------|
| 哔哩哔哩 | **已实现，待受控账号验收** | 唯一已完成端到端代码实现与本地 HTTP 契约测试的直连发送链路；发布前仍需在获许可房间完成受控账号回显验收。 |
| 斗鱼 | **已通过本机 Cookie 认证实现** | 用户通过扫码登录或手动输入保存自己的本机账号 Cookie 后，可主动发送一条普通文字弹幕。这不代表斗鱼向 rLive 授予了公开写入 API；真实服务验收和条款合规仍由用户自行负责。 |
| 虎牙 | **已通过本机 Cookie 认证实现** | 用户手动保存自己的本机账号 Cookie 后，可主动发送一条普通文字弹幕。这不代表虎牙向 rLive 授予了公开写入 API；真实服务验收和条款合规仍由用户自行负责。 |
| 抖音 | **需要官方授权** | 已有签名服务仅用于接收实时消息，不能推导出发送权限。应以官方直播 SDK / 明确的互动授权能力为前提，并先确认桌面端适配。 |
| 快手 | **不建议** | rLive 目前尚无快手实时弹幕接收链路；在没有官方双向互动契约前，先做“只发送”没有可验证的产品和技术基础。若获得官方能力，应先重新评估为“需要官方授权”。 |

这里的 **已实现，待受控账号验收** 表示 rLive 已完成代码与本地 HTTP 契约验证，但尚需在获许可房间完成真实服务回显验收；**已通过本机 Cookie 认证实现** 表示 rLive 已有只在本机运行、由用户主动触发的发送链路，会校验保存的账号 Cookie、文本和短暂冷却；它**不**表示平台已向 rLive 授予公开应用写入范围，也不保证任一账号或房间一定接收该消息。**需要官方授权** 表示只有获得平台书面/控制台授予的对应写入范围后才可排期；**不建议** 是当前项目的实现决策，不等同于宣称该能力在任何条件下都不可能实现。

B 站、斗鱼和虎牙发送功能被刻意限制为本机账号能力，而非通用报文重放或自动化入口：三者共同受默认关闭的本机 `danmaku_send_enabled` 开关控制，并仍各自校验 Cookie 和平台条件；该开关不随配置导出或导入。rLive 不上传保存的 Cookie、不接收任意报文/指纹参数、不提供批量、定时、自动回复或对不确定写入自动重试。发送 command 在本机成功返回后，当前前端会话会显示琥珀色「待平台回显」本地提示，但它不是平台回显，也不会按相同文本自动与真实回显合并或消失。一次本机写入成功后，仍应等待正常房间弹幕连接回显并完成真实服务验证。用户必须自行确认自己的账号、房间和使用方式符合平台条款与当地法律。

## 逐平台依据与可行路径

### 哔哩哔哩：已实现，待受控账号验收

rLive 已有真实房间号、Cookie 存储、后端发送校验和普通聊天回显链路，并以本地 HTTP 服务验证表单、Cookie/CSRF 请求头、成功和限流映射。除 B 站自己的登录条件外，发送还需要启用与斗鱼、虎牙共用的默认关闭本机开关 `danmaku_send_enabled`。该链路的接口形态、登录前提及安全边界见 [B 站发送弹幕调研](B站发送弹幕调研.md)。发布前仍需使用受控账号和获许可房间确认真实服务端回显。

该实现不扩大为自动化能力：仍应只允许用户主动发起的普通文本，保持服务端校验、速率限制、失败不盲目重试，以及不处理礼物和支付。

### 斗鱼：已通过本机 Cookie 认证实现

斗鱼发送框现会建立短时、已认证的弹幕会话并提交一条普通文字弹幕。用户还需先在「设置 → 账号」最上方启用与 B 站、虎牙共用的「启用发送功能」。在「设置 → 账号 → 斗鱼」中，用户可通过扫码登录取得本机账号 Cookie，或手动输入 Cookie。发送功能需要 `acf_username`、`acf_stk` 与 `acf_ltkid`（也兼容旧的 `_acf_ltkid_` 写法）。Cookie 仅保存在当前设备的账号存储中，不显示在日志内，也不会交给第三方签名服务。

- 现有 rLive 实现：`src-tauri/src/danmaku/douyu.rs` 已完成登录房间、加入群组、心跳、接收 `chatmsg`，以及已认证的单条发送。网络写入前会重验共用本机开关、数字房间号、非空单行且不超过 100 个 UTF-16 单元的文本，并施加保守的按房间 3 秒冷却；不自动重试。写入 command 成功返回后，前端仅显示「我 / 本地已提交，待平台回显」本地提示，正常房间弹幕才是独立的送达信号。
- 公开资料限制：[斗鱼开放平台 API 接口目录](https://open.douyu.com/source/)将“房间弹幕”列为“拉取弹幕”和“接入弹幕”；本次查阅的目录仍未记录公开的普通观众文字写入 API。因此，该实现不能表述为已获官方 API 授权的接入。
- 用户责任：Socket 写入或后续房间回显都不能替代真实服务验收。请仅在自己的账号和获准发言的房间测试，遵守服务端审核/限频及斗鱼的现行条款。

发送只会在用户点击发送时触发，不包含礼物、支付、批量/定时发送、自动回复、自动重试或 Cookie 导出。

### 虎牙：已通过本机 Cookie 认证实现

rLive 现会解析当前虎牙房间，并使用用户手动保存的 Cookie 建立已认证发送会话，提交一条普通文字弹幕。用户还需先在「设置 → 账号」最上方启用与 B 站、斗鱼共用的「启用发送功能」。在「设置 → 账号 → 虎牙」中粘贴包含数字账号 ID（`yyuid` 或 `udb_uid`）及不透明登录凭据（`udb_n` 或 `udb_cred`）的 Cookie。虎牙当前不提供扫码登录，因此需要手动输入 Cookie。Cookie 仅保存在当前设备的账号存储中，不会记录到日志，也不会上传到其他服务。

- 现有 rLive 实现：`src-tauri/src/danmaku/huya.rs` 处理 TARS/WebSocket 房间流量以及已认证的单条发送。发送前会重验共用本机开关、房间元数据、Cookie 字段、非空单行且不超过 30 个 UTF-16 单元的文本和短暂本机冷却；对于不确定的写入不自动重试。写入 command 成功返回后，前端仅显示「我 / 本地已提交，待平台回显」本地提示，正常房间弹幕仍是独立的送达信号。
- 公开资料限制：[虎牙开放平台](https://open.huya.com/) 与 [虎牙游戏联运 SDK 文档](https://dev.huya.com/docs/live-sdk/)展示的是合作/SDK 能力；本次查阅未确认适合 Tauri 桌面客户端的公开普通文字写入 API。本机 Cookie 发送功能不等同于平台授予的应用写入契约。
- 用户责任：真实服务验证、审核/限频、房间可发言资格以及是否符合虎牙条款，均由用户自行确认。一次本机发送结果不能保证虎牙已接受或展示该消息。

该功能始终由用户主动触发，不提供礼物、支付、批量/定时发送、自动回复、自动重试或 Cookie 导出。

### 抖音：需要官方授权

当前抖音实时弹幕链路先取得短时签名 WSS 地址，再接收推送。该签名只证明“可以建立接收连接”，不授予以某一用户身份写入聊天室的能力。

- 依据：[抖音 SDK 直播能力方案](https://developer.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/solution)。官方资料说明第三方 App 在用户授权后可获得完整直播互动体验；这是一套受授权 SDK 产品能力，不是可从当前接收连接推导出的独立桌面发送 API。
- 现有 rLive 实现：`src-tauri/src/danmaku/douyin.rs` 仅调用固定本机 `http://127.0.0.1:18080/sign` 签名服务、建立 WSS、心跳、确认帧和解码入站消息。签名服务说明见 [抖音弹幕签名服务接入](抖音弹幕签名服务.md)。
- 可行前提：抖音确认适用于桌面产品的接入形态，授予对应应用和用户的互动写入权限，并提供审核、风控、限频与错误处理要求。

不应将 `Cookie`、短时签名 URL 或网页端行为参数视为可移植的“发送凭据”。

### 快手：不建议

rLive 的快手接入目前使用公开推荐、分类和房间初始状态数据；实时弹幕接收尚未实现。因此无法在本项目中验证“发出后由实时流回显”的基本闭环。

- 依据：`src-tauri/src/sites/kuaishou.rs` 与 [用户指南的当前能力表](用户指南.md)均明确快手“暂不支持实时弹幕”。[快手开放平台](https://open.kuaishou.cn/)提供开发者入口，但本次公开材料查阅未确认无合作授权即可使用的普通直播间文字发送契约。
- 当前决策：不为发送功能逆向网页请求、登录态或消息签名；不在尚无接收能力时新增仅发送的 UI。
- 重新评估条件：先取得官方实时互动/写入能力和桌面适用授权，再完成接收、身份状态、发送、回显、限频和错误恢复的闭环。

## 安全与责任边界

已实现的 B 站、斗鱼、虎牙发送以及后续任何发送能力，都应保持以下约束：

1. 默认关闭的本机统一发送开关与平台各自的已认证账号条件均满足时才显示发送框；该开关不导出、不导入。每次仅能由用户主动发送一条普通直播间文字弹幕；不提供批量、循环、定时、自动回复、自动重试、礼物或支付。
2. Cookie 仅保存在本机 SQLite 账号存储中；不得写入日志、配置导出、回显给用户或传给无关服务。
3. 后端会在尝试网络写入前校验账号就绪状态、房间身份、文本和保守的本机冷却。平台自身的审核与限频始终具有最终效力。
4. 写入 command 在本机成功返回后，应用仅生成当前前端会话中的本地待回显标记（列表「我 / 本地已提交，待平台回显」，飘屏琥珀色 `【我·待平台回显】`）。它不冒充平台聊天，不会按相同文本与真实回显自动合并或消失；用户仍应等待正常房间弹幕连接回显，网络结果不确定时应视作未知状态，而非自动重新发送。
5. 每位用户都应自行在有权发言的账号和房间完成真实服务验证，并遵守现行平台条款、审核规则和当地法律。浏览器 Cookie 不是平台授予应用写入权限的证明。
6. 若平台发布官方 OAuth/SDK/写入契约、修改规则、拒绝该流程或撤销访问，应重新评估并在合适时关闭功能，之后再将其描述为受支持能力。

## 调研边界

公开文档会变更，且部分平台资料仅向已入驻合作方开放。本页记录的是 2026-07-27 可公开访问资料与 rLive 现有接入的交叉结论：未在公开目录中找到接口，不证明平台绝对不存在该能力；实现本机 Cookie 流程也不证明已获得官方应用授权或能够长期通过真实服务验收。获得新的官方合同、权限页、SDK 文档或平台行为变化后，应更新本页并重新做受控验证。
