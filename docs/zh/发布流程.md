# 发布流程

本仓库将持续集成与正式发布分开：PR 和 `master` 推送只运行检查与测试；只有推送版本标签才会构建、签名并创建 Release 草稿。

## 触发条件

1. 确认 `package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 的版本完全一致。
2. 提交版本变更并推送，例如 `git tag v2.0.0 && git push origin v2.0.0`。
3. `.github/workflows/release.yml` 会拒绝与版本不一致的标签，且签名构建通过后才创建 GitHub draft Release。

Release 草稿不会自动公开。审核 Windows、macOS、Android、Linux 产物和 `SHA256SUMS.txt` 后，再在 GitHub Release 页面手动发布。

> [!WARNING]
> 桌面录制已固定依赖进程内 FFmpeg，三个平台都从同一份官方 FFmpeg 9.0.1 源码（相同 SHA-256）按需裁剪自建，只启用录制实际用到的组件。Windows 由 `scripts/prepare-windows-ffmpeg.ps1` 用 runner 自带的 MSYS2 与 MinGW-w64 构建 shared SDK，TLS 走系统原生 schannel，三个 DLL 连同 LGPL 许可证和构建说明纳入 NSIS/MSI；`--enable-gpl` 不再启用，脚本断言 `CONFIG_GPL`、`CONFIG_NONFREE`、`CONFIG_VERSION3`、`CONFIG_GPLV3`、`CONFIG_LGPLV3` 全为 0，原先因 Gyan `full_build-shared` 而需要的 GPLv3 合规审计不再适用。macOS 由 `scripts/prepare-macos-ffmpeg.sh` 静态链接 LGPL 最小构建（签名已核对），产物不再依赖 Homebrew。Linux 由 `scripts/prepare-linux-ffmpeg.sh` 静态链接同一套组件，发行版 `libav*-dev` 已从构建依赖中移除，工作流用 `readelf -d` 断言四个包的 ELF 都没有 `libav*`/`libswresample` 的 NEEDED 项。
>
> CI 现状：Windows、macOS（arm64 与 Intel）、Linux、Android 全部 job 已通过。三个桌面平台的 FFmpeg 都已固定版本、校验和与组件白名单，且都验证为 LGPL 2.1+。

## 版本递增规则

- 一次提交按完整改动的最高影响级别只递增一次。仅修复用户可见 bug 时递增 patch；包含向后兼容的新功能时递增 minor 并将 patch 归零；本次数据与 IPC 断代固定使用 `2.0.0`。同一提交同时包含 fix 与 feat 时按 minor 处理。
- 纯文档、测试、格式、构建维护或不改变产品行为的重构不自动递增版本。
- major 版本只能在用户明确指定后更新，不能仅因识别到破坏性变更就自动递增。
- 版本递增与功能改动放在同一个提交中，并同步修改 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`；随后刷新 `src-tauri/Cargo.lock`，确认根包版本及三处权威版本一致。版本标签仍由发布流程单独、明确地创建。

## 2.0 数据断代核验

发布 `v2.0.0` 前必须按 [2.0 严格断代](2.0严格断代.md) 完成断代核验并保留记录：确认空白数据库能初始化为 schema `3`，schema `1`、`2`、未知版本和无版本旧库均被拒绝且不改写；确认设置、profile v2、LAN Sync v2、localStorage v2 和录制 config/metadata v2 的旧格式均被拒绝或跳过。升级前需在旧版本自行导出 profile，并备份旧数据库和录制目录；2.0 不提供内置迁移或旧录制回放支持。没有这些记录时，不得推送 `v2.0.0` 正式 tag。

## 一次性 GitHub 配置

创建名为 `release` 的 GitHub Environment，将它限制为 `v*` 标签并按团队需要设置审核人。签名 secrets 只能配置在该 Environment；PR 和普通 CI 永远不会读取它们。

| 用途 | 名称 | 类型 |
| --- | --- | --- |
| Android keystore 文件的 Base64 | `ANDROID_KEYSTORE_BASE64` | secret |
| Android keystore 密码 | `ANDROID_KEYSTORE_PASSWORD` | secret |
| Android key alias | `ANDROID_KEY_ALIAS` | secret |
| Android key 密码 | `ANDROID_KEY_PASSWORD` | secret |
| Android 证书 SHA-256 指纹（可选） | `ANDROID_CERT_SHA256` | variable |

仓库 Actions 设置还必须允许 `GITHUB_TOKEN` 在最终发布 job 中拥有 `contents: write` 权限。

## Android 签名

首次生成 keystore 时，将原始 `.jks` 放在仓库外的安全位置。示例：

```bash
keytool -genkeypair -v -keystore rlive-release.jks -alias rlive \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w 0 rlive-release.jks
```

把 Base64 输出作为 `ANDROID_KEYSTORE_BASE64` 保存。不要提交 `.jks`、`keystore.properties`、密码或 Base64 文本。发布工作流会在临时目录还原文件，写入被忽略的 Gradle properties，使用 arm64 目标构建并执行 `apksigner`、`jarsigner` 验证，最后清理签名文件。

### 本机签名构建

密钥库保存在仓库外后，先收紧文件权限并确认 alias 与证书指纹；`keytool` 会在本机提示输入密码，不要把密码传给聊天或写进命令历史：

```bash
chmod 600 /home/shenss/upload-keystore.jks
keytool -list -v -keystore /home/shenss/upload-keystore.jks
```

在 `src-tauri/gen/android/app/keystore.properties` 创建一个权限为 `600` 的本地文件（该文件已被 Git 忽略），填入实际值：

```properties
storeFile=/home/shenss/upload-keystore.jks
storePassword=<keystore 密码>
keyAlias=<keytool 输出的 Alias name>
keyPassword=<私钥密码>
```

然后构建并验签：

```bash
bun run tauri -- android build --ci --target aarch64 --apk --aab
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --verbose --print-certs \
  src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
jarsigner -verify -strict \
  src-tauri/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab
```

本地 `keystore.properties` 不会被同步脚本复制到 Windows 镜像，避免明文密码遗留在 `D:\\dev\\rLive`。

### GitHub Environment 配置

1. 打开 `Settings → Environments → New environment`，创建精确名称为 `release` 的环境。
2. 在该环境启用所需审核人，并在 deployment branches/tags 中仅允许 `v*` 标签。
3. 在 **Environment secrets** 中添加 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`。可在私有 WSL 终端执行 `base64 -w 0 /home/shenss/upload-keystore.jks | clip.exe`，将剪贴板中的单行文本粘贴到第一个 secret；不要将其贴到聊天或仓库。
4. 在 **Environment variables** 中添加 `ANDROID_CERT_SHA256`（上面 `keytool` 输出的 SHA-256 指纹）。推荐配置它，以让发布工作流验证实际使用的证书。
5. 在 `Settings → Actions → General → Workflow permissions` 允许 `GITHUB_TOKEN` 读写仓库内容；否则最终 job 无法创建 Release 草稿。

正式 tag 会并行构建 Windows x64、macOS（Apple Silicon 与 Intel）、Android arm64-v8a 和 Linux x86_64 产物。Android 使用上面的 Environment secrets 签名；Windows 安装包当前不做 Authenticode 签名，安装或首次启动时可能显示 SmartScreen 提示；macOS DMG 不做 Apple 签名与公证，首次打开需在「系统设置 → 隐私与安全性」中允许，或对应用执行 `xattr -cr`；Linux `.deb` 不做仓库级签名。

三个桌面平台的 FFmpeg 都已固定版本、校验和与组件白名单。Windows 由 `scripts/prepare-windows-ffmpeg.ps1` 自建裁剪版 shared SDK，并将所需 `avformat`、`avcodec`、`avutil` 和许可说明纳入 NSIS/MSI；macOS 由 `scripts/prepare-macos-ffmpeg.sh` 构建静态库并以 `--features ffmpeg-static` 链接进二进制，因此不需要 `Frameworks` 目录、install name 重写或额外签名范围，工作流用 `otool -L` 断言二进制与 DMG 内应用都没有 `libav*` 动态依赖；Linux 由 `scripts/prepare-linux-ffmpeg.sh` 同样构建静态库并以 `--features ffmpeg-static` 链接，`libav*-dev` 已从构建依赖移除，工作流用 `readelf -d` 断言 release staging、DEB、RPM 和 AppImage 四种布局的 ELF 都没有 `libav*`/`libswresample` 的 NEEDED 项。DEB、RPM 和 AppImage 仍会携带私有 CPU-only Sherpa/ONNX Runtime `.so` 并为标准安装布局设置相对 RUNPATH。发布核验必须在未安装 FFmpeg 开发包的干净机器执行启动和实际 HLS/FLV 录制。

Linux 三个包的 RUNPATH 口径不同。`build.rs` 为应用 ELF 链接 `$ORIGIN` 与 `$ORIGIN/../lib/rLive` 两条，DEB、RPM 与 release staging 都保留这个值；AppImage 由 linuxdeploy 打包，它把捆绑库集中到 `usr/lib` 并按自身布局重写 RUNPATH 为 `$ORIGIN/../lib`，原值被覆盖。工作流的 `verify_runtime` 因此接受空格分隔的候选列表，只对 AppImage 额外放行 `$ORIGIN/../lib`，其余三路仍只认 `$ORIGIN/../lib/rLive`。放宽仅限 RUNPATH 字面量，`ldd` 断言保留：当 RUNPATH 只有 `$ORIGIN/../lib` 而运行库仍留在 `rLive/` 子目录时 `ldd` 会报 `not found`，此时 AppImage 本身不可用，必须失败而不是放过。

### AppImage 精简未引用的运行库

`libsherpa-onnx-cxx-api.so` 是 sherpa 的 C++ 封装，本项目既不链接（不出现在任何 NEEDED 项里）也不 `dlopen` 它（`asr.rs` 只按名字打开 CUDA 驱动），linuxdeploy 因此从不把它部署到 `usr/lib`，它只留在 `usr/lib/rLive/` —— 而该目录在 RUNPATH 被重写后已不在任何搜索路径上。工作流在 `bun run bundle:linux` 之后、校验之前删除这个文件，再用 tauri 缓存里的 `linuxdeploy-plugin-appimage` 重新打包镜像。实测产物由 89.854 MB 降到 89.787 MB。

只删这一个文件。`libonnxruntime.so` 与 `libsherpa-onnx-c-api.so` 同样在 `usr/lib` 和 `usr/lib/rLive/` 各有一份逐字节相同的副本，但 squashfs 会对相同数据块去重，两处实际共享同一份数据：实测把它们也删掉只再省 0.003 MB，却要额外引入逐文件比对、退化场景判断，并使 `usr/lib/rLive` 消失、迫使 `verify_runtime` 为 AppImage 另设一套清单口径。保留它们即维持 tauri 的原始布局，`verify_runtime` 也能继续沿用与 DEB/RPM 相同的精确清单比对，只需把已删除的 C++ 封装从期望清单中排除。

删除前仍校验假设：扫描 AppDir 内所有 ELF 的 NEEDED 项，只有确认无人引用才删除，否则保留并跳过重新打包。

重打包必须直接调用 appimage 输出插件，不能重跑 `linuxdeploy --plugin gtk --output appimage`：gtk 插件不幂等，它用不带 `-f` 的 `ln -s` 为 GTK 模块建符号链接，第二次运行会在 tauri 那次已建好的 27 个链接上报 `File exists` 并退出 1，连带 linuxdeploy 一起失败（v2.6.15 实测）。依赖部署在首次 bundle 时已完成，剩下要做的仅是重新打包 AppDir，这正是该插件的职责。插件自身不打包，它会在自身二进制同目录及 `PATH` 中查找 `appimagetool`（其发布包已随附）。

macOS 与 Linux 静态 FFmpeg 的构建口径相同：官方 `ffmpeg-9.0.1.tar.xz`，SHA-256 `cf38e0e28c7e5605942c4a77755349b0145804a397af37eb1fb4c77cb237f635`，已用官方签名密钥 `FCF986EA15E6E293A5644F10B4322F04D67658D8` 验证。构建不传 `--enable-gpl`，仅启用录制实际使用的组件（FLV/HLS/MPEG-TS/MOV/Matroska 解复用、FLV/MPEG-TS 复用、file/http/https/tls/tcp/crypto 协议），结果为 LGPL v2.1+。`configure` 在依赖缺失时会把组件降级为警告并仍以 0 退出，脚本因此改为断言 `config_components.h` 中的 `CONFIG_*` 宏，避免 HTTPS 等能力被静默去掉后只在用户机器上暴露。

两个平台只在 TLS 后端上不同：macOS 用系统自带的 Secure Transport，Linux 用 OpenSSL。Linux 不选 GnuTLS 是权衡后的结果——`configure` 把 `gnutls` 放在普通的 `EXTERNAL_LIBRARY_LIST`，只有同时传 `--enable-gpl` 时才拒绝 `openssl`（见 `configure` 中 OpenSSL 的许可判断），所以两者对本项目的 LGPL 构建都可用；但 Debian 的 `gnutls.pc` 声明 `Libs.private: -lgmp` 并 `Requires.private` nettle/hogweed/libtasn1/libidn2/p11-kit，静态链接会引入 LGPLv3 的 GMP 并要求这些静态库齐备，而 `libssl.pc` 只需 libcrypto；且应用自身经 reqwest 的 native-tls 本来就链接 OpenSSL，复用同一后端不引入第二套 TLS 实现。已本地核对该配置的 `configure` 输出为 `License: LGPL version 2.1 or later`，且 `CONFIG_GPL`、`CONFIG_NONFREE`、`CONFIG_VERSION3`、`CONFIG_GPLV3` 均为 0。

`configure` 把缺少 nasm 视为致命错误而非静默丢弃汇编优化，因此 `prepare-linux-ffmpeg.sh` 会先预检 `nasm`、`pkg-config`、`make` 与 OpenSSL 开发包并给出安装提示；它不自行安装依赖，以便非 root 开发者也能使用。发布工作流通过 apt 提供这些依赖。本地打包可用 `bun run bundle:linux -- --ffmpeg-static` 复现发布口径，不带该开关时仍使用 pkg-config 找到的系统 FFmpeg。

发布资产含义：

- `rLive_<版本>_windows-x64-setup.exe`：Windows x64 NSIS 安装程序，默认按当前用户安装，无需管理员权限；新安装优先把数据写入可写的安装目录，不可写时回退 `%APPDATA%\rlive`。
- `rLive_<版本>_windows-x64.msi`：Windows x64 MSI 安装包，通常按机器安装到 `Program Files`；该目录不可写时，数据回退到 `%APPDATA%\rlive`。
- `rLive_<版本>_macos-arm64.dmg`：Apple Silicon Mac 磁盘映像，ASR 运行库静态编入应用，无需运行时下载；未做签名与公证。
- `rLive_<版本>_macos-x64.dmg`：Intel Mac 磁盘映像，同上。
- `rLive_<版本>_android-arm64-v8a.apk`：供 arm64-v8a Android 设备直接安装，最低 Android API 24。
- `rLive_<版本>_linux-amd64.deb`：Debian / Ubuntu x86_64 安装包，内置桌面本地字幕所需的 CPU-only Sherpa/ONNX Runtime。
- `rLive_<版本>_linux-x86_64.rpm`：RPM 发行版 x86_64 安装包，内置与 DEB 相同的 CPU-only 字幕运行库。
- `rLive_<版本>_linux-x86_64.AppImage`：无需安装的 Linux x86_64 应用镜像，内置 CPU-only 字幕运行库。
- `SHA256SUMS.txt`：全部安装资产的 SHA-256 校验和。

Windows 安装包不内置 ASR 运行库，首次启用字幕时由应用下载。

### Windows 安装包载荷断言

只声明 `bundle.resources` 白名单不足以保证这一点。NSIS 只安装白名单，而 Tauri 的 WiX 打包会把 EXE 同目录下所有 `*.dll` 追加进 MSI（上游 `tauri-bundler` 对此留有 TODO），而 `sherpa-onnx-sys` 的 build script 为了链接会把整套 ASR 运行库复制到 release 目录。两者叠加的结果是 MSI 长期多带了约 387 MB ASR DLL，其中 `onnxruntime_providers_cuda.dll` 单个 354 MB；这些文件被装到程序目录也不会被加载，因为 `asr.rs` 只从用户数据目录的 `asr-runtime/` 探测并加载 provider。

发布工作流因此在 `tauri bundle` 前把 FFmpeg 三个 DLL 与 `WebView2Loader.dll` 之外的 DLL 移到 `RUNNER_TEMP`，并在 `finally` 中无条件移回，避免打包失败后 release 目录残缺影响重跑。

打包后对两个安装包各自的真实载荷做断言，而不是只检查安装包旁边有没有散落的 DLL——后者正是此前多个版本未能发现该问题的原因：

- MSI 读 `File` 表。7z 只能看到 WiX 生成的组件 id（形如 `PathFile_I26a8b29…`），真实文件名必须来自该表；查询用系统自带的 `WindowsInstaller` COM，在 Windows PowerShell 下执行。
- NSIS 读 Tauri 渲染后交给 makensis 的 `installer.nsi`，即 `target/release/nsis/<arch>/installer.nsi`，它是安装内容的权威清单，也免去为解包 `.exe` 而依赖工作流别处未使用的 7-Zip。

两侧都要求：DLL 只能是 `avutil`/`avcodec`/`avformat` 与 `WebView2Loader`，且五个暂存文件（三个 FFmpeg DLL 加两个许可与说明文件）都在。

### Linux 本地打包

在安装 Linux 构建依赖后运行：

```bash
bun run bundle:linux
```

该命令会先构建 `src-tauri/target/release/rlive` 并暂存 Sherpa/ONNX Runtime，再为 DEB、RPM 与 AppImage 生成临时 Tauri resources 配置；不能将 `target/release/*.so*` 直接写入静态 Tauri 配置，因为 Tauri 会在 Rust 编译前校验资源 glob。可仅构建某一类安装包，例如 `bun run bundle:linux -- --bundles deb`。加 `--ffmpeg-static` 可复现发布口径的静态 FFmpeg 链接，此前需先执行 `scripts/prepare-linux-ffmpeg.sh` 并按其提示装好 `nasm`、`pkg-config`、`make` 与 `libssl-dev`。

Linux 发布包只使用 CPU-only Sherpa/ONNX Runtime，不需要 NVIDIA 驱动、CUDA 或 cuDNN。

如果另行构建 AAB 上传应用商店，确认自动生成的 Android `versionCode` 比已发布版本更大；不要手工编辑 Tauri 生成的 `tauri.properties`。

## 发布前核验

1. 下载 Release 草稿中的 `setup.exe`、`.msi`、`.dmg`、`.apk`、`.deb`、`.rpm`、`.AppImage` 与 `SHA256SUMS.txt`。
2. 在空目录运行 `sha256sum -c SHA256SUMS.txt`，确认校验和一致。
3. 在 Windows x64、macOS、arm64 Android 真机和 Debian / Ubuntu x86_64 上分别验证安装、联网和核心播放路径；Linux 还应验证 RPM 发行版和 AppImage 启动。Android 额外确认 APK 签名；macOS 确认未签名应用可通过「隐私与安全性」或 `xattr -cr` 正常打开。
4. 临时解包 Linux DEB、RPM 与 AppImage，确认不设置 `LD_LIBRARY_PATH` 时 `ldd` 没有 `not found`。DEB 与 RPM 另需确认 `/usr/lib/rLive` 中的 CPU-only Sherpa/ONNX Runtime `.so` 清单与 release staging 完全一致，`rlive` 的 RUNPATH 包含 `$ORIGIN/../lib/rLive`；AppImage 的 RUNPATH 为 `$ORIGIN/../lib`，运行库在 `usr/lib` 与 `usr/lib/rLive` 各有一份，且 `usr/lib/rLive` 中不应再有 `libsherpa-onnx-cxx-api.so`，理由见上文「AppImage 精简未引用的运行库」。Windows 安装包不得内置 ASR DLL，首次启用字幕时应下载并初始化运行库；该约束现由发布流程自动断言（见上文「Windows 安装包载荷断言」），人工核验可只做抽查；安装到当前用户可写目录的 NSIS 新安装应把 `rlive.db`、`logs/`、`models/` 和 `asr-runtime/` 写在可执行文件所在目录，安装到 `Program Files` 的 MSI 则回退到 `%APPDATA%\rlive`。同时核对 Windows 安装包包含三个 FFmpeg DLL（`avutil`、`avcodec`、`avformat`，裁剪后不再需要 `swresample`）、LGPL 许可证与构建说明。Linux 与 macOS 相反，应确认产物**不含** FFmpeg 运行库：`readelf -d usr/bin/rlive | grep NEEDED` 不应出现 `libav*` 或 `libswresample`，macOS 用 `otool -L` 同样核对。
5. 审核版本说明后才发布草稿。

解包 RPM 时注意：`rpm2cpio` 与 `rpm2archive` 都经 librpm，而 librpm 在交出载荷前会校验 payload 摘要，因此 librpm 侧的拒绝在两者上表现相同，互相之间不构成回退。`rpm2cpio` 失败时返回已拷贝字节数并把 0 视为错误，且不写 stderr，症状是「非零退出 + 无任何输出 + `rpm -qp` 仍能读出 header」。此时用 `rpm -Kv` 逐项查看摘要校验结果，并改用 `bsdtar`（`libarchive-tools`）：libarchive 自带独立的 rpm 过滤器，跳过 header 直接解压载荷、不校验摘要。其条目前缀为 `./usr/...`，`tar -x` 会剥掉 `./` 并自动补齐中间目录。工作流即按此顺序回退。

`TAURI_SIGNING_PRIVATE_KEY` 是 Tauri updater 的签名密钥，不等同于 Android keystore；当前发布流程不使用它。
