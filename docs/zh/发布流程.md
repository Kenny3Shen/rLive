# 发布流程

本页说明 rLive 的正式发布怎么触发、需要哪些一次性配置、会产出哪些资产，以及发布前必须核验什么。
准备打 tag 发版、配置签名 secrets、排查 CI 打包失败或核对 Release 草稿时看这篇。

本仓库将持续集成与正式发布分开：PR 和 `master` 推送只运行检查与测试；只有推送版本标签才会构建、签名并创建 Release 草稿。

## 触发条件

1. 确认 `package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 的版本完全一致。
2. 提交版本变更并推送，例如 `git tag v2.0.0 && git push origin v2.0.0`。
3. `.github/workflows/release.yml` 会拒绝与版本不一致的标签，且签名构建通过后才创建 GitHub draft Release。

Release 草稿不会自动公开。审核 Windows、macOS、Android、Linux 产物和 `SHA256SUMS.txt` 后，再在 GitHub Release 页面手动发布。

## 版本递增规则

版本号只在准备发布时递增。日常提交（包括功能与修复）不改版本号，仓库里的版本始终代表上一个已发布版本，避免多个未发布提交各自留下半成品版本。

发布前用一个独立的版本提交完成递增，递增幅度按上次发布以来累积的全部改动的最高影响级别定一次：

- 只有用户可见 bug 修复时递增 patch。
- 含向后兼容的新功能时递增 minor 并将 patch 归零；同时包含 fix 与 feat 时按 minor 处理。
- major 只能在明确指定后更新，不能仅因识别到破坏性变更就自动递增。
- 累积改动只有文档、测试、格式、构建维护或不改变产品行为的重构时不需要发布，也不递增版本。

同步修改 `package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 三处权威版本，随后刷新 `src-tauri/Cargo.lock` 并确认根包版本一致（`cargo metadata --no-deps` 或任意 cargo 命令即可回写）。该提交推送后再单独创建版本标签。

## 一次性 GitHub 配置

创建名为 `release` 的 GitHub Environment，将它限制为 `v*` 标签并按团队需要设置审核人。签名 secrets 只能配置在该 Environment；PR 和普通 CI 永远不会读取它们。

| 用途 | 名称 | 类型 |
| --- | --- | --- |
| Android keystore 文件的 Base64 | `ANDROID_KEYSTORE_BASE64` | secret |
| Android keystore 密码 | `ANDROID_KEYSTORE_PASSWORD` | secret |
| Android key alias | `ANDROID_KEY_ALIAS` | secret |
| Android key 密码 | `ANDROID_KEY_PASSWORD` | secret |
| Android 证书 SHA-256 指纹（可选，推荐） | `ANDROID_CERT_SHA256` | variable |

配置步骤：

1. `Settings → Environments → New environment`，创建精确名称为 `release` 的环境。
2. 启用所需审核人，并在 deployment branches/tags 中仅允许 `v*` 标签。
3. 在 **Environment secrets** 添加上表四个 secret。可在私有终端执行 `base64 -w 0 /home/shenss/upload-keystore.jks | clip.exe`，把剪贴板中的单行文本粘贴到第一个 secret；不要贴到聊天或仓库。
4. 在 **Environment variables** 添加 `ANDROID_CERT_SHA256`，以让工作流验证实际使用的证书。
5. 在 `Settings → Actions → General → Workflow permissions` 允许 `GITHUB_TOKEN` 读写仓库内容（`contents: write`），否则最终 job 无法创建 Release 草稿。

`TAURI_SIGNING_PRIVATE_KEY` 是 Tauri updater 的签名密钥，不等同于 Android keystore；当前发布流程不使用它。

## Android 签名

首次生成 keystore 时，将原始 `.jks` 放在仓库外的安全位置：

```bash
keytool -genkeypair -v -keystore rlive-release.jks -alias rlive \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w 0 rlive-release.jks
```

不要提交 `.jks`、`keystore.properties`、密码或 Base64 文本。发布工作流会在临时目录还原文件，写入被忽略的 Gradle properties，使用 arm64 目标构建并执行 `apksigner`、`jarsigner` 验证，最后清理签名文件。

### 本机签名构建

先收紧文件权限并确认 alias 与证书指纹；`keytool` 会在本机提示输入密码，不要把密码写进命令历史：

```bash
chmod 600 /home/shenss/upload-keystore.jks
keytool -list -v -keystore /home/shenss/upload-keystore.jks
```

在 `src-tauri/gen/android/app/keystore.properties` 创建权限 `600` 的本地文件（已被 Git 忽略）：

```properties
storeFile=/home/shenss/upload-keystore.jks
storePassword=<keystore 密码>
keyAlias=<keytool 输出的 Alias name>
keyPassword=<私钥密码>
```

构建并验签：

```bash
bun run tauri -- android build --ci --target aarch64 --apk --aab
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --verbose --print-certs \
  src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
jarsigner -verify -strict \
  src-tauri/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab
```

本地 `keystore.properties` 不会被同步脚本复制到 Windows 镜像，避免明文密码遗留在 `D:\dev\rLive`。另行构建 AAB 上传应用商店时，确认自动生成的 Android `versionCode` 比已发布版本更大；不要手工编辑 Tauri 生成的 `tauri.properties`。

## 打包与签名现状

正式 tag 会并行构建 Windows x64、macOS（Apple Silicon 与 Intel）、Android arm64-v8a 和 Linux x86_64 产物，全部 job 已通过。Android 使用上述 Environment secrets 签名；其余平台当前不做平台级签名：

- Windows 安装包不做 Authenticode 签名，安装或首次启动可能显示 SmartScreen 提示。
- macOS DMG 不做 Apple 签名与公证，首次打开需在「系统设置 → 隐私与安全性」允许，或对应用执行 `xattr -cr`。
- Linux `.deb` 不做仓库级签名。

## FFmpeg 自建与许可证约束

桌面录制固定依赖进程内 FFmpeg，三个平台都从同一份官方 `ffmpeg-9.0.1.tar.xz` 源码（SHA-256 `cf38e0e28c7e5605942c4a77755349b0145804a397af37eb1fb4c77cb237f635`，已用官方签名密钥 `FCF986EA15E6E293A5644F10B4322F04D67658D8` 验证）按需裁剪自建，只启用录制实际用到的组件，结果为 LGPL v2.1+。

组件白名单：FLV/HLS/MPEG-TS/MOV/Matroska 解复用、FLV/MPEG-TS 复用、file/http/https/tls/tcp/crypto/httpproxy 协议。`httpproxy` 必不可少——配置 HTTP 代理后，HTTPS 录制由 libavformat 的 tls 协议经 `httpproxy://` 建立 CONNECT 隧道，缺失时录制只报 "Protocol not found"。

为什么必须断言宏而不是看 `configure` 退出码：`configure` 在依赖缺失时会把组件降级为警告并仍以 0 退出，能力被静默去掉只会在用户机器上暴露。因此脚本断言 `config_components.h` 中的 `CONFIG_*` 宏，并断言 `CONFIG_GPL`、`CONFIG_NONFREE`、`CONFIG_VERSION3`、`CONFIG_GPLV3`、`CONFIG_LGPLV3` 全为 0（不传 `--enable-gpl`）。

各平台口径：

- Windows（`scripts/prepare-windows-ffmpeg.ps1`）：用 runner 自带的 MSYS2 与 MinGW-w64 构建 shared SDK，TLS 走系统原生 schannel；`avutil`、`avcodec`、`avformat` 三个 DLL 连同 LGPL 许可证和构建说明纳入 NSIS/MSI（裁剪后不再需要 `swresample`）。
- macOS（`scripts/prepare-macos-ffmpeg.sh`）：静态库以 `--features ffmpeg-static` 链接进二进制，不需要 `Frameworks` 目录、install name 重写或额外签名范围，产物不再依赖 Homebrew；工作流用 `otool -L` 断言二进制与 DMG 内应用都没有 `libav*` 动态依赖。
- Linux（`scripts/prepare-linux-ffmpeg.sh`）：同样静态链接，发行版 `libav*-dev` 已从构建依赖移除；工作流用 `readelf -d` 断言 release staging、DEB、RPM 和 AppImage 四种布局的 ELF 都没有 `libav*`/`libswresample` 的 NEEDED 项。

TLS 后端差异：macOS 用系统 Secure Transport，Linux 用 OpenSSL。Linux 不选 GnuTLS 是许可与依赖权衡——Debian 的 `gnutls.pc` 静态链接会引入 LGPLv3 的 GMP，而 `libssl.pc` 只需 libcrypto，且应用自身经 reqwest 的 native-tls 本来就链接 OpenSSL。

`prepare-linux-ffmpeg.sh` 会先预检 `nasm`、`pkg-config`、`make` 与 OpenSSL 开发包并给出安装提示（`configure` 把缺少 nasm 视为致命错误），但不自行安装依赖，以便非 root 开发者也能使用；发布工作流通过 apt 提供这些依赖。

发布核验必须在未安装 FFmpeg 开发包的干净机器执行启动和实际 HLS/FLV 录制。

## Windows 安装包载荷断言

只声明 `bundle.resources` 白名单不足够：NSIS 只安装白名单，而 Tauri 的 WiX 打包会把 EXE 同目录下所有 `*.dll` 追加进 MSI，`sherpa-onnx-sys` 的 build script 又为了链接把整套 ASR 运行库复制到 release 目录。两者叠加曾让 MSI 长期多带约 387 MB 不会被加载的 ASR DLL（`asr.rs` 只从用户数据目录的 `asr-runtime/` 加载 provider）。

工作流因此在 `tauri bundle` 前把 FFmpeg 三个 DLL 与 `WebView2Loader.dll` 之外的 DLL 移到 `RUNNER_TEMP`，并在 `finally` 中无条件移回，避免打包失败后 release 目录残缺影响重跑。

打包后必须断言两个安装包各自的真实载荷，而不是只看安装包旁边有没有散落 DLL——后者正是此前多个版本漏掉该问题的原因。MSI 查 `File` 表（用系统自带的 `WindowsInstaller` COM，7z 只能看到 WiX 组件 id），NSIS 查 `target/release/nsis/<arch>/installer.nsi`。两侧都要求：DLL 只能是 `avutil`/`avcodec`/`avformat` 与 `WebView2Loader`，且五个暂存文件（三个 FFmpeg DLL 加两个许可与说明文件）都在。

## Linux 打包与 RUNPATH 口径

本地打包在安装 Linux 构建依赖后运行 `bun run bundle:linux`。该命令会先构建 `src-tauri/target/release/rlive` 并暂存 Sherpa/ONNX Runtime，再为 DEB、RPM 与 AppImage 生成临时 Tauri resources 配置（不能把 `target/release/*.so*` 直接写入静态配置，Tauri 会在 Rust 编译前校验资源 glob）。可只构建某一类，例如 `bun run bundle:linux -- --bundles deb`；加 `--ffmpeg-static` 复现发布口径的静态链接，此前需先执行 `scripts/prepare-linux-ffmpeg.sh`。

Linux 发布包只使用 CPU-only Sherpa/ONNX Runtime，不需要 NVIDIA 驱动、CUDA 或 cuDNN。DEB、RPM 和 AppImage 都携带私有 CPU-only Sherpa/ONNX Runtime `.so`。

三个包的 RUNPATH 口径不同：`build.rs` 为应用 ELF 链接 `$ORIGIN` 与 `$ORIGIN/../lib/rLive`，DEB、RPM 与 release staging 保留该值；AppImage 由 linuxdeploy 打包，它把捆绑库集中到 `usr/lib` 并按自身布局重写 RUNPATH 为 `$ORIGIN/../lib`。工作流的 `verify_runtime` 因此接受候选列表，只对 AppImage 额外放行 `$ORIGIN/../lib`。放宽仅限 RUNPATH 字面量，`ldd` 断言保留：当 RUNPATH 只有 `$ORIGIN/../lib` 而运行库仍留在 `rLive/` 子目录时 `ldd` 会报 `not found`，此时 AppImage 不可用，必须失败而不是放过。

AppImage 另外精简一个未引用的运行库 `libsherpa-onnx-cxx-api.so`：本项目既不链接也不 `dlopen` 它，linuxdeploy 从不把它部署到 `usr/lib`，它只留在 RUNPATH 重写后已不在搜索路径上的 `usr/lib/rLive/`。工作流在 `bun run bundle:linux` 之后、校验之前删除它并重新打包镜像。要点：

- 删除前扫描 AppDir 内所有 ELF 的 NEEDED 项，确认无人引用才删；否则保留并跳过重新打包。
- 只删这一个文件。`libonnxruntime.so` 与 `libsherpa-onnx-c-api.so` 的两处副本被 squashfs 去重，删掉几乎不省体积，却会使 `usr/lib/rLive` 消失并迫使 `verify_runtime` 另设一套清单口径。
- 重打包必须直接调用 appimage 输出插件，不能重跑 `linuxdeploy --plugin gtk --output appimage`：gtk 插件不幂等，第二次运行会在已建好的符号链接上报 `File exists` 并退出 1（v2.6.15 实测）。

## 发布资产

- `rLive_<版本>_windows-x64-setup.exe`：NSIS 安装程序，默认按当前用户安装，无需管理员权限；新安装优先把数据写入可写的安装目录，不可写时回退 `%APPDATA%\rlive`。
- `rLive_<版本>_windows-x64.msi`：MSI 安装包，通常按机器安装到 `Program Files`；该目录不可写时数据回退 `%APPDATA%\rlive`。
- `rLive_<版本>_macos-arm64.dmg` / `rLive_<版本>_macos-x64.dmg`：Apple Silicon 与 Intel 磁盘映像，ASR 运行库静态编入应用，无需运行时下载；未做签名与公证。
- `rLive_<版本>_android-arm64-v8a.apk`：供 arm64-v8a 设备直接安装，最低 Android API 24。
- `rLive_<版本>_linux-amd64.deb` / `rLive_<版本>_linux-x86_64.rpm` / `rLive_<版本>_linux-x86_64.AppImage`：均内置桌面本地字幕所需的 CPU-only Sherpa/ONNX Runtime。
- `SHA256SUMS.txt`：全部安装资产的 SHA-256 校验和。

Windows 安装包不内置 ASR 运行库，首次启用字幕时由应用下载。

## 发布前核验

1. 下载 Release 草稿中的 `setup.exe`、`.msi`、`.dmg`、`.apk`、`.deb`、`.rpm`、`.AppImage` 与 `SHA256SUMS.txt`。
2. 在空目录运行 `sha256sum -c SHA256SUMS.txt`，确认校验和一致。
3. 在 Windows x64、macOS、arm64 Android 真机和 Debian / Ubuntu x86_64 上分别验证安装、联网和核心播放路径；Linux 还应验证 RPM 发行版和 AppImage 启动。Android 额外确认 APK 签名；macOS 确认未签名应用可通过「隐私与安全性」或 `xattr -cr` 正常打开。
4. 临时解包 Linux DEB、RPM 与 AppImage，确认不设置 `LD_LIBRARY_PATH` 时 `ldd` 没有 `not found`：
   - DEB 与 RPM：`/usr/lib/rLive` 中的 CPU-only `.so` 清单与 release staging 完全一致，`rlive` 的 RUNPATH 包含 `$ORIGIN/../lib/rLive`。
   - AppImage：RUNPATH 为 `$ORIGIN/../lib`，运行库在 `usr/lib` 与 `usr/lib/rLive` 各有一份，且 `usr/lib/rLive` 中不应再有 `libsherpa-onnx-cxx-api.so`。
   - Linux 与 macOS 应确认产物**不含** FFmpeg 运行库：`readelf -d usr/bin/rlive | grep NEEDED` 不应出现 `libav*` 或 `libswresample`，macOS 用 `otool -L` 同样核对。
5. Windows 安装包不得内置 ASR DLL，首次启用字幕时应下载并初始化运行库；该约束已由发布流程自动断言，人工核验可只做抽查。同时核对安装包包含三个 FFmpeg DLL、LGPL 许可证与构建说明；NSIS 新安装应把 `rlive.db`、`logs/`、`models/` 和 `asr-runtime/` 写在可执行文件所在目录，装到 `Program Files` 的 MSI 则回退 `%APPDATA%\rlive`。
6. 审核版本说明后才发布草稿。

解包 RPM 时注意：`rpm2cpio` 与 `rpm2archive` 都经 librpm 并校验 payload 摘要，因此两者表现相同、互不构成回退。`rpm2cpio` 失败的症状是「非零退出 + 无任何输出 + `rpm -qp` 仍能读出 header」。此时用 `rpm -Kv` 查看摘要校验结果，并改用 `bsdtar`（`libarchive-tools`）：它自带独立的 rpm 过滤器，跳过 header 直接解压载荷、不校验摘要。工作流即按此顺序回退。
