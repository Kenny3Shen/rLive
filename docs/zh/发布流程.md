# 发布流程

本仓库将持续集成与正式发布分开：PR 和 `master` 推送只运行检查与测试；只有推送版本标签才会构建、签名并创建 Release 草稿。

## 触发条件

1. 确认 `package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 的版本完全一致。
2. 提交版本变更并推送，例如 `git tag v0.1.0 && git push origin v0.1.0`。
3. `.github/workflows/release.yml` 会拒绝与版本不一致的标签，且签名构建通过后才创建 GitHub draft Release。

Release 草稿不会自动公开。审核 Windows、macOS、Android、Linux 产物和 `SHA256SUMS.txt` 后，再在 GitHub Release 页面手动发布。

> [!WARNING]
> 桌面录制已固定依赖进程内 FFmpeg。Windows 已固定 Gyan FFmpeg 9.0.1 `full_build-shared` SDK、校验 SHA-256，并将四个必需 DLL、GPLv3 许可证和构建说明纳入 NSIS/MSI 安装包；发布前仍需完成应用整体的 GPLv3 合规审计。Linux 和 macOS 尚未固定 FFmpeg SDK、打包运行库或完成许可审计，因此在补齐这些步骤前不得推送正式 tag。只安装开发头文件只能让 CI 编译通过，不能保证产物在用户机器启动。

## 版本递增规则

- 一次提交按完整改动的最高影响级别只递增一次。仅修复用户可见 bug 时递增 patch，例如 `0.15.1` → `0.15.2`；包含向后兼容的新功能时递增 minor 并将 patch 归零，例如 `0.15.2` → `0.16.0`。同一提交同时包含 fix 与 feat 时按 minor 处理。
- 纯文档、测试、格式、构建维护或不改变产品行为的重构不自动递增版本。
- major 版本只能在用户明确指定后更新，不能仅因识别到破坏性变更就自动递增。
- 版本递增与功能改动放在同一个提交中，并同步修改 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`；随后刷新 `src-tauri/Cargo.lock`，确认根包版本及三处权威版本一致。版本标签仍由发布流程单独、明确地创建。

## 1.0 数据断代核验

发布 `v1.0.0` 前必须按 [1.0 兼容性清理](1.0兼容性清理.md) 完成数据断代演练并保留记录，包括 0.x profile 导出、1.0 空库导入、旧库与错误 profile 拒绝，以及旧录制回放。没有可用的最后一个 0.x 过渡版本或演练记录时，不得推送正式 tag。

## 一次性 GitHub 配置

创建名为 `release` 的 GitHub Environment，将它限制为 `v*` 标签并按团队需要设置审核人。签名 secrets 只能配置在该 Environment；PR 和普通 CI 永远不会读取它们。

| 用途 | 名称 | 类型 |
| --- | --- | --- |
| Android keystore 文件的 Base64 | `ANDROID_KEYSTORE_BASE64` | secret |
| Android keystore 密码 | `ANDROID_KEYSTORE_PASSWORD` | secret |
| Android key alias | `ANDROID_KEY_ALIAS` | secret |
| Android key 密码 | `ANDROID_KEY_PASSWORD` | secret |
| Android 证书 SHA-256 指纹（可选） | `ANDROID_CERT_SHA256` | variable |

仓库 Actions 设置还必须允许 `GITHUB_TOKEN` 在最终发布 job 中拥有 `contents: write` 权限。

## Android 签名

首次生成 keystore 时，将原始 `.jks` 放在仓库外的安全位置。示例：

```bash
keytool -genkeypair -v -keystore rlive-release.jks -alias rlive \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w 0 rlive-release.jks
```

把 Base64 输出作为 `ANDROID_KEYSTORE_BASE64` 保存。不要提交 `.jks`、`keystore.properties`、密码或 Base64 文本。发布工作流会在临时目录还原文件，写入被忽略的 Gradle properties，使用 arm64 目标构建并执行 `apksigner`、`jarsigner` 验证，最后清理签名文件。

### 本机签名构建

密钥库保存在仓库外后，先收紧文件权限并确认 alias 与证书指纹；`keytool` 会在本机提示输入密码，不要把密码传给聊天或写进命令历史：

```bash
chmod 600 /home/shenss/upload-keystore.jks
keytool -list -v -keystore /home/shenss/upload-keystore.jks
```

在 `src-tauri/gen/android/app/keystore.properties` 创建一个权限为 `600` 的本地文件（该文件已被 Git 忽略），填入实际值：

```properties
storeFile=/home/shenss/upload-keystore.jks
storePassword=<keystore 密码>
keyAlias=<keytool 输出的 Alias name>
keyPassword=<私钥密码>
```

然后构建并验签：

```bash
bun run tauri -- android build --ci --target aarch64 --apk --aab
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --verbose --print-certs \
  src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
jarsigner -verify -strict \
  src-tauri/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab
```

本地 `keystore.properties` 不会被同步脚本复制到 Windows 镜像，避免明文密码遗留在 `D:\\dev\\rLive`。

### GitHub Environment 配置

1. 打开 `Settings → Environments → New environment`，创建精确名称为 `release` 的环境。
2. 在该环境启用所需审核人，并在 deployment branches/tags 中仅允许 `v*` 标签。
3. 在 **Environment secrets** 中添加 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`。可在私有 WSL 终端执行 `base64 -w 0 /home/shenss/upload-keystore.jks | clip.exe`，将剪贴板中的单行文本粘贴到第一个 secret；不要将其贴到聊天或仓库。
4. 在 **Environment variables** 中添加 `ANDROID_CERT_SHA256`（上面 `keytool` 输出的 SHA-256 指纹）。推荐配置它，以让发布工作流验证实际使用的证书。
5. 在 `Settings → Actions → General → Workflow permissions` 允许 `GITHUB_TOKEN` 读写仓库内容；否则最终 job 无法创建 Release 草稿。

正式 tag 会并行构建 Windows x64、macOS（Apple Silicon 与 Intel）、Android arm64-v8a 和 Linux x86_64 产物。Android 使用上面的 Environment secrets 签名；Windows 安装包当前不做 Authenticode 签名，安装或首次启动时可能显示 SmartScreen 提示；macOS DMG 不做 Apple 签名与公证，首次打开需在「系统设置 → 隐私与安全性」中允许，或对应用执行 `xattr -cr`；Linux `.deb` 不做仓库级签名。

恢复桌面正式发布前，仍需为 Linux 和 macOS 选择固定版本、固定校验和且许可证配置明确的 FFmpeg SDK。Windows 已将所需 `avformat`、`avcodec`、`avutil`、`swresample` 和许可说明纳入 NSIS/MSI；macOS 将 dylib 放入应用 `Frameworks` 并重写 install name 与签名范围；Linux DEB、RPM 和 AppImage 会携带私有 CPU-only Sherpa/ONNX Runtime `.so` 并为标准安装布局设置相对 RUNPATH。发布核验必须在未安装 FFmpeg 开发包的干净机器执行启动和实际 HLS/FLV 录制。

发布资产含义：

- `rLive_<版本>_windows-x64-setup.exe`：Windows x64 NSIS 安装程序，默认按当前用户安装，无需管理员权限；新安装优先把数据写入可写的安装目录，不可写时回退 `%APPDATA%\rlive`。
- `rLive_<版本>_windows-x64.msi`：Windows x64 MSI 安装包，通常按机器安装到 `Program Files`；该目录不可写时，数据回退到 `%APPDATA%\rlive`。
- `rLive_<版本>_macos-arm64.dmg`：Apple Silicon Mac 磁盘映像，ASR 运行库静态编入应用，无需运行时下载；未做签名与公证。
- `rLive_<版本>_macos-x64.dmg`：Intel Mac 磁盘映像，同上。
- `rLive_<版本>_android-arm64-v8a.apk`：供 arm64-v8a Android 设备直接安装，最低 Android API 24。
- `rLive_<版本>_linux-amd64.deb`：Debian / Ubuntu x86_64 安装包，内置桌面本地字幕所需的 CPU-only Sherpa/ONNX Runtime。
- `rLive_<版本>_linux-x86_64.rpm`：RPM 发行版 x86_64 安装包，内置与 DEB 相同的 CPU-only 字幕运行库。
- `rLive_<版本>_linux-x86_64.AppImage`：无需安装的 Linux x86_64 应用镜像，内置 CPU-only 字幕运行库。
- `SHA256SUMS.txt`：全部安装资产的 SHA-256 校验和。

Windows 安装包不内置 ASR 运行库，首次启用字幕时由应用下载。

### Linux 本地打包

在安装 Linux 构建依赖后运行：

```bash
bun run bundle:linux
```

该命令会先构建 `src-tauri/target/release/rlive` 并暂存 Sherpa/ONNX Runtime，再为 DEB、RPM 与 AppImage 生成临时 Tauri resources 配置；不能将 `target/release/*.so*` 直接写入静态 Tauri 配置，因为 Tauri 会在 Rust 编译前校验资源 glob。可仅构建某一类安装包，例如 `bun run bundle:linux -- --bundles deb`。

Linux 发布包只使用 CPU-only Sherpa/ONNX Runtime，不需要 NVIDIA 驱动、CUDA 或 cuDNN。

如果另行构建 AAB 上传应用商店，确认自动生成的 Android `versionCode` 比已发布版本更大；不要手工编辑 Tauri 生成的 `tauri.properties`。

## 发布前核验

1. 下载 Release 草稿中的 `setup.exe`、`.msi`、`.dmg`、`.apk`、`.deb`、`.rpm`、`.AppImage` 与 `SHA256SUMS.txt`。
2. 在空目录运行 `sha256sum -c SHA256SUMS.txt`，确认校验和一致。
3. 在 Windows x64、macOS、arm64 Android 真机和 Debian / Ubuntu x86_64 上分别验证安装、联网和核心播放路径；Linux 还应验证 RPM 发行版和 AppImage 启动。Android 额外确认 APK 签名；macOS 确认未签名应用可通过「隐私与安全性」或 `xattr -cr` 正常打开。
4. 临时解包 Linux DEB、RPM 与 AppImage，确认其 `/usr/lib/rLive` 中的 CPU-only Sherpa/ONNX Runtime `.so` 清单与 release staging 完全一致，`rlive` 的 RUNPATH 包含 `$ORIGIN/../lib/rLive`，且不设置 `LD_LIBRARY_PATH` 时 `ldd` 没有 `not found`。Windows 安装包不得内置 ASR DLL，首次启用字幕时应下载并初始化运行库；安装到当前用户可写目录的 NSIS 新安装应把 `rlive.db`、`logs/`、`models/` 和 `asr-runtime/` 写在可执行文件所在目录，安装到 `Program Files` 的 MSI 则回退到 `%APPDATA%\rlive`。同时核对 Windows 安装包包含四个 FFmpeg DLL、上游许可证与构建说明。
5. 审核版本说明后才发布草稿。

`TAURI_SIGNING_PRIVATE_KEY` 是 Tauri updater 的签名密钥，不等同于 Android keystore；当前发布流程不使用它。
