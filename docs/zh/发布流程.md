# 发布流程

本仓库将持续集成与正式发布分开：PR 和 `master` 推送只运行检查与测试；只有推送版本标签才会构建、签名并创建 Release 草稿。

## 触发条件

1. 确认 `package.json`、`backend/Cargo.toml` 与 `backend/tauri.conf.json` 的版本完全一致。
2. 提交版本变更并推送，例如 `git tag v0.1.0 && git push origin v0.1.0`。
3. `.github/workflows/release.yml` 会拒绝与版本不一致的标签，且两个签名构建都通过后才创建 GitHub draft Release。

Release 草稿不会自动公开。审核 APK、AAB、Windows 安装包和 `SHA256SUMS.txt` 后，再在 GitHub Release 页面手动发布。

## 一次性 GitHub 配置

创建名为 `release` 的 GitHub Environment，将它限制为 `v*` 标签并按团队需要设置审核人。签名 secrets 只能配置在该 Environment；PR 和普通 CI 永远不会读取它们。

| 用途 | 名称 | 类型 |
| --- | --- | --- |
| Android keystore 文件的 Base64 | `ANDROID_KEYSTORE_BASE64` | secret |
| Android keystore 密码 | `ANDROID_KEYSTORE_PASSWORD` | secret |
| Android key alias | `ANDROID_KEY_ALIAS` | secret |
| Android key 密码 | `ANDROID_KEY_PASSWORD` | secret |
| Android 证书 SHA-256 指纹（可选） | `ANDROID_CERT_SHA256` | variable |
| Windows 代码签名 PFX 的 Base64 | `WINDOWS_CERTIFICATE_BASE64` | secret |
| Windows PFX 密码 | `WINDOWS_CERTIFICATE_PASSWORD` | secret |
| Windows RFC 3161 时间戳地址 | `WINDOWS_TIMESTAMP_URL` | variable |

仓库 Actions 设置还必须允许 `GITHUB_TOKEN` 在最终发布 job 中拥有 `contents: write` 权限。

## Android 签名

首次生成 keystore 时，将原始 `.jks` 放在仓库外的安全位置。示例：

```bash
keytool -genkeypair -v -keystore rlive-release.jks -alias rlive \
  -keyalg RSA -keysize 4096 -validity 10000
base64 -w 0 rlive-release.jks
```

把 Base64 输出作为 `ANDROID_KEYSTORE_BASE64` 保存。不要提交 `.jks`、`keystore.properties`、密码或 Base64 文本。发布工作流会在临时目录还原文件，写入被忽略的 Gradle properties，使用 arm64 目标构建并执行 `apksigner`、`jarsigner` 验证，最后清理签名文件。

### 本机签名构建

密钥库保存在仓库外后，先收紧文件权限并确认 alias 与证书指纹；`keytool` 会在本机提示输入密码，不要把密码传给聊天或写进命令历史：

```bash
chmod 600 /home/shenss/upload-keystore.jks
keytool -list -v -keystore /home/shenss/upload-keystore.jks
```

在 `backend/gen/android/app/keystore.properties` 创建一个权限为 `600` 的本地文件（该文件已被 Git 忽略），填入实际值：

```properties
storeFile=/home/shenss/upload-keystore.jks
storePassword=<keystore 密码>
keyAlias=<keytool 输出的 Alias name>
keyPassword=<私钥密码>
```

然后构建并验签：

```bash
bun run tauri -- android build --ci --target aarch64 --apk --aab
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --verbose --print-certs \
  backend/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
jarsigner -verify -strict \
  backend/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab
```

本地 `keystore.properties` 不会被同步脚本复制到 Windows 镜像，避免明文密码遗留在 `D:\\dev\\rLive`。

### GitHub Environment 配置

1. 打开 `Settings → Environments → New environment`，创建精确名称为 `release` 的环境。
2. 在该环境启用所需审核人，并在 deployment branches/tags 中仅允许 `v*` 标签。
3. 在 **Environment secrets** 中添加 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`。可在私有 WSL 终端执行 `base64 -w 0 /home/shenss/upload-keystore.jks | clip.exe`，将剪贴板中的单行文本粘贴到第一个 secret；不要将其贴到聊天或仓库。
4. 在 **Environment variables** 中添加 `ANDROID_CERT_SHA256`（上面 `keytool` 输出的 SHA-256 指纹）。推荐配置它，以让发布工作流验证实际使用的证书。
5. 在 `Settings → Actions → General → Workflow permissions` 允许 `GITHUB_TOKEN` 读写仓库内容；否则最终 job 无法创建 Release 草稿。

正式 tag 同时构建 Windows 和 Android。因此创建 `v*` tag 前，还必须提供 Windows 的两个 secrets 和时间戳 variable，详见下文；Android JKS 不能替代 Windows Authenticode 证书。

发布资产含义：

- `rLive_<版本>_android-arm64-v8a.apk`：供 arm64-v8a Android 设备直接安装，最低 Android API 24。
- `rLive_<版本>_android-arm64-v8a.aab`：供 Google Play Console 或其他应用商店上传，不适合直接安装。

每次上传应用商店前，确认自动生成的 Android `versionCode` 比已发布版本更大；不要手工编辑 Tauri 生成的 `tauri.properties`。

## Windows 签名

将可用于 Authenticode 的 PFX 在仓库外转换成单行 Base64 后保存为 Environment secret。例如在 PowerShell：

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\secure\rlive-signing.pfx"))
```

工作流仅在临时 Windows runner 的 `CurrentUser\My` 证书库导入该 PFX，并让 Tauri 签名应用本体和 NSIS 安装包。它随后以 `Get-AuthenticodeSignature` 校验状态和证书指纹；证书、密码或时间戳地址缺失会使正式发布失败。

正式 Windows 资产为 `rLive_<版本>_x64-setup.exe`。它是安装包，而不是裸 `rlive.exe`。

## 发布前核验

1. 下载 Release 草稿中的全部资产与 `SHA256SUMS.txt`。
2. 在空目录运行 `sha256sum -c SHA256SUMS.txt`，确认校验和一致。
3. 在 Windows 测试安装 NSIS 包；在 arm64 Android 真机验证 APK 的签名、安装、联网和核心播放路径。
4. 审核版本说明后才发布草稿。

`TAURI_SIGNING_PRIVATE_KEY` 是 Tauri updater 的签名密钥，不等同于 Android keystore 或 Windows Authenticode PFX；当前发布流程不使用它。
