# B 站 VOD 推荐实时性调查（APP API）

日期：2026-11-15。调查源码基线 `a3a1efa1`，rLive `9.4.0`。下列调查保留修复前的观察，初轮没有修改生产代码；后续修复见文末「第一轮修复与验收」。调查脱敏采样见 [vod-recommend-freshness-2026-11-15.json](../bench/vod-recommend-freshness-2026-11-15.json)。

## 结论

需要区分「页面没有重新取推荐」与「重新取得的推荐仍包含旧视频」：两种现象本轮都复现了。

1. **页面长时间不更新的原因已确认是前端缓存策略。** VOD 推荐继承 `staleTime=Infinity`，缓存仍在时，离开再返回不会自动重新取推荐。Windows 主窗口的一份推荐已缓存约 40 分钟，切到设置再返回后，`dataUpdatedAt`、全部条目均不变，没有 `video_get_recommend` 请求。
2. **手动刷新确实取到新列表，上游没有卡在同一批内容。** 主窗口连续三次刷新，第一页面分别返回 20 条；后两次的首页与紧邻上一轮首页均零重叠。首次刷新与之前两页的 35 条唯一视频只有 3 条重叠。
3. **APP 推荐包含旧视频是真实的上游结果。** 主窗口第一次刷新后的 20 条，逐条通过应用已使用的 WBI 签名详情接口核对 `pubdate`：发布日期距采样时刻中位数 **3.78 天**，其中 **3 条超过 7 天**，分别约 **19.74、20.71、21.79 天**。首页不显示日期不能说明这些视频是新发布。
4. **本次不是 TV 授权失效。** `oauth2/info` 返回 `code=0`，剩余有效期 11345358 秒。固定设备的直接 API 对照全部命中 `all_0.router-*`，不是无设备头时的 `gateway_fb_*`。该前缀只能证明推荐引擎路径生效，不能单独证明账号身份；令牌有效性由独立授权接口确认。
5. **只补刷新参数尚无改善证据。** 相同令牌、相同设备，交错测试现有参数与增加 `pull=true&flush=8&idx=0&recsys_mode=0` 的参数。两个组均持续换内容；增加参数组仍有更老的视频。样本不足以说明某个参数导致改善或退化，不能据此直接修改默认请求。

推荐返回的 `data.config` 还包含 `auto_refresh_time=1200`、`auto_refresh_time_by_appear=1800`、`auto_refresh_time_by_active=1800`、`auto_refresh_by_behavior=1`。当前解析器完全丢弃这份配置，前端也没有按它管理推荐新鲜度。这进一步说明 APP 返回不只是无状态视频数组；本轮没有验证这些字段的完整单位、触发条件或服务端约束，不把它们直接作为新功能契约。

## 实测口径

桌面使用已有 Windows Debug 主窗口，WebView2 `157.0.4341.46`，CSS 视口 `1920 × 1032`、`devicePixelRatio=1`。镜像的 `VideoPage.tsx` 与 `app_feed.rs` 和 WSL 源码一致。主窗口偏好为 `app`、代理为 `auto`，没有更改账号、推荐源、画质或播放设置。

`playwright-cli` 接入该会话时受 `shared_worker` 断言影响，改用主窗口现有页面的 CDP WebSocket，读取真实 Query 状态，并通过 `Input.dispatchMouseEvent` 点击导航和刷新按钮。没有新建没有 Tauri IPC 的标签页，没有替换接口或媒体，没有编写 JS 夹具。

直接 API 对照使用已保存的 TV 授权和一个固定设备标识。保存的 Web Cookie 不含 `buvid3`，所以从现有指纹接口取设备号；**这个号不是主窗口进程已经持有的设备号**。直接对照适合比较参数，不能替代主窗口采样。直接请求沿用 WSL 当前环境代理，未证明它与 Windows `auto` 的实际出口相同。

### 主窗口观察

| 操作 | 结果 |
| --- | --- |
| 进入已缓存推荐 | 两页共 35 条唯一视频，数据约 40 分钟未更新 |
| 切设置，再返回视频 | 数据时间戳和条目不变，推荐请求数为 0 |
| 第一次手动刷新 | 首页 20 条，与之前两页只有 3 条重叠 |
| 第二、第三次手动刷新 | 首页各 20 条，与紧邻上一轮首页均零重叠 |
| 第一次刷新首页的发布日期核对 | 20/20 详情成功，发布日期年龄中位数 3.78 天，3/20 超过 7 天，最长 21.79 天 |

另一次详细刷新采样记录到两个真正的 IPC：先 `POST video_get_recommend`、`page=1`，约 4.9 秒后自动发起同命令的 `page=2`；整个列表到空闲约 9.16 秒。相伴的 `OPTIONS` 是预检，**不计作 IPC**。

原因是 `resetQueries` 只重新取首页，但当前大视口的底部哨兵仍在 240px 预取范围内，`useInfiniteScroll` 随后触发补货。这没有恢复旧尾页，也不是把已有所有页串行重取；它解释了为什么当前配置下用户感受到的刷新等待可能多于一次首页请求。历史性能文档中的「刷新恒为一次首页往返」不能覆盖这种布局和自动补货条件。

### 直接 API 参数对照

固定参数为 `build=8130300&mobi_app=android&platform=android&device=phone&style=2&column=4`。带令牌时复用现有 TV `appkey/ts/sign` 签名规则，不携带 Web Cookie。每轮依次请求基线、刷新参数组、补货参数组，共三轮；每条返回只计 `goto=av/vertical_av` 且没有显式广告标记的 UGC。

| 组别 | 三批 UGC 数 | 唯一视频数 | 日期样本数 | 日期年龄中位数 | 超过 7 天 | 最长年龄 |
| --- | --- | --- | --- | --- | --- | --- |
| 现有基线参数 | 7、6、8 | 21 | 21 | 2.64 天 | 3/21 | 23.81 天 |
| 增加 `pull=true&flush=8&idx=0&recsys_mode=0` | 5、8、7 | 20 | 20 | 3.82 天 | 6/20 | 27.52 天 |
| 增加 `pull=false&flush=0&idx=<上一刷新批末尾 idx>&recsys_mode=0` | 6、7、8 | 21 | 未查日期 | — | — | — |

这九批业务码均为 0、前缀均为 `all_0.router-*`，跨批没有重复视频。`idx` 对照使用真实返回值，没有拿 IPC 页码冒充上游游标。它只能说明该参数组合可返回内容，不能证明可靠分页语义。

辅助对照是不带 `access_key`、保留 Web Cookie 和同一个设备号的三批，得到 11、9、9 条；它不是严格匿名实验，不能据此推出 Cookie 是否参与个性化。无设备头的单独请求得到 `gateway_fb_*`，证明必须检查推荐来源，不能只看 `code=0`。

发布日期只为本轮诊断，使用 `GET /x/web-interface/view` 并添加现有 WBI 签名，不把它加回生产首页。共核对 72 个视频，全部 HTTP 200、业务码 0；先前被移除的 `/x/v3/fav/resource/infos` 未被请求。

## 调查时确认的实现缺口

| 位置 | 调查时行为 | 影响与证据边界 |
| --- | --- | --- |
| `src/shared/api/browsingQueryPolicy.ts`，`src/features/video/VideoPage.tsx` | 推荐继承永久新鲜、闲置回收 1 小时 | 缓存仍存在时不会因年龄重新取推荐；40 分钟返回不更新已复现。1 小时是未使用缓存的回收时长，不是推荐有效期 |
| `src-tauri/src/sites/bilibili/video.rs::video_recommend` | APP 分支忽略 IPC `page` | 初次进入、刷新、补货都进入同一个无状态请求；这不是 Rust 在缓存推荐 |
| `src-tauri/src/sites/bilibili/video/app_feed.rs::app_feed_params` | 只有六个固定业务参数 | 缺少操作和推荐会话状态，但本轮没有证明补参数能够改善发布日期分布 |
| `app_feed.rs::parse_app_feed` 与 `VideoItem` | 不保留 `data.config`、`idx`、`track_id`、`report_flow_data` | 上游刷新提示和推荐上下文没有传入应用后续链路；后续要区分推荐来源或实现会话需先扩展现有边界 |
| `src-tauri/src/commands/video_history.rs::video_history_add` | 只写本地 SQLite 历史 | 没有把 rLive 内观看行为反馈给 B 站，也没有推荐曝光上报。不能把本地续播历史当成服务端推荐已经学习的证据；影响大小和所需协议尚未实测 |
| `app_feed.rs::collect_app_feed` | 每次四批并发，达到目标后不继续解析剩余批 | 上游请求都已发出，未使用的候选会被丢弃。现有去重只覆盖本次取批和前端跨页，不能阻止跨刷新再次推荐；这不是“不取新内容”的直接原因 |
| `VideoPage.tsx::refresh` 与 `useInfiniteScroll` | 重置首页后，哨兵可以立即补货 | 已复现首页之后自动请求第二页，增加刷新期间的网络等待 |

[PiliPlus 当前实现](https://github.com/bggRGjQaUbCoE/PiliPlus/blob/master/lib/http/video.dart) 可作为待验证参考：除 `flush/idx/pull/recsys_mode` 外，还使用不同 `build`、`mobi_app=android_i`、`column=2` 和额外请求头。本轮只测试了表中的增量参数，未完整复刻其他客户端，也没有将不同客户端的请求头和参数直接植入 rLive。

## 建议的后续顺序

1. 先修推荐自己的缓存新鲜度边界。为 VOD 推荐设有限过期窗口，在超时重新进入推荐时只更新首页；沿用现有 Query 和刷新边界，避免默认 infinite-query 失效导致所有已加载页逐页重取，也避免用户正在浏览时定时换掉列表。热门、分区树等其他浏览查询是否调整另行评估。
2. 将推荐来源和操作状态纳入现有 Rust 请求与 IPC 契约，先验证 `config`、`idx`、刷新/补货参数的真实语义，再确定行为。当前对照不支持把“补四个参数”当成已验证修复。
3. 如果目标是「看过某类内容后推荐立即跟进」，单独调查观看和曝光反馈协议。只加本地历史过滤会隐藏已看条目，不能替代服务端推荐学习。
4. 如果目标是「首页优先最近发布的视频」，需要明确产品规则和可靠日期来源。APP 推荐本身没有提供发布时间排序或时间范围契约；缩短缓存只会更及时地拿到同一类推荐，不能保证都是新稿件。应用已有搜索的发布时间筛选和 UP 投稿的「最新发布」可满足明确的时间查询，但本轮不改推荐源或首页逻辑。

## 初轮调查的验证与限制

本轮主窗口与直接接口采样均为真实数据；没有使用重复请求去等待预期答案。参数对照为单账号、固定新设备、短时间顺序采样，无法推断长期推荐模型或推广到其他账号。没有和官方 APP 同时做同账号、同设备、同出口对照，也没有测试 Android 交互。

现有前端 `video-feed` 与 `bilibili-app-expiry` 聚焦测试共 4 项通过；`cargo test --lib sites::bilibili::video::app_feed::` 的 16 项测试全部通过。测试用于确认现有分页、解析、取批和认证分类边界，不证明线上推荐新鲜度。报告和脱敏数据入库，含凭据的临时数据库副本与原始响应不入库；临时数据库副本已删除，主窗口探针已清理并返回原来的直播页面。

## 第一轮修复与验收

第一轮先修已复现的前端缓存问题：APP 与 Web 推荐各自使用 **20 分钟本地有效期**，按首页实际抓取时间判断过期，后续翻页不延长首页年龄。20 分钟是本轮本地策略，上游 `data.config` 的完整单位、触发条件和契约仍待验证。

有效期内返回保留多页缓存；已有首页过期后，重新进入推荐、切回推荐页签或恢复窗口活动时只取首页。账号相关失效通知也通过同一首页刷新入口处理。推荐页隐藏、离场或文档处于后台时不因缓存过期发起刷新；相邻面板原有的冷启动预热仍保留。没有定时替换用户正在浏览的列表。

刷新期间保留旧列表，成功后替换为新首页并回到顶部，失败保留旧页并提供重试。失败期间暂停补货并隐藏补货入口，防止旧页补货清除首页更新失败提示；普通下一页失败仍保留原补货重试。首页刷新会合并同一来源与授权版本的并发请求，取消正在补货的查询并丢弃迟到结果，防止旧尾页覆盖新首页。首页更新结束后刷新控件结束等待，大窗口不足一屏时继续正常补货。

实现沿用现有 `video_get_recommend` IPC、TanStack Query、刷新控件和可见性边界，未调整 Rust APP 请求参数或增加观看、曝光上报。热门、番剧、影视继续使用原有浏览缓存策略。

### Windows 主窗口验收

脱敏结果见 [vod-recommend-freshness-fix-2026-11-15.json](../bench/vod-recommend-freshness-fix-2026-11-15.json)。正常场景使用真实 IPC 和 APP 推荐结果；通过把已有真实首页的 `fetchedAt` 改为 21 分钟前模拟到期，未等待 20 分钟，也没有伪造视频条目。首页刷新场景临时使用 `1024 × 480` CSS 视口，补货场景恢复 `1920 × 1032`。

| 场景 | 验收结果 |
| --- | --- |
| 有效期内切设置再返回 | 推荐 POST 为 0，时间戳和全部页不变 |
| 切到热门，模拟推荐过期后发送焦点事件 | 推荐 POST 为 0，隐藏推荐不更新 |
| 过期切回推荐 | 只请求 `page=1`，成功后只保留新首页 |
| 活动推荐在有效期内收到当前 Query 失效通知 | 不改 Cookie，自动请求 `page=1` |
| 活动推荐仅修改首页年龄，不发送激活事件 | 推荐 POST 为 0，不因数据变化自动替换列表 |
| 活动推荐过期后发送焦点事件 | 只请求 `page=1`，首页更新时间推进 |
| 手动刷新 | 按钮在刷新期间禁用，首页完成后恢复，只请求 `page=1` |
| 恢复大窗口触发填屏补货 | 请求 `page=2` 时刷新按钮已可用，首页 `fetchedAt` 保持不变 |
| 首页更新失败的故障注入 | 旧列表保留，显示「推荐视频更新失败」和重试，隐藏补货入口 |
| 失败期间恢复大窗口 | 没有补货请求，错误反馈仍保留 |
| 关闭故障拦截，点击重试 | 真实 APP API 成功取得新首页，错误消失，恢复补货能力 |

焦点验收使用合成 `window focus` 事件，未做系统最小化/恢复或 Android 生命周期实测。故障场景通过 CDP `Fetch` 拦截推荐 IPC 并返回 `Tauri error`，验证的是 UI 失败分支，**不是上游网络失败实测**；视频条目、账号和代理设置均未修改。重试成功快照只含首页，随后退出验证、恢复大视口又触发一次正常第二页补货，数据中单列记录。

验证结束后清除请求拦截、视口覆盖和临时 QueryClient 引用，返回原 VOD 播放页面并恢复原播放状态。

### 检查与剩余边界

`bun run check` 通过；`video-recommendations-query`、`video-feed`、`refresh-fab-visibility` 和 `video-settings` 的聚焦测试共 **20 项通过、0 失败、75 个断言**。其中使用真实 TanStack `QueryClient` / `InfiniteQueryObserver` 覆盖首页年龄、并发刷新、失败保留、取消迟到补货、授权隔离和失效通知。`git diff --check` 通过。本轮没有 Rust 改动，因此未重复运行初轮已通过的 Rust 测试。

这轮修复使本地缓存更及时地取到新一批推荐。上游仍可能返回旧稿件，`data.config`、推荐会话参数和观看、曝光反馈协议仍待验证；未承诺推荐按发布时间排序或根据本地观看历史即时学习。
