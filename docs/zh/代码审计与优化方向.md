# rLive 代码审计与优化方向

## 结论与范围

本轮交付分两部分：**实现抖音 Cookie 推荐灰度**，以及**审计后续优化方向**。下文的性能与功能建议
除明确列为本轮完成者外，均**尚未实施**，不是发布承诺，也不是已测得的提速报告。

- 审计基线：`7ce8ec22ca83dfa6546b193e2a05ece5eb4aa32f`，叠加本轮抖音改动；记录于 2026-09-21。
- 方法：静态阅读前后端实现、核对已有测试与文档，对关键发现复核具体控制流；不以 TODO 或文件大小判断质量。
- **结构确认**：能从代码证明机制或缺口存在；不代表已测出发生频率或用户侧耗时。
- **测量假设**：需要 profiling / 受控实验后才能决定是否实现。
- 优先级：P0 为正确性/资源完整性前置修复，P1 为下一轮优先，P2 为数据支持后推进。
- 本轮没有全平台性能基准、Android 真机专项或 macOS 实机验证，不给出百分比提速承诺。

核心判断：先修复会导致反复失败的缓存与生命周期问题，再减少跨实例等待和重复 I/O；功能上优先
把“状态是否可信、失败后如何恢复”说明白，而不是继续扩张未经验证的平台能力。

## 本轮已完成：抖音 Cookie 推荐灰度

入口 `/shorts/douyin` 的「Cookie 推荐流（灰度）」默认关闭，仅本次进入生效，是**用户自选灰度**，
不包含远程百分比放量系统。

- Rust 从既有账号库读取 Cookie，要求登录字段，复用 `ttwid`、`a_bogus`、应用代理及错误映射请求 `tab/feed`。
- 每次一批，最多 10 条受支持的视频元数据；保留混合画幅，过滤广告、图集、直播及不支持的媒体。
- 手动上一条/下一条、追加和刷新；跨批去重，全重复/空批/上游结束停止；每轮最多 20 批。
- 只对当前作品取流，共用原生 MP4 播放与 UUID 代理所有权；Cookie 不传给 CDN，推荐缓存不持有媒体 URL。
- 验证、失效、空结果与失败可见，不静默降级为匿名推荐；账号设置导航会卸载旧推荐，请求途中账号变化也会拒绝旧响应。
- 不移植 B 站的三槽滑动、作者流、弹幕和历史，不宣称 Cookie 必然带来账号级个性化。

实现：[站点](../../src-tauri/src/sites/douyin/video.rs)、[命令](../../src-tauri/src/commands/douyin_video.rs)、
[入口](../../src/features/shorts/DouyinVideoPage.tsx)、[共享播放](../../src/features/shorts/DouyinVideoPlayer.tsx)。
操作与完整边界见[短视频功能](短视频功能.md)。

## 一、性能优化方向

### 优先级摘要

| 优先级 | 方向 | 证据 | 收益目标 | 风险 |
| --- | --- | --- | --- | --- |
| P0 | P-01 分片缓存完整性及同键写入 | 结构确认 | 避免坏缓存导致持续重试/卡顿 | 中：缓存协议正确性 |
| P1 | P-02 播放生命周期按实例排队 | 结构确认 | 多画面互不阻塞 | 中：取消与所有权 |
| P1 | P-03 关注刷新批量事务 | 结构确认 | 降低全局 DB 锁占用与写放大 | 低至中：并发用户修改 |
| P1 | P-04 桌面窗口监听的迟到清理 | 结构确认 | 避免长期监听及 IPC 累积 | 低 |
| P1 | P-05 缓存字节预算和后台写入额度 | 结构确认，负载收益待测 | 有界 RSS / 磁盘与维护任务 | 中 |
| P2 | P-06 代理策略隔离的 HTTP Client 复用 | 结构确认，收益待测 | 减少代理建池/握手 | 中：路由、认证隔离 |
| P2 | P-07 延迟弹幕的有界调度 | 结构确认，负载收益待测 | 控制多画面 retained heap 与 timer | 中：顺序/溢出语义 |
| P2 | P-08 代理响应与连接资源预算 | 结构确认 | 异常上游/慢客户端下稳定 | 中：不能串行化正常分片 |
| P2 | P-09 FLV/MPEG-TS Worker 实验 | 测量假设 | 减轻解复用的主线程竞争 | 较高：平台兼容性 |

### P-01：缓存必须只提交完整分片

**证据**：[stream_proxy.rs](../../src-tauri/src/stream_proxy.rs#L2963) `handle_client` 的分片写缓存分支
（约 2963–3006 行）在下游 `write_all` 失败时 `break`，随后仍以“键存在且缓冲非空”提交，
没有要求正常读至上游 EOF 或长度等于 `end - start + 1`。缓存命中分支（约 2690–2732 行）
也未按预期 Range 验证正文长度。[disk_cache.rs](../../src-tauri/src/disk_cache.rs#L112) `put`
使用固定 `{key}.tmp`，同键并发写者会操作同一个临时文件，rename 本身不能保证内容不互相干扰。

**方向**：提交前验证正常完成和精确长度；客户端离开时放弃缓存，不能把前缀作为完整条目提交；
命中也做长度校验并在无效时重新下载；同键采用唯一临时文件或互斥，再决定是否做请求合并。
这是正确性前置修复，不能通过提高命中率掩盖。

**验收**：本地可控上游按块返回，首块后客户端断开；再次请求必须回源。增加短体、超长体、
读取失败、同键并发写用例，完整命中必须逐字节一致。现有 `media_cache_serves_cached_segments_without_upstream`
夹具宣称 `0-799` 却只返回 `SEGMENT`，应改为长度一致的正常夹具并另建畸形响应测试。
本轮仅确认控制流缺口，未进行真实媒体损坏复现。

### P-02：不要用一个全局队列串行所有播放器

**证据**：[useWebPlayer.ts](../../src/features/room/player/useWebPlayer.ts#L558) 的模块级
`proxyLifecycleQueue` 被全部实例共享；硬启动在队列内等待 `50ms + 两次 rAF`、媒体节点和 IPC，
软切换也在队列内等待 `switchVideoJsPlaybackSource`（约 1268–1307 行）。
[videoJsPlayer.ts](../../src/features/room/player/videoJsPlayer.ts#L382) 的切换就绪预算为 12 秒。
Rust 代理已有按 session 隔离的资源，不需要所有播放器互等。

**方向**：先改为实例级串行；再拆开代理变更与媒体 `canplay` 等待，保留 generation/取消边界。
固定延时是否能替换为“新媒体节点已挂载”的确认，需独立实验，不直接删掉防黑屏流程。

**验收**：A 切源永不 `canplay` 时，B 的启动/停止不得等待 A 的超时；测试六路同时启动、
连续切源与退出，记录排队、代理就绪、适配器挂载、首帧的 p50/p95，每个 session 仍只有一个所有者。

### P-03：关注状态刷新只写变化字段，并用一个事务提交

**证据**：[commands/follow.rs](../../src-tauri/src/commands/follow.rs#L168) `refresh_follows`
已有网络并发上限 5，且网络等待不持 DB 锁；但收尾在共享锁内循环完整 `upsert`，无批量事务。
[db/follow.rs](../../src-tauri/src/db/follow.rs#L93) 重复编码 tags 等不变字段；`list_auto_record`
先读取全部关注再过滤。应用 DB 是 [AppState](../../src-tauri/src/state.rs) 的共享 `Mutex<Connection>`。

**方向**：事务 + 复用 prepared statement + 状态字段定向更新；保留最后重读/竞态检查，不能覆盖
用户刚改的标签、自动录制标记或复活已删除关注。自动录制筛选下推 SQL，索引由查询计划决定。
已有 WAL / NORMAL / busy timeout，不把“开启 WAL”当新建议，也不先引入连接池。

**验收**：固定网络结果，测 100/1000/5000 条关注落库、锁等待、WAL 增量和并发设置读 p95；
一轮刷新一次事务，标签/删除竞态测试通过。若同步 DB 段仍显著阻塞，再考虑专用 DB 执行通道。

### P-04：补齐异步窗口监听注册的迟到清理

**证据**：[useWebPlayer.ts](../../src/features/room/player/useWebPlayer.ts#L1704) 桌面全屏 effect
先 `await sync()`，再 `unlisten = await appWindow.onResized(...)`；cleanup 只调用当时已赋值的
`unlisten`。若卸载发生在任一 await 中，之后迟到的订阅没有回收；`disposed` 只阻止设置 mode，
没有阻止旧 resize 回调发出窗口 IPC。

**方向**：异步步骤返回后检查 disposed；迟到获得的 unlisten 立即执行，sync 开始前也校验生命周期。
参照已有弹幕 event bus 的 generation 防护，不新增大型框架。

**验收**：用 deferred Promise 分别阻塞初次 sync 和注册，在完成前卸载，再释放 Promise；
unlisten 恰好一次，旧实例不再发 IPC，反复进出房间监听数量回到基线。

### P-05：缓存预算从“提交次数”改为“字节 + 在途额度”

**证据**：[media_cache.rs](../../src-tauri/src/media_cache.rs) 规定单分片最大 32MiB，
Android / 桌面预算 128 / 512MiB；[disk_cache.rs](../../src-tauri/src/disk_cache.rs) 每 64 次提交才 sweep。
理论上两次 sweep 之间可新增 63 个接近上限的条目，即约 2016MiB，**这只是上界推导，不是实测占用**。
`get` 在读取整个文件后才检查 TTL。分片内存缓冲与后台 `spawn put` 无共享额度；超限后 `clear()`
保留 capacity，且后续循环仍可能再次累积；sweep 也没有单飞保护。

**方向**：读正文前判断 TTL；超限后彻底释放缓冲并只转发；建立共享字节预留和有界后台写队列，
额度不足时跳过缓存而不阻塞播放；按字节触发单飞清扫。目录快照已用 `spawn_blocking`，应保留。

**验收**：2/6 路、大分片与慢盘组合，测 RSS 峰值、在途字节、写队列、磁盘超额和清扫时长。
明确“磁盘预算 + 有界在途预留”的容忍范围，缓存满时不能令前台排队。

### P-06：复用绑定同一代理策略的元数据 Client

**证据**：[http_client.rs](../../src-tauri/src/http_client.rs#L55) `client_for_proxy` 在无代理时
复用 `OnceLock<Client>`，有代理时每次构建。站点按命令创建，故跨命令不能共用该连接池；
一个站点实例内部多次请求仍会复用，不能描述为“每个 HTTP 请求都重建”。

**方向**：小容量缓存按完整代理策略隔离的 Client，含认证差异；代理变化后新请求立即走新策略，
旧请求自然完成。不复用账号站点对象，不把禁止重定向、普通 API 和无限媒体客户端混为一套。

**验收**：用可计数本地代理测 Client 构建、TCP/TLS 建连和重复命令耗时；同策略可复用、换策略
不走旧代理，不记录代理认证信息。收益必须实测后决定是否上线。

### P-07：延迟弹幕改为单调时钟的有界到期队列

**证据**：[DanmuJsDanmaku.tsx](../../src/features/room/danmaku/DanmuJsDanmaku.tsx#L635)
把每批事件闭包保留到各自 timer 到期，最长延迟 60 秒。隐藏/退出已有清 timer，不是无清理泄漏；
但队列没有数量/字节上限，过滤在到期后才执行。适配器已有的 80 条/5 秒零尺寸待处理队列并不覆盖这条路径。

**方向**：一个到期队列/调度 timer，限定消息数、估算字节与最大滞留；明确普通消息/SC 的溢出策略
和延迟调整语义。提前过滤不得破坏用户中途变更设置的约定。

**验收**：合成 20 批/秒、0/10/30/60 秒延迟，测 retained heap、timer 数与出队耗时；
长时间压力不无界增长、正常负载不乱序、隐藏和换会话后清零。不要把理论满载当作普通直播流量。

### P-08：统一代理文本上限和连接停滞预算

**证据**：[stream_proxy.rs](../../src-tauri/src/stream_proxy.rs#L2434) `run_proxy_loop`
已有 `JoinSet` 归属和 stop 时 abort，但 accept 后 handler 数无上限；本地首部读取没有期限。
明确识别的 HLS 清单与错误正文使用 `.text()` 全量读取；只有嗅探 HLS 分支有 4MiB 上限。
已有上游连接/逐读超时，不能给无限直播错误地加总时长限制。

**方向**：有限文本统一有界收集与完成期限，首部完整读取并限制字节/时间，下游长时间不读时结束连接；
handler 上限须兼容并发 Range/HLS，不得通过所有分片串行来“优化”。

**验收**：超大清单、持续小块错误体、分段首部、慢下游，在规定预算内结束；正常多 Range 仍并行，
stop 后上下游连接归零。主要收益是异常资源稳定，正常播放收益尚未测量。

### P-09：Worker 与缓冲参数只作为实验，不直接改默认值

**证据**：[useWebPlayer.ts](../../src/features/room/player/useWebPlayer.ts#L348) 的
`liveFlvPlaybackOptions` / `liveMpegtsPlaybackOptions` / `iptvFlvPlaybackOptions` 禁用 Worker，
已有 SourceBuffer 清理、追赶和多画面额外缓冲。[videoJsPlayer.ts](../../src/features/room/player/videoJsPlayer.ts)
已经按协议懒加载，原生 MP4 不加载流内核。

**假设与实验**：解复用可能与 React/弹幕争主线程，也可能不是主要成本。固定输入，比较单路/六路、
弹幕与同步开关下 Worker 开/关，测 scripting、long task、丢帧、首帧、重缓冲、RSS 和销毁。
只有兼容性与全部指标不回退才上线；若瓶颈是解码，不继续凭配置猜测。

### F-01：把“保存了 Cookie”与“平台确认登录”分开

**现状与证据**：[commands/account.rs](../../src-tauri/src/commands/account.rs) 的 `AccountStatus`
已区分 `None/Valid/Expired/Unknown`；抖音等缺少低成本探针时返回 Unknown。
但 [SettingsPage.tsx](../../src/features/settings/SettingsPage.tsx#L623) `AccountCard` 将任何有 Cookie
且非 Expired 的状态显示为「已登录」，因此 Unknown 被升级成了确定事实。

另一个具体缺口在 `parse_bilibili_profile`（约 332–354 行）：全部非零 API code 都返回
`Verified(None)`，`isLogin=true` 但 `uname` 缺失/不可展示时也会得到 None；上层把 None 当 Expired。
设置页 `autoLogout` 随后调用 `account_clear_cookie`。代码没有独立表达“已登录但无可展示名字”，
也没有把非登录错误与明确过期充分分开；这是条件路径审计，不是线上误登出的发生率报告。

**方向**：Unknown 显示「已保存，未验证」，将登录是否成立与显示名分成两个结果；只让明确未登录
证据标记 Expired。验证码、限流、异常结构保留 Cookie 并给重试/官方网页入口，默认不因未知状态删除凭据。
不把抖音 Cookie 推荐请求成功当作有效性或个性化认证。

**验收**：`isLogin=true` 且无 uname、网络错误、非登录业务错误、明确未登录、Unknown 各自有 UI/命令测试；
Unknown/临时错误不清 Cookie，明确退出才删除，改变账号后相关缓存和能力状态更新。

### F-02：关注刷新返回部分成功摘要，而不只有列表

**现状与证据**：[commands/follow.rs](../../src-tauri/src/commands/follow.rs#L168) `refresh_follows`
对单房间 `get_room_live_status(...).await.ok()` 丢弃错误类型；收尾还把参与结果的 `updated_at` 设为本轮时间。
[followRefresh.ts](../../src/features/follow/followRefresh.ts) 有 60 秒周期、在途去重、保留列表机制，
但 IPC 只返回 `FollowUser[]`，前端无法知道本轮是全成功还是部分探测失败，也不能定向重试失败项。

**方向**：保留现有关注列表与自动刷新，增加成功/失败/跳过摘要、最近成功检测时间及安全错误类别。
把 Unknown、未开播、正在直播分开；失败项可手动重试，不以全页失败替代可用条目，也不将旧直播状态当成新确认。
可与 P-03 共享命令边界，但 UI 反馈与数据库批处理分别提交、分别验收。

**验收**：10 个关注中 3 个超时，仍显示 7 个有效结果、3 个待确认及重试入口；只重试那 3 个，
期间删除/改标签不被覆盖；账号验证失败提示更新账号而不是标记主播未开播。

### F-03：IPTV 的“网络可达”不等于“媒体已验证可播”

**现状与证据**：[iptv/mod.rs](../../src-tauri/src/iptv/mod.rs) 的 `probe_channel` 已有总超时、
首字节检查、HTML 排除和 HLS 标记验证，不能说现有探针只看 HTTP 200。
但它见到 `#EXTM3U` 就可成功，不验证所引用媒体分片是否可读/可解码。
`check_channels` 与前端 [availability.ts](../../src/features/iptv/availability.ts) 均只按 URL 去重，
尽管 `IptvChannelCheck` 同时有 headers；相同 URL、不同 Referer/UA 的条目可能被共享一个结果。
[availabilityStore.ts](../../src/features/iptv/availabilityStore.ts) 也以 URL 为键，只有整轮完成时间，
没有每条结果的检测时间。现有 source 切换 epoch 和会话内缓存是应保留的能力。

**方向**：以完整播放配置身份区分检查结果；结果分成「未检测 / 网络可达 / 媒体验证 / 失败 / 已陈旧」。
默认保留轻量探测，仅用户主动选择时做有字节/并发预算的深探测；按条目时间决定重查，不自动全扫所有源。
不要把 IPTV-org 的端点可达性当作内容授权或长期可播保证。

**验收**：同 URL 不同请求头分别返回 403/200，不能串用状态；有效清单但首片 403 不显示为已验证可播；
源切换后的迟到结果仍无效，探测失败原因及检测时间可见，用户能重查失败/过期条目。

### F-04：在已有 ASR 取消机制上增加可靠续传

**现状与证据**：[commands/asr.rs](../../src-tauri/src/commands/asr.rs) 已有 enable/disable，
[asr.rs](../../src-tauri/src/asr.rs#L1112) `download_model_file` 已用 generation 中断、每 250ms 更新进度并校验大小，
不是“没有取消/进度”。但它每次普通 GET 后 `File::create` 新建临时文件；准备阶段删除旧 `.part`，
错误/取消也清理临时包，因此网络中断后不能续传已下载部分。Windows 运行库另有 SHA-256 校验。

**方向**：以资产版本/校验摘要绑定下载任务，用户可选择暂停保留部分、重试续传或删除；支持 Range/If-Range
并校验服务端响应，不支持续传时明确回退完整下载。全部完成并校验后才能解压/加载，不能把 .part 当有效模型。
继续只在用户明确启用后下载，Android 不因此引入桌面 ASR 图谱。

**验收**：下载到 40% 断网后可继续；服务端忽略 Range、ETag 改变、资产版本更新、部分文件损坏和取消后重启
均有测试；不得加载混合版本资产，状态能区别暂停、重试、校验、解压与就绪。

### F-05：录制管理增加可预览的保留策略，而不是自动删文件

**现状与证据**：[recording.rs](../../src-tauri/src/recording.rs) 已有自动分割、崩溃恢复、路径隔离、
剩余空间检查（保留 512MiB、运行期定期检查），`delete` 拒绝删除活动/收尾中的录制；
[commands/recording.rs](../../src-tauri/src/commands/recording.rs) 删除后清理续播进度。
当前 `RecordingItem` / `AppSettings` 没有受保护标记和按天数/容量的保留策略，因此长期自动录制仍需用户逐步管理库存。

**方向**：先做按空间/日期筛选、清理预览和“保护此录制”，再提供默认关闭、仅本机的保留规则。
清理对象只限应用登记的已完成分卷，不碰正在录制/收尾、正在回放或受保护内容；媒体、弹幕、ASS、元数据与进度一致处理。
空间不足默认停录并说明原因，不能未经授权删除历史文件来腾空间。

**验收**：预览准确列出将回收字节与排除原因；多存储根、损坏元数据、路径越界、并发结束/删除、
受保护和回放中的录制均有测试；关闭保留功能不删任何文件。该项风险高，必须先确认产品删除策略。

### F-06：诊断导出组合现有能力，且先预览再分享

**现状与证据**：[diagnostics.rs](../../src-tauri/src/commands/diagnostics.rs) 已提供当前/上一份日志的
256KiB 尾部；[AppLogField.tsx](../../src/features/settings/AppLogField.tsx) 已能查看、复制、清空和打开目录。
播放器另有 [playbackTelemetry.ts](../../src/features/room/player/playbackTelemetry.ts) 内存快照与
`stream_proxy_telemetry`，但日志查看器的导出动作只是复制当前文本，没有统一包含版本、WebView、播放阶段与代理聚合指标。

**方向**：新增“生成诊断摘要”，复用日志、播放/代理指标及版本信息；导出前展示字段与时间窗，允许用户移除内容。
账号只展示保存/验证状态，不打包 Cookie 或数据库；移除 URL query/user-info、私有 M3U、绝对用户路径、
字幕/聊天正文与观看内容，未知字段默认不导出。由用户主动保存/复制，不自动上传。

**验收**：向日志/指标夹具注入假 token、带认证代理、签名 URL 和用户目录，输出必须脱敏；
无播放会话、日志缺失、Android 无桌面指标时正常退化；保留问题所需错误码与阶段耗时，摘要规模有上限。

## 三、测量和实施约束

### 先修正遥测口径

复用 [playbackTelemetry.ts](../../src/features/room/player/playbackTelemetry.ts) 和既有诊断，不另建平行采集系统：

- `startup_ms` 从 telemetry session 创建起算；当前创建点在部分排队、DOM 或代理等待之后，
  不能当完整“点击到首帧”。补总耗时和阶段耗时。
- 每个播放器观察同一 WebView 的 long task，多路结果不可相加；应用级统一计数更可信。
- 全局环最多 120 快照、每路 2 秒一份，六路仅约 40 秒跨度，不是单路四分钟。
- `live_latency_seconds` 是 seekable 尾部差，不是采集到屏幕的绝对延迟。
- 只记录耗时、大小、计数、协议和匿名 session；不采集 Cookie、token、字幕正文、签名 URL 或完整上游响应。

### 验证顺序

1. P0 用本地上游夹具复现并修复，补回归；缓存收益测试必须在完整性成立后进行。
2. P1 分主题落地，每次只改一个变量，保留软切换硬回退、取消、代理所有权与账号隔离。
3. Windows 主窗口记录版本、WebView、协议、清晰度、并发路数、冷热缓存和代理设置，比较 p50/p95。
4. 目标涉及触摸、解码器/内存和 Worker 时再上 Android；macOS 不能用 Windows 结果代替。
5. P2 先测量，再设预算和验收；不把大规模架构改造当作默认答案。

### 不应重复建设与未覆盖项

已有按协议懒加载、原生媒体、session/generation 围栏、代理连接池、Rust 弹幕批处理、前端事件总线、
细粒度 Zustand selector、SQLite WAL、历史数量上限、虚拟历史列表等机制，不能把它们写成“待引入”。
普通视频瀑布流仍是全量 DOM，短视频元数据会随浏览增长；这是可继续做长会话 profiling 的方向，
本轮没有测量其收益，不直接开大规模列表迁移。

本轮没有完整审计第三方播放器内部、ASR 推理性能、FFmpeg 录制 CPU/I/O、图片代理、应用启动/包体，
也没有覆盖全部平台接口、网络异常组合或所有 UI 路由。本文是有范围的方向审计，不是“全库无其他问题”的保证。

与已有[性能优化](性能优化.md)的关系：该文保留此前具体修复与实机对比；本文列本轮新发现和未来方向，
不把历史测量挪作本轮结果。行号可能随代码演进变化，定位时以文件和函数名为准。
