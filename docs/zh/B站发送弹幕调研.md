# B 站发送弹幕调研

更新时间：2026-07-27。本文记录 rLive 正式支持 B 站单条弹幕发送的实现边界与安全约束。

## 结论

该能力依赖登录 Cookie 的非公开写接口。rLive 已正式支持**默认关闭的本机统一发送授权**：该授权同时控制 B 站、斗鱼和虎牙，但 B 站路径仍只允许用户主动发起的单条普通滚动文本。正式支持不代表把它扩展为自动化能力，也不代表这是 B 站公开的第三方写入 API；不支持礼物、批量、循环、定时、自动回复、样式权限或自动重试。

## 已确认的接口形态

参考 `bilibili-api-python` 17.4.2 的直播实现，单条直播弹幕使用：

```text
POST https://api.live.bilibili.com/msg/send
```

请求需要真实直播间号和已登录的 Cookie：

- 必需：`SESSDATA`、`bili_jct`；`bili_jct` 同时作为 `csrf` 与 `csrf_token`。
- 建议保留：`buvid3`、`buvid4`、`DedeUserID`，以保持网页登录态的一致性。
- 基础表单：`roomid`、`msg`、`mode=1`、`bubble=0`、`rnd`（Unix 秒）、`color=16777215`、`fontsize=25`、`csrf`、`csrf_token`。
- 位置模式：滚动 `mode=1`、底部 `mode=4`、顶部 `mode=5`；颜色、字号等样式可能受账号或房间权限限制。

现有 `LiveRoomDetail.room_id` 已保存真实房间号，后端也已有 B 站 Cookie、共享 HTTP 客户端和统一错误模型，因此无需为每条消息重新查询房间详情。

## 当前正式实现

1. 「设置 → 账号」最上方有默认关闭的本机统一发送授权 `danmaku_send_enabled`，同时控制 B 站、斗鱼和虎牙；它不会随配置导出或导入。B 站发送框还会检查保存的 Cookie 是否同时含 `SESSDATA` 和 `bili_jct`，未满足任一条件时严格禁用。
2. 输入框只在 B 站房间播放器功能栏中间显示；点击或按 Enter 会直接提交，发送中按钮锁定，并可见地显示成功、失败或权限状态。
3. 后端再次校验共用的本机发送授权、真实数字房间号、空白/控制字符、当前网页端默认的 20 个 UTF-16 码元上限和 Cookie，不信任前端状态。该上限来自官方网页端的 `danmakuLengthLimit`（会随账号/服务端策略变化）；目前 rLive 没有受支持的读取契约，因此以观察到的默认值 20 执行。
4. 每个房间使用 3 秒进程内冷却；服务端 10030 / 10031 / 10039 与 HTTP 429 统一提示“发送过快”。
5. 超时或网络故障不重试，提示“发送状态未知，请到直播间确认”。发送 command 在本机成功返回后，前端会显示仅当前会话可见的待回显提示：列表标明「我 / 本地已提交，待平台回显」，飘屏以琥珀色显示 `【我·待平台回显】`。这不是平台回显；真实 WebSocket 回显仍保留原样，且不会按相同文本自动合并、确认或移除本地提示。
6. 发送请求使用禁止重定向跟随的 HTTP 客户端，避免携带 Cookie 的请求被转交给重定向目标。Cookie、CSRF、发送内容和上游原始错误都不写日志或返回到 UI。Cookie 只留在本机 SQLite。

测试覆盖 Cookie/文本校验、发送冷却，以及本地 HTTP 契约（表单、Cookie/CSRF 请求头、成功与 HTTP 限流映射）。发布前仍应使用受控账号和获许可房间手动核实真实回显；不要对公共直播间实施自动化发送。

## 安全前置

`tauri-plugin-mcp-bridge` 现在只在 debug 构建装载；发布构建不暴露该本机自动化桥，因此不能绕过本机发送授权或用户主动操作的 UI 入口直接调用写 command。后端仍独立执行本机发送授权、Cookie、文本、房间号和冷却校验，前端禁用只是一层 UX 防护。
