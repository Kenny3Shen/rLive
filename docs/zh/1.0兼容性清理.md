# 1.0 兼容性清理

## 目标与边界

rLive 1.0 将应用自身的数据和 IPC 契约固定为首个正式 schema，不再在主程序启动路径内维护 0.x 数据迁移。这里的“兼容性”只指旧 rLive 版本留下的数据库、配置字段、profile 和 localStorage 结构；浏览器/WebView 能力差异、直播平台接口回退、网络故障恢复和第三方库补丁属于当前运行环境支持，不在删除范围内。

## 1.0 已删除的兼容层

- SQLite 使用 `PRAGMA user_version = 1`。空数据库按 1.0 schema 原子创建；已有但版本不是 1 的数据库返回 `db_schema_unsupported`，不会自动补列、删旧索引或裁剪旧数据。
- 未配置 `app-data-bootstrap.json` 时只选择当前默认数据目录，不再探测并接管旧系统数据目录中的 `rlive.db`。
- `AppSettings` 删除 `motion_mode`、`playback_smart_line_selection`、`playback_stall_auto_switch_enabled`、`iptv_availability_auto_check` 和 `iptv_availability_auto_check_interval_hours`；完整设置拒绝未知字段或缺失的 1.0 可移植字段。
- `settings_get` 只接受 `{ settings, has_saved_settings }`；前端不再接受直接返回 `AppSettings` 的旧后端。
- profile 固定为 `version: 1`，拒绝其他版本、未知字段和缺失的 1.0 可移植字段。
- 设置与多画面 localStorage 分别使用 `rlive-settings-v1`、`rlive-multi-room-v1`，不再执行旧 key 或 `secondarySlot` 迁移。
- `PlayUrl.protocol`、`IptvChannel.protocol`、`follow_add.live_started_at`、IPTV 检查请求头和 `recording_start` 的完整输入字段成为必填 IPC 契约。
- 删除 `sites::all()`、`BilibiliDanmakuComposer`、旧动效模式解析和旧房间导航 helper。

## 升级前处理

0.x 用户不能把原 `rlive.db` 直接交给 1.0。发布 1.0 前应使用升级前的 0.x 客户端完成以下操作：

1. 从「设置 → 数据管理」导出配置档案，并单独备份 `rlive.db`。
2. 备份所有录制 bundle；录制目录不在 profile 内。
3. 为 1.0 选择空应用数据目录，首次启动后导入配置档案。
4. 若 profile 被 1.0 拒绝，回到导出它的 0.x 客户端更新到最后一个过渡版本后重新导出，不要手工删字段绕过校验。

正式发布前需要提供并验证最后一个 0.x 过渡版本；否则现有用户没有受支持的升级路径。

## 暂时保留

已有录制文件仍是唯一保留的 rLive 数据兼容面：旧 `metadata.json` 缺失字段、无关键帧索引 FLV 和旧 HLS bundle 仍可读取。直接删除会让不可再生成的本地媒体失去索引或回放入口，因此应先提供批量转换/校验工具和真实旧样本回归，再在后续 major 版本移除。

以下代码也继续保留，但不属于 rLive 版本兼容：

- AudioWorklet 失败后的 ScriptProcessor、标准/WebKit Fullscreen、剪贴板降级和 Android WebView 方向处理。
- B 站弹幕接口回退、抖音 SSR、Twitch 广告清单恢复、播放线路重建和 IPTV 手动重试。
- `danmu.js@1.2.1` loader 与固定弹幕选轨补丁；升级依赖并通过回归测试后才能删除。

## 发布门槛

- 三处权威应用版本和 `Cargo.lock` 根包版本均为 `1.0.0`。
- 新库创建、旧库拒绝、profile schema 拒绝和新 localStorage key 有自动化覆盖。
- `bun run check`、`bun test tests/`、Rust 测试和 `bun run build` 通过。
- 使用最后一个 0.x 版本完成一次“导出 profile → 1.0 空库导入”演练，并保存至少一份旧 FLV、旧 HLS 和缺字段 metadata 回归样本。
- 发布说明明确数据库断代、录制保留范围和恢复步骤。
