# 开发指南

从源码运行、检查和构建 rLive。第一次上手只需要读「环境要求」和「启动」两节；桌面 release 构建、FFmpeg 依赖和 Android 相关内容按需往下看。

- 平台适配与后端分层：[架构说明](架构说明.md)
- 打标签发布与产物核验：[发布流程](发布流程.md)
- Android 环境、构建与真机调试：[Android 开发与构建](Android开发与构建.md)

## 环境要求

| 依赖 | 用途 |
| ---- | ---- |
| [rustup](https://www.rust-lang.org/tools/install) + Rust `nightly-2026-11-04` | Tauri 后端；版本由 `rust-toolchain.toml` 固定 |
| [Bun](https://bun.sh/) | 前端依赖与脚本入口 |
| [Tauri 2 前置环境](https://v2.tauri.app/start/prerequisites/) | 各平台 WebView 与构建工具链 |
| clang / libclang | 桌面 `ffmpeg-next 9.0.0` 的 bindgen（`ffmpeg-sys-next` 同样固定 9.0.0，原因见 `src-tauri/Cargo.toml`） |
| FFmpeg headers + link libraries + 运行库 | 桌面录制；通过 `pkg-config` 或 `FFMPEG_DIR` 定位 |

Android 不编译桌面 FFmpeg、录制和本地 ASR 模块，因此不需要 FFmpeg 与 libclang 桌面配置。

根目录的 `rust-toolchain.toml` 固定了本地、CI 与发布构建使用的同日 nightly。首次在仓库内运行 Cargo / Tauri 时，rustup 会读取该文件并安装缺失的工具链；也可显式安装并确认：

```bash
rustup toolchain install nightly-2026-11-04 --profile minimal --component rustfmt --component clippy
rustup show active-toolchain
```

升级日期时，必须同步修改 `rust-toolchain.toml` 与 `.github/workflows/` 中所有 `Set up Rust` 步骤，不能只更新本机默认工具链。

### Rust 编译缓存

`[profile.dev]` 使用 `opt-level = 1`、`debug = 0`、`incremental = false`，`[profile.test]` 同样关闭调试信息和增量缓存。这样开发产物会执行基础优化，又不保留体积可观的 Rust 增量缓存和调试信息；`debug_assertions` 仍然开启，因此 Tauri / Android 的 debug 构建和调试通道不受影响。

`[profile.release]` 保持 `opt-level = 3`、`lto = true`、`panic = "abort"` 和 `strip = true`，并显式关闭调试信息与增量缓存。release 优化仍会让干净构建耗时较长，这是产物体积与运行性能的取舍。

默认 dev 构建不包含 Rust 源级调试符号。需要单步调试 Rust 时，在 `src-tauri/` 下临时覆盖 profile；不要把这项设置写回默认配置：

```bash
cd src-tauri
CARGO_PROFILE_DEV_DEBUG=2 cargo build --locked
```

Windows PowerShell 7：

```powershell
Set-Location src-tauri
$env:CARGO_PROFILE_DEV_DEBUG = "2"
cargo build --locked
Remove-Item Env:CARGO_PROFILE_DEV_DEBUG
```

`target/` 还可能包含开发时生成的数据库、日志和录制文件，不要在不确认内容时对整个目录执行 `cargo clean`。

### Rust 编译体积实测

本节只比较干净构建的 Rust 产物，不与历史累积缓存直接混算。历史 `target` 还包含增量编译、Android target、rust-analyzer 和旧版根目录产物，其清理收益只能说明缓存治理效果，不能当作 Cargo profile 的体积优化。

测量环境为 Linux `x86_64-unknown-linux-gnu`（WSL），源码提交 `14ea8afc19633a30e43666444432bf49f123adb2`。两次构建使用同一份源码和 `Cargo.lock`，保留 `target-cpu=x86-64-v2`，均从 `src-tauri/` 执行：

```bash
cargo build --locked --bin rlive -j 2
```

目录体积使用 `du -B1 -s`（文件系统实际分配字节），`rlive` 可执行文件使用 `stat` 的逻辑字节数。为使含运行时数据的 `target/debug` 与独立基线目录可比，`debug_artifact_bytes` 只统计 Cargo 编译产物，排除 `bundle/`、`cache/`、`logs/`、`recordings/`、`rlive.db*` 和 `.recording-manager.lock`。完整原始记录见 [`rust-target-2026-11-04.json`](../bench/rust-target-2026-11-04.json)。

#### 干净构建对照

stable 基线使用当前锁文件，但通过 `CARGO_PROFILE_DEV_OPT_LEVEL=0`、`CARGO_PROFILE_DEV_DEBUG=2`、`CARGO_PROFILE_DEV_INCREMENTAL=true` 还原旧默认 profile。因此它与 nightly 配置的差值表示“工具链 + dev profile”的组合效果，不能单独归因为 nightly。

| 工具链与 profile | Rust 编译产物 | `rlive` | 构建耗时 | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: |
| stable 1.98.0（`88d9e12ae`，2026-08-18，LLVM 22.1.8）；`opt-level=0`、`debug=2`、`incremental=true` | 5,946,322,944 B（5.538 GiB） | 421,414,952 B（401.893 MiB） | 228.01 s | 2,187,280 KiB |
| nightly 1.101.0（`708c94ef0`，2026-11-03，LLVM 23.1.5）；`opt-level=1`、`debug=0`、`incremental=false` | 1,402,908,672 B（1.307 GiB） | 36,766,872 B（35.064 MiB） | 348.50 s | 1,979,712 KiB |

同口径变化：

- Rust 编译产物减少 4,543,414,272 B，降至基线的 23.593%，即 **-76.4071%**。
- `rlive` 减少 384,648,080 B，降至基线的 8.725%，即 **-91.2754%**。
- 构建耗时增加 120.49 s，即 **+52.844%**。两次构建都只有 1 次样本，不能据此推断稳定复现的编译速度，更不能宣称编译加速。
- `/usr/bin/time` 记录的最大子进程 RSS 从 2,187,280 KiB 降至 1,979,712 KiB（约 -9.49%）。该值不是并发进程的总内存占用。

nightly 的 Cargo 使用新的产物布局，依赖与测试产物主要写入 `target/debug/build/<crate>/`；因此本记录中的 `deps = 0` 是布局变化，不是产物丢失或测量遗漏。当前固定工具链为 `nightly-2026-11-04`。

测量时 nightly 对 `asr.rs` 和录制测试中的 `fetch_update` 发出 deprecated 警告；后续已将两处调用改为 `try_update`，保持原有内存序与计数逻辑，当前构建不再出现该警告。原始测量记录保留当时的状态。

本次没有测量 release 产物、运行时性能或 FPS，不能把 dev 产物体积变化表述为运行性能收益；release profile 原本已启用 `opt-level = 3`、LTO 和 `strip`。

#### 历史缓存清理

切换前 `target` 总量为 187,163,463,680 B（174.310 GiB）。清理只删除 Linux / Android / rust-analyzer 的编译缓存和旧版根目录 Rust 产物，保留数据库及哈希、开发日志、录制目录、缓存、bundle 和文档。额外发现的旧测试 ELF `debug/bilibili_app_isolated_tests` 是单链接独立文件，逻辑大小为 64,412,008 B、实际分配 64,299,008 B；将该文件计入后，按整个 `target` 的前后快照计算，排除独立 stable 基线后为 656,703,488 B（626.281 MiB），净释放 186,506,760,192 B（173.698 GiB）。

该结果来自整个目录的前后差值，没有把各子目录删除量相加；硬链接可能让子目录求和重复计数。清理快照取自 nightly 重建前的缓存清理阶段，不包含随后生成的构建与测试产物；完整流程的最终目录见下节。这里的 174 GiB 历史目录与上面的 5.538 GiB 干净产物口径不同，不能合并成“配置将 target 从 174 GiB 降到 5.5 GiB”的结论。

#### 测试验证

nightly 工具链和优化后的 dev / test profile 通过了 Rust 库测试：

```bash
cargo test --locked --lib -j 2
```

结果为 838 passed、0 failed、1 ignored，共 839 项测试，其中 1 项未执行；测试运行时间为 18.43 s，该时间不含测试代码的编译时间。测试前后再次核对了保留的数据库文件哈希以及 `cache/`、`logs/`、`recordings/`、`bundle/`、`doc/` 目录占用，均未变化。优化后的 `rlive` 也确认不含 DWARF 调试信息。

#### 最终整目录结果

完整流程结束后的快照包含 nightly dev 构建、Rust 库测试产物、旧 bundle / doc / cache，以及保留的运行数据和日志。独立 stable 基线目录已通过 `cargo clean --target-dir target/size-baseline` 删除，没有清理实际运行数据。

| 时点 | `target` 总量 | 相对历史快照 |
| --- | ---: | ---: |
| 切换前历史快照 | 187,163,463,680 B（174.310 GiB） | - |
| nightly 构建与测试后 | 2,272,800,768 B（2.117 GiB） | 净减少 184,890,662,912 B（172.193 GiB），**-98.78566%** |

该整目录降幅是一次性旧缓存清理与 nightly dev / test profile 重建共同造成的结果，不能单独归因于编译优化，也不能把它等同于每次干净构建都会获得的固定比例。干净构建之间的可比数据以上面的 debug 产物和 `rlive` 对照为准。

本节只验证了 Linux/WSL 的 dev 构建与 Rust 库测试。WSL 侧已重新安装 nightly 对应的 5 个交叉 target 标准库，但这不是跨平台构建结果；Windows 的独立实测见下一节，macOS、Android 和 release 产物仍未构建或测量。

#### Windows 干净构建验证

Windows 对照使用同一提交 `14ea8afc19633a30e43666444432bf49f123adb2`、同一份 `Cargo.lock` 和源码树。Windows 镜像没有 `.git`，因此显式把 WSL 侧 HEAD 传给测量脚本。Rust 源树 SHA-256 为 `828d5d7c823a35f5de446c5c1540d7608d7ca7d01f1909255d95b62d5bffa91f`，与 WSL 侧一致；`Cargo.lock`、`Cargo.toml`、`build.rs`、`src-tauri/.cargo/config.toml` 和 `rust-toolchain.toml` 五个配置的哈希也在构建前后核对一致。完整记录见 [`rust-target-windows-2026-11-04.json`](../bench/rust-target-windows-2026-11-04.json)。

环境为 Windows 11 `x86_64-pc-windows-msvc`、PowerShell 7.6.9、MSVC 19.44.35228、`D:\dev\FFmpeg` 和 `D:\dev\LLVM-22.1.8\bin`。两次构建均从 `src-tauri/` 执行，固定 `-j 2` 和 `RUSTFLAGS="-C target-cpu=x86-64-v2"`，分别使用独立、干净的 `baseline-target` 与 `optimized-target`：

```powershell
rustup run stable cargo build --locked --bin rlive --target-dir <baseline-target> -j 2
rustup run nightly-2026-11-04 cargo build --locked --bin rlive --target-dir <optimized-target> -j 2
```

stable 基线通过 `CARGO_PROFILE_DEV_OPT_LEVEL=0`、`CARGO_PROFILE_DEV_DEBUG=2`、`CARGO_PROFILE_DEV_INCREMENTAL=true` 还原旧 profile；nightly 使用仓库当前的 `opt-level=1`、`debug=0`、`incremental=false`。因此差值仍表示“工具链 + dev profile”的组合效果，不能单独归因于 nightly。

| 指标 | stable 1.98.0（旧 profile） | nightly 1.101.0（新 profile） | 变化 |
| --- | ---: | ---: | ---: |
| `target` 实际分配（硬链接去重） | 6,427,462,920 B（5.986 GiB） | 1,574,620,520 B（1.466 GiB） | 减少 4,852,842,400 B，**-75.5017%** |
| `target` 逻辑总量（重复计算硬链接） | 7,032,296,494 B（6.549 GiB） | 1,612,075,276 B（1.501 GiB） | 减少 5,420,221,218 B，**-77.0761%** |
| `rlive.exe` | 39,634,432 B（37.798 MiB） | 26,347,520 B（25.127 MiB） | 减少 13,286,912 B，**-33.5237%** |
| `rlive.pdb` | 261,074,944 B（248.980 MiB） | 11,726,848 B（11.184 MiB） | 减少 249,348,096 B，**-95.5082%** |
| EXE + PDB | 300,709,376 B（286.78 MiB） | 38,074,368 B（36.31 MiB） | 减少 262,635,008 B（250.47 MiB），**-87.3385%** |
| `debug/incremental` 实际分配 | 1,119,732,144 B | 0 B | **-100%** |
| 干净构建耗时 | 307 s | 433 s | 增加 126 s，**+41.0423%** |

构建耗时取 Cargo 日志 `Finished` 行的整秒值，不是脚本原始 `Stopwatch` 的小数秒；`debug/incremental` 的逻辑总量也从 1,119,110,582 B 降为 0 B。

Windows 的体积使用 `FILE_STANDARD_INFO.AllocationSize` 统计实际分配字节，并按卷序列号与文件索引去重硬链接；逻辑字节逐文件累加 `Length`，因此会重复计算硬链接。用 `rust-toolchain.toml` 标定时，逻辑大小 170 B、实际分配 176 B。该口径与 Linux/WSL 的 `du` 结果不能直接混合相加。

> [!IMPORTANT]
> `optimized` 的测试前构建快照属于**重建口径**：首轮脚本在库测试失败后提前退出，未保留当时内存中的最终汇总。因此当前数据是 `optimized-target` 测试后总量减去唯一的测试 crate 目录 `debug/build/rlive/dc9025a027530f11`（逻辑 35,407,594 B、实际分配 35,414,080 B）得到，未删除或移动文件。baseline 快照未经重建。该表用于比较构建产物结构，不应被描述为同一时刻直接采样的原快照。

nightly 的 Cargo 将依赖与构建产物主要写入 `debug/build/<crate>/`，所以 `deps` 为 0 是布局变化，不是产物丢失。`debug/build` 在 nightly 中记录为逻辑 1,573,992,908 B、实际分配 1,574,608,048 B。测试完成后，优化目录实际分配为 1,610,034,600 B；该值包含测试产物，不是上表的测试前结果。

复现入口位于 Windows 同步镜像；先同步源码，再把 WSL HEAD 显式传给脚本：

```bash
bash scripts/sync-to-windows.sh
```

```powershell
# 在 D:\dev\rLive 执行；镜像无 .git，SourceCommit 必须取 WSL 的 HEAD。
pwsh -File .\scripts\measure-windows-rust.ps1 -SourceCommit <WSL-HEAD>
```

默认输出到 `src-tauri/target/measurements/rust-2026-11-04/`，包含两个独立 target、构建与测试日志和 JSON。脚本不会清理镜像原有的 Windows `target` 或运行数据。重复测量应传入新的 `-OutputRoot`；只有明确接受删除旧测量缓存时才对同一目录传 `-Force`，它不会删除测量根目录之外的缓存。本次两个独立测量目录均保留，没有据此声称清理了旧 Windows 整目录缓存或释放了对应空间。

库测试命令为 `rustup run nightly-2026-11-04 cargo test --locked --lib --target-dir <optimized-target> -j 2`。首轮全量结果为 832 passed、1 failed、1 ignored；失败项为 `account::bilibili_app::tests::expired_credentials_and_invalid_paths_fail_without_network`，期望 `bilibili_app_auth_required`，实际收到 `bilibili_app_auth_unavailable`。该路径的 `validate` 是权威服务端校验，不按本地过期状态提前拦截，所以测试名虽然带 `without_network`，实际仍依赖网络。精确重跑该单测通过，随后在**同一测试产物**上全量重跑为 833 passed、0 failed、1 ignored。这里保留实网瞬态/非确定性边界，不能声称已经证明该失败与 nightly 无关；可确认的是没有修改业务源码，且重跑通过。

测量结束后才通过 RsProxy 补齐同一 nightly 的 rustfmt 和 clippy 组件，补装不计入构建时间。此次没有构建 release、安装包，也没有启动或验证 GUI、播放器及 `D:\rLive` 的现有安装版，因此不能据此声明这些验证通过。

## 启动

```bash
git clone https://github.com/Kenny3Shen/rLive.git
cd rLive
bun install
bun run tauri dev
```

`bun run dev` 只启动 Vite，可用于调试纯 UI。直播请求、本机代理、数据库和字幕依赖 Rust 后端，必须通过 Tauri 启动。

## 检查与构建

```bash
bun run check        # oxlint + 两个 tsconfig 的类型检查
bun test tests/      # 前端单元测试
bun run build        # tsc --noEmit + vite build
bun run tauri build  # 当前平台安装包
```

按改动风险选最聚焦的检查即可，不必每次全跑。Rust 格式和 lint 检查应覆盖测试目标：

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --lib --tests -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

### 单元测试夹具（`tests/helpers/`）

跨文件重复的测试装配集中在 `tests/helpers/`：`async.ts` 提供可控 Promise 与宏任务等待，`storage.ts` 提供独立内存存储与访问失败桩，`video.ts` 补齐视频条目的必填字段，`media.ts` 提供最小媒体状态。场景特有的默认值、微任务 tick 数、媒体副作用和断言保留在各测试中；精简时不以删除边界用例或改变时序换取行数。

### 真实主窗口验证

JS 浏览器夹具、独立 HTML 页面及测试媒体样本已移除。交互验证直接使用应用主窗口，接入方式见下文「桌面端实机调试」。

1. 同步源码并启动 Windows Debug 主窗口，通过 CDP 接入已有页面；从真实卡片、按钮进入目标功能，不新建标签页或用 `pushState` 跳过入口副作用。
2. 按改动检查正常、失败、快速重复操作和离页清理；播放器同时观察媒体时间、暂停状态、顶部与底部控制栏，以及控制台错误。播放页缩回动画结束时应同步移除旧页面，不能在取消动画后再延帧卸载；检查旧弹幕不闪回，并覆盖快速返回后重入及 `commitStyles()` 不可用的兼容路径。页面动效读取历史索引前必须确认 `history.state.key` 与已提交的 `location.key` 一致；POP 时浏览器会先改写 history state，未对齐时必须沿用旧索引，不能让旧播放页重播入场。断言优先使用稳定的 `data-*` 标记与可访问名称，不依赖排版类名。
   VOD 第一层返回还要覆盖同一返回按钮的 50ms 内快速连点：旧行为从 `/video/play`（`idx=2`）连退到 `/`（`idx=0`），修复后单次与连点都停在 `/video`（`idx=1`）；返回按钮按 `location.key` 核对当前历史条目，并拒绝同一条目重复提交返回。
3. 触摸或 WebView 专属问题再到 Android 验证。长按用真机手动按住；事件探针、媒体查询、视口模拟在结束后恢复。发送评论、弹幕等写操作会触达真实账号，未经明确授权不要执行。

#### 播放弹层回归

在 Windows 主窗口通过真实入口进入目标页面，直接操作并断言以下场景；不保留独立 JS 回归夹具：

- 直播播放页：临时派发媒体失败事件，检查错误弹窗持续显示时「弹幕 / 关注 / 设置」可切换；结束时清除事件探针并关闭弹窗。
- 带章节的 B 站短视频：检查评论 dock 关闭时，紧凑竖屏/横屏点击章节能展开底部/右侧抽屉，选章跳转并收起，播放/暂停状态不变；结束时清除 CDP 视口模拟。稿件须有至少两章，不伪造平台数据。

主窗口验证覆盖响应式布局与点击，不替代 Android 真机触摸验证。

### React 生命周期约束

渲染期只读取用于界面的 state/props；长期事件回调需要的最新值在 `useLayoutEffect` 同步。HUD 的 `data-visible`、`aria-hidden`、`inert` 在提交后对齐，避免显隐计时器触发整页重渲染。外部媒体、ASR、IPC 会话的同步复位及动效提交快照可保留有说明的局部 lint 豁免，不关闭全局 React 规则。原生播放、系统全屏和触摸手势仍需客户端或真机验证。

### 列表卡片与关注操作

关注列表使用 TanStack Query 的共享缓存，卡片只在缓存已有数据时显示关注态，不主动为每张卡片订阅并发起 `follow_list`。卡片操作菜单打开时预热房间详情和关注列表；点击关注后立即显示忙碌状态并拒绝重复提交。写入成功后先按主播身份合并本次提交的数据，保留列表顺序和自动录制等既有字段，再在后台与后端对齐；缓存尚未建立时不把单条记录当作完整列表。分组选择弹层仅在首次关注后挂载，退场动画结束后卸载，避免大批卡片在首屏同步创建弹层表单、查询和变更钩子。

按钮响应验证在 Windows Debug 主窗口通过 CDP 注入临时计时探针，从真实点击事件开始计时。返回操作分别记录路由变化、下一帧目标卡片的 `elementFromPoint` 命中和主线程长任务，异步按钮记录忙碌状态首次出现；网络请求完成时间单独看，不把加载动画结束时间当作点击响应时间。

2026-11-07 在 1280 × 720、完整动效的 WebView2 开发构建中实测：

| 操作 | 结果 |
| --- | --- |
| 播放页返回首页，卡片恢复点击 | 优化前 582 / 599 / 619ms，优化后 207 / 228 / 225ms；三次中位约 600 → 225ms |
| 返回时首页重挂载的主线程长任务 | 优化前 221 / 239 / 256ms，优化后 196 / 212 / 210ms；仍有进一步减少列表挂载成本的空间 |
| 卡片关注 | 优化前约 295ms 才出现分组弹层；优化后约 6ms 显示「正在处理…」，本次分组弹层约 271ms 出现 |
| 动态背景开关 | 约 4ms 更新开关状态，测试后恢复原值 |
| 推荐列表刷新 | 约 17ms 显示忙碌状态，完成后恢复可点击 |
| 播放 / 暂停 | 点击至媒体事件约 24ms |
| 静音 / 取消静音 | 点击至媒体事件约 41ms |

直播推荐实时变化，优化前后列表分别为 145 和 140 张卡片，以上是开发构建的观测值。退场尚未完成时通过真实鼠标再次点击卡片，已确认目标卡片命中、旧 HUD 不抢输入、正常重新进入且仅保留一个媒体节点；也验证了搜索返回、侧栏切换、播放设置、更多操作以及关注后取消关注。测试新增的关注已撤销。Android 长按及触摸焦点交接需在真机另行验证。

## Windows 开发（WSL 源码 + Windows 运行）

源码维护在 WSL，构建和运行在 Windows 侧的同步镜像目录（见[同步到 Windows 镜像](#同步到-windows-镜像)）。Windows 侧统一用 **PowerShell 7**（`pwsh`）：`scripts/build-windows.ps1` 与 `scripts/prepare-windows-ffmpeg.ps1` 头部都声明 `#Requires -Version 7.0`，在系统自带的 Windows PowerShell 5.1 上会直接报版本不匹配而拒绝运行。

```powershell
pwsh -File .\scripts\build-windows.ps1   # release 构建
bun run tauri dev                         # 开发运行
```

本地语音字幕的 CrispASR 运行库在应用首次启用字幕时下载并在运行时加载，构建不需要 CUDA Toolkit 或 cuDNN；调试 CUDA 推理只需要 NVIDIA 驱动。

`build-windows.ps1` 会自动调用 `vcvars64.bat` 并准备 FFmpeg 与 LLVM。手动执行 Cargo/Tauri 命令时，需要 Visual Studio 的 `x64 Native Tools` 环境（MSVC headers 与 Windows SDK），并至少设置：

```powershell
$env:LIBCLANG_PATH = "D:\dev\LLVM-22.1.8\bin"
$env:Path = "$env:LIBCLANG_PATH;$env:Path"
```

### FFmpeg 与 LLVM

`scripts/build-windows.ps1` 优先读取进程级或用户级的 `FFMPEG_DIR` 与 `LIBCLANG_PATH`，并把同时包含 `libclang.dll` 和 `clang.exe` 的 MSVC-compatible LLVM `bin` 目录加入当前构建进程的 `PATH`。把依赖放在开发盘时，可用完整 FFmpeg SDK `D:\dev\FFmpeg` 与独立 LLVM `D:\dev\LLVM-22.1.8\bin`，再设置对应环境变量。

未设置 `FFMPEG_DIR` 时，脚本才用 MSYS2 与 MinGW-w64 自建裁剪版 FFmpeg 9.0.2 shared SDK，并缓存到 `%LOCALAPPDATA%\rLive\build`；缺失的 MSYS2 工具链（`make`、`diffutils`、`mingw-w64-x86_64-gcc`、`mingw-w64-x86_64-nasm`、`mingw-w64-x86_64-pkgconf`）由脚本用 pacman 补齐。构建会校验官方 FFmpeg 源码 SHA-256，只启用录制与视频下载用到的组件，并把 `avformat`、`avcodec`、`avutil`、LGPL 2.1 许可证和构建说明放到 `rlive.exe` 同目录。

下载合并要求 MOV 解复用器与 MP4 封装器，组件白名单必须包含 `--enable-muxer=flv,mpegts,mp4`。三个桌面平台的准备脚本都检查 `CONFIG_MP4_MUXER`，且配置变化时不复用旧缓存；使用外部 `FFMPEG_DIR` 时须自行保证 SDK 与实际加载的 DLL 都支持 MP4。缺少 MP4 时，下载到 100% 仍会在创建输出文件时失败，详见[视频下载的合并失败排查](视频下载.md#六合并失败排查)。

SDK 只编译 `avformat`、`avcodec`、`avutil`，不编译 Matroska、zlib、swresample 和视频编码器；保留尺寸/音频帧解析、H.264/HEVC/AAC/AAC-LATM 参数探测与 `extract_extradata` 序列头提取。HLS 不能仅靠视频 parser 得到完整主流参数，因此探测解码器不能删；输出仍为流复制。Windows 用 `--disable-pthreads --enable-w32threads` 避免依赖开发机 PATH 中的 `libwinpthread-1.dll`。完整白名单与平台差异见[发布流程](发布流程.md#ffmpeg-自建与许可证约束)。

> [!IMPORTANT]
> 不要把 Android NDK 的 LLVM 路径用于桌面构建。桌面目标需要 MSVC-compatible LLVM；Android 使用单独的 NDK clang 配置，Linux/WSL 下执行 `bun run tauri -- android ...` 时 `scripts/tauri.ts` 会自动注入 NDK 的 bindgen、`cc-rs` 和 linker 环境。

携带上游许可证不代表应用整体分发合规已经完成。

## 桌面端实机调试

前端在真实 WebView 里运行时（而非纯浏览器 + mock），才能复现 MSE、触摸合成、IPC
与代理转发的真实行为。Windows 与 Linux 的调试通道不同。

### Windows（WebView2 + CDP + playwright）

WebView2 支持 CDP：给 dev 进程注入 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，WSL 侧即可用 playwright 接入真实主窗口。

1. **同步镜像**：`bash scripts/sync-to-windows.sh`（代码在 `D:\dev\rLive` 构建运行，改一次源码同步一次）。
2. **停掉所有 rLive 实例**：安装版与残留 dev 进程都要退出。它们共享 WebView2 数据目录 `%LOCALAPPDATA%\com.shenss.rlive\EBWebView`，**先启动的实例决定浏览器进程参数**，后来者的 `--remote-debugging-port` 被忽略。
3. **起 dev 会话**（独立脚本 `D:\dev\rlive-tauri-dev.ps1`，不放进镜像）：

   ```powershell
   $env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = "--remote-debugging-port=9223 --remote-allow-origins=*"
   Set-Location D:\dev\rLive
   bun run tauri dev 2>&1 | Tee-Object -FilePath D:\dev\rlive-tauri-dev.log
   ```

   从 WSL 起要用 `Start-Process pwsh ... -WindowStyle Hidden`，否则进程随 WSL 会话被回收。
4. **接入**（镜像网络回环直通 Windows 127.0.0.1）：

   ```bash
   curl -s http://127.0.0.1:9223/json/version    # 返回 Edg/<版本> 即就绪
   playwright-cli -s=rwin attach --cdp=http://127.0.0.1:9223
   playwright-cli -s=rwin snapshot
   ```

> [!IMPORTANT]
> 只在主窗口页面上调试：CDP 新建的标签页**不注入 Tauri IPC**（`window.__TAURI_INTERNALS__` 不存在，页面显示「未连接 rLive 客户端」），也不要关它的标签。

务实要点：

- **依赖缓存**：`target/debug` 已有同配置的依赖产物时 Rust 侧启动较快；首次全量或 profile 变化后需要重新编译。项目默认关闭增量缓存，以控制 `target` 体积。
- **端口独占**：Windows dev 会话的 vite 占 1420，而镜像网络让 WSL 与 Windows 共享 loopback，因此**它与 WSL 侧的 `bun run dev` / `tauri android dev` 互斥**，同时起会让后者的 `beforeDevCommand` 直接失败退出。
- **视口模拟必须清理**：项目 `.playwright/cli.config.json` 设置 `browser.contextOptions.viewport: null`，让 CDP 接入真实窗口而非默认固定视口；已有会话需退出后重新连接才能应用配置。`page.setViewportSize` / `Emulation.setDeviceMetricsOverride` 会把真实主窗口的网页视口锁定到测试尺寸；恢复“旧宽高”仍是固定视口，之后拖动原生窗口会出现卡片不随窗口调整的假象。响应式验证使用独立 CDP 会话，并在 `finally` 调用 `Emulation.clearDeviceMetricsOverride`，随后 detach。实机缩放回归应对比 `window.innerWidth/innerHeight` 与 Tauri `innerSize / scaleFactor`，并截屏检查，而不只修改模拟视口。
- **无 `hasTouch`**：桌面 CDP 会话拿不到触摸能力，`page.touchscreen.*` 会报 `hasTouch must be enabled`。仅检查触摸事件分支时可合成 `pointerType: "touch"` 的 PointerEvent；合成事件不经过合成器，不能替代真机手势验证。
- Rust 改动触发自动重建并重启应用，重启后重新 attach；前端改动走 Vite HMR，但**镜像不会自动同步**。
- 排查 MSE/分片/代理用 `playwright-cli requests` / `eval` 直接读真实页面状态。

### Linux（WebKitGTK）

Linux 端是 WebKitGTK，不支持 CDP，playwright 无法接入。两个替代通道：

- **右键检查**：debug 构建（`bun run tauri dev`）默认启用 devtools，在页面上
  右键即可打开 WebKit 检查器（元素、网络、控制台、媒体缓冲都有）。
- **远程检查**：需要从另一台机器看时，给进程设置
  `WEBKIT_INSPECTOR_SERVER=127.0.0.1:9223` 后启动，再用 WebKit 系浏览器
  （如 GNOME Web）打开 `http://127.0.0.1:9223` 连接检查器。

## Android 调试要点

Android 前端跑在系统 WebView，只有 **debug 构建且 ABI 匹配**的 APK 能接 CDP；release 包不创建 `webview_devtools_remote_<pid>` socket。

```bash
bun run tauri -- android build --debug --target aarch64   # 模拟器用 x86_64
adb install -r src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk

PID=$(adb shell pidof com.shenss.rlive | tr -d '\r\n ')
adb forward tcp:9222 localabstract:webview_devtools_remote_$PID
curl -s http://localhost:9222/json/version    # 核对 Android-Package 是本应用
playwright-cli -s=rand attach --cdp=http://localhost:9222
```

务实要点：

- **socket 要按本应用 pid 取**：设备上常有多个 WebView 各开一个 socket，直接从 `/proc/net/unix` 抓第一个会连到别的应用（`/json/version` 的 `Android-Package` 一看就知道）。
- **手势用真实触摸注入**：`adb shell input tap/swipe`，坐标按 `物理 = CSS × devicePixelRatio` 换算；断言用 CDP 读真实状态（`currentTime`、play/pause 计数、`data-visible`、`inert`）。
- **入口要走真实交互**：`pushState` 直接跳到目标 URL 会跳过沿途组件的副作用（如列表卡片先写播放列表 store 再导航），同一 URL 因此可能呈现不同状态，手势/状态类 bug 复现必须点进去。
- **组件栈只有 dev 构建有**：生产 React 只给 minified 错误码。`vite build --mode development` 并不产出 dev React（vendor chunk 仍是生产版），要组件栈只能 `bun run tauri -- android dev`——它与 Windows dev 会话争 1420 端口，二者不能同时开。
- 手机需开「USB 调试」并保持亮屏（熄屏时 WebView 挂起）。
- **触摸/手势最终必须真机复现**：模拟器注入没有真实手指微抖，镜像 WebView 版本也落后于真机。

完整环境配置、模拟器启动、事件探针和排错清单见 [Android 开发与构建](Android开发与构建.md)。
