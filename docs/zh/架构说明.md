# rLive 架构说明

## 1. 总体结构

顶层采用标准 Tauri 布局，按前后端拆分：

```
rLive/
├── src/          # React UI（Vite 入口与页面）
├── src-tauri/    # Tauri 2 + Rust（commands / sites / DB）
├── tests/        # 前端单元测试
├── docs/         # 中文文档
└── scripts/      # WSL 同步、Windows 桌面构建、Windows Android 真机
```

```
┌─────────────────────────────────────────────┐
│  React UI (src/)                              │
│  首页 / 关注 / 分类 / 历史 / 录制 / IPTV / 多画面 / 设置 / 房间页 │
│  xgplayer 协议插件播放 · 多会话代理 · danmu.js DOM 弹幕 · SC │
└──────────────────┬──────────────────────────┘
                   │ Tauri commands / events
┌──────────────────▼──────────────────────────┐
│  Rust (src-tauri/)                            │
│  LiveSite · stream_proxy · danmaku WS · ASR · DB │
│  RecordingManager · local playback server          │
└─────────────────────────────────────────────┘
```

| 目录 | 职责 |
|------|------|
| `src/` | 前端：页面、播放控制、弹幕适配层、设置 |
| `src-tauri/src/sites/` | 各站点 HTTP / 签名 / 房间解析 |
| `src-tauri/src/danmu_rs/` | 弹幕 WebSocket 与协议解析 |
| `src-tauri/src/stream_proxy.rs` | 本机流媒体代理、HLS 改写、线路探测与脱敏聚合遥测 |
| `src-tauri/src/dlna.rs` | DLNA 投屏：SSDP 设备发现、AVTransport 控制与带令牌的局域网流中继 |
| `src-tauri/src/iptv/` | 代理感知的 M3U 获取、大小限制、频道元数据解析与有界可用性探测 |
| `src-tauri/src/asr.rs` | sherpa-onnx Zipformer/标点/CAMPPlus 模型下载、流式会话生命周期、转写与匿名说话人聚类 |
| `src-tauri/src/recording.rs` | 桌面直播录制任务、可配置多目录存储、FFmpeg worker 调度、弹幕 sidecar、崩溃恢复与本地回放 HTTP 服务 |
| `src/features/recording/` | 录制状态查询、播放器录制控制、录制库列表与本地回放控件 |
| `src-tauri/src/db/` | SQLite：关注、历史、设置、Cookie |
| `scripts/` | WSL 同步、Windows 桌面构建、Windows Android 真机开发 |

SQLite 文件连接使用 WAL 日志和 `synchronous=NORMAL`，为单条历史写入降低同步落盘开销，并配置 5 秒锁等待、8 MiB 页缓存和检查点后的 WAL 保留上限。2.0 schema 使用 `PRAGMA user_version = 3`：空库在事务中一次性创建表、索引和清理触发器；已有版本 `1`、`2`、未知版本，或无版本但已经包含表的数据库返回 `db_schema_unsupported`，启动路径不会迁移、补列、删除或改写旧库。观看历史按 `watched_at + site_id + room_id` 建立稳定排序索引，最多保留最近 2,000 个不同直播间；弹幕发送历史分别使用站点内和全局时间索引，保持每个平台 50 条的上限。

桌面端通过 `app_paths::AppDirectories` 在任何数据库或日志打开前解析应用根目录。Windows 和 Linux 优先使用可写的可执行文件所在目录，macOS 使用 `.app` 所在的外部目录；`Program Files`、Linux `/usr/bin`、只读 AppImage mount 或其他不可写位置回退到系统应用数据目录。应用数据根目录由程序自动选择，不提供设置页迁移操作。SQLite 为 `rlive.db`，日志为 `logs/`，图片磁盘缓存为 `cache/images/`，模型为 `models/`，Windows 按需下载的字幕运行库为 `asr-runtime/`，默认本地录制 bundle 为 `recordings/`；录制目录切换记录保存在根目录的 `recording-storage-v2.json`，其中 `schema_version` 必须为 `2`。旧配置文件只记录 warning 并忽略。

远程头像、封面、分类图标和缩略图统一经 `normalizeImageUrl` 进入 localhost 图片代理，弹幕图片表情经 `danmakuImageRequestUrl` 走同一条路径（代理未就绪时回落到直连 CDN，直播层与录制回放共用），直播封面改用 `normalizeCoverUrl`，它在代理地址上附加 `nocache=1`：封面 URL 要么每次抓拍都换名（虎牙 `live-cover.msstatic.com` 把秒级时间戳写进文件名，斗鱼 `asrpic` 同理），要么 URL 固定而画面几分钟一换（Twitch `previews-ttv`），前者会用永不复用的条目挤掉真正重复的头像，后者会让用户看到冻结的预览；这类请求仍走代理注入 Referer，但只给 120 秒 WebView 缓存，不读也不写磁盘缓存。代理仍使用随机临时端口，但在响应返回后把可识别的 PNG、JPEG、GIF、WebP、AVIF 或 BMP 原始字节写入 `cache/images/<hash前2位>/<完整hash>`；缓存按 30 天 TTL 和桌面 256 MiB / Android 64 MiB 上限淘汰，命中时每天最多更新一次 mtime。淘汰同时回收进程中断在 `write` 与 `rename` 之间残留的 `.tmp-` 文件（超过 1 小时未提交），这些文件不计入设置页显示的缓存用量。目录遍历在单个阻塞任务内用 `std::fs` 完成，避免上万个文件产生同等数量的线程池任务。缓存写入是 best-effort，目录不可写不会影响图片代理。

## 2. 播放路径

1. `LiveSite::get_play_urls` 返回带 `source_id`、安全标签、显式协议、平台优先级、URL 和 headers 的结构化 `PlayUrl[]`。
2. 前端按 `site_id + room_id` 恢复最近一次手动线路选择，优先匹配 `source_id`，缺失时回退到保存的序号；没有记忆时遵循平台顺序。
3. 前端请求 `stream_proxy_start`，Rust 在 `127.0.0.1` 为当前 `sessionId` 准备独立监听器，并在就绪后只替换同一会话的旧活动代理。
4. 播放器通过本机 `stream_proxy` 访问 `http://127.0.0.1:<port>/...`，代理向上游带正确 UA/Referer；HLS 清单中的子清单、密钥与分片会在本机代理中改写到受限的 localhost 资源路径。
5. 前端统一由 `xgplayer` 管理媒体元素和播放器生命周期：直播 FLV 与裸 MPEG-TS 使用 `xgplayer-mpegts.js` / `mpegts.js` 并通过 `mediaDataSource.type` 区分容器，所有 HLS 使用 `xgplayer-hls.js` / `hls.js`，原生媒体交给 `<video>`；流媒体内核只保留这两套。
6. 房间播放器每 2 秒采样媒体与代理聚合指标，最多保留 120 条内存快照；不上传、不持久化，也不保存 URL 或 headers。

HLS 播放列表可以引用 MPEG-TS（`.ts`）分片，但这不等于裸 MPEG-TS 流。`hls.js` 先解析 m3u8 清单，再依据分片序号、时间轴、不连续标记和加密信息拉取、转封装 `.ts` 并写入 MSE。裸 `.ts` 地址没有 m3u8 清单，不能进入这套 HLS 状态机，因此 IPTV 的连续 MPEG-TS 流仍由 `xgplayer-mpegts.js` / `mpegts.js` 处理。斗鱼连续 FLV 上游关闭时，前端在 `mpegts.js` 报告 `loading_complete` 后重新获取房间详情与网页播放签名，再刷新清晰度、线路并完整重建会话。

每次播放器会话会携带唯一 session ID；`stream_proxy` 以 `sessionId` 为键并存活动监听器和启动预留，停止请求只会关闭同一会话持有的代理。因此快速离开并再次进入同一房间时，旧清理不会误关新代理，多画面的多路流也不会互相抢占监听器。房间与 IPTV 播放页复用 `src/shared/components/player/PlayerControls.tsx` 的 React 控制层，不启用浏览器 `<video controls>` 或 xgplayer 默认皮肤。控制层以透明方式叠放在画面底部，播放闲置后自动隐藏；播放、静音、画中画和全屏共享相同状态接口，房间按需追加线路、清晰度、弹幕、ASR 和侧栏。ASR 控制与相关设置仅在 Tauri 桌面端挂载；Android 原生桥管理 Activity 级亮度、系统 `STREAM_MUSIC` 音量、全屏方向和全屏期间的沉浸式系统栏，房间与 IPTV 的音量入口共享设备媒体音量。非 Android 平台仍直接写当前播放器的 `<video>` 音量。

桌面 `/multi-room` 路由由 `src/features/multi-room/` 管理 2/4/6 画面槽位、拖拽交换和独立播放会话。槽位 0 统一承担主画面的音频、弹幕、ASR 与全屏职责；容量、排列、房间、音量以及直播时钟同步方式与各路偏移由 Zustand persist 保存到设备 localStorage `rlive-multi-room-v2`，不进入 SQLite 或 profile。时钟同步在前端以每秒一次的纯函数控制环完成，FLV/TS 所需的壁钟锚点来自 `stream_proxy` 的 `first_media_at_ms`。具体布局、角色切换、全屏所有权和同步算法见[播放器技术文档](播放器技术文档.md#41-多画面播放)。

`waiting` / `stalled` 只计入内存遥测，不再触发自动换线或重载；B 站 HLS 的重复 fatal 事件仍保留 20 秒原地恢复窗口，避免短暂上游波动造成频繁重建。默认开启的「软切换」会在 HLS、MPEG-TS、FLV 同协议线路间通过 xgplayer `switchURL` 保留外层播放器与媒体元素；FLV 同时替换内部 `mpegts.js` core，协议变化、API 不可用或切换失败会回到完整重建。完整数据契约、故障转移、遥测字段、参数与性能验收见[播放器技术文档](播放器技术文档.md)。

IPTV 前端将 `/iptv` 作为仅用于发现的首页：展示响应式来源切换、分类、搜索、关注、会话级可用状态和频道列表，进入时不会创建播放器或代理会话，也不会默认播放第一个流。自定义 HTTP(S) M3U 地址只能在「设置 → 网络」保存；首页选中 `source=custom` 时从本机设置解析，地址本身不会写入路由、历史或配置包。`iptv_load_playlist` 与 `iptv_check_channels` 都从本机设置读取代理；前者重新获取当前 M3U，后者接受最多 32 个一批的去重频道请求，以 12 路并发和 7 秒单项上限读取首批媒体数据，并额外校验 HLS 清单头、空响应与 HTML 验证页。前端把当前筛选结果限制为 120 个、按 24 个一批调用并渐进合并结果；状态不进入 URL、数据库或配置包，更新/换源即清除。

IPTV 关注使用独立的 `iptv_favorites` SQLite 表，以 `source_id + channel_url` 为主键并持久化频道快照；用户归组存于独立的 `favorite_group_id`，M3U `group_name` 只保留为源元数据。自定义分组定义存于 `iptv_favorite_groups`，删除分组会在同一事务内清空频道引用。`iptv_favorite_list` 接受可选 `source_id`：播放页按源读取，关注页先读取全量缓存，再按当前 `source` 对应的稳定来源 ID 筛选；TanStack Query 会同步更新全量与按源缓存。关注页通过 `view=iptv` 与直播关注分开，频道源和当前自定义分组分别写入 `source`、`group` 查询参数。Shell 只承载关注类型一级页签，频道源 Select 与直播平台/状态 Select 都由关注页侧栏负责；桌面端在左栏顶部显示，移动端显示在分组横条上方。已配置的自定义 M3U 与内置来源由 `playlistSourcesForSettings` 共用构造。自定义分组保留在桌面左栏和移动端横向栏。关注页 Tab 在移动端由 `useHorizontalSwipe` 的双面板 track 跟手切换，点击 Tab 使用短暂淡入平移；IPTV 分组内容复用 `PagePan` 按分组顺序平移。关注列表优先使用最新列表元数据，频道不在最新 M3U 中时回退到保存的快照，因此仍可进入 `/iptv/play`。不同自定义 M3U 用地址派生的本地哈希命名空间隔离，原始 M3U 地址不进入关注表或播放路由；当前配置的自定义来源通过同一哈希读取对应关注快照。配置档案导出 IPTV 分组和内置公开源关注，自定义源关注不离开设备。点击频道才会创建播放会话；播放页返回会恢复进入播放前的 IPTV 发现页或关注页。

DLNA 投屏由 `src-tauri/src/dlna.rs` 与 `commands/dlna.rs` 实现：SSDP M-SEARCH 同时探测 MediaRenderer、根设备与 `ssdp:all`，按 LOCATION 去重后拉取设备描述 XML（正则有界提取 friendlyName 与 AVTransport controlURL），控制面通过 SOAP 调用 SetAVTransportURI/Play/Stop。由于电视端自行拉流且无法携带平台请求头、也访问不到绑定 `127.0.0.1` 的 `stream_proxy`，投屏走独立中继：绑定 `0.0.0.0` 临时端口，仅接受携带本次会话随机令牌的请求并拒绝回环目标，按投屏时登记的 headers 回源转发字节流；HLS 清单中的相对/绝对子地址与 `URI="…"` 属性都会改写为中继地址。中继地址使用 `if_addrs` 枚举的局域网私有 IPv4。设备控制复用无 Cookie 的独立 reqwest 客户端，不接触账号登录态。

## 2.1 会话所有权边界

播放路径由两个相邻但独立的会话概念组成，二者的所有权不得合并。

**播放恢复会话**从直播间详情解析当前播放源，并在清晰度切换、线路切换、播放失败、播放地址过期和稳定播放之间维护有界恢复状态。它拥有播放元数据的获取与缓存同步、用户线路记忆、重试与续签预算、过期异步结果失效，以及当前播放源的选择。

**媒体生命周期会话**从一个已解析的播放源开始，经由 `stream_proxy`、xgplayer 协议插件和 HTML media element，直到播放器销毁。它拥有 proxy session generation、xgplayer 创建与销毁、协议内恢复、自动播放、媒体状态、音量、全屏和画中画；页面舞台布局、手势仲裁和业务导航不属于它。

两者的 seam 只有一个方向：播放恢复会话选择 `PlayUrl`，媒体生命周期会话消费 `PlayUrl` 并只报告已经发生的 transport facts（开始播放、流结束、解码失败、HTTP 状态、协议错误）。重建当前媒体、续签播放地址、降低清晰度、切换线路、延迟重试或终止恢复，均由播放恢复会话根据这些事实、站点规则和剩余预算决定；transport 不跨 seam 输出带有恢复决定的字段，任何一方也不得直接修改另一方的预算或内部 generation。

每个播放器实例拥有独立的播放恢复会话和媒体生命周期状态。不同实例可以通过 TanStack Query 复用播放元数据缓存，但不共享重试与续签预算、timer、generation、当前清晰度或当前线路；一个实例的播放失败不得消耗或改写另一个实例的恢复状态。底层 `stream_proxy` 操作通过 module 内部共享的串行队列保持有序，但队列不转移实例所有权，旧 generation 的清理只能停止自己拥有的 proxy session。

用户主动切换清晰度、切换线路或手动刷新时，该 intent 的优先级高于自动恢复：播放恢复会话必须取消待执行的自动恢复 timer、递增 intent generation，并使旧 generation 的元数据结果和延迟动作失效；自动恢复不得在稍后覆盖用户的明确选择。

直播房间与 IPTV 共用同一个媒体生命周期 module。直播 adapter 把媒体事实交给播放恢复会话决定重试、换线、续签或降画质；IPTV adapter 维护频道内的有界自动重连预算。两个 adapter 可以选择不同的缓冲、软切换、临时空源保留和遥测 profile，但不得各自重新实现 proxy 或 xgplayer 生命周期。同理，各直播站点的恢复差异属于播放恢复会话的内部规则，不为每个站点建立独立恢复 adapter；只有出现第二种需要独立替换这些规则的真实 implementation 时，才为站点恢复策略建立新的 seam。

播放恢复会话的核心 implementation 不依赖 React 生命周期。React adapter 负责创建和销毁会话、订阅会话 snapshot，并转发用户 intent 与 transport facts；元数据获取和 cache 同步仍由会话拥有，但通过可替换 adapter 执行。

上述边界属于既有产品行为的约束，不隐含调整各站点重试次数、恢复延迟、线路记忆、Twitch 解码降级、播放地址续签预算、IPTV 两次自动重连及其延迟、缓冲 profile、音量会话语义或用户提示。测试通过会话 interface 覆盖完整场景，只有 storage、metadata 等 adapter 保留独立契约测试。

## 2.2 录制路径

录制与播放共用结构化 `PlayUrl`。播放器把当前 URL、协议、headers、直播身份和按次离页策略传给 `recording_start`；关注页快捷入口则通过 `followRecording.ts` 获取房间详情，按默认清晰度和线路记忆解析同一结构，再以后台任务启动，因此无需先创建播放器或进入直播间。

房间页启动录制时不复用播放器正在拉的地址，而是通过 `recordingSource.ts` 的 `fetchRecordingPlayUrl` 向站点另取一条线路：播放器始终走 Rust `stream_proxy`，录制（除 Twitch HLS 广告恢复外）直连上游，同一地址意味着两条独立连接，而按请求签名且每个签名只允许一个消费者的站点（斗鱼为已知案例）会掉第二条，录制在开始数秒后以 `Input/output error` 中断。新线路按 `source_id` 而非下标匹配当前观看线路，因为重新请求可能重排或减少 CDN；取不到时回退共享地址，录到总比录不到好。关注页快捷入口本来就是重新解析地址，因此从未出现该冲突；IPTV 播放页地址不带按请求签名，保持复用。

关注记录的 `auto_record` 是逐主播开关。挂在 `AppRuntime` 的自动录制控制器会在设置加载后立即调用 `follow_refresh_auto_record`，之后每分钟只轮询启用记录；每个直播 session 只提交一次自动开始，离线或 `live_started_at` 变化后才允许下一次，已有录制按 source key 或平台/房间身份跳过。轮询仅在桌面 Tauri 进程运行期间存在，不创建系统驻留任务。

Rust `RecordingManager` 在进程级持有最多 4 个后台 session，因此路由卸载本身不会结束任务。FLV、HLS 和 MPEG-TS 统一进入 FFmpeg worker，不再通过 `engine` 字段或 `recording_capabilities` 暴露双后端选择；原生 MP4/WebM URL 仅使用最小直连保存。HLS 输入的录制 metadata 和文件协议改写为 MPEG-TS，最终文件扩展名为 `.ts`，但传给 FFmpeg 的源协议仍为 HLS。`continue_on_leave` 默认 `true`（`CONTINUE_ON_LEAVE_DEFAULT`，后台录制恒开，仅显式传 `false` 才退出），因此离开播放页不再拦截；未指定该字段的旧请求同样按后台继续处理。manager 将运行中与正在收尾的任务分别放在 `sessions`、`finalizing`，停止中的任务继续占用身份和并发名额，删除、重复开始和重复停止不能越过收尾边界。独立 `start_gate` 串行化开始任务的检查与提交；任一步失败都会清理尚未提交的 bundle。开始流程通过 `fs2` 检查目标卷至少保留 512 MB，FFmpeg 和原生直连 worker 每 5 秒复查；低于保护线时停止读取并进入既有 trailer、同步和原子发布流程。FFmpeg worker 另有三类坏流判定，命中后均走同一收尾流程并保留已录内容：写入过首包后 30 秒内没有新媒体包（`Stalled`，`rw_timeout` 只覆盖 socket 不再吐字节，覆盖不到连接存活但无可用数据）、包落在建表时不存在的流索引上（`SourceChanged`，部分 CDN 下播后在同一 URL 推送无关节目；主动丢弃的未选 HLS 清晰度不计入）、单条输出轨连续 12 个包无法写入（`TrackUnwritable`，按轨计数，避免正常轨把坏轨的失败计数清零）。删除录制时存储根由 `find_bundle_in_root` 返回，不从 `bundle.parent()` 反推——两级结构下 parent 是房间目录，而库索引以存储根为键，反推会导致缓存条目残留、刷新后已删录制重新出现；房间下最后一次录制被删除时其空目录一并回收。每个 session 先写入独立目录的 `metadata.json`，媒体写入 `.part`，收尾成功后同步并原子改名为按「用户名_标题_开始时间」生成的最终媒体文件。

`recording_auto_split_minutes` 在 `recording_start` 时转换为不可变的 FFmpeg 分段时长；0 表示关闭，允许范围为 0–1440 分钟。FFmpeg interrupt callback 在达到截止时间后结束当前 worker，写完 trailer 并原子发布当前 bundle，再由同一个 `ActiveSessionState` 创建下一 bundle 继续读取同一播放源。活动状态同时保存当前段和全部历史段 ID，因此首段旧卡片仍能停止当前分段；切换分段时不释放后台弹幕连接，但每段拥有独立的 `danmaku.jsonl`。仅 `Flv`、`Hls`、`MpegTs` 进入此流程，`Native` 直连录制不设置分段截止时间。

`src-tauri/src/recording_ffmpeg.rs` 实现进程内 Rust FFmpeg worker。桌面目标直接依赖 `ffmpeg-next`，不提供可关闭 feature 或无 FFmpeg 录制 stub；依赖关闭 device/filter/swscale/swresample，只打开 `format`（传递 `codec`），最小直接库集合为 `libavformat`、`libavcodec` 和 `libavutil`。worker 在 `spawn_blocking` 中初始化 libavformat，使用带 interrupt callback 与 dictionary 的输入上下文；输入参数由 `build_input_options` 按源协议构造，包含源 headers、HTTP(S) proxy、探测/读超时，以及在所有协议上启用的 `fflags=+discardcorrupt`（损坏包直接丢弃，不进入 muxer）。libavformat 的 HTTP 重连参数（`reconnect`、`reconnect_streamed`、`reconnect_on_network_error`、`reconnect_on_http_error`、`reconnect_delay_max`）**仅对 HLS 启用**：分段协议重连后从分片边界续读是安全的，而 FLV、MPEG-TS 是连续字节流，重连只在字节层续接、不认容器边界，会把新响应的 FLV 头与 `onMetaData` 写进未完成的 H.264 slice，产出容器完好但解码失败的文件。连续流断开时任务直接结束，由 manager 将后续内容录入新会话；FLV 断流续录方案见[未来路线图](未来路线图.md) R2.3。`recording_start` 在短 DB 锁内读取并归一化 FFmpeg 设置，将读写超时、最大重连延迟和 HLS 分片重试次数作为不可变任务快照传入 worker，运行中的任务不受后续设置修改影响；其中最大重连延迟与分片重试次数只影响 HLS。FLV/MPEG-TS 复制所有音视频轨；HLS master 只选择最佳视频及同 program 音频，并把其他 stream/program 标记为 `AVDISCARD_ALL`，避免持续下载未使用清晰度。packet 先通过共享微秒 epoch 归一起始 DTS；重连时钟回退时，新 epoch 接到已写边界，仍在途的其他轨旧尾包继续使用旧 offset，PTS/DTS 同步平移以保留 B-frame composition delay；缺失、超界或异常跳变的 PTS/DTS 改写为单调合成时间轴，恢复正常包时重新锚定，连续少量写入异常则跳过该包。随后再按输入/输出 time base 重标并 `write_interleaved`。停止信号打断阻塞读取，写完 trailer 后才发布最终文件。该路径不解码、不编码、不转码。

HLS 清单轮询、variant 选择、分片、AES-128 key、`EXT-X-MAP` 和 `#EXT-X-BYTERANGE` 全部交给 libavformat，不再维护第二套 Rust playlist parser 或本地分片归档器。新录制只发布一个 `.ts`，通用 metadata 事务写入仍以 `.tmp` / `.bak` 和进程级互斥保护。回放服务只接受当前 metadata v2 能定位的媒体；旧版本 `.m3u8` bundle 不进入索引或回放路径。本地 HTTP 回放服务按 URL 路径段编码媒体文件名，并在文件边界检查前逐段解码，因此中文或空格文件名可回放且不能借编码路径跨出录制 bundle。

Twitch HLS 在进入 FFmpeg 前使用录制 manager 独立持有的 `StreamProxy` session。代理只负责受限 URL 映射和动态清单入口：短时 token 过期、401/403、广告临时文本/拼接清单或异常 `#EXT-X-ENDLIST` 时，按目标清晰度（必要时最接近档位）重新签名并更新当前 child playlist；分片解析与媒体写入仍全部由 FFmpeg 完成。代理生命周期与录制任务一致，不依赖页面播放器的 proxy session，任务结束后按 recording id 精确销毁。

`StreamProxy::start` 只绑定 loopback 监听器，本身不请求 `/live`，因此录制在交给 FFmpeg 之前必须调用 `wait_for_playable_manifest` 预热：网页播放器会持续重载清单直到出现媒体，而 libavformat 只调用一次 `avformat_open_input`，如果这唯一一次拿到的是恢复路径的占位清单（全部分片带 `#EXT-X-GAP`，广告期、token 失效或上游失败时产生），探测读不到任何媒体，整个录制在写入第一个字节前就以 `Invalid data found when processing input` 失败且不留媒体文件。预热按 1 秒间隔轮询本地 `/live`，判定依据是 `#EXTINF` 与 `#EXT-X-GAP` 的配对关系而非清单是否合法，最长等待 `TWITCH_RECORDING_WARMUP_BUDGET`（20 秒）；超时报「直播清单暂时没有可录制的分片」，期间收到停止信号立即以中断结束。恢复路径回退到占位清单和恢复预算耗尽都记为 `warn`，因为发布日志固定 `rlive_lib=warn`，`debug` 会让这条失败链路没有任何痕迹；日志不记录清单 URL，Twitch 播放列表 URL 携带签名 token。

代理改写出的本机分片地址必须带扩展名。`rewrite_hls_manifest` 把子清单、AES-128 key、`EXT-X-MAP` 和媒体分片映射到 `/hls/{id}`，`hls_path_extension` 会把上游路径的扩展名（仅接受 5 字符以内的 ASCII 字母数字）补回本机地址，得到 `/hls/{id}.mp4`；`resolve_upstream_target` 解析时先去掉后缀，因此带扩展名与旧的裸形式都能还原同一注册项。扩展名只从 path 读取，Twitch 分片地址形如 `.mp4?dna=<token>`，签名 token 不得进入本机路径。原因是 FFmpeg 8 起 HLS demuxer 默认开启 `extension_picky`，扩展名不在 `allowed_segment_extensions` 内的分片会被直接拒绝，`avformat_open_input` 以 `Invalid data found when processing input` 失败，录制同样一个字节都不写；浏览器 MSE 播放器不看扩展名，所以播放正常、只有录制失败。

由此带来的验证要求：Linux 开发机的 FFmpeg 6.1.1 根本没有 `extension_picky` 选项，而 Windows 应用链接 `scripts/prepare-windows-ffmpeg.ps1` 固定的 FFmpeg 9.0.1（`avformat-63.dll`）。Rust 测试在 Linux 全绿并不足以证明桌面版录制可用，涉及 HLS 输入或 demuxer 选项的改动需要用 `/mnt/d/dev/FFmpeg/bin/ffprobe.exe`、`ffmpeg.exe` 对本机代理端点复核一次。

读取失败的归类先看中断条件，再看 demuxer 错误。录制 worker 通过传给 `input_with_interrupt_and_dictionary` 的中断回调打断 libavformat，回调只报告两件事：用户取消和到达自动分割时限。一旦回调已经生效，`packet.read` 返回的错误描述的是被打断的 I/O，与直播流本身无关——HLS demuxer 会把被打断的分片请求报成 `AVERROR_EOF` 而不是 `AVERROR_EXIT`。`classify_read_failure` 因此先判断 `cancelled` 与 `split_due`，再匹配错误：只有在没有中断的情况下 `Error::Eof` 才意味着「直播流已结束」。此前只在 `Error::Exit` 分支里查询取消标志，用户点「终止录制」后完整的录制会被记成 `interrupted` 并附带「直播流已结束」，媒体文件却是完好的。该归类由 `classify_read_failure` 的单元测试固定；`recording.rs` 中停止 HLS 录制的集成测试只覆盖端到端契约，被打断的读取具体返回错误还是最后一个缓冲包由 libavformat 决定，本地小分片场景下它会 flush，循环因此在自己的取消检查处结束。

HLS 的探测预算与连续流不同：`probesize=8000000`、`analyzeduration=10000000`、`fpsprobesize=10`、`max_probe_packets=512`。Twitch 是 fMP4，单个媒体分片约 2 MB，连续流那档 32 KB 探测往往在 `#EXT-X-MAP` 初始化分片内就结束，导致清单能打开但流信息不完整。FLV、MPEG-TS 保留 `probesize=32768`、`analyzeduration=1000000`，其编解码信息在首个 tag 即可确定，小预算能让启动更快并留在 manager 的 15 秒优雅停止窗口内。

录制元数据不进入 SQLite，而是与媒体组成可复制的自包含目录。bundle 采用两级结构 `recordings/<platform>_<roomid>/<username>_<starttime>/`：外层按房间聚合，直播使用「`site_id_room_id`」，IPTV 缺少房间号时从 `source_key` 末段取频道标识；内层是单次录制会话，使用主播名加本地开始时间，时间戳格式与媒体文件名一致。bundle ID 就是该 bundle 相对录制根目录的两级路径（如 `douyu_6979222/玩机器丶Machine_20260820-192158`），因此同一房间的多次录制天然归入同一外层目录，仅在同秒冲突时给内层追加序号。外层目录用 `create_dir_all` 保证存在，内层通过原子 `create_dir` 占用，命名冲突检查覆盖当前及全部历史录制根目录，防止索引 ID 碰撞；路径组件会过滤 Windows 非法字符、限制 UTF-8 字节长度，并要求存在非空的平台与房间标识。`is_safe_recording_id` 是防止跨出录制根目录的唯一关口：只接受恰好两级普通目录名，拒绝 `..`、绝对路径、空或点目录、反斜杠以及多余分隔符。本地回放服务按两个 URL 路径段传递 bundle ID，逐段解码后重新拼回再做安全校验。2.2 之前的单层 bundle（`recordings/<platform>_<roomid>/` 直接放媒体）不再被扫描识别，磁盘文件保持原样但不出现在录制库中。应用退出时先禁止新任务并向所有运行中 session 广播取消，在共享的 15 秒期限内等待媒体 trailer、弹幕关闭和最终 metadata。manager 持有的超时任务会 hard abort，但不在同一进程继续改写 bundle；因此保留 `recording` metadata 和临时文件，由下次启动统一恢复并标记 `interrupted`。正常最终化与异常抢救由 session 级互斥保证只执行一次，metadata 写入失败会显式转为 `failed`。最终化和启动恢复会使用 libavformat 探测已发布媒体的实际时长，并逐行解析 `danmaku.jsonl` 重建弹幕数量；有效批次后的截断末行不会让整条 sidecar 失效。

manager 启动时扫描当前目录及已知历史目录，只接受带 `schema_version: 2` 且字段完整、无未知字段的 metadata；旧版本、缺字段、未知字段、损坏 metadata 或无法读取的 bundle 只记录 warning 并跳过，不自动删除。对当前版本录制事务留下的有效 `.bak` / `.tmp` 和 `.part` 仍执行启动恢复，将仍处于 `recording` 的 metadata 标记为 `interrupted`，随后按根目录建立内存 `RecordingLibraryIndex`。索引保存 `StoredRecording` 快照和根目录修改时间；`recording_list` 通常只读取索引及最多 4 个活动 session 快照，根目录成员变化时才重新解析该目录的 metadata。开始、最终化、删除和切换新目录都会增量维护索引；切换新目录时会在无活动录制的前提下将当前版本 bundle 整体迁移，并通过可恢复配置提交结果。索引不是持久化事实源，丢失后仍从当前版本自包含 bundle 重建。`recording_list`、`recording_start`、`recording_stop`、`recording_delete`、`recording_playback_url`、`recording_danmaku_url`、`recording_danmaku_export_ass`、`recording_storage_info` 和 `recording_set_storage_path` 构成录制 IPC 边界。

`recording_start` 要求完整的 `RecordingStartInput`：`include_danmaku` 决定是否写入弹幕轨，`continue_on_leave` 记录本次任务是否允许无提示离页，未指定时固定为 `true`（后台录制不再有全局设置，`recording_continue_after_leave` 只被读取后丢弃）。窗口 `CloseRequested` 始终先 `prevent_close`；`recording.active_count() > 0` 时改为发出 `app-exit-requested` 事件交给前端确认，由 `app_confirm_exit` 完成 `stop_all_graceful` 后退出，没有活动任务或事件发送失败时按原路径直接停止服务并退出。`danmu_rs::dispatch_batches` 以 `live:{site_id}:{room_id}` 作为 source key，将已批处理的事件以 `{ offset_ms, events }` JSONL 行写入 bundle 内的 `danmaku.jsonl`；事件中的后端 `user_id` 通过模型的 `serde(skip)` 保持本机私有。同时启用弹幕和后台录制时，路由 cleanup 将前台连接按 source key 转入 `background_tasks`；批次保留旧 generation，前端会忽略但 sidecar 继续接收。新房间连接、旧 cleanup 乱序、录制收尾和重进同房间都在 manager 锁与二次状态检查下处理，避免串写、重复连接或遗留任务；最后一个对应录制结束后自动 abort 后台连接。媒体复制不做转码，弹幕也不会烧录进视频。

`/recordings` 一级页只负责用户分组和录播 Card 列表：范围 Tab 写入 `view` 查询参数（`all` / `recording` / `recorded`），平台筛选写入 `platform` 查询参数，左侧用户分组通过 `site_id + user_name` 聚合，右侧显示当前用户的录播，页面不创建播放器或请求媒体 URL。页面自身没有 header：Tab 和「保存位置」按钮由 `Shell` 顶栏渲染，页面通过 `useRecordingHeaderState` 发布当前范围、各范围数量和动作，与 `/history` 共用同一套「页面持有状态、Shell 持有控件」模式。当前版本录制 metadata 分别保存 `LiveRoomDetail.cover` 与 `LiveRoomDetail.user_avatar`，右侧 Card 使用直播间封面，左侧用户图标和二级页主播信息使用主播头像；IPTV 继续保存频道 Logo。已保存 Card 进入 `/recordings/play/:roomDir/:sessionDir` 二级播放页，并在返回时恢复平台与用户筛选。播放路由为 bundle ID 的两级各分配一个路径段，由 `recordingPlaybackPath` 与 `recordingIdFromPlaybackParams` 成对构造和还原；把整个 ID 当作单段 `encodeURIComponent` 会产生 `%2F`，react-router 只做半解码，还原出的 ID 匹配不到任何录制。该路由由 `Shell` 作为沉浸式播放器页面承载，使用直播页同款顶栏和“左播放器、右信息栏”结构；`RecordingPlayer` 再将本地 loopback URL 交给与直播播放路径相同的 `xgplayer` 核心和协议插件，并复用 `PlayerControls` 的悬浮控制层。录制功能只追加媒体时间轴、倍速选项和回放弹幕设置，不维护另一套传输控件。新 FLV 录制通过 FFmpeg `flvflags=add_keyframe_index` 写入时间到字节位置索引；2.0 不读取旧录制 bundle，也不为旧 FLV 补索引或修复 metadata/index。播放器直接调用 `mpegts.js` 协议内核 seek，使未缓冲的大跨度跳转立即发起 HTTP Range 请求；失败重建窗口缩短为 4 秒。当前版本录制目录切换失败时保留原 bundle，并继续使用当前目录。`recording_danmaku_url` 只返回已结束录制的 sidecar loopback URL；`RecordedDanmakuCanvas` 按 `video.currentTime` 选择当前可见窗口并绘制，跳转后不会补放旧队列或提前聚合未来消息。行分配由 `recordedDanmakuLayout.ts` 在舞台尺寸或弹幕设置变化时整段预计算：媒体时间可以双向跳转，因此轨道只能取自与当前位置无关的数据，逐帧取模分配行号会让密集弹幕在同一行首尾相撞。该模块复用 `recording_ass.rs` 的占位规则（每行记录 `freeFrom` / `leftAt`、安全间距、延迟上限 5 秒后丢弃），使应用内回放与 ASS 导出得到同一套不重叠布局；合并组按其能达到的最大 `×N` 预留宽度，可见计数仍只统计已发生的成员。Canvas 从 `useSettingsStore` 读取直播间同一组弹幕区域、透明度、字号、描边、速度、合并窗口、礼物过滤、醒目留言与屏蔽词设置，渲染层仍与直播使用的 danmu.js 实时适配层分离。协议图片表情由 `recordedDanmakuSpans.ts` 接入：直播飘屏把 `DanmakuEvent.spans` 渲染成 DOM `<img>`，Canvas 无法复用该路径，因此该模块把同一批经校验的 span 切成可测量的文本/图片分段，让行占位按真实宽度（图片按 `1.35 × 字号`）预留，并用带上限的 `HTMLImageElement` 缓存按 URL 只请求一次；请求前设置 `referrerPolicy = "no-referrer"`（B 站 CDN 拒绝 `tauri://…` Referer），加载完成后在暂停状态触发一次重绘。未到达的表情保留占位不移动后续分段，失败则回退为 `[表情]`，与 DOM 层一致；SC 前缀逻辑统一由 `content.ts` 的 `floatingRichSpans` 提供，两个渲染器不再各写一份。

`recording_danmaku_export_ass` 把已结束录制的 `danmaku.jsonl` 转换为 ASS 滚动字幕，写入同一 bundle 并复用媒体主名（`stream.flv` → `stream.ass`），使外部播放器按同名规则自动加载。转换在 `src-tauri/src/recording_ass.rs` 内完成：命令先在 db 锁内快照独立的 `AppSettings.recording_ass` 构建 `AssExportOptions`，正则只编译一次，再在 `spawn_blocking` 中流式读取 sidecar 并写入临时文件，成功后原子发布；过滤与布局不会因播放页弹幕设置变化而漂移。配置覆盖目标分辨率、字体、字号、透明度、描边、阴影、粗体、滚动通过时间、显示区域、溢出策略、内容合并、礼物/醒目留言和屏蔽规则。滚动排版参考 DanmakuFactory（MIT）：每行记录「上一条尾部让出安全间距」和「上一条离屏」两个时刻，两者都不冲突才占用该行。安全间距为 `0.1 × 字号`（最多画面宽度的一半），宽度估算叠加 1.02 安全系数并计入描边/阴影扩张，避免低估宽度造成同行追尾；两者取偏紧凑的下限，只消除首尾相接而不额外拉开间距，因此在不重叠的前提下保留更多弹幕。所有行都冲突时按 `overflow_policy` 分流：`overlap` 回退到最早空出的行并保留全部弹幕（2.4 及之前的行为），`drop` 丢弃，默认的 `delay` 在 `max_delay_seconds` 内把弹幕推迟到最早可用时刻、超限才丢弃；延迟会改变起始时间，因此布局完成后再按起始时间稳定重排写出，ASS 事件仍然递增。返回值只计实际写出的条数，因此全部被丢弃时依旧返回 `recording_danmaku_empty`。内容合并以锚条时间为固定窗口，避免周期性刷屏沿滑动链把计数累加到早已离屏的弹幕上。弹幕正文经转义后写入，`{}`、裸 `\n`/`\N`/`\h` 与控制字符都不会成为 libass 覆盖指令；颜色只接受 `#RGB`/`#RRGGBB`，其余回退为白色。按设置过滤后为空时返回 `recording_danmaku_empty`，临时文件会清理且不会覆盖已有字幕。

**斗鱼签名注意：** 通过 `quickjs-rusty` 在本机执行 CryptoJS 与房间混淆脚本。QuickJS 原生提供 `escape` / `unescape` / `String.prototype.substr`，仅保留 `global`、`window`、`self` 和空 `console` 的浏览器对象别名；签名函数通过类型化参数调用，不拼接 JavaScript 源码。

**虎牙注意：** 解析 HTML 中的 JSON 时必须按 UTF-8 字符边界处理，避免中文页 panic。

**抖音注意：** `DouyinSite` 从账号库注入用户 Cookie；匿名 `ttwid` 引导结果在进程内缓存（30 分钟 TTL，仅存首页响应新增的匿名 Cookie），站点实例按命令创建时直接复用，避免每个列表请求重新下载约 1 MB 的直播首页，已保存的登录值始终优先于缓存值。首页推荐优先调用网页端 feed 接口 `webcast/feed/`（无需验签，每页并发拉取两批轮换房间合并去重，由前端跨页去重，刷新只重取第一页），feed 不可用时回退到分区接口；分区列表调用网页端分页接口 `webcast/web/partition/detail/room/v2/`，其浏览器验签参数 `a_bogus` 由 `sites/douyin/a_bogus.rs` 在本机以纯 Rust（SM3 + RC4）计算，不需要 JS 运行时；每页 15 条、`offset` 按页递增，因此「加载更多」真实可用。分类树的 `id,type` 会拆成 `partition` 与 `partition_type`（均须为数字），「全部 X」条目 id 为 `0` 时回退到父分区。上游不下发 `has_more`，只有满页且 `offset` 前进时才继续翻页，避免重复拉取。首页首屏若验签失败会回退到 `hot_live` SSR。短房间号优先从 SSR 房间页取得内部 `id_str`，再调用不携带 `.douyin.com` Cookie 或 `msToken` 的公开 reflow 接口取得播放数据，避免受浏览器验签保护的网页进房接口导致 `code=101`。播放 URL 只保存在房间 `raw` 的临时数据中。搜索调用官方网页直播搜索接口，需要完整登录 Cookie，用户可扫码或手动保存；二维码和搜索仍可能遇到网页访问验证，应用不会自动绕过。实时弹幕由 `danmu_rs/douyin_sign.rs` 在本机用 QuickJS 执行 `webmssdk` 计算短时签名，`danmu_rs/douyin.rs` 组装 WSS 查询串并直连；Cookie 头使用保存 Cookie 加本次临时 `ttwid` / `msToken`，临时值不序列化、不持久化。

**Twitch 注意：** `TwitchSite` 通过公开 GraphQL 获取直播列表、房间详情和 HLS 播放 token。推荐与分类不使用 Relay `after:` cursor：Twitch 会对所有游标请求执行浏览器完整性校验，没有同会话挑战上下文时返回 `IntegrityCheckFailed`，所以适配器改为沿 `broadcasterLanguages` 翻页。页 1 从不限语言的全局热门分片开始，随后按固定顺序遍历 26 个语言代码；每页并发请求 3 个分片，后端与前端分别按 login 和 `site_id + room_id` 去重。页码直接映射到分片窗口，不维护 cursor 状态；即使冷门分类的一个窗口为空，只要后面仍有分片，`has_more` 就继续为真。该路径仅需公开网页 `Client-ID`，不创建隐藏 WebView，不获取或转存完整性令牌，桌面与 Android / iOS 行为一致。搜索的 `CHANNEL` target 使用可算术生成的 offset cursor，不受这项完整性限制。Twitch 的公开网页 GraphQL 与语言枚举仍可能变化，详见 [Twitch 平台 API 文档](Twitch平台API文档.md)。

斗鱼发送由 `danmu_rs/douyu.rs` 处理：它重验共用的 `danmaku_send_enabled`、房间、文本和 3 秒本机冷却，并使用用户本机保存的完整会话字段。2026-07-27 的受控诊断发现旧路径采用过期 `loginreq` / 聊天载荷、跳过网页登录后协商并忽略 `chatres` / `error`；当前实现已替换为网页对齐的认证状态机、稳定设备身份、统一 WSS 代理与平台回包解析，并已在个人直播间成功验证。运行时仍将本地提交、`chatres(res=0)` 平台接收与正常收弹幕连接的真实回显分开处理；详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。虎牙发送由 `danmu_rs/huya.rs` 处理：同样先重验共用授权，需要扫码或手动保存含数字账号 ID（`yyuid` 或 `udb_uid`）及登录凭据（`udb_n` / `udb_cred` / `udb_biztoken`）的本机 Cookie，解析房间元数据后校验单条、单行且最多 30 个 UTF-16 单元的文本再写入。扫码实现见 `account/huya_qr.rs`。所有发送路径均不得记录、导出或上传 Cookie，也不得对不确定写入自动重试。

`RoomPage` 持有 B 站 / 斗鱼 / 虎牙的房间会话级自动发送调度器，并把同一控制器提供给标题栏、全屏更多操作和移动端房间操作抽屉，因此它不依赖右侧「设置」标签的挂载状态。它完全在前端复用既有的平台单条发送 command 与校验/状态检查，不新增 Tauri command、数据库字段、`AppSettings` 字段或配置导入导出数据。开关、文本和发送间隔只存于会话内；间隔默认 20 秒，可在 10–3600 秒间调整。只有共用本机授权、当前平台 Cookie/可发送状态和文本校验都有效时才能开启。开启时立即发送首段，将换行和连续空白压缩为一个空格，再按 grapheme 拆成最多 20 个用户可见字符且满足平台 UTF-16 上限的片段；单个超出上限的 grapheme 为校验错误。请求串行不重叠，后续发送起始至少相隔当前会话设置的发送间隔，修改间隔会重排下一次发送，末段后回到首段循环。编辑文本、切房（同时清空会话文本）、离开/卸载播放器、关闭应用或任一发送失败都会立即停止本会话并展示原因；失败或未知写入不会自动重试。

标题栏右侧、移动端「更多房间操作」和全屏「更多操作」中的「定时关闭」由 `RoomPage` 持有房间会话级 `useSleepTimer`，各入口共享同一绝对截止时间。它不写入 SQLite、`AppSettings` 或配置导入导出；菜单关闭后仍保留计时。截止时间到达后，Tauri 客户端调用当前窗口的 `close()` 退出应用；浏览器预览没有原生窗口时仅提示不可用。离开当前房间会清理未完成的定时器，避免旧房间的截止时间影响新会话。

前端不会从本机 command 返回值合成弹幕。右侧列表与画面飘屏只应在房间连接收到平台真实 `DanmakuEvent` 回显后显示消息，并保留平台原有样式；一次本机写入结果不是平台确认。斗鱼会区分本地提交、`chatres` 平台接收与真实回显，三者仍不可混为一谈。

## 5. 本地语音字幕

本地语音字幕仅在 Tauri 桌面客户端启用。`supportsLocalAsr` 同时校验 Tauri runtime 与 `desktop` 平台；Android 和 iOS 不查询或准备模型、不采集 PCM，并隐藏系统设置、房间设置和播放器入口。

前端 `AudioCapturePipeline` 从播放器 `HTMLVideoElement` 创建共享 `MediaElementAudioSourceNode`，优先加载独立 `AudioWorkletProcessor`。Worklet 在 Web Audio 渲染线程保持原声直通、将声道混合为单声道，并按设置中的 `0.2–1.0 秒`更新间隔（默认 `0.2 秒`）生成无重叠分块；主线程只接收可转移的完整 `Float32Array`，再降采样为 16 kHz 单声道 f32 PCM。旧 WebView 不支持 worklet 或模块加载失败时回退到 `ScriptProcessorNode`。little-endian 原始字节经 Base64/Tauri IPC 传输。`useAsrCaptions` 串行调用 `asr_transcribe`，一个任务执行时只覆盖保存最新待办分块，慢设备不会积累无界队列。endpoint final 与当前 partial 分行显示，父容器使用 `white-space: pre-line` 和自然断词，最多保留两行。

字幕翻译只接收 endpoint final，不发送实时 partial、PCM、热词或声纹。`useCaptionTranslation` 使用独立的 4 项有界队列和 12 秒过期时间，不阻塞 ASR；同一 final 批次中的 segment 通过 `google-translate-api-x` 合并为一次 `batchexecute` 请求，重复 `(from, to, text)` 结果进入 160 项 LRU 缓存，单次请求 8 秒超时。原文和译文语言均允许 `auto`。切房、换源、关闭字幕或修改语言会递增 epoch 并丢弃迟到结果。请求经 Tauri HTTP 发出并继承应用代理，capability 只允许 `https://translate.google.com/**`。Google 返回 `429` 时停止当前翻译队列且不自动重试，原字幕继续显示。

Rust `AsrManager` 在用户明确启用后才下载固定的中英双语 Zipformer 压缩包（`511,274,346` 字节）；自动标点开启时再下载 CT-Transformer 中英标点 int8 压缩包（`64,717,756` 字节），说话人开关启用后按需下载 CAMPPlus 中英声纹 ONNX（`28,281,164` 字节）。Windows Release 还会先下载 `221,905,418` 字节的官方 shared runtime，校验固定 SHA-256 后解压到用户数据目录的 `asr-runtime/`；EXE 本身只保留 delay-load 导入，不携带 ASR DLL。模型默认总量约 `550 MiB`，关闭标点时约 `488 MiB`，开启说话人时约 `576 MiB`。下载写入 `.part` 文件并校验精确长度，bzip2/tar 解压在 blocking 线程池执行；状态依次经过 `downloading`、`extracting`、`loading`、`ready`。前端显式处理 `extracting`，因此首次解压不会因状态分支缺失导致页面黑屏。

`NativeAsrSession` 持有一个 `OnlineRecognizer`、一个跨 IPC 分块复用的 `OnlineStream` 和可选的 `OfflinePunctuation`。Windows x86_64 的 `asr_provider` 支持 `auto`、`cuda`、`cpu`；自动模式通过 CUDA Driver API 读取设备 0 的 Compute Capability，要求官方预编译 runtime 支持的 6.1 及以上，并检查 CUDA/cuDNN 依赖和随应用提供的 provider 文件；不可用时回退 CPU，并将实际 provider 与原因返回前端。Linux 和 macOS 始终使用 CPU provider，Linux 构建固定链接 CPU-only shared runtime，不包含或探测 CUDA provider。Windows CUDA provider 会传递给 Zipformer、标点和声纹模型；VAD 开关控制识别器的 CPU 静音端点规则，当前没有独立 VAD ONNX 会话。无热词时 Zipformer 使用 `greedy_search`，有热词时使用 `modified_beam_search` 并读取原子替换的本地 hotwords 文件；关闭时仍保留 20 秒最长语句边界。标点关闭时不创建标点 native 对象。可选 `NativeSpeakerSession` 对每句 final 的缓存 PCM 提取 CAMPPlus embedding，以 `0.55` 余弦阈值和 `0.68` 切换滞回维护最多 8 个匿名说话人；少于 `0.6 秒` 的短句沿用最近标签，只有 final 携带匿名 `speaker_id`。切房、切换媒体源或关闭字幕会重置 stream、PCM 和聚类编号。CPU provider 下识别最多使用 8 个线程，标点与声纹模型最多使用 2 个线程；同一 native 会话由互斥锁串行驱动。

`asr_enabled`、`asr_vad_enabled`、`asr_punctuation_enabled`、`asr_speaker_diarization_enabled`、`asr_hotwords`、`asr_window_seconds` 和 `asr_translation_*` 是设备本地设置，不随配置包导入导出；`asr_font_size` 是可移植的显示设置。模型文件、hotwords、PCM、embedding、聚类质心与字幕均不进入 SQLite。完整说明见[本地语音字幕](本地语音字幕.md)。

- 运行：Windows `scripts/windows-sync.conf` 中 `WINDOWS_SYNC_PATH` 指定目录 → `rlive.exe`
- 一键开发：`./scripts/build-windows-from-wsl.sh`

Windows 构建脚本使用 MSVC + sherpa-onnx shared import library，并把 `sherpa-onnx-c-api.dll` 配置为 delay-load。构建阶段仍会暂存 CUDA-capable ASR runtime 以供链接，但发布工作流不把这些 ASR DLL 放入 NSIS/MSI，首次启用字幕时由应用下载、校验并加载运行库。这一点不能只靠 `bundle.resources` 白名单：NSIS 只安装白名单，而 Tauri 的 WiX 打包会把 EXE 同目录下所有 `*.dll` 一并写入 MSI（上游 `tauri-bundler` 对此留有 TODO），因此发布工作流在打包前把 FFmpeg 与 `WebView2Loader` 之外的 DLL 移出 release 目录，打包结束后（含失败路径）再移回。FFmpeg 不使用这一延迟下载机制：`scripts/prepare-windows-ffmpeg.ps1` 下载固定为 FFmpeg 9.0.1 且校验 SHA-256 的官方源码（与 macOS、Linux 同一份），用 runner 自带的 MSYS2 与 MinGW-w64 按需自建裁剪版 shared SDK，只启用录制用到的 demuxer、muxer 与 protocol，TLS 走系统原生 schannel，构建后断言 12 个 `CONFIG_*` 组件为 1、五个许可证宏为 0，并把 import library 从 `bin` 归位到 `lib`；随后设置 `FFMPEG_DIR`、`LIBCLANG_PATH`，并把同一套 MSVC-compatible LLVM `bin` 目录加入 `PATH` 供 `cc-rs` 找到 `clang.exe`。裁剪后 DLL 总体积约 2.3 MB，此前的 Gyan `full_build-shared` 为 116 MB。桌面目标不能使用 Android NDK 的 LLVM；`scripts/build-windows.ps1` 与 `scripts/build-windows-from-wsl.sh` 会先加载 MSVC headers 和 Windows SDK。`avformat`、`avcodec`、`avutil`、LGPL 2.1 许可证与自建构建说明会放在 EXE 同目录，NSIS 和 MSI 都必须携带这些文件；`swresample` 已随裁剪一并禁用，import graph 只有 avformat→avcodec→avutil。Linux x86_64 固定使用 `sherpa-onnx-v1.13.4-linux-x64-shared-lib.tar.bz2` CPU-only shared runtime，DEB 和 RPM 把运行库安装到 `/usr/lib/rLive`，不包含或探测 CUDA provider；AppImage 由 linuxdeploy 重写 RUNPATH 并把运行库收集到 `usr/lib`，发布工作流据此删除 `usr/lib/rLive` 中无人引用的 `libsherpa-onnx-cxx-api.so`（见[发布流程](发布流程.md)「AppImage 精简未引用的运行库」）。macOS（Apple Silicon 与 Intel）使用静态链接的 sherpa-onnx（CPU 推理），ASR 运行库直接编入二进制，发布 DMG 无需运行时下载运行库，也不做 Apple 签名与公证。Android 通过 Tauri CLI 使用 NDK 工具链；Rust target 通过条件编译排除 ASR module、commands、state 及 `sherpa-onnx`、ONNX Runtime 和模型解压依赖，移动端不暴露字幕功能，也不会下载字幕模型。命令与依赖见[Android 开发与构建](Android开发-Windows.md)。

Windows、Linux 和 macOS 桌面目标固定引入 `ffmpeg-next = 9.0.0`，签名脚本引擎 `quickjs-rusty` 也需要 clang/libclang 供 bindgen 生成 FFI。构建环境需要 ABI 匹配的 headers、link libraries、`pkg-config` / `FFMPEG_DIR` 和 libclang；Android 构建使用 NDK clang，Linux/WSL 下的 `scripts/tauri.mjs` 会在非 `cargo-ndk` 的 Tauri 流程中自动注入 bindgen 的 NDK sysroot、`cc-rs` 编译器与 Cargo linker。运行环境必须装载与构建时匹配的 `libav*` 及传递依赖。缺失动态库会在进程装载阶段失败，不能通过 IPC 回退。Windows 使用自建的裁剪版 LGPL 2.1 shared SDK，并将三个运行库与许可说明纳入 NSIS/MSI 两种交付物；Linux 与 macOS 由 `scripts/prepare-linux-ffmpeg.sh`、`scripts/prepare-macos-ffmpeg.sh` 构建同一套组件的静态库，以 `--features ffmpeg-static` 链接进二进制，运行环境不再需要系统 `libav*`。

Release：`lto = "thin"`、`panic = "abort"`，故后端 panic 会导致进程退出，站点解析必须避免未处理 panic。
