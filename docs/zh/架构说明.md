# rLive 架构说明

## 1. 总体结构

顶层采用标准 Tauri 布局，按前后端拆分：

```
rLive/
├── src/          # React UI（Vite 入口与页面）
├── src-tauri/    # Tauri 2 + Rust（commands / sites / DB）
├── tests/        # 前端单元测试
├── docs/         # 中文文档
└── scripts/      # WSL 同步、Windows 桌面构建、Windows Android 真机
```

```
┌─────────────────────────────────────────────┐
│  React UI (src/)                              │
│  首页 / 关注 / 分类 / 历史 / IPTV / 设置 / 房间页 │
│  xgplayer 协议插件播放 · Canvas 弹幕 · SC 叠加层 │
└──────────────────┬──────────────────────────┘
                   │ Tauri commands / events
┌──────────────────▼──────────────────────────┐
│  Rust (src-tauri/)                            │
│  LiveSite · stream_proxy · danmaku WS · ASR · DB │
└─────────────────────────────────────────────┘
```

| 目录 | 职责 |
|------|------|
| `src/` | 前端：页面、播放控制、弹幕引擎、设置 |
| `src-tauri/src/sites/` | 各站点 HTTP / 签名 / 房间解析 |
| `src-tauri/src/danmaku/` | 弹幕 WebSocket 与协议解析 |
| `src-tauri/src/stream_proxy.rs` | 本机流媒体代理（CORS / Referer） |
| `src-tauri/src/iptv/` | 代理感知的 M3U 获取、大小限制、频道元数据解析与有界可用性探测 |
| `src-tauri/src/asr.rs` | CrispASR Qwen3 模型下载、CPU/GPU 会话生命周期与转写 |
| `src-tauri/src/db/` | SQLite：关注、历史、设置、Cookie |
| `scripts/` | WSL 同步、Windows 桌面构建、Windows Android 真机开发 |

## 2. 播放路径

1. `LiveSite::get_play_urls` 拿到带 headers 的 FLV/HLS 地址。  
2. 前端请求 `stream_proxy_start`，Rust 在 `127.0.0.1` 起本地服务。  
3. 浏览器访问 `http://127.0.0.1:<port>/...`，代理向上游带正确 UA/Referer。  
4. 前端统一由 `xgplayer` 管理媒体元素和播放器生命周期：直播 FLV 使用官方 `xgplayer-flv`，HLS 使用 `xgplayer-hls.js`，IPTV 裸 MPEG-TS 使用 xgplayer 兼容插件。HLS 清单中的子清单、密钥与分片会在本机代理中改写到受限的 localhost 资源路径。

每次播放器会话会携带唯一 session ID；停止请求只会关闭同一会话持有的代理，因此快速离开并再次进入同一房间时，旧清理不会误关新代理而造成黑屏。播放控制以透明层叠放在画面底部，播放闲置后自动隐藏，指针、点击或键盘操作会再次显示。

IPTV 前端将 `/iptv` 作为仅用于发现的首页：展示响应式来源切换、源更新时间、分类、搜索、会话级可用状态和频道列表，进入时不会创建播放器或代理会话，也不会默认播放第一个流。自定义 HTTP(S) M3U 地址只能在「设置 → 网络」保存；首页选中 `source=custom` 时从本机设置解析，地址本身不会写入路由、历史或配置包。`iptv_load_playlist` 与 `iptv_check_channels` 都从本机设置读取代理；前者重新获取当前 M3U，后者接受最多 32 个一批的去重频道请求，以 12 路并发和 7 秒单项上限读取首批媒体数据，并额外校验 HLS 清单头、空响应与 HTML 验证页。前端把当前筛选结果限制为 120 个、按 24 个一批调用并渐进合并结果；状态不进入 URL、数据库或配置包，更新/换源即清除。点击频道才会进入独立、沉浸式的 `/iptv/play` 路由并创建播放会话；该页返回会恢复带来源、分类和搜索条件的频道列表。

## 3. 站点模块

| 模块 | 说明 |
|------|------|
| `sites/bilibili/` | 房间、画质、播放、弹幕 token |
| `sites/huya/` | 移动端页 `HNF_GLOBAL_INIT`、anticode、FLV |
| `sites/douyu/` | betard / homeH5Enc、Boa + CryptoJS 签名、getH5Play |
| `sites/douyin/` | `a_bogus` 验签分区列表（推荐/分区可翻页）、SSR 分类、Cookie 会话、SSR → reflow 房间详情/画质/播放、登录搜索 |
| `sites/twitch.rs` | 公开首屏直播列表 / 分类 / 搜索、房间详情与 HLS 播放 token |
| `sites/registry.rs` | 元数据 + `is_ready` |

**斗鱼签名注意：** Boa 需 polyfill `escape` / `unescape` / `String.prototype.substr`，且 CryptoJS 挂到 `globalThis`。

**虎牙注意：** 解析 HTML 中的 JSON 时必须按 UTF-8 字符边界处理，避免中文页 panic。

**抖音注意：** `DouyinSite` 从账号库注入用户 Cookie，并在每个站点实例首次使用时访问直播首页刷新临时 `ttwid` 会话。推荐与分区列表调用网页端分页接口 `webcast/web/partition/detail/room/v2/`，其浏览器验签参数 `a_bogus` 由 `sites/douyin/a_bogus.rs` 在本机以纯 Rust（SM3 + RC4）计算，不需要 JS 运行时；每页 15 条、`offset` 按页递增，因此「加载更多」真实可用。推荐页并非真实分区，使用合成分区 `720/1`；分类树的 `id,type` 会拆成 `partition` 与 `partition_type`（均须为数字），「全部 X」条目 id 为 `0` 时回退到父分区。上游不下发 `has_more`，只有满页且 `offset` 前进时才继续翻页，避免重复拉取。首页首屏若验签失败会回退到 `hot_live` SSR。短房间号优先从 SSR 房间页取得内部 `id_str`，再调用不携带 `.douyin.com` Cookie 或 `msToken` 的公开 reflow 接口取得播放数据，避免受浏览器验签保护的网页进房接口导致 `code=101`。播放 URL 只保存在房间 `raw` 的临时数据中。搜索调用官方网页直播搜索接口，需要完整登录 Cookie，用户可扫码或手动保存；二维码和搜索仍可能遇到网页访问验证，应用不会自动绕过。实时弹幕由 `danmaku/douyin_sign.rs` 在本机用 Boa 执行 `webmssdk` 计算短时签名，`danmaku/douyin.rs` 组装 WSS 查询串并直连；Cookie 头使用保存 Cookie 加本次临时 `ttwid` / `msToken`，临时值不序列化、不持久化。

**Twitch 注意：** `TwitchSite` 通过公开 GraphQL 获取直播列表、分类、搜索、房间详情和 HLS 播放 token。公开接口的 cursor 翻页会触发完整性校验，因此所有浏览结果都只返回可靠的首屏并设置 `has_more = false`，不伪造翻页。

## 4. 弹幕模块

| 文件 | 协议 |
|------|------|
| `danmaku/bilibili.rs` | 二进制帧 + zlib/brotli + JSON cmd |
| `danmaku/douyin.rs` | 本地 MSSDK 签名 → WSS；PushFrame / gzip / 最小 protobuf 解码与 ack |
| `danmaku/douyin_sign.rs` | Boa + `assets/douyin_webmssdk.js` 计算 WSS `signature` |
| `danmaku/douyu.rs` | STT + 小端帧；`native-tls`；端口 8501–8506；借用式逐包解析与进场包早期丢弃；当前网页协议对齐的本机 Cookie 普通弹幕发送 |
| `danmaku/huya.rs` | TARS join + uri=1400 聊天；本机 Cookie 认证的普通弹幕发送 |
| `danmaku/twitch.rs` | 匿名 IRC WebSocket 聊天 |
| `danmaku/tars.rs` | 最小 TARS 编解码 |
| `danmaku/mod.rs` | 按站点启动/断开，事件名 `danmaku` |

`DanmakuEvent` 带可选 `SuperChatInfo` 与有序的 `DanmakuContentSpan`。哔哩哔哩 `SUPER_CHAT_MESSAGE` 会在 Rust 层校验并提取消息 ID、金额、币种、时长、颜色元数据和发送者头像 URL，随后通过 Tauri 事件传给前端。SC 前端再次校验头像 URL，仅以无 Referer 方式加载受信任的 B 站 CDN；不会补查或持久化用户资料。播放器左下角最多叠放 3 张卡片，按置顶时长退出；卡片将头像、发送者、金额和倒计时置于身份区，经校验的主色与底色用于下方正文带。普通 B 站聊天会从 `info[0][13].url` 与 `info[0][15].extra.emots` 提取图片表情；只接受 B 站 CDN 的 HTTPS URL，并保留文字/图片原始顺序。

B 站连接关闭、读取失败、认证被拒或长时间无数据时不会以“连接结束”终止：客户端会轮换网关，刷新短时 token 与主机列表后退避重连，并将重连状态写入系统消息。

B 站正式发送在 `danmaku/bilibili.rs`：仅 `POST /msg/send` 的单条普通文本；后端先重验与抖音、斗鱼、虎牙共用且默认关闭的本机授权 `danmaku_send_enabled`，再校验 `SESSDATA` / `bili_jct`、房间号和文本，并按房间保守冷却。携带 Cookie 的写请求禁止跟随重定向，且不自动重试。

斗鱼发送由 `danmaku/douyu.rs` 处理：它重验共用的 `danmaku_send_enabled`、房间、文本和 3 秒本机冷却，并使用用户本机保存的完整会话字段。2026-07-27 的受控诊断发现旧路径采用过期 `loginreq` / 聊天载荷、跳过网页登录后协商并忽略 `chatres` / `error`；当前实现已替换为网页对齐的认证状态机、稳定设备身份、统一 WSS 代理与平台回包解析，并已在个人直播间成功验证。运行时仍将本地提交、`chatres(res=0)` 平台接收与正常收弹幕连接的真实回显分开处理；详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。虎牙发送由 `danmaku/huya.rs` 处理：同样先重验共用授权，需要扫码或手动保存含数字账号 ID（`yyuid` 或 `udb_uid`）及登录凭据（`udb_n` / `udb_cred` / `udb_biztoken`）的本机 Cookie，解析房间元数据后校验单条、单行且最多 30 个 UTF-16 单元的文本再写入。扫码实现见 `account/huya_qr.rs`。抖音发送由 `danmaku/douyin.rs` 处理：同样先重验共用授权与登录 Cookie，解析内部 `room_id` 后用本机 MSSDK 签名参数 `POST /webcast/room/chat/`；详见[抖音平台 API 文档](抖音平台API文档.md)。所有路径均不得记录、导出或上传 Cookie，也不得对不确定写入自动重试。

`PlayerPane` 在 `DanmakuSettingsPanel` 之上持有 B 站 / 斗鱼 / 虎牙的房间会话级自动发送调度器，因此切走右侧「设置」标签后仍会随当前直播间运行。它完全在前端复用既有的平台单条发送 command 与校验/状态检查，不新增 Tauri command、数据库字段、`AppSettings` 字段或配置导入导出数据。开关、文本和发送间隔只存于会话内；间隔默认 20 秒，可在 10–3600 秒间调整。只有共用本机授权、当前平台 Cookie/可发送状态和文本校验都有效时才能开启。开启时立即发送首段，将换行和连续空白压缩为一个空格，再按 grapheme 拆成最多 20 个用户可见字符且满足平台 UTF-16 上限的片段；单个超出上限的 grapheme 为校验错误。请求串行不重叠，后续发送起始至少相隔当前会话设置的发送间隔，修改间隔会重排下一次发送，末段后回到首段循环。编辑文本、切房（同时清空会话文本）、离开/卸载播放器、关闭应用或任一发送失败都会立即停止本会话并展示原因；失败或未知写入不会自动重试。

前端不会从本机 command 返回值合成弹幕。右侧列表与 Canvas 只应在房间连接收到平台真实 `DanmakuEvent` 回显后显示消息，并保留平台原有样式；一次本机写入结果不是平台确认。斗鱼会区分本地提交、`chatres` 平台接收与真实回显，三者仍不可混为一谈。

前端：

- `useDanmakuConnection`：哔哩哔哩 / 虎牙 / 斗鱼 / 抖音 / Twitch 进房 `danmaku_connect`；前后端 epoch 栅栏保证切房时过期 connect / disconnect 不能覆盖新房间；抖音在本机签名失败或 WSS 断连时返回可重试提示，Twitch 使用匿名 IRC
- `DanmakuPanel`：按 `requestAnimationFrame` 合批、限制等待队列、非平滑自动滚动的消息列表；统一隐藏进场提示及可选礼物，右侧列表保留每条通过筛选的房间消息；B 站、斗鱼、虎牙房间可挂载手动单条发送框，它与 PlayerPane 持有的自动发送调度器都要求默认关闭的本机发送授权及各自的账号条件；显示仍只以平台真实回显为准
- `CanvasDanmaku` + `danmakuEngine`：顶部向下分配飘屏轨道；普通聊天同样按内容进行 5 秒聚合；B 站图片表情由小型 LRU 图片/位图缓存按原始顺序绘制，尚未加载时保留文字回退；无活跃项目时不再请求动画帧，消息/设置/尺寸变化时恢复；显示区域、行数和字重实时生效
- `SuperChatOverlay` + `superChat.ts`：仅 `super_chat`，将安全校验后的 B 站主色/底色用于播放器左下卡片，并负责金额/时长、去重和有界帧合批
- `DanmakuSettingsPanel`：房间侧栏即时设置，并接收 PlayerPane 当前会话的自动发送控制器；`FollowPanel`：直播优先的关注列表与替换式直接路由切换，房间返回会回首页而非上一间直播间
- `danmaku/filter`：预编译屏蔽词、有界内容聚合器与飘屏文案

设置字段（SQLite / `AppSettings`）：`danmaku_area`、`danmaku_line_count`、`danmaku_opacity`、`danmaku_font_size`、`danmaku_font_weight`、`danmaku_speed`、`danmaku_filter_repeats`、`danmaku_filter_gifts`、`super_chat_enabled`、`danmaku_shield_words`、`danmaku_send_enabled`、`asr_enabled`、`asr_compute_mode`、`asr_vad_enabled`、`asr_font_size`、`iptv_custom_m3u_url`。`asr_font_size` 为播放器字幕字号，默认 `20`，前端限制为 `12–48`；它是可移植显示设置。`danmaku_filter_gifts` 与 `super_chat_enabled` 默认 `true`，旧配置缺失时同样按开启处理；`danmaku_send_enabled`、`asr_enabled` 与 `asr_vad_enabled` 默认 `false`。自动发送的文本、发送间隔、片段位置和启用状态刻意不进入设置、数据库或配置包。Cookie 独立保存在 `cookies` 表。配置导出还会排除发送授权、ASR 启用/设备/VAD 设置与自定义 M3U，导入时保留当前设备值，但会合并 `asr_font_size`。

## 5. 本地语音字幕

前端 `AudioCapturePipeline` 从播放器 `HTMLVideoElement` 创建一个共享 `MediaElementAudioSourceNode`，将声道混合为单声道，并保持原声复制到输出节点，避免开启 ASR 改变直播音量。采集器以初始 6 秒、范围 1–8 秒的自适应窗口和 0.25 秒重叠切片，再降采样为 CrispASR 要求的 16 kHz f32 PCM；滚动 PCM 与声道混音缓冲会复用。`useAsrCaptions` 串行调用 `asr_transcribe`：一个任务执行时只覆盖保存最新待办片段，并根据 RTF、排队等待和丢弃情况调整下一窗口大小，因此慢设备不会积累无界队列。字幕叠加层读取 `asr_font_size` 作为 CSS `font-size`，字号变化不触发模型或采集器重建。

Rust `AsrManager` 在用户明确启用后才下载和加载固定的 `qwen3-asr-0.6b-q4_k.gguf`。下载固定到模型仓库提交，校验精确长度后原子替换临时文件。会话使用 CrispASR `crispasr_session_open_with_params` v2：CPU 模式传 `use_gpu=0` / `n_gpu_layers=0`，GPU 模式传 `use_gpu=1` / `n_gpu_layers=-1`；GPU 后端由 `asr-cuda`、`asr-vulkan` 或 `asr-metal` Cargo feature 在构建期加入，CPU 后端始终保留，多个 feature 可共同启用。没有 GPU feature 时，设置状态明确回落到 CPU。线程数由 `available_parallelism()` 自动读取并用于 ggml intra-op，实时解码 token 上限设为 256。模型会话由互斥锁串行使用，转写与模型释放均在阻塞线程池执行；设备切换以 generation 栅栏取消过期装载，避免旧任务覆盖新设置。

VAD 开启时，`AsrManager` 按需下载固定提交中的 `ggml-silero-v6.2.0.bin` 并校验 `885,098` 字节。每个自适应窗口先调用 `crispasr_vad_slices`；返回零片段时直接返回空字幕，避免上游 `crispasr_session_transcribe_vad` 对空切片回退普通 Qwen3 转写。有语音时再调用该 session API，让 CrispASR 裁剪/拼接语音并重映射时间戳。Silero 上下文由 CrispASR 进程级缓存；切换 VAD 复用当前 Qwen3 session。

`asr_enabled`、`asr_compute_mode` 和 `asr_vad_enabled` 是设备本地设置，不随配置包导入导出；`asr_font_size` 是可移植的显示设置，会随配置合并。模型文件、PCM 与字幕均不进入 SQLite。完整说明见[本地语音字幕](本地语音字幕.md)。

## 7. 构建与交付

- 开发：WSL `/home/.../rLive`  
- 运行：Windows `D:\dev\rLive` → `rlive.exe`  
- 一键：`./scripts/build-windows-from-wsl.sh`  

Windows 构建脚本的 `-AsrBackend auto` 会按 CUDA → Vulkan → CPU 检测工具链；也可显式传 `cuda`、`vulkan` 或 `cpu`。其他平台通过 `asr-cuda`、`asr-vulkan`、`asr-metal` Cargo feature 选择 GPU 库，CPU 后端始终保留。

Release：`lto = "thin"`、`panic = "abort"`，故后端 panic 会导致进程退出，站点解析必须避免未处理 panic。

## 8. 扩展建议

| 目标 | 建议入口 |
|------|----------|
| 抖音分页 | 当前仅提供 SSR 首屏；后续网页接口需要浏览器验签与 cursor，未来若支持需用户可见的真实浏览器 / WebView 会话和 cursor 模型；不生成签名、不绕过访问验证，也不使用 SSR offset 伪分页 |

| 更多 SC 字段 | 扩展 `DanmakuEvent` 与 B 站 SUPER_CHAT 解析 |
