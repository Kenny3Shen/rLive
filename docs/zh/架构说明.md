# rLive 架构说明

这篇文档是架构导航：帮你建立 rLive 的整体模型，说明每个子系统的职责边界、跨模块契约，以及代码在哪。适合首次接触代码库、或要改动跨越前后端的人先读。

具体实现细节在专题文档里：播放与多画面见[播放器技术文档](播放器技术文档.md)，录制与回放见[录制与回放](录制与回放.md)，IPTV 与投屏见[IPTV与投屏](IPTV与投屏.md)，语音字幕见[本地语音字幕](本地语音字幕.md)，UI 与动效见[UI与动画技术说明](UI与动画技术说明.md)，各平台协议见对应的平台 API 文档，环境与命令见[开发指南](开发指南.md)。

## 1. 顶层结构

前端负责界面、播放器生命周期和会话编排；后端负责一切需要跨域请求、签名、长连接、文件与数据库的工作。两者只通过既有 Tauri commands（请求/响应）和 events（`danmaku`、录制与退出通知等推送）通信，前端不复制 Rust 的平台业务逻辑。

| 目录 | 职责 |
|------|------|
| `src/app/` | Shell、路由编排、Android 返回与系统栏桥接 |
| `src/features/` | 业务域：`room`、`multi-room`、`recording`、`iptv`、`follow`、`asr`、`settings` 等 |
| `src/components/ui/`、`src/shared/` | 通用 UI、IPC 入口、stores、手势与动效 |
| `src-tauri/src/sites/` | 各站点 HTTP / 签名 / 房间与播放地址解析 |
| `src-tauri/src/danmu_rs/` | 弹幕 WebSocket 连接、协议解析与发送 |
| `src-tauri/src/stream_proxy.rs` | 本机流媒体代理：请求头注入、HLS 改写、线路探测与遥测聚合 |
| `src-tauri/src/recording.rs`、`recording_ffmpeg.rs`、`recording_ass.rs` | 录制任务调度、libavformat remux worker、弹幕转 ASS |
| `src-tauri/src/iptv/` | M3U 获取与解析、频道元数据、有界可用性探测 |
| `src-tauri/src/dlna.rs` | DLNA 设备发现、AVTransport 控制与局域网流中继 |
| `src-tauri/src/asr.rs` | sherpa-onnx 模型管理与本地流式转写会话 |
| `src-tauri/src/db/` | SQLite：关注、历史、设置、Cookie、IPTV 关注 |
| `src-tauri/src/image_proxy.rs`、`image_cache.rs` | 远程图片代理与磁盘缓存 |
| `src-tauri/src/account/`、`profile/`、`settings/`、`lan_sync.rs` | 扫码登录、配置导入导出、设置边界、局域网同步 |
| `scripts/` | WSL 同步、Windows 桌面构建、Android 真机开发 |

## 2. 播放路径

站点解析出结构化播放源，前端选线后一律经本机代理喂给 xgplayer。

- `LiveSite::get_play_urls` 返回带 `source_id`、协议、平台优先级、URL 和 headers 的 `PlayUrl[]`；前端按 `site_id + room_id` 恢复上次手动选线（优先匹配 `source_id`），无记忆时按平台顺序。
- `stream_proxy_start` 为当前 `sessionId` 在 `127.0.0.1` 开独立监听器；播放器只访问 `http://127.0.0.1:<port>/...`，代理向上游补 UA/Referer，并把 HLS 清单里的子清单、密钥与分片改写到受限的 localhost 路径。
- 媒体内核只有两套：FLV 与裸 MPEG-TS 走 `xgplayer-mpegts.js`，所有 HLS 走 `xgplayer-hls.js`，原生容器交给 `<video>`。裸 `.ts` 没有清单，不能进入 HLS 状态机，这是 IPTV 连续流仍用 mpegts 内核的原因。
- 控制层统一是 `src/shared/components/player/PlayerControls.tsx`，不启用 `<video controls>` 或 xgplayer 皮肤；Android 的亮度、系统媒体音量、方向与沉浸式系统栏由 Kotlin 原生桥管理。
- 桌面 `/multi-room` 用同一媒体会话跑 2/4/6 路，槽位 0 承担音频、弹幕、ASR 与全屏；直播时钟同步在前端做纯函数控制环，壁钟锚点取自代理的 `first_media_at_ms`。
- 播放遥测每 2 秒采样，只留内存快照，不上传、不持久化、不保存 URL 与 headers。

DLNA 投屏是播放路径的旁支：电视端自行拉流，既带不了平台请求头也访问不到回环代理，因此 `dlna.rs` 另起一个绑定 `0.0.0.0` 的中继，只接受携带本次会话随机令牌的请求并拒绝回环目标，HLS 清单同样改写到中继地址。设备控制用无 Cookie 的独立客户端，不接触登录态。

## 3. 会话所有权边界

播放由两个相邻但不可合并的会话概念组成，实现在 `src/features/room/playback/playbackRecoverySession.ts` 与 `src/features/room/player/useWebPlayer.ts`。

- **播放恢复会话**拥有播放元数据获取与缓存同步、线路记忆、重试与续签预算、过期异步结果失效，以及当前播放源的选择。
- **媒体生命周期会话**从一个已解析的 `PlayUrl` 开始，拥有 proxy session generation、xgplayer 创建销毁、协议内恢复、自动播放、媒体状态、音量、全屏与画中画；页面布局、手势仲裁和导航不属于它。
- seam 是单向的：恢复会话选择 `PlayUrl`，媒体会话只回报已发生的 transport facts（开始播放、流结束、解码失败、HTTP 状态、协议错误），不输出恢复决定；重建、续签、降清晰度、换线、延迟重试由恢复会话依据事实、站点规则和剩余预算决定。
- 每个播放器实例有独立的恢复会话与媒体状态。实例间可共享 TanStack Query 的元数据缓存，但不共享预算、timer、generation、当前清晰度与线路。
- 用户 intent 优先于自动恢复：切清晰度、换线、手动刷新会取消待执行 timer 并递增 intent generation，使旧 generation 的结果与延迟动作失效。
- 直播与 IPTV 共用同一媒体生命周期 module，各自只提供 adapter（直播交由恢复会话决策，IPTV 维护频道内有界重连预算）；各站点的恢复差异是恢复会话的内部规则，不为每个站点建 adapter。
- 恢复会话核心不依赖 React 生命周期，React 层只负责创建销毁、订阅 snapshot、转发 intent 与 facts。

## 4. 录制路径

录制与播放共用 `PlayUrl` 结构，但走独立连接、独立地址、独立进程内 worker。

- 入口有两条：播放器把当前身份与协议传给 `recording_start`；关注页 `followRecording.ts` 自行取房间详情解析播放源，直接起后台任务，无需进入直播间。
- 房间页不复用播放器正在拉的地址，而由 `recordingSource.ts` 另取一条线路（按 `source_id` 匹配当前线路，取不到才回退共享地址）。原因是按请求签名且每个签名只允许一个消费者的站点（斗鱼为已知案例）会掉第二条连接。
- `RecordingManager` 在进程级持有后台 session，并发上限每次 `recording_start` 从设置 `recording_max_concurrent`（默认 4，钳制到 1..=6）读取后传入，因此调设置不影响已在录的任务，下一次启动即生效。路由卸载不结束任务；运行中与收尾中的任务分列 `sessions` / `finalizing`，收尾期间仍占用身份与并发名额。后台录制恒开，`continue_on_leave` 默认 `true`。
- FLV、HLS、MPEG-TS 统一进 `recording_ffmpeg.rs` 的 libavformat worker（只 remux，不解码转码），原生 MP4/WebM 用最小直连保存。HLS 输入按 MPEG-TS 落盘为 `.ts`，清单轮询、variant 选择、AES-128 key 与 `EXT-X-MAP` 全交给 libavformat。
- libavformat 的 HTTP 重连参数**仅对 HLS 启用**：分段协议重连后从分片边界续读是安全的，FLV / MPEG-TS 是连续字节流，重连只在字节层续接会写出容器完好但解码失败的文件；连续流断开时任务直接结束，后续内容录进新会话。
- Twitch HLS 例外地经录制 manager 独立持有的 `StreamProxy`，用于广告与 token 过期时重签清单，生命周期与录制任务一致、不依赖页面播放器的 proxy session。它带来两条容易回归的硬约束，改动 Twitch 录制或 HLS demuxer 选项时必须同时满足：
  - **必须预热清单**：`StreamProxy::start` 只绑监听器、不请求 `/live`，而 libavformat 只调用一次 `avformat_open_input`。若这唯一一次拿到广告期的占位清单（分片全带 `#EXT-X-GAP`），探测读不到媒体，录制在写入第一个字节前就以 `Invalid data found when processing input` 失败。因此交给 FFmpeg 前先按 `#EXTINF` 与 `#EXT-X-GAP` 的配对关系轮询等待可录清单（上限 20 秒）。
  - **本机分片地址必须带扩展名**：FFmpeg 8 起 HLS demuxer 默认开启 `extension_picky`，扩展名不在白名单内的分片直接被拒，同样是一个字节都不写。`rewrite_hls_manifest` 因此用 `hls_path_extension` 把上游 path 的扩展名补回本机地址，`resolve_upstream_target` 解析时再去掉后缀。扩展名只从 path 读取——Twitch 分片形如 `.mp4?dna=<token>`，签名 token 不得进入本机路径。
  - 由此产生的验证要求：Linux 开发机常见的 FFmpeg 6.1 根本没有 `extension_picky`，Rust 测试在 Linux 全绿不足以证明桌面录制可用。涉及 HLS 输入或 demuxer 选项的改动需用 Windows 侧 `ffprobe.exe` / `ffmpeg.exe` 对本机代理端点复核一次。
- 逐主播 `follows.auto_record` 由 `AppRuntime` 上的控制器每分钟轮询启用记录，每个直播 session 只提交一次自动开始；仅在桌面进程运行期间存在，不创建系统驻留任务。
- 应用退出时先禁止新任务并广播取消，在共享 15 秒窗口内等 trailer、弹幕关闭与 metadata 落盘；超时的 bundle 保留原状，由下次启动统一恢复并标记 `interrupted`。

## 5. 弹幕路径

Rust 建长连接并统一成事件模型，前端只渲染平台真实回显。

- `danmu_rs/mod.rs` 按站点启动/断开连接，事件名固定 `danmaku`；`DanmakuEvent` 带可选 `SuperChatInfo` 与有序的 `DanmakuContentSpan`（文本与受限 CDN 图片表情），后端 `user_id` 通过 `serde(skip)` 保持本机私有。
- 前端 `useDanmakuConnection` 用前后端 epoch 栅栏保证切房时过期的 connect / disconnect 不能覆盖新房间。
- 渲染分两层：`DanmuJsDanmaku` 直接驱动 `danmu.js`，在播放器内叠两个实例（`scroll` 承担普通实时弹幕并只映射用户显示区域，`top` 承担自己发送的消息与 SC）；`DanmakuPanel` 是按帧合批、有界队列的右侧列表。两层共享 `danmaku/filter` 的屏蔽词、用户屏蔽与内容聚合。
- 发送是可选能力，受默认关闭的本机授权 `danmaku_send_enabled` 约束，B 站、斗鱼、虎牙各需自己的完整 Cookie 与文本校验，均有房间级冷却、禁止跟随重定向、不对不确定写入自动重试。抖音不支持发送。
- 一次本机写入成功不等于平台确认：本地提交、平台 ack（如斗鱼 `chatres`）与真实回显必须分开处理，前端不从 command 返回值合成弹幕。
- 会话级的自动发送调度器和定时关闭由 `RoomPage` 持有，只存在于当前房间会话，不写 SQLite、`AppSettings` 或配置包。

## 6. 本地语音字幕路径

仅桌面 Tauri 启用（`supportsLocalAsr` 同时校验 runtime 与 `desktop` 平台），Android / iOS 不采集音频也不下载模型。

- 前端 `AudioCapturePipeline` 从播放器的 `HTMLVideoElement` 建共享音频源，优先用 AudioWorklet 在音频线程原声直通、混单声道、按更新间隔切无重叠分块，主线程降采样为 16 kHz f32 PCM 后经 IPC 传给 Rust；旧 WebView 回退 `ScriptProcessorNode`。
- `useAsrCaptions` 串行调用 `asr_transcribe`，执行中只保留最新一个待办分块，慢设备不会累积无界队列。
- Rust `AsrManager` 只在用户显式启用后下载 Zipformer、可选标点与可选声纹模型（Windows Release 另需按需下载官方 shared runtime），状态经 `downloading → extracting → loading → ready`。
- `NativeAsrSession` 复用一个识别器与跨分块的 stream；Windows x86_64 可选 CUDA provider 并在不可用时回退 CPU，Linux / macOS 固定 CPU。
- 模型、热词、PCM、声纹 embedding 与字幕文本都不进 SQLite、不出设备。翻译是独立可选路径，只发送 endpoint final 文本。

## 7. IPTV 路径

`/iptv` 是纯发现页，`/iptv/play` 是独立播放页；进入发现页不创建播放器或代理会话，也不默认播首个频道。

- `iptv_load_playlist` 与 `iptv_check_channels` 都从本机设置读代理；可用性探测按批去重、并发有界、单项超时，并额外识别空响应与 HTML 验证页。探测结果只存会话内存，不入 URL、数据库或配置包。
- 自定义 M3U 地址只能在「设置 → 网络」保存，不写入路由或配置包；不同自定义源用地址派生的本地哈希隔离命名空间。
- IPTV 关注用独立的 `iptv_favorites` / `iptv_favorite_groups` 表，以 `source_id + channel_url` 为主键并存频道快照，因此频道从最新 M3U 消失后仍可进入播放页。用户归组与 M3U 自带的 `group_name` 是两个字段。
- 配置包只导出内置公开源的关注与分组，自定义源关注不离开设备。

## 8. 存储与数据边界

`app_paths::AppDirectories` 在任何数据库或日志打开前解析应用根目录：Windows / Linux 优先可写的可执行文件目录，macOS 用 `.app` 外部目录，只读位置回退系统应用数据目录。根目录下有 `rlive.db`、`logs/`、`cache/images/`、`models/`、`asr-runtime/`、默认 `recordings/`，路径由程序自动选择，不提供迁移设置。

- **SQLite**（WAL、`PRAGMA user_version = 3`）存关注、观看历史、设置、Cookie、弹幕收藏与发送历史、IPTV 关注。空库一次性建表，旧版本或未知版本直接返回 `db_schema_unsupported`，启动路径不迁移、不补列、不改写旧库。
- **录制 bundle** 自包含且可复制，不进 SQLite：两级结构 `recordings/<platform>_<roomid>/<username>_<starttime>/`，内含 `metadata.json`（`schema_version: 2`）、媒体文件与 `danmaku.jsonl`。bundle ID 就是这两级相对路径，`is_safe_recording_id` 是防止跨出录制根目录的唯一关口。内存 `RecordingLibraryIndex` 只是缓存，丢失后可从 bundle 重建。
- **设备本地状态**不入配置包：逐房间线路记忆、多画面布局（localStorage）、IPTV 可用性、发送授权、ASR 开关与热词、自定义 M3U 地址。配置包 profile v2 只接受当前 portable 字段，缺版本、旧字段或未知字段都拒绝，少数显式登记的新增字段才按默认值补齐。
- **图片**统一经 localhost 代理并落 `cache/images/`（带 TTL 与容量上限）；直播封面走 `normalizeCoverUrl` 附加 `nocache=1`，只用短时 WebView 缓存不落盘，因为各平台封面 URL 要么每次抓拍换名、要么固定 URL 而画面几分钟一换。
- **不离开设备**的数据：Cookie 与登录态、ASR 模型与音频、录制媒体与弹幕 sidecar、播放遥测、自定义 M3U 地址。

## 10. 构建与交付

开发在 WSL，运行在 Windows 同步目录，一键流程见[开发指南](开发指南.md)。

- 桌面三平台固定引入 `ffmpeg-next`，构建需 ABI 匹配的 headers、link libraries 与 libclang；缺失动态库会在进程装载阶段失败，无法通过 IPC 回退。
- Windows 用自建的裁剪版 LGPL shared FFmpeg SDK，随 NSIS/MSI 交付运行库与许可说明；Linux / macOS 静态链接同一套组件。
- ASR 运行库按平台差异交付：Windows 首次启用字幕时下载校验、Linux 随包安装 CPU-only runtime、macOS 编入二进制。Android 通过条件编译整体排除 ASR。
- Release 使用 `panic = "abort"`，后端 panic 会终止进程，站点解析必须避免未处理 panic。
- 完整发布流程与平台差异见[发布流程](发布流程.md)，Android 构建与调试见[Android 开发与构建](Android开发-Windows.md)。
