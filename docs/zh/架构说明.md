# rLive 架构说明

## 1. 总体结构

顶层采用标准 Tauri 布局，按前后端拆分：

```
rLive/
├── src/          # React UI（Vite 入口与页面）
├── src-tauri/    # Tauri 2 + Rust（commands / sites / DB）
├── tests/        # 前端单元测试
├── docs/         # 中文文档
└── scripts/      # WSL 同步、Windows 桌面构建、Windows Android 真机
```

```
┌─────────────────────────────────────────────┐
│  React UI (src/)                              │
│  首页 / 关注 / 分类 / 历史 / 录制 / IPTV / 多画面 / 设置 / 房间页 │
│  xgplayer 协议插件播放 · 多会话代理 · danmu.js DOM 弹幕 · SC │
└──────────────────┬──────────────────────────┘
                   │ Tauri commands / events
┌──────────────────▼──────────────────────────┐
│  Rust (src-tauri/)                            │
│  LiveSite · stream_proxy · danmaku WS · ASR · DB │
│  RecordingManager · local playback server          │
└─────────────────────────────────────────────┘
```

| 目录 | 职责 |
|------|------|
| `src/` | 前端：页面、播放控制、弹幕适配层、设置 |
| `src-tauri/src/sites/` | 各站点 HTTP / 签名 / 房间解析 |
| `src-tauri/src/danmu_rs/` | 弹幕 WebSocket 与协议解析 |
| `src-tauri/src/stream_proxy.rs` | 本机流媒体代理、HLS 改写、线路探测与脱敏聚合遥测 |
| `src-tauri/src/iptv/` | 代理感知的 M3U 获取、大小限制、频道元数据解析与有界可用性探测 |
| `src-tauri/src/asr.rs` | sherpa-onnx Zipformer/标点/CAMPPlus 模型下载、流式会话生命周期、转写与匿名说话人聚类 |
| `src-tauri/src/recording.rs` | 桌面直播录制任务、可配置多目录存储、FFmpeg worker 调度、弹幕 sidecar、崩溃恢复与本地回放 HTTP 服务 |
| `src/features/recording/` | 录制状态查询、播放器录制控制、录制库列表与本地回放控件 |
| `src-tauri/src/db/` | SQLite：关注、历史、设置、Cookie |
| `scripts/` | WSL 同步、Windows 桌面构建、Windows Android 真机开发 |

SQLite 文件连接使用 WAL 日志和 `synchronous=NORMAL`，为单条历史写入降低同步落盘开销，并配置 5 秒锁等待、8 MiB 页缓存和检查点后的 WAL 保留上限。观看历史按 `watched_at + site_id + room_id` 建立稳定排序索引，最多保留最近 2,000 个不同直播间；迁移旧数据库时只裁剪超限记录并复用空闲页，不在启动阶段执行阻塞性的 `VACUUM`。弹幕发送历史分别使用站点内和全局时间索引，继续保持每个平台 50 条的既有上限。可运行 `bash scripts/benchmark-history-sqlite.sh`，在临时目录中复现旧版与当前实现的读取、独立写入和稳定态存储对比。

桌面端通过 `app_paths::AppDataStorage` 在任何数据库或日志打开前解析应用根目录。新安装在 Windows 和 Linux 优先使用可写的可执行文件所在目录，macOS 则使用 `.app` 所在的外部目录，避免向签名 bundle 写入数据；`Program Files`、Linux `/usr/bin`、只读 AppImage mount 或其他不可写位置会回退到系统应用数据目录。稳定的 `app-data-bootstrap.json` 存在系统 config 目录，`app_data_storage_info` / `app_data_set_storage_path` 只修改下次启动选择，不在 SQLite 和日志仍打开时热迁移数据。bootstrap 与 `recording-storage.json` 通过同目录临时文件、备份和启动恢复完成替换，以兼容 Windows 无法直接覆盖 rename；有效 bootstrap 指向的自定义目录不可用，或 bootstrap 不可读、损坏且没有有效事务侧文件时，应用会明确停止启动而不会静默打开另一份数据库。无 bootstrap 且旧系统 data root 已有 `rlive.db` 时会自动保留并持久化旧位置；用户显式恢复默认后不会再次被旧数据库接管。SQLite 为 `rlive.db`，日志为 `logs/`，模型为 `models/`，Windows 按需下载的字幕运行库为 `asr-runtime/`，默认本地录制 bundle 为 `recordings/`；录制目录切换记录保存在根目录的 `recording-storage.json`。内部 canonical path 可保留 Windows verbatim 前缀，但所有 IPC、录制配置和文件定位路径统一通过 `path_to_string` 转成普通盘符或 UNC 形式。WebView 的 localStorage 和缓存仍交由 Tauri 默认目录管理。Android 继续使用应用沙箱。

## 2. 播放路径

1. `LiveSite::get_play_urls` 返回带 `source_id`、安全标签、显式协议、平台优先级、URL 和 headers 的结构化 `PlayUrl[]`。
2. 前端按 `site_id + room_id` 恢复最近一次手动线路选择，优先匹配 `source_id`，缺失时回退到保存的序号；没有记忆时遵循平台顺序。
3. 前端请求 `stream_proxy_start`，Rust 在 `127.0.0.1` 为当前 `sessionId` 准备独立监听器，并在就绪后只替换同一会话的旧活动代理。
4. 播放器通过本机 `stream_proxy` 访问 `http://127.0.0.1:<port>/...`，代理向上游带正确 UA/Referer；HLS 清单中的子清单、密钥与分片会在本机代理中改写到受限的 localhost 资源路径。
5. 前端统一由 `xgplayer` 管理媒体元素和播放器生命周期：直播 FLV 与裸 MPEG-TS 使用 `xgplayer-mpegts.js` / `mpegts.js` 并通过 `mediaDataSource.type` 区分容器，所有 HLS 使用 `xgplayer-hls.js` / `hls.js`，原生媒体交给 `<video>`；流媒体内核只保留这两套。
6. 房间播放器每 2 秒采样媒体与代理聚合指标，最多保留 120 条内存快照；不上传、不持久化，也不保存 URL 或 headers。

HLS 播放列表可以引用 MPEG-TS（`.ts`）分片，但这不等于裸 MPEG-TS 流。`hls.js` 先解析 m3u8 清单，再依据分片序号、时间轴、不连续标记和加密信息拉取、转封装 `.ts` 并写入 MSE。裸 `.ts` 地址没有 m3u8 清单，不能进入这套 HLS 状态机，因此 IPTV 的连续 MPEG-TS 流仍由 `xgplayer-mpegts.js` / `mpegts.js` 处理。斗鱼连续 FLV 上游关闭时，前端在 `mpegts.js` 报告 `loading_complete` 后重新获取房间详情与网页播放签名，再刷新清晰度、线路并完整重建会话。

每次播放器会话会携带唯一 session ID；`stream_proxy` 以 `sessionId` 为键并存活动监听器和启动预留，停止请求只会关闭同一会话持有的代理。因此快速离开并再次进入同一房间时，旧清理不会误关新代理，多画面的多路流也不会互相抢占监听器。房间与 IPTV 播放页复用 `src/shared/components/player/PlayerControls.tsx` 的 React 控制层，不启用浏览器 `<video controls>` 或 xgplayer 默认皮肤。控制层以透明方式叠放在画面底部，播放闲置后自动隐藏；播放、静音、画中画和全屏共享相同状态接口，房间按需追加线路、清晰度、弹幕、ASR 和侧栏。ASR 控制与相关设置仅在 Tauri 桌面端挂载；Android 原生桥管理 Activity 级亮度、系统 `STREAM_MUSIC` 音量、全屏方向和全屏期间的沉浸式系统栏，房间与 IPTV 的音量入口共享设备媒体音量。非 Android 平台仍直接写当前播放器的 `<video>` 音量。

桌面 `/multi-room` 路由使用 `src/features/multi-room/` 的导播矩阵，可选择 4 或 6 画面布局。4 画面有两种排列：左主右副使用 3×3 网格，主画面占左侧 3×2，3 个副槽纵向占据右侧；均分排列使用 2×2 网格，4 个槽尺寸相同，但槽位 0 仍是音频、弹幕与全屏角色上的主画面。6 画面使用 3×3 网格，左下 2×2 为主画面，其余槽位沿上方和右侧分布。超过 4 路时拒绝切换到 4 画面，确保没有不可见播放器。拖拽可将画面移入空槽，或与另一个已占用槽交换；不维护额外的副画面位置元数据。拖动主画面到空槽时会安排其他画面补到主槽，以保持主画面角色；双击副画面或点击「设为主画面」仍会直接交换槽位 0 与目标副画面。发生主副交换时，新主解除静音（0% 恢复 80%），全部副路静音，但各路音量数值不被清除。首路默认 80%，新增副路默认 0% 且静音。多画面复用房间详情、播放控制器和 `useWebPlayer`；弹幕、SC 与 ASR 只挂在主画面一路，弹幕叠加层默认关闭并可在控制栏开启，副路和主路都不创建房间侧栏。全屏同样归属主画面：`useWebPlayer` 的 `fullscreenOwner` 只对主路为真，主路容器带 `data-player-stage` / `data-fullscreen`，全屏时脱离网格铺满窗口，而不是放大整个矩阵。容量与排列选择、当前槽位和各路音量由 Zustand persist 保存到设备 localStorage `rlive-multi-room`，不进入 SQLite 或配置导入导出。

`waiting` / `stalled` 只计入内存遥测，不再触发自动换线或重载；B 站 HLS 的重复 fatal 事件仍保留 20 秒原地恢复窗口，避免短暂上游波动造成频繁重建。默认开启的「软切换」会在 HLS、MPEG-TS、FLV 同协议线路间通过 xgplayer `switchURL` 保留外层播放器与媒体元素；FLV 同时替换内部 `mpegts.js` core，协议变化、API 不可用或切换失败会回到完整重建。完整数据契约、故障转移、遥测字段、参数与性能验收见[播放器技术文档](播放器技术文档.md)。

IPTV 前端将 `/iptv` 作为仅用于发现的首页：展示响应式来源切换、分类、搜索、关注、会话级可用状态和频道列表，进入时不会创建播放器或代理会话，也不会默认播放第一个流。自定义 HTTP(S) M3U 地址只能在「设置 → 网络」保存；首页选中 `source=custom` 时从本机设置解析，地址本身不会写入路由、历史或配置包。`iptv_load_playlist` 与 `iptv_check_channels` 都从本机设置读取代理；前者重新获取当前 M3U，后者接受最多 32 个一批的去重频道请求，以 12 路并发和 7 秒单项上限读取首批媒体数据，并额外校验 HLS 清单头、空响应与 HTML 验证页。前端把当前筛选结果限制为 120 个、按 24 个一批调用并渐进合并结果；状态不进入 URL、数据库或配置包，更新/换源即清除。

IPTV 关注使用独立的 `iptv_favorites` SQLite 表，以 `source_id + channel_url` 为主键并持久化频道快照；用户归组存于独立的 `favorite_group_id`，M3U `group_name` 只保留为源元数据。自定义分组定义存于 `iptv_favorite_groups`，删除分组会在同一事务内清空频道引用。`iptv_favorite_list` 接受可选 `source_id`：播放页按源读取，关注页先读取全量缓存，再按当前 `source` 对应的稳定来源 ID 筛选；TanStack Query 会同步更新全量与按源缓存。关注页通过 `view=iptv` 与直播关注分开，频道源和当前自定义分组分别写入 `source`、`group` 查询参数。Shell 只承载关注类型一级页签，频道源 Select 与直播平台/状态 Select 都由关注页侧栏负责；桌面端在左栏顶部显示，移动端显示在分组横条上方。已配置的自定义 M3U 与内置来源由 `playlistSourcesForSettings` 共用构造。自定义分组保留在桌面左栏和移动端横向栏。关注页 Tab 在移动端由 `useHorizontalSwipe` 的双面板 track 跟手切换，点击 Tab 使用短暂淡入平移；IPTV 分组内容复用 `PagePan` 按分组顺序平移。关注列表优先使用最新列表元数据，频道不在最新 M3U 中时回退到保存的快照，因此仍可进入 `/iptv/play`。不同自定义 M3U 用地址派生的本地哈希命名空间隔离，原始 M3U 地址不进入关注表或播放路由；当前配置的自定义来源通过同一哈希读取对应关注快照。配置档案导出 IPTV 分组和内置公开源关注，自定义源关注不离开设备。点击频道才会创建播放会话；播放页返回会恢复进入播放前的 IPTV 发现页或关注页。

## 2.1 录制路径

录制与播放共用结构化 `PlayUrl`。播放器把当前 URL、协议、headers、直播身份和按次离页策略传给 `recording_start`；Rust `RecordingManager` 在进程级持有最多 4 个后台 session，因此路由卸载本身不会结束任务。FLV、HLS 和 MPEG-TS 统一进入 FFmpeg worker，不再通过 `engine` 字段或 `recording_capabilities` 暴露双后端选择；原生 MP4/WebM URL 仅使用最小直连保存。HLS 输入的录制 metadata 和文件协议改写为 MPEG-TS，最终文件扩展名为 `.ts`，但传给 FFmpeg 的源协议仍为 HLS。`continue_on_leave` 默认 `false`，直播间与 IPTV 播放页通过 `RecordingLeaveGuard` 阻止离页并显示三选一确认；显式开启后台继续时不拦截。manager 将运行中与正在收尾的任务分别放在 `sessions`、`finalizing`，停止中的任务继续占用身份和并发名额，删除、重复开始和重复停止不能越过收尾边界。独立 `start_gate` 串行化开始任务的检查与提交；任一步失败都会清理尚未提交的 bundle。每个 session 先写入独立目录的 `metadata.json`，媒体写入 `.part`，收尾成功后同步并原子改名为按「用户名_标题_开始时间」生成的最终媒体文件。

`src-tauri/src/recording_ffmpeg.rs` 实现进程内 Rust FFmpeg worker。桌面目标直接依赖 `ffmpeg-next`，不提供可关闭 feature 或无 FFmpeg 录制 stub；依赖关闭 device/filter/swscale/swresample，只打开 `format`（传递 `codec`），最小直接库集合为 `libavformat`、`libavcodec` 和 `libavutil`。worker 在 `spawn_blocking` 中初始化 libavformat，使用带 interrupt callback 与 dictionary 的输入上下文，传入源 headers、HTTP(S) proxy、探测/读超时和网络重连选项。`recording_start` 在短 DB 锁内读取并归一化 FFmpeg 设置，将读写超时、最大重连延迟和 HLS 分片重试次数作为不可变任务快照传入 worker，运行中的任务不受后续设置修改影响。FLV/MPEG-TS 复制所有音视频轨；HLS master 只选择最佳视频及同 program 音频，并把其他 stream/program 标记为 `AVDISCARD_ALL`，避免持续下载未使用清晰度。packet 先通过共享微秒 epoch 归一起始 DTS；重连时钟回退时，新 epoch 接到已写边界，仍在途的其他轨旧尾包继续使用旧 offset，PTS/DTS 同步平移以保留 B-frame composition delay，随后再按输入/输出 time base 重标并 `write_interleaved`。停止信号打断阻塞读取，写完 trailer 后才发布最终文件。该路径不解码、不编码、不转码。

HLS 清单轮询、variant 选择、分片、AES-128 key、`EXT-X-MAP` 和 `#EXT-X-BYTERANGE` 全部交给 libavformat，不再维护第二套 Rust playlist parser 或本地分片归档器。新录制只发布一个 `.ts`，通用 metadata 事务写入仍以 `.tmp` / `.bak` 和进程级互斥保护。回放服务继续支持历史 `.m3u8` bundle，以免旧录制失去访问入口；该回放兼容分支不参与新直播流录制。本地 HTTP 回放服务按 URL 路径段编码媒体文件名，并在文件边界检查前逐段解码，因此中文或空格文件名可回放且不能借编码路径跨出录制 bundle。

Twitch HLS 在进入 FFmpeg 前使用录制 manager 独立持有的 `StreamProxy` session。代理只负责受限 URL 映射和动态清单入口：短时 token 过期、401/403、广告临时文本/拼接清单或异常 `#EXT-X-ENDLIST` 时，按目标清晰度（必要时最接近档位）重新签名并更新当前 child playlist；分片解析与媒体写入仍全部由 FFmpeg 完成。代理生命周期与录制任务一致，不依赖页面播放器的 proxy session，任务结束后按 recording id 精确销毁。

录制元数据不进入 SQLite，而是与媒体组成可复制的自包含目录；应用退出时先禁止新任务并向所有运行中 session 广播取消，在共享的 15 秒期限内等待媒体 trailer、弹幕关闭和最终 metadata。manager 持有的超时任务会 hard abort，但不在同一进程继续改写 bundle；因此保留 `recording` metadata 和临时文件，由下次启动统一恢复并标记 `interrupted`。正常最终化与异常抢救由 session 级互斥保证只执行一次，metadata 写入失败会显式转为 `failed`。manager 在开始和最终化后通过 `recording-changed` Tauri event 通知前端失效 Query，增长中的时长和体积仍由轮询兜底。启动时扫描当前目录及已知历史目录，恢复 metadata 替换过程中遗留的 `.bak`、清理未发布的 `.tmp`，并将仍处于 `recording` 的 metadata 或残留 `.part` 标记为 `interrupted`。`recording_list`、`recording_start`、`recording_stop`、`recording_delete`、`recording_playback_url`、`recording_danmaku_url`、`recording_storage_info` 和 `recording_set_storage_path` 构成录制 IPC 边界。

直播录制可在 `RecordingStartInput.include_danmaku` 中请求弹幕轨，并用 `continue_on_leave` 记录本次任务是否允许无提示离页；两个字段都通过 `serde(default)` 兼容旧调用。`danmu_rs::dispatch_batches` 以 `live:{site_id}:{room_id}` 作为 source key，将已批处理的事件以 `{ offset_ms, events }` JSONL 行写入 bundle 内的 `danmaku.jsonl`；事件中的后端 `user_id` 通过模型的 `serde(skip)` 保持本机私有。同时启用弹幕和后台录制时，路由 cleanup 将前台连接按 source key 转入 `background_tasks`；批次保留旧 generation，前端会忽略但 sidecar 继续接收。新房间连接、旧 cleanup 乱序、录制收尾和重进同房间都在 manager 锁与二次状态检查下处理，避免串写、重复连接或遗留任务；最后一个对应录制结束后自动 abort 后台连接。媒体复制不做转码，弹幕也不会烧录进视频。

`/recordings` 一级页只负责用户分组和录播 Card 列表：平台筛选写入 `platform` 查询参数，左侧用户分组通过 `site_id + user_name` 聚合，右侧显示当前用户的录播，页面不创建播放器或请求媒体 URL。直播录制上下文分别保存 `LiveRoomDetail.cover` 与 `LiveRoomDetail.user_avatar`，右侧 Card 使用直播间封面，左侧用户图标和二级页主播信息使用主播头像；IPTV 继续保存频道 Logo，旧录制缺少 `user_avatar` 时回退到原有 `cover` 值。已保存 Card 进入 `/recordings/play/:recordingId` 二级播放页，并在返回时恢复平台与用户筛选。该路由由 `Shell` 作为沉浸式播放器页面承载，使用直播页同款顶栏和“左播放器、右信息栏”结构；`RecordingPlayer` 再将本地 loopback URL 交给与直播播放路径相同的 `xgplayer` 核心和协议插件，并复用 `PlayerControls` 的悬浮控制层。录制功能只追加媒体时间轴、倍速选项和回放弹幕设置，不维护另一套传输控件。新 FLV 录制通过 FFmpeg `flvflags=add_keyframe_index` 写入时间到字节位置索引，旧 FLV 首次打开时在后台线程尝试补写同一索引；播放器直接调用 `mpegts.js` 协议内核 seek，使未缓冲的大跨度跳转立即发起 HTTP Range 请求，失败重建窗口缩短为 4 秒。迁移失败时保留原文件并继续使用兼容路径。`recording_danmaku_url` 只返回已结束录制的 sidecar loopback URL；`RecordedDanmakuCanvas` 按 `video.currentTime` 选择当前可见窗口并绘制，跳转后不会补放旧队列或提前聚合未来消息。Canvas 从 `useSettingsStore` 读取直播间同一组弹幕区域、透明度、字号、描边、速度、合并窗口、礼物过滤、醒目留言与屏蔽词设置，渲染层仍与直播使用的 danmu.js 实时适配层分离。

**Twitch 注意：** `TwitchSite` 通过公开 GraphQL 获取直播列表、房间详情和 HLS 播放 token。推荐与分类不使用 Relay `after:` cursor：Twitch 会对所有游标请求执行浏览器完整性校验，没有同会话挑战上下文时返回 `IntegrityCheckFailed`，所以适配器改为沿 `broadcasterLanguages` 翻页。页 1 从不限语言的全局热门分片开始，随后按固定顺序遍历 26 个语言代码；每页并发请求 3 个分片，后端与前端分别按 login 和 `site_id + room_id` 去重。页码直接映射到分片窗口，不维护 cursor 状态；即使冷门分类的一个窗口为空，只要后面仍有分片，`has_more` 就继续为真。该路径仅需公开网页 `Client-ID`，不创建隐藏 WebView，不获取或转存完整性令牌，桌面与 Android / iOS 行为一致。搜索的 `CHANNEL` target 使用可算术生成的 offset cursor，不受这项完整性限制。Twitch 的公开网页 GraphQL 与语言枚举仍可能变化，详见 [Twitch 平台 API 文档](Twitch平台API文档.md)。

斗鱼发送由 `danmu_rs/douyu.rs` 处理：它重验共用的 `danmaku_send_enabled`、房间、文本和 3 秒本机冷却，并使用用户本机保存的完整会话字段。2026-07-27 的受控诊断发现旧路径采用过期 `loginreq` / 聊天载荷、跳过网页登录后协商并忽略 `chatres` / `error`；当前实现已替换为网页对齐的认证状态机、稳定设备身份、统一 WSS 代理与平台回包解析，并已在个人直播间成功验证。运行时仍将本地提交、`chatres(res=0)` 平台接收与正常收弹幕连接的真实回显分开处理；详见[斗鱼平台 API 文档](斗鱼平台API文档.md)。虎牙发送由 `danmu_rs/huya.rs` 处理：同样先重验共用授权，需要扫码或手动保存含数字账号 ID（`yyuid` 或 `udb_uid`）及登录凭据（`udb_n` / `udb_cred` / `udb_biztoken`）的本机 Cookie，解析房间元数据后校验单条、单行且最多 30 个 UTF-16 单元的文本再写入。扫码实现见 `account/huya_qr.rs`。所有发送路径均不得记录、导出或上传 Cookie，也不得对不确定写入自动重试。

`RoomPage` 持有 B 站 / 斗鱼 / 虎牙的房间会话级自动发送调度器，并把同一控制器提供给标题栏、全屏更多操作和移动端房间操作抽屉，因此它不依赖右侧「设置」标签的挂载状态。它完全在前端复用既有的平台单条发送 command 与校验/状态检查，不新增 Tauri command、数据库字段、`AppSettings` 字段或配置导入导出数据。开关、文本和发送间隔只存于会话内；间隔默认 20 秒，可在 10–3600 秒间调整。只有共用本机授权、当前平台 Cookie/可发送状态和文本校验都有效时才能开启。开启时立即发送首段，将换行和连续空白压缩为一个空格，再按 grapheme 拆成最多 20 个用户可见字符且满足平台 UTF-16 上限的片段；单个超出上限的 grapheme 为校验错误。请求串行不重叠，后续发送起始至少相隔当前会话设置的发送间隔，修改间隔会重排下一次发送，末段后回到首段循环。编辑文本、切房（同时清空会话文本）、离开/卸载播放器、关闭应用或任一发送失败都会立即停止本会话并展示原因；失败或未知写入不会自动重试。

标题栏右侧、移动端「更多房间操作」和全屏「更多操作」中的「定时关闭」由 `RoomPage` 持有房间会话级 `useSleepTimer`，各入口共享同一绝对截止时间。它不写入 SQLite、`AppSettings` 或配置导入导出；菜单关闭后仍保留计时。截止时间到达后，Tauri 客户端调用当前窗口的 `close()` 退出应用；浏览器预览没有原生窗口时仅提示不可用。离开当前房间会清理未完成的定时器，避免旧房间的截止时间影响新会话。

前端不会从本机 command 返回值合成弹幕。右侧列表与画面飘屏只应在房间连接收到平台真实 `DanmakuEvent` 回显后显示消息，并保留平台原有样式；一次本机写入结果不是平台确认。斗鱼会区分本地提交、`chatres` 平台接收与真实回显，三者仍不可混为一谈。

设置字段（SQLite / `AppSettings`）：`danmaku_area`、`danmaku_opacity`、`danmaku_font_size`、`danmaku_font_stroke`、`danmaku_speed`、`danmaku_merge_window_seconds`、`danmaku_filter_gifts`、`super_chat_enabled`、`danmaku_shield_words`、`danmaku_send_enabled`、`asr_enabled`、`asr_vad_enabled`、`asr_punctuation_enabled`、`asr_speaker_diarization_enabled`、`asr_hotwords`、`asr_window_seconds`、`asr_font_size`、`asr_translation_enabled`、`asr_translation_from`、`asr_translation_to`、`iptv_custom_m3u_url`。`danmaku_speed` 是普通滚动弹幕的 CSS 像素速度，范围 `50–200 px/s`、默认 `100 px/s`，不影响 `top` 实例中的固定弹幕和 SC。`danmaku_area` 默认 `0.25`，只作为 `scroll` 实例的 danmu.js 原生 `area.end` 使用，`area.start` 固定为 `0`；`top` 实例不读取该设置，始终使用完整高度。`danmaku_opacity` 默认 `0.8` 并同时作用于普通实时飘屏和 SC；无保存配置时 `danmaku_font_size` 桌面默认 `20`、移动默认 `16`，已有保存值保持不变。`danmaku_font_stroke` 为播放器弹幕可选黑色描边宽度，范围 `0–1.5 px`、步长 `0.5 px`、默认 `0`；值为 0 时实时 DOM 移除 `-webkit-text-stroke` 与 `paint-order`，回放 Canvas 跳过 `strokeText`，开启后使用 `paint-order: stroke fill` 避免描边遮住小字号笔画。旧保存值超过新上限时在设置边界收敛为 `1.5 px`。播放器弹幕字重固定为 B 站直播默认粗体 `700`，不再持久化；旧配置中的 `danmaku_font_weight` 会作为未知字段忽略。`danmaku_merge_window_seconds` 为普通聊天合并窗口，范围 `0–30` 秒、默认 `10` 秒，`0` 表示关闭合并重复消息（原 `danmaku_filter_repeats` 开关已随设置移除，旧记录中的该字段会被忽略）；`asr_window_seconds` 保留旧字段名，但语义是设备本地 Zipformer PCM 更新间隔，范围 `0.2–1.0 秒`、默认 `0.2 秒`；`asr_vad_enabled` 控制静音端点检测，默认开启；`asr_punctuation_enabled` 控制按需加载的 CT-Transformer，默认开启；`asr_speaker_diarization_enabled` 控制可选 CAMPPlus endpoint 说话人区分，默认关闭；`asr_hotwords` 是最多 100 个本地领域词，默认空；`asr_translation_*` 保存默认关闭的 Google 翻译授权和 `from` / `to` 语言；`asr_font_size` 为播放器字幕字号，默认 `20`，前端限制为 `12–48`，是可移植显示设置。`danmaku_filter_gifts` 与 `super_chat_enabled` 默认 `true`；`danmaku_send_enabled`、`asr_enabled` 与 `asr_translation_enabled` 默认 `false`。配置导出排除发送授权、ASR 启用/VAD/标点/说话人/热词/更新间隔/翻译设置与自定义 M3U，导入时保留当前设备值，但会合并 `asr_font_size`；旧配置中已移除的字段会被当作未知字段忽略且不再导出。

播放器只使用并持久化 `playback_soft_switch_enabled`。`playback_smart_line_selection` 与 `playback_stall_auto_switch_enabled` 仅作为旧数据库和配置包的兼容字段保留，前端不再显示或读取。逐房间线路记忆使用设备本地 `rlive-playback-line-preferences`，最多保留最近 100 个房间，不进入配置导入导出。

## 5. 本地语音字幕

本地语音字幕仅在 Tauri 桌面客户端启用。`supportsLocalAsr` 同时校验 Tauri runtime 与 `desktop` 平台；Android 和 iOS 不查询或准备模型、不采集 PCM，并隐藏系统设置、房间设置和播放器入口。

前端 `AudioCapturePipeline` 从播放器 `HTMLVideoElement` 创建共享 `MediaElementAudioSourceNode`，优先加载独立 `AudioWorkletProcessor`。Worklet 在 Web Audio 渲染线程保持原声直通、将声道混合为单声道，并按设置中的 `0.2–1.0 秒`更新间隔（默认 `0.2 秒`）生成无重叠分块；主线程只接收可转移的完整 `Float32Array`，再降采样为 16 kHz 单声道 f32 PCM。旧 WebView 不支持 worklet 或模块加载失败时回退到 `ScriptProcessorNode`。little-endian 原始字节经 Base64/Tauri IPC 传输。`useAsrCaptions` 串行调用 `asr_transcribe`，一个任务执行时只覆盖保存最新待办分块，慢设备不会积累无界队列。endpoint final 与当前 partial 分行显示，父容器使用 `white-space: pre-line` 和自然断词，最多保留两行。

字幕翻译只接收 endpoint final，不发送实时 partial、PCM、热词或声纹。`useCaptionTranslation` 使用独立的 4 项有界队列和 12 秒过期时间，不阻塞 ASR；同一 final 批次中的 segment 通过 `google-translate-api-x` 合并为一次 `batchexecute` 请求，重复 `(from, to, text)` 结果进入 160 项 LRU 缓存，单次请求 8 秒超时。原文和译文语言均允许 `auto`。切房、换源、关闭字幕或修改语言会递增 epoch 并丢弃迟到结果。请求经 Tauri HTTP 发出并继承应用代理，capability 只允许 `https://translate.google.com/**`。Google 返回 `429` 时停止当前翻译队列且不自动重试，原字幕继续显示。

Rust `AsrManager` 在用户明确启用后才下载固定的中英双语 Zipformer 压缩包（`511,274,346` 字节）；自动标点开启时再下载 CT-Transformer 中英标点 int8 压缩包（`64,717,756` 字节），说话人开关启用后按需下载 CAMPPlus 中英声纹 ONNX（`28,281,164` 字节）。Windows Release 还会先下载 `221,905,418` 字节的官方 shared runtime，校验固定 SHA-256 后解压到用户数据目录的 `asr-runtime/`；EXE 本身只保留 delay-load 导入，不携带 ASR DLL。模型默认总量约 `550 MiB`，关闭标点时约 `488 MiB`，开启说话人时约 `576 MiB`。下载写入 `.part` 文件并校验精确长度，bzip2/tar 解压在 blocking 线程池执行；状态依次经过 `downloading`、`extracting`、`loading`、`ready`。前端显式处理 `extracting`，因此首次解压不会因状态分支缺失导致页面黑屏。

`NativeAsrSession` 持有一个 `OnlineRecognizer`、一个跨 IPC 分块复用的 `OnlineStream` 和可选的 `OfflinePunctuation`。Windows 和 Linux x86_64 的 `asr_provider` 支持 `auto`、`cuda`、`cpu`；自动模式通过 CUDA Driver API 读取设备 0 的 Compute Capability，要求官方预编译 runtime 支持的 6.1 及以上，并检查对应平台的 CUDA/cuDNN 依赖和随应用提供的 provider 文件；不可用时回退 CPU，并将实际 provider 与原因返回前端。Linux CUDA runtime 已接入但尚未完成完整硬件和发行版测试。不能直接单独加载 CUDA provider 文件，因为 provider 需要由 ONNX Runtime 完成初始化。CUDA provider 会传递给 Zipformer、标点和声纹模型；VAD 开关控制识别器的 CPU 静音端点规则，当前没有独立 VAD ONNX 会话。无热词时 Zipformer 使用 `greedy_search`，有热词时使用 `modified_beam_search` 并读取原子替换的本地 hotwords 文件；关闭时仍保留 20 秒最长语句边界。标点关闭时不创建标点 native 对象。可选 `NativeSpeakerSession` 对每句 final 的缓存 PCM 提取 CAMPPlus embedding，以 `0.55` 余弦阈值和 `0.68` 切换滞回维护最多 8 个匿名说话人；少于 `0.6 秒` 的短句沿用最近标签，只有 final 携带匿名 `speaker_id`。切房、切换媒体源或关闭字幕会重置 stream、PCM 和聚类编号。CPU provider 下识别最多使用 8 个线程，标点与声纹最多使用 2 个线程；同一 native 会话由互斥锁串行驱动。

`asr_enabled`、`asr_vad_enabled`、`asr_punctuation_enabled`、`asr_speaker_diarization_enabled`、`asr_hotwords`、`asr_window_seconds` 和 `asr_translation_*` 是设备本地设置，不随配置包导入导出；`asr_font_size` 是可移植的显示设置。模型文件、hotwords、PCM、embedding、聚类质心与字幕均不进入 SQLite。完整说明见[本地语音字幕](本地语音字幕.md)。

## 7. 构建与交付

- 开发：WSL `/home/.../rLive`  
- 运行：Windows `scripts/windows-sync.conf` 中 `WINDOWS_SYNC_PATH` 指定目录 → `rlive.exe`
- 一键：`./scripts/build-windows-from-wsl.sh`  

Windows 构建脚本使用 MSVC + sherpa-onnx shared import library，并把 `sherpa-onnx-c-api.dll` 配置为 delay-load。构建阶段仍会暂存 CUDA-capable ASR runtime 以供链接，但发布工作流在打包前删除这些 ASR DLL，验证 EXE 会在缺少 ASR runtime 时正常启动；首次启用字幕时由应用下载、校验并加载运行库。FFmpeg 不使用这一延迟下载机制：`scripts/prepare-windows-ffmpeg.ps1` 参考 rust-ffmpeg 的 MSVC CI，下载固定为 FFmpeg 9.0.1 且校验 SHA-256 的 Gyan `full_build-shared` SDK，设置 `FFMPEG_DIR`、`LIBCLANG_PATH` 和 DLL 搜索路径。`avformat`、`avcodec`、`avutil`、`swresample`、GPLv3 许可证与上游构建说明会放在 EXE 同目录，NSIS、MSI 和便携 ZIP 都必须携带这些文件。Linux x86_64 默认使用 `sherpa-onnx-v1.13.4-linux-x64-gpu.tar.bz2`，`.deb` 把 shared runtime 安装到 `/usr/lib/rlive`，另有包含 `rlive` 与 `lib/` 运行库（rpath 指向 `$ORIGIN/lib`）的便携 ZIP；主机使用 CUDA 时仍需 CUDA 11.x/cuDNN 8.x。Linux CUDA 路径尚未完成完整硬件和发行版测试。macOS（Apple Silicon 与 Intel）使用静态链接的 sherpa-onnx（CPU 推理），ASR 运行库直接编入二进制，发布 DMG 无需运行时下载运行库，也不做 Apple 签名与公证。Android 通过 Tauri CLI 使用 NDK 工具链；Rust target 通过条件编译排除 ASR module、commands、state 及 `sherpa-onnx`、ONNX Runtime 和模型解压依赖，移动端不暴露字幕功能，也不会下载字幕模型。命令与依赖见[Android 开发与构建](Android开发-Windows.md)。

Windows、Linux 和 macOS 桌面目标固定引入 `ffmpeg-next = 9.0.0`。构建环境需要 ABI 匹配的 headers、link libraries、`pkg-config` / `FFMPEG_DIR` 和供 bindgen 使用的 libclang；运行环境必须装载与构建时匹配的 `libav*` 及传递依赖。缺失动态库会在进程装载阶段失败，不能通过 IPC 回退。Windows 已固定 Gyan GPLv3 shared SDK 并将运行库与许可说明纳入三种交付物；Linux/macOS 正式发布仍需固定对应 SDK、配置 RPATH 或 install name，并完成许可证审计。

Release：`lto = "thin"`、`panic = "abort"`，故后端 panic 会导致进程退出，站点解析必须避免未处理 panic。
