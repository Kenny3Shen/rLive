## 结论（原始基线）

**弹幕飘动本身不是瓶颈**——2026-10-12 把滚动弹幕改为合成器动画（WAAPI）之后，桌面在屏 575 条弹幕
仍保持 171 FPS，主线程 Task 只占 701 ms/s，其中飘动动画的样式重算 309 ms/s 是主要构成。

**真正的瓶颈是 `DanmakuPanel` 侧栏列表**。它每条消息挂一个 Base UI `Popover` + `useDanmakuActions`
（3 个 `useState`、3 个 `useSettingsStore` 订阅、一个 `useQuery`），单行成本是纯文本行的约 5 倍。
在 Android 上，**25 条/秒**就把主线程吃到 54%（Script 539 ms/s），FPS 掉到 45.4；上滚展开到 1200 行
窗口后 FPS 只有 16.8。

次要瓶颈：渲染层每帧对每条在屏弹幕做样式重算（与条数线性）、`remove(id)` 的 O(分组×时间轴) 扫描、
VOD `setComments` 的全量时间轴重建。

## 一、链路总览

```
Rust 站点 WS → DanmakuEventSender.try_send → dispatch_batches（50ms ticker / 512 条上限）
  → app.emit("danmaku-batch") → eventBus 单监听器校验 → 扇出到各 sink
      ├─ LiveDanmaku.renderEvents → danmakuCommentFromEvent → DanmakuRenderer.emit
      │     → 原生 danmaku 2.0.10 rAF：轨道分配 + WAAPI 位移
      └─ DanmakuPanel 订阅 → 有界队列 → rAF/定时冲刷 → React 列表
```

| 环节 | 实测 | 判定 |
| --- | --- | --- |
| Rust 批处理（50ms / 512 条 / 2048 容量 `try_send`） | 未观测到堆积 | 合理，不动 |
| `eventBus` 校验 + 扇出 | 单监听器、预校验、异常隔离 | 合理，不动 |
| `LiveDanmaku.renderEvents` | 批内 `activeScrollCount` 累加已避免 O(n²)（[LiveDanmaku.tsx](../../src/features/room/danmaku/LiveDanmaku.tsx) 第 414 行） | 合理，不动 |
| `DanmakuRenderer.emit` | **1.74 µs/条**（1200 条/秒下 10 秒共 5754 条，累计 10 ms） | 不是瓶颈 |
| `DanmakuRenderer` 每帧渲染 | 在屏 575 条时 Style **309 ms/s** | **次要瓶颈** |
| `DanmakuPanel` 列表行 | 单行约 2 ms 主线程（生产）；Android 25 条/秒即掉到 45 FPS | **首要瓶颈** |

## 二、瓶颈一：`DanmakuPanel` 列表行（首要）

### 根因

每条消息渲染的组件链（[DanmakuPanel.tsx](../../src/features/room/DanmakuPanel.tsx)）：

- 第 124 行 `SelectableDanmakuRow`：`useState` + `useDanmakuActions`
- 第 144 行 `useDanmakuActions`（[useDanmakuActions.ts](../../src/features/room/danmaku/useDanmakuActions.ts)）：`useQueryClient()`、3 个 `useState`、3 个 `useSettingsStore` 订阅、1 个 `useQuery`
- 第 169 / 178 行 `Popover` / `PopoverTrigger`：Base UI 的 `useOpenStateTransitions`、`useTriggerDataForwarding`、`useHoverReferenceInteraction`、`useRenderElement`、`mergeInto`、`useStableCallback`
- 第 617 行 `items.map()`：**全量渲染**，无虚拟化；配合第 38 行 `MAX_PER_FLUSH = 32`，每个冲刷帧最多挂 32 个新 `Popover` 子树

### 实测：行实现对照（桌面生产构建，150 条/秒，300 行窗口）

| 行实现 | Script ms/s | Style ms/s | Layout ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: |
| 真实 `DanmakuPanel` 行 | **293.7** | 15.5 | 15.4 | 391.5 |
| 精简行（纯 `div` + 文本，同 300 行、同追加节奏） | **59.8** | 43.0 | 91.8 | 281.8 |

Script 差 **4.9 倍**，折算单行约 **1.96 ms** vs **0.40 ms**。精简行 Style/Layout 反而更高（缺 `will-change`
与绝对定位），说明差距全部来自 React 协调与 Base UI 组件，**不在文本排版**。

### 实测：弹幕层 vs 面板（桌面生产构建，逐级提升事件率）

| 事件率 | 弹幕层在屏 | 层 Script ms/s | 层+面板 Script ms/s | 面板增量 |
| ---: | ---: | ---: | ---: | ---: |
| 25 条/秒 | 9 | ~12 | 167.5 | **+155** |
| 100 条/秒 | 11 | ~19 | 252.4 | **+233** |
| 400 条/秒 | 10 | ~29 | 291.8 | **+263** |
| 800 条/秒 | 11 | ~36 | 195.1 | **+159** |

弹幕层的 Script 几乎不随事件率变化（9→36 ms/s，因为在屏数被轨道准入锁在 ~10 条），而面板部分恒在
150~260 ms/s——**面板是唯一随事件率增长的项**。

### 实测：每次冲刷的提交延迟（桌面 dev React，30 行/批）

12 批连续注入，每批 30 行，批间 150 ms：中位 **154.8 ms**，全部落在 153~176 ms。即每批 30 行要花
~155 ms 主线程。**该数字含 dev React 开销**（生产折算见上表约 2 ms/行），仅用于说明提交延迟的稳定性。

### 实测：窗口放宽到 1200 行时崩塌（桌面生产构建）

| 场景 | 行数 | FPS | p95 | 卡顿帧 | Script ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 钉住底部 | 300 | 60.0 | 16.7 | 0 | 248.3 | 352.2 |
| 上滚（保留历史） | **1 200** | **36.5** | **50.1** | **86** | **904.1** | 994.2 |

`DANMAKU_LIST_MAX_SCROLLED_UP = 1_200`（[listWindow.ts](../../src/features/room/danmaku/listWindow.ts) 第 21 行）
意味着读者一上滚，React 就要在每次提交里协调 1200 个带 `Popover` 的行。

### 实测：Android 上更早崩塌

| 场景 | 事件率 | 行数 | FPS | p95 | max | 卡顿帧 | Script ms/s | Task ms/s | longtask |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 仅弹幕层 | 1 000 条/秒 | — | 59.3 | 16.7 | 16.8 | 0 | 152.3 | 430.8 | 0 |
| 层 + 面板 | 25 条/秒 | 300 | **45.4** | 49.9 | 83.3 | 89 | **538.7** | 797.5 | 2 次 / 51 ms |
| 层 + 面板 | 200 条/秒 | 300 | **34.4** | 66.7 | 100 | 117 | **640.9** | 864.4 | 74 次 / 4 371 ms |
| 层 + 面板（上滚） | 100 条/秒 | 975 | 46.3 | 50.1 | 100 | 38 | 539.7 | 792.8 | 24 次 / 1 473 ms |
| 层 + 面板（上滚） | 300 条/秒 | 1 200 | **16.8** | **233.4** | 267 | 54 | 714.6 | 942.5 | 25 次 / 3 662 ms |

对比第 1 行与第 2 行：**Android 上弹幕层 1000 条/秒完全无卡顿（59.3 FPS、0 卡顿帧）**，
但加上侧栏面板后 25 条/秒就出现 89 个卡顿帧。面板在 Android 上占主线程 54%~64%。

### 原始优化建议

1. **虚拟滚动**：项目已在用 `@tanstack/react-virtual`（`src/features/history/historyVirtual.ts`）。
   行高近似固定（`leading-relaxed` + `py-1`），`estimateSize` 可用常量，无需测量。
2. **把交互从行内提升到面板级单例**：列表只渲染纯文本行；点击时事件委托把 `id` 交给面板顶部的一个
   `Popover`，菜单锚定到点击坐标。这一项单独就能消掉 `SelectableDanmakuRow`、`PopoverTrigger`、
   `useDanmakuActions`、`DanmakuEmojiText` 的全部每行开销。
3. 虚拟化后 `DANMAKU_LIST_MAX_SCROLLED_UP` 与 `scrollTopAfterDanmakuListTrim` 的滚动补偿逻辑可以
   **整体删除**——虚拟滚动天然没有"移除顶部行导致位移"的问题。这是净减代码。

预期：Script 从 250~290 ms/s 降到接近精简行的 60 ms/s；1200 行窗口从 36.5 FPS 恢复到 60；
Android 从 34~45 FPS 恢复到 60。以上是原始预期，**不等同于下述实现已达到的实测数字**。

### 已落地实现

`DanmakuPanel` 已改为 `@tanstack/react-virtual` 可变高度列表，保留既有批量摄入和隐藏页签队列：

- **只挂载可视区及前后各 6 行缓冲**。列表行仅渲染用户名和原始文本；普通消息使用原生 `button`，
  系统消息不可选择。列表不再创建 `DanmakuRichText` / `DanmakuEmojiText`，平台表情以正文中的文字表示，
  视频上的富文本弹幕层不变。保留用户名色彩、自发消息边框和长文本换行。
- **菜单最多一个，按需挂载**。面板通过 `data-danmaku-id` 事件委托选择目标，单个 `Popover` 锚定点击坐标；
  键盘激活锚定行中心。复制、收藏、`+1`、屏蔽仍复用 `useDanmakuActions`，仅打开菜单才挂载查询与设置订阅。
  目标改变重建菜单状态，旧请求结果不污染新目标；Escape 后归还行焦点，隐藏/换房/停用/目标被淘汰时关闭。
- **数据与 DOM 分开限额**。钉底与上滚统一保留最新 1200 条，仍有界而非无限保存；
  删除 `DANMAKU_LIST_MAX_SCROLLED_UP`、钉底 300 条的分支和 `scrollTopAfterDanmakuListTrim`。
  使用稳定行键与 `anchorTo: "end"` 保持仍被保留的阅读锚点，锚点本身淘汰后退到保留窗口开头。
  淘汰的数据同时清理测高缓存。旧的整段 `scrollHeight` 差值补偿、两次状态提交均已删除。
- **修正原始建议中的两个假设**：行会因正文长度和视口宽度换行，所以不能仅用常量高度定位，
  估高为 33px（14px × 1.625 + 8px 内边距 + 2px 边框，按虚拟器测高规则取整），只对挂载行实测；
  复测发现原 30px 估高会让每批普通单行也触发测高修正，已校准。虚拟化本身不保证顶部裁剪不跳动，仍需要稳定键锚定。
  底部跟随由提交后的同步 `scrollTop` 更新完成，不启用 `scrollToEnd` 的跨帧重试，避免快速上滚被拉回。

### 剩余 P0：设备预算（已移除）

> **该实现已从代码中移除**，以下保留为历史记录。
> 曾实现：普通滚动弹幕的设备上限为桌面 300 条；移动端，或有效 `hardwareConcurrency ≤ 4`、
> `deviceMemory ≤ 4` 的低端设备为 150 条。最终预算为 `min(设备上限, max(120, 轨道数 × 12))`。
> 缺少或非法硬件信息不触发硬件降档，移动端判据独立生效。该上限只阻止新的普通滚动弹幕进入，
> 不主动移除已经在屏弹幕；SC 和自己的弹幕继续绕过普通滚动上限。实现位于 `danmakuAdapter.ts`。
> 移除后回退到 `DANMAKU_MAX_ACTIVE_COMMENTS = 800`（无设备判据），VOD 和 renderer 原有总防线不变。
> 本节之后的 P0 复测数据均采集自含该预算的构建，**在屏峰值与 4× 节流 FPS 不可与当前构建直接比较**。

### 主要发现

基线虽然在全屏中看不到弹幕列表，却仍挂载了 5876 个带 `content-visibility:auto` 的 `li`。
播放期间，Chromium 持续执行 `IntersectionObserverController::computeIntersections`。
这里是浏览器对 `content-visibility` 的内部可见性计算，不是应用自行创建了 5876 个 JS observer。

单独 5 秒 Trace 中，该同名事件的累计耗时为 **484.1 → 15.7 ms/s**（基线 → 当前）。
早期在基线页面临时去掉行级 `content-visibility` 也使该事件不再进入热点，形成独立定位证据；
但单纯去掉样式仍留下全部行的布局与 DOM 成本，因此最终改成虚拟列表。

> **口径纠正：**早期临时 Trace 脚本把嵌套的 `RunTask` 与 `ThreadControllerImpl::RunTask` 相加，
> 曾输出「主线程忙碌约 1500 ms/s」，该汇总无效且已弃用。现在主线程总耗时只引用 CDP
> `TaskDuration`；Trace 表示单种事件的 inclusive duration，不跨事件相加，也不称为 self time。
> Trace 与下表的 Performance 采样分别执行，避免混入追踪本身的额外开销。

## Android 120Hz 实测：高刷下的表现

### 场景与控制条件

同一台模拟器以 `-vsync-rate 120 -no-snapshot-load` 冷启动，并在系统侧设 `peak_refresh_rate` /
`min_refresh_rate` = 120.0。实测确认 `dumpsys display` 的 `mActiveSfDisplayMode.vsyncRate=120.00001`、
`presentationDeadlineNanos=8333333`，SurfaceFlinger `activeMode` 为 `vsyncRate=120.00 Hz`。
AVD `config.ini` 的 `hw.lcd.vsync` 保持 60，采样结束后已 `delete` 两项系统覆盖（重启即回 60Hz）。

真实播放部分沿用上一节的单构建 A/B（基线 `407fd71d` / 当前 `VideoDanmakuList`）、同一稿件与
41–49s 采样窗口；直播部分沿用生产夹具的 `layer` / `both` / `bus` 三档。

### 关键机制：刷新率跟随内容，跨对照不能直接比 FPS

同一页面里只有 rAF 循环时，帧间隔中位数为 **16.7ms**（60Hz 档）；加入一个**真的被绘制**的
微小合成动画后变为 **8.4ms**（120Hz 档）。Android 的显示节奏跟随内容，没有持续动画时就退回低档：

| 注入内容 | FPS | 中位帧间隔 | 120Hz 档占比 |
| --- | ---: | ---: | ---: |
| 无注入 | 64.2 | 16.7ms | 13% |
| 仅 `opacity`（不产生绘制） | 65.0 | 16.7ms | 15% |
| 带背景色（产生绘制） | 92.7–96.1 | 8.4ms | 71–75% |

由此得出两条口径要求：**不能用「隐藏弹幕后的 FPS」当作对照基准**（隐藏后系统自己降档）；
也不能用无背景的动画元素去固定节奏（它不产生绘制，拉不起刷新率）。下面的对照因此分两种口径：
`pace=off` 暴露系统自适应行为，`pace=on` 注入一个 2×2 的已绘制合成动画把节奏固定在 120Hz 档。

### 真实 VOD 单构建 A/B（固定 120Hz 节奏）

| `on` | 基线 | **half** | 68.0–68.9 | 16.6ms | 59.9–60.9% | 29.4–32.5 | 33.9–34.5 | 20.0–20.7 | **878.7–882.1** |

关闭弹幕（`off`）后基线仍只有 60Hz 档——因为 `off` 只隐藏弹幕层，隐藏的全量列表仍存在。
`masked` 两版都满帧，说明去掉那部分可见性计算后基线也不再受限。

读表时注意 **Style 一列当前版本反而更高（44–46 vs 34 ms/s）**，这不是倒退：当前版本真的在按 120Hz
节奏送帧，单位时间内的动画样式重算次数约是 60Hz 档的两倍；基线正是因为主线程被占满而没能升档。
所以这里要比的是「能否维持节奏」与「Task 余量」，不是 Style 绝对值。

**这是跳帧而不是系统降档**：同场景轮询 SurfaceFlinger 8 次全部为 `vsyncRate=120.00001`，
而 rAF 中位间隔为 16.6ms（120Hz 档仅 44%）。即刷新率仍是 120Hz，主线程跟不上。

固定节奏下的 Trace 对照（5s，同名事件 inclusive duration，不可跨事件相加）：

| 版本 | `computeIntersections` | `RunTask` |
| --- | ---: | ---: |
| 基线 | **666.5** | **920.3** |
| 当前 | **18.5** | **342.1** |

未固定节奏的对照方向一致（基线 `computeIntersections` 690.0 / `RunTask` 904.7，当前 22.1 / 301.6）。

## 三、瓶颈二：渲染层每帧样式重算（次要）

### 根因

滚动弹幕的位移由 WAAPI 合成器动画承担（方向正确），但原生 `danmaku` 引擎的 rAF 仍每帧遍历
`runningList`：调用 `allocate` / `willCollide` 做轨道准入，给每条弹幕计算 `comment.x`，并在我们的
`render` 钩子里调用 `syncMotion` 比对动画与媒体时钟。同时每条弹幕带 `will-change:transform`
（[danmakuRenderer.ts](../../src/features/room/danmaku/danmakuRenderer.ts) 第 665 行）。
（该属性的真实作用见下文「P2 回测」：图层由 WAAPI 动画提升，它不是必需的。）

### 实测：在屏密度曲线（桌面 dev，1920×1080，14px 字号，面积 100%）

| 在屏条数 | FPS | Script ms/s | Style ms/s | Task ms/s |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 172.1 | 1.8 | 0 | 13.8 |
| 51 | 172.8 | 7.4 | 21.0 | 65.8 |
| 100 | 171.3 | 11.5 | 40.0 | 106.7 |
| 200 | 172.9 | 23.2 | 87.9 | 216.1 |
| 302 | 172.7 | 39.3 | 135.4 | 331.5 |
| 401 | 170.5 | 47.1 | **185.2** | **434.0** |

Style 与条数严格线性（约 0.46 ms/s per 条）。注意 **FPS 未下降**（动画走合成器），但主线程被占用
意味着**留给解码、IPC、React 的余量被吃掉**——一旦叠加 CPU 受限或页面上有其他工作，就会掉帧。

### 实测：CPU 节流下的崩塌（桌面 dev，在屏 ~500 条）

这是**低端设备（含移动端中低端机）的真实风险模型**：`MAX_ACTIVE = 800` 允许的密度在 4× 节流下
只能跑 41 FPS。

### 实测：动画实现对照（同一批 400 个绝对定位节点）

| 实现 | 在屏 | FPS | Script ms/s | Style ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| **现状：WAAPI + `will-change`** | 431 | 171.5 | 65.7 | **239.5** | 551.3 |
| WAAPI，动画 `pause()` | 419 | 170.4 | 54.7 | **21.9** | 143.7 |

| 纯 CSS `@keyframes`（无 DOM 引擎） | 400 | 172.5 | 2.7 | **308.5** | 552.8 |

判读：

- **`pause()` 使 Style 从 239.5 掉到 21.9 ms/s** → 这 240 ms/s 完全来自"N 个运行中动画"的每帧动画样式
  计算，与 JS 无关（Script 几乎不变）。
- **回退到原生每帧写 `transform` 后 Style 飙到 625.6、FPS 掉到 96.9** → 2026-10-12 的合成器动画改造
  **方向正确，不要回退**。
- **纯 WAAPI 只有 130.4，DOM 引擎却是 239.5** → 差值 ~109 ms/s 来自引擎每帧对每条弹幕的
  `comment.x` 赋值、`allocate`/`willCollide` 计算，以及 `will-change` 的图层开销（见「P2 回测」，
  后者的开销已被证伪）。
- **CSS `@keyframes` 比 WAAPI 更差（308.5 vs 130.4）** → 不要用 CSS 关键帧替换 WAAPI（每节点都要解析
  关键帧变量）。在普通 Chromium 上同样成立（WAAPI 54.5 vs CSS 110.0）。

### 实测：合成开销（Tracing，在屏 382 条）

| 事件 | ms/s |
| --- | ---: |
| `Paint` | 7.4 |
| `RasterTask` | 未出现在采样中（舞台只走合成） |
| `UpdateLayer` | 11.0 |
| `PrePaint` | 42.5 |
| `Layerize` | 45.0 |
| `PaintArtifactCompositor::Update` | 44.7 |
| `Commit` | 54.1 |
| `AnimationHost::TickAnimations` | 223.6 |
| `LocalFrameView::UpdateStyleAndLayout` | 326.2 |

`will-change:transform` 一度被认为把每条弹幕提升为独立合成层，575 条时 `Layerize` + `PrePaint` + `Commit`
合计约 140 ms/s，而它换来的 `Paint` 收益只有 7.4 ms/s。**A/B 实测去掉 `will-change` 无改善**
（Style 254.9 vs 248.8，Script 69.6 vs 74.1）；后续 P2 回测进一步确认层数由 WAAPI 动画提升，
与该属性无关。当前 Style 成本不来自它——**建议先做面板重写，再回来评估渲染层成本**。

### P2 回测：合成层策略（负结果）

P0/P1 落地后在屏数回到约 750，具备回测条件。夹具新增 `willChange` 维度
（`node` 现状 / `none` 去掉 / `group` 移到组容器），用 `!important` 样式表覆盖节点内联值，
不改生产代码；`prepare` 阶段核对 `getComputedStyle` 实际值，覆盖失效即报错。

| 平台 | 对照 | 策略 | 在屏 | 合成层总数 | 运行中 WAAPI 动画 | FPS | Style ms/s |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| WebView2 | 同页切换 | `node` | 377 | 374 | 367 | 107.0 | 239.6 |
| WebView2 | 同页切换 | `none` | 376 | **382** | 375 | 108.4 | 250.8 |
| WebView2 | 同页切换 | `node`（复归） | 386 | 386 | 379 | 109.2 | 249.3 |
| Chromium | `node` vs `none`（3 轮中位） | `node` | 756 | — | — | 49.3 | 238.2 |
| Chromium | `node` vs `none`（3 轮中位） | `none` | 756 | — | — | 41.8 | 240.3 |
| Chromium | `node` vs `group`（3 轮中位） | `node` | 756 | — | — | 60.1 | 135.0 |
| Chromium | `node` vs `group`（3 轮中位） | `group` | 756 | — | — | 60.1 | 138.4 |
| Android | `node` vs `none`（3 轮中位） | `node` | 756 | — | — | 30.4 | 255.9 |

注意两组 Chromium 行来自不同轮次（同轮内可比，跨轮绝对值不可相减）；WebView2 的同页切换是唯一
把密度锁定的对照。

判读：

- **P2 的前提不成立**。同页切换时合成层数跟随「运行中 WAAPI 动画数」（相差恒定的 7 层非弹幕层），
  与 `will-change` 无关（去掉后反而多 8 层）。CDP `LayerTree.compositingReasons` 显示每条弹幕层同时带
  `ActiveTransformAnimation` 与 `WillChangeTransform`——图层是**动画**提升的，`will-change` 只是
  附加了一个原因。把提示移到组容器因此不可能减少层数。
- **性能无差异**。同页对照 FPS 107.0 / 108.4 / 109.2，Style 239.6 / 250.8 / 249.3，全在噪声内；
  Chromium 与 Android 的交替轮次同样无稳定差异（`node` vs `group` 在 Chromium 上都是 60.1 FPS）。
- **但 `will-change` 不是死代码**。删除 `Element.prototype.animate` 强制走「原生每帧写 `transform`」
  的回退路径（即第 661 行注释描述的场景）后，去掉它出现明确劣化：Style 53.8 → 158.7 ms/s、
  Task 212.9 → 318.9 ms/s（重复轮 96.9 → 235.8）。它只在 WAAPI 不可用时生效，而那种情况下
  它正是「只走合成、不逐帧重绘光栅」的唯一保障。该回退对照在 headless Chromium 上采集（无 GPU），
  层数不代表真实合成，但 Style/Task 的相对差异有效。
- 结论：**保留现状，不做 P2**。生产代码仅更新注释，说明该属性的真实作用与适用路径。

原始数据归档：[P2 回测数据](../bench/danmaku-p2-2026-10-13.json)。

### 优化方向

1. **设备分档已移除**。`danmakuMaxActiveComments` 一度按移动端或硬件档位限制普通滚动弹幕（桌面 300，移动端及低端设备 150，与轨道预算取小值、最低 120），现已回退为无设备判据的 `DANMAKU_MAX_ACTIVE_COMMENTS = 800` 总防线。如需重新引入，应先解决此前 Android 复测中「在屏上限生效但 FPS 未改善、p95 反而升高」的问题。
2. **合成层策略（P2，已回测为负结果）**：`will-change` 从节点移到组容器不会减少层数，因为图层
   由 WAAPI 的活跃 transform 动画提升；在屏 750 时三种策略性能一致。已保留现状。

## 四、瓶颈三：`remove(id)` 的 O(分组 × 时间轴) 扫描

### 根因

[danmakuRenderer.ts](../../src/features/room/danmaku/danmakuRenderer.ts) 第 209 行的 `remove` 对每个分组做两次
全量 `filter`，并在其中调用 `definitions.get()`；`LiveDanmaku.removeRecord` 另外用 `indexOf` 线性扫描
`recordOrderRef` 与 `superChatIdsRef`。

### 实测（原始基线）

| 时间轴规模 | 移除 20 条耗时 |
| ---: | ---: |
| 60 000 条 | **63.3 ms** |

一次 63 ms 的主线程阻塞。触发路径：SuperChat 到期计时器（每条一个 `setTimeout`）、屏蔽用户
（`useLayoutEffect` 里对全部记录循环）、面板的 `+1`。VOD 中调用密度低，但直播 SC 集中到期时会连续触发。

### 优化方向（已落地）

`remove(id)` 改为 O(1)：记墓碑（`removedIds`）并从在屏列表摘出，不扫描时间轴；
时间轴里的条目由原生推进游标时经 `setup` 钩子跳过，墓碑累积到 `COMPACT_THRESHOLD = 512` 时
一次性压实（`compact()`）。压实是唯一需要 O(时间轴) 的操作，且会在 `appendComments` 入口再触发一次。

### P1 复测（同一构建 A/B，`f2c05886` 基线 vs 当前）

夹具：`tests/browser/danmaku-timeline-bench.ts`（共享主体）+ `tests/danmaku-timeline-ab.browser.js`（A/B runner）。
基线与当前实现编入同一 bundle，同一页面内前后对照；`setComments` 按规模点取 best-of-2，
每个规模点用新渲染器，避免上一条时间轴的 GC 成本污染下一次调用。
`remove` 均为 6 万条上移除 20 条、3 轮取中位数。

| 平台 | 指标 | 基线 | 当前 | 变化 |
| --- | --- | ---: | ---: | ---: |
| Windows Chromium | remove 20 条 @60k（中位） | 131.9 ms | **0.1 ms** | 1319× |
| Windows WebView2（主窗口） | remove 20 条 @60k（中位） | — | **0.1 ms** | — |
| Android 16 x86_64（4 核 / 2GB） | remove 20 条 @60k（中位） | 209.3 ms | **0.2 ms** | 1047× |

墓碑把尖峰从每次 `remove` 移到阈值触发的压实：连续移除 4 000 条（每 512 条压实一次）的
单次最慢一步，Windows Chromium 从基线 146.9 ms 降到 **20.4 ms**，Android 从 36.6 ms 降到 **6.0 ms**。
压实不是零成本，但它只发生在墓碑累积处，且峰值仍低于基线的每次调用。

## 五、瓶颈四：`setComments` 全量时间轴重建（VOD）

### 根因

[VideoDanmakuLayer.tsx](../../src/features/video/VideoDanmakuLayer.tsx) 第 230 行每次 `comments` 变化都调用
`renderer.setComments()`，而 `setComments` 会重建**全部**分组的 `comments` 数组（`grouped` / `seen` /
`sort` / `lowerBound`）。VOD 分段加载的语义是**追加**，不是替换。

### 实测（单次 `setComments` 中位耗时）

| 时间轴规模 | 耗时 |
| ---: | ---: |
| 10 000 | 5.8 ms |
| 30 000 | 19.1 ms |
| 60 000 | 40.4 ms |
| 120 000 | **75.2 ms** |

分段加载累计（每次 +6 000 条）：

| 段 | 时间轴 | 耗时 |
| ---: | ---: | ---: |
| 1 | 6 000 | 3.0 ms |
| 2 | 12 000 | 4.2 ms |
| 3 | 18 000 | 5.7 ms |
| 4 | 24 000 | 7.7 ms |
| 5 | 30 000 | 10.0 ms |
| 6 | 36 000 | 17.9 ms |
| 7 | 42 000 | 13.0 ms |
| 8 | 48 000 | 16.5 ms |
| **累计** | | **78 ms** |

单次不致命，但它是纯 O(N log N) 重建，**随视频时长线性增长**——10 万条以上的长视频会变成肉眼可见的卡顿。

### 优化方向（已落地）

renderer 新增 `appendComments(comments)`：只对未登记的 id 做 `groupFor` + 有序插入，
常见路径（新段接在末尾且全在未来）整批 `push`，不动游标也不重建数组；乱序或含过去时间时
整批归并 + `lowerBound` 重定位游标，语义与 `setComments` 一致（过去的不补投）。
内部用 `timelineIds` 去重，`setComments` 整体替换时整个 Set 一次换掉。
`VideoDanmakuLayer` 同时缓存每条目转换结果（按 `fontSize|fontStroke|opacity|reducedMotion` 为 key），
并在“已推送 id 全部存在且对象身份不变”时走 `appendComments`，否则回退 `setComments`。

### P1 复测（同一构建 A/B）

### 稳态无回归（同一构建 A/B，Windows WebView2 主窗口）

P1 改的是时间轴操作的延迟尖峰，不应影响稳态帧率。用 P0 夹具（真实组件、原生 IPC）复跑确认：

## 六、已确认**不是**瓶颈的部分

| 环节 | 证据 |
| --- | --- |
| `DanmakuRenderer.emit` | 1 200 条/秒注入时 **1.74 µs/条**，10 秒共 5 754 条累计 10 ms |
| `canAttach` 的 O(n²) | 在屏 550 条时 32 条候选迭代 18 143 次，但自耗时仅 **0.1~0.2 ms/s**（插桩）；一帧 12~14 ms 基本被 `emit` 的 DOM 创建吃掉。**当前不是主因**，但迭代次数随在屏数线性增长，属已埋下的地雷 |
| 后端批处理 | 50 ms ticker / 512 条上限 / 2 048 容量 `try_send`，前端侧无堆积 |
| 轨道分配 `allocate` / `willCollide` | 600 条/秒下合计约 147 ms / 6.2 s（dev），可接受 |
| `LiveDanmaku` 事件摄入 | 批内 `activeScrollCount` 累加已避免 O(n²)；`eventBus` 单监听器 + 预校验 + 异常隔离 |

## 七、重写优先级

| 优先级 | 对象 | 方案 | 预期 |
| --- | --- | --- | --- |
| **P0（已落地）** | `DanmakuPanel` 列表行 | 虚拟滚动 + 面板级单例交互；单行估高校准到 33px | 生产 Chromium 上滚 Task 159.0 → 37.4 ms/s；Android 60 FPS 目标未证实 |
| **P0（已落地，后已回退）** | 渲染层在屏预算 | 移动端/低端设备 150，桌面 300，与轨道预算取小值（见本轮复测） | 高密度 Chromium 4×：25.2 → 60.1 FPS；WebView2 4×：14.8 → 78.5 FPS；在屏约 750 → 300。**该预算已移除，此行为历史数据** |
| **P0（已落地）** | `VideoDanmakuList` 全量列表 | 虚拟化 + 非活动零行，保留后台前插阅读锚点 | Android 真实 VOD 单构建 `on` Task 734.5–833.5 → 296.2–296.5 ms/s；当前 56.3–56.6 FPS，非稳定 60 |
| **P0（已验证）** | 120Hz 显示节奏 | 上项收益在高刷下同样成立 | 固定 120Hz 节奏：基线掉回 60Hz 档（Task 878.7–882.1、`computeIntersections` 666.5），当前满帧（Task 249.8–287.3、18.5） |
| **P1（已落地）** | `DanmakuRenderer.remove(id)` | 墓碑 + 阈值压实（`COMPACT_THRESHOLD = 512`） | 60 000 条移除 20 条：Chromium 131.9 → 0.1 ms、Android 209.3 → 0.2 ms；压实单次尖峰 146.9 → 20.4 ms |
| **P1（已落地）** | `setComments` | 新增 `appendComments` 增量合并；`VideoDanmakuLayer` 缓存转换结果 | 12 万条后追加 6 000 条：Chromium 89.4 → 1.8 ms、Android 129.8 → 4.7 ms |
| **P2（已回测，不做）** | 合成层数量 | `will-change` 分档 / 移到组容器 | **负结果**：层数由 WAAPI 动画提升，与 `will-change` 无关；同页对照 FPS 107.0 / 108.4 / 109.2、Style 239.6 / 250.8 / 249.3，无差异。但它在无 WAAPI 的回退路径上必需（Style 53.8 → 158.7 ms/s），故保留 |

### 明确不建议改动的方向

- **不要回退合成器动画**：原生每帧写 `transform` 时 Style 625.6 ms/s、FPS 96.9，是现状（239.5 / 171.5）的 2.6 倍劣化。
- **不要用 CSS `@keyframes` 替换 WAAPI**：实测 Style 308.5 vs 130.4（无引擎对照），WebView2 与普通 Chromium 一致。
- **不要为直播层引入 canvas 渲染器**：原型实测在屏 192 条时，Canvas 逐帧 `fillText` 的 Script 是
  **240.0 ms/s**、离屏文字缓存 143.3 ms/s，**均高于现状 DOM+WAAPI 的 62.2 ms/s**（对照表见下）。
  Canvas 只在"每帧全量重绘 + 富文本极少"时划算，而本项目的弹幕有大量内联表情图片，需要额外的图片
  解码与缓存管理。`RecordedDanmakuCanvas` 用于回放（离线、无交互）是合适的，直播层不合适。

| 渲染方案（在屏约 190~560 条） | FPS | Script ms/s | Style ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: |
| DOM + WAAPI（现状） | 171.8 | 62.2 | 240.8 | 546.2 |
| Canvas 逐帧 `fillText` | 172.1 | **240.0** | 0 | 411.8 |
| Canvas + 离屏文字缓存 | 162.7 | **143.3** | 0 | 451.9 |

## 八、可复跑采样

以下步骤复现本文数据。压测夹具为**临时文件**（`/tmp` 下，未入库）；如需长期回归，建议把渲染层部分
固化为 `tests/*.browser.js`，参照 [danmaku-performance.browser.js](../../tests/danmaku-performance.browser.js)
的写法（该夹具覆盖"空闲基线 / VOD 40 条每秒 + 固定弹幕 / 直播 60 条每秒"三档，不含侧栏面板）。

### 桌面主窗口（CDP）

```bash
bash scripts/sync-to-windows.sh
# 停掉所有 rLive 实例（共享 WebView2 数据目录），再带调试端口启动
#   WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9223 --remote-allow-origins=*"
#   bun run tauri dev
playwright-cli attach --cdp=http://127.0.0.1:9223
playwright-cli --s=default goto "http://localhost:1420/settings"   # 干净路由，避免残留监听器
```

在页面内用 `tests/browser/harness.js` 的 `setupHarness` 挂真实组件，通过事件插件的 emit 命令注入
`danmaku-batch`（`connection_epoch` 必须与 `setExpectedDanmakuConnectionEpoch` 设的值一致，否则
`eventBus` 会按围栏丢弃整批）。采样用 `page.context().newCDPSession(page)` 的
`Performance.getMetrics()` 取增量，用 `PerformanceObserver({type:"longtask"})` 取长任务。

**关键坑**：`import()` 被测模块时**不要加 `?t=` 缓存击穿参数**——`LiveDanmaku.tsx` 与
`eventBus.ts` 会因此拿到两份模块实例，`setExpectedDanmakuConnectionEpoch` 设在 A 上、`dispatch`
读的是 B，表现为"事件发出但一条也不渲染"。`DanmakuPanel` 需要 `QueryClientProvider` 包裹，
否则 `useDanmakuActions` 抛 `No QueryClient set` 并让整棵树静默卸载。

### Android 模拟器

```bash
# Windows emulator，从 WSL 用 pwsh 7 的 Start-Process 起（管道会杀进程）
# adb reverse 让 dev APK 的 localhost:1420 指到 Windows 侧 vite
adb reverse tcp:1420 tcp:1420
adb forward tcp:9222 localabstract:webview_devtools_remote_$(adb shell pidof com.shenss.rlive)
playwright-cli attach --cdp=http://localhost:9222
```

WSL 的 `adb reverse` 无法把端口接到**另一个 Windows 进程**；若 Windows 侧 1420 被占用或不可达，
在 WSL 内起 `bun run dev --port 1421`，再 `adb reverse tcp:1420 tcp:1421`。启动模拟器前必须用
WSL 的 `adb kill-server` 清理 Windows adb daemon，否则 `forward`/`reverse` 会在两个 server 之间错位。

## 九、已知限制

- **Android 数据来自 x86_64 模拟器**（4 核、Chrome 133），非真机 aarch64。不同会话出现过空闲低帧率、
  解码/调度抖动，绝对 FPS 不作为真机保证；保留同一构建对照与关闭渲染的控制样本。
  120Hz 实测见专节，模拟器 rAF 上限约 92～95 次/秒，不能据此宣称达到 120 FPS。
- **生产构建的弹幕层在屏数只有 10~30 条**（轨道准入先拒绝），因此生产环境没能复现 dev 高密度场景；
  400/575 条曲线是在 dev 页面用 12px 字号 + 1920×1080 构造的上限探测。
- **行成本对照表**中的"精简行"是同一页面内构造的对照组件，不是项目内既有实现；它证明的是
  "React 协调 + Base UI 组件"这一层的成本量级，不代表可直接替换的方案。
- **`canAttach` 的 O(n²) 结论是预防性的**：当前自耗时仅 0.1~0.2 ms/s，未构成当下瓶颈。
- **未测**：真机触摸点选（`useDanmakuPinInteraction`）与 SuperChat 富文本路径的渲染成本（SC 走独立
  固定组、条数上限 3，预期不构成瓶颈）；Windows / 真机 VOD 全链路；真机高刷（本轮 120Hz 为模拟器）。
  Android 模拟器的真实视频解码 + 弹幕并行已在独立 VOD 小节补测，不能与早期纯计算表混比。
- 所有测量在 WebView2 154 / Chrome 133 完成；生产对照用的普通 Chromium 与项目 `chrome120` 目标同代，
  但 `Style` / `Task` 的绝对值与 WebView2 存在平台差异（同场景下 WebView2 的 Style 约为 Chromium 的 2 倍），
  **只做同一平台内的前后对比**。
