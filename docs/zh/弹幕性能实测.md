## 结论

**弹幕引擎迁移（2026-10-15，`danmu` 替换 `weizhenye/Danmaku`）在桌面 WebView2 上无回归，且在屏密度回到旧引擎的车道准入水平。**

桌面 1280×720、150 条/秒、20 批/秒、预填 1200 条，正序/反序各一轮：

| 场景 | 指标 | 迁移后实测 | 说明 |
| --- | --- | ---: | --- |
| 钉底/上滚/隐藏列表（150 条/秒） | FPS / p95 | **198.9–200.1 / 5.2–7.3 ms** | 桌面 rAF 上限约 200 次/秒，FPS 不具区分度 |
| 同上 | longtask | **0** | 全部样本均为 0 |
| 同上 | 在屏弹幕 | **20–25 条** | 与旧引擎的车道准入密度（历史记录 10–30 条）一致 |
| 同上 | Script / Style | **104–120 / 22–27 ms/s** | 逐帧写 `transform` 已取消，位移改由 CSS transition 在合成器推进 |
| 注入器地板（`drop`） | Task | **25–108 ms/s** | 与渲染无关的 IPC + 批次校验成本 |

Android 真机（Huawei MatePad 11 / Snapdragon 865，横屏 1024×640，同夹具同口径）：

| 场景 | 指标 | 迁移后实测 | 旧引擎同口径 | 说明 |
| --- | --- | ---: | ---: | --- |
| 150 条/秒（钉底/上滚/隐藏） | FPS | **58.0–59.8** | 56–59 | 持平 |
| 同上 | p95 | **23.4–26.7 ms** | 29–30 ms | 卡顿帧减少 |
| 同上 | Task | **786.1–823.4 ms/s** | 901.5–927.9 | 含注入器地板 |

旧引擎数字取自 [danmaku-android-device-2026-10-15.json](../bench/danmaku-android-device-2026-10-15.json)；
本轮房间不同（斗鱼 36252 未开播，改用 B 站 23197314），只作同设备同夹具的量级对照。

关键取舍（同轮实测）：

- **`mode: 'strict'` 而不是 `adaptive`**。`adaptive` 在轨道占满时会随机挑一条轨道直接上屏：实测同车道 5 条弹幕停在同一个 `x`（相邻间距 **−250px**，即整条弹幕宽度），文字互相覆盖；150 条/秒下平均重叠对数 **31.6**。`strict` 改为留在待投队列等车道空出，同口径实测平均重叠对数 **0.11**（最差采样 2 对），所有车道相邻间距 **≥ 3px**。
- **在屏预算按车道容量取值**（`DANMAKU_LANE_ACTIVE_COMMENTS = 5`，下限同值）。库本身在 `strict` 下会一直排队而不是丢弃，因此必须由调用方按车道容量卡住新弹幕，否则会在高密度房间积压出数十秒的显示延迟。旧引擎的 `canAttach` 语义（饱和即丢弃）由此保留；渲染器侧与直播批次准入共用 `danmakuMaxActiveComments`，两处判据不会漂移。该预算与所选算法无关，始终生效。
- **固定弹幕改走 `pushFlexibleDanmaku` + `direction: 'none'`**，由库的 `setTimeout(actualDuration())` 到期，暂停与钉住自动顺延，不再需要按时长分组维护多个原生实例。

**Android 真机复测（2026-10-15，Huawei MatePad 11 / Snapdragon 865）确认渲染层与面板均无回归，并定位到真正的卡顿变量是「每批事件数」而非每秒总条数。**

150 条/秒、20 批/秒、预填 1200 条（面板 25 行），正序/反序/对照轮：

| 场景 | 指标 | 真机实测 | 说明 |
| --- | --- | ---: | --- |
| 注入器地板（epoch 不匹配，事件被丢弃） | Task ms/s | **677.5** | IPC 序列化 + 批次校验的固定成本，非渲染；面板仅 7 行时为 379.5 |
| 渲染层 + 面板（钉底） | Task ms/s | **901.5–927.9** | 减去地板后渲染增量约 224–250 |
| 隐藏列表（`visibility:hidden`） | Task ms/s | 911.8–924.4 | 与可见列表无差 |
| 仅渲染层（面板列 `display:none`） | Task ms/s | 874.3 | 去掉面板列只省约 3% |
| 仅面板（渲染层隐藏） | Task ms/s | 891.1 | — |
| 重复场景噪声基线 | Task ms/s | 951.7 / 929.4 | 同场景两测差约 2% |

真机上的三个要点：

- **面板不再是瓶颈**。虚拟化后隐藏列表、隐藏整个面板列都只带来个位数百分比变化，主线程成本由渲染层与 IPC 批次共同主导；模拟器 P0 的钉底回归在真机上**不复现**（钉底稳态面板滚动事件 0–15.8 次/秒，与 FPS/Task 无一致相关）。
- **卡顿由每批事件数决定，不由平均吞吐决定**。同样 150 条/秒：5 批/秒（30 条/批）掉到 **42.2 FPS、p95 61.1–80.7 ms**；20 批/秒为 **56–59 FPS、p95 29–30 ms**；40 批/秒回到 **55.9 FPS、p95 28.1 ms**。三者 Task 都在 860–980 ms/s，说明瓶颈是**单批同步处理时长**，不是每秒总工作量。
- **帧节奏在 20 批/秒附近进入平台期**：150 条/秒、20 批/秒下 p95 29–30 ms，但 `>25ms` 帧仍有约 7–10 个/秒（非零卡顿）；批次率降到 5 批/秒（30 条/批）时 p95 升到 61–81 ms、`>33ms` 帧从 10–16 增至 63–67/9 秒，FPS 掉到 42。真机 longtask 计数基本为 0（单批阻塞多在 25–33 ms 区间，未达 50 ms 长任务阈值）。

## 结论（历史，模拟器）

**面板虚拟化在「上滚读历史」与「真实 VOD 隐藏列表」两个场景收益明确；「钉底跟随」场景曾是回归，现已修复**（见「[钉底跟随修复](#钉底跟随修复)」）。下表是修复前的历史数据。

| 场景 | 指标 | 基线 | 当前 | 判定 |
| --- | --- | ---: | ---: | --- |
| Android 面板上滚 150 条/秒 | Task ms/s | 318.2 | **167.6** | 收益 1.9× |
| Android 真实 VOD 弹幕开启 | Task ms/s | 583.9–599.4 | **215.9–235.1** | 收益约 2.6× |
| Android 面板钉底 150 条/秒 | Task ms/s | 193.2 | **286.0** | **回归 1.5×** |
| Android 手机组合 25 条/秒 | Task ms/s | 290.2 | **342.3** | **回归 1.2×** |
| Android 渲染层单独（无面板） | Task ms/s | 188.2 | 186.9 | 持平 |
| 桌面 Chromium 全部场景 | Task ms/s | — | — | 全部改善，无回归 |

回归只在 Android WebView + 面板**钉底自动跟随**时出现，桌面 Chromium 同夹具、同视口不复现；
根因与证据见「[本轮新发现](#本轮新发现钉底跟随在-android-上是回归)」，修复后同包对照钉底 Task 下降约 45%。

另外两条历史结论不变：`remove(id)` 与 `setComments` 的 P1 优化有效（见[归档](#归档)）；
合成层策略（P2）为负结果，不做。

### 主线程成本归属

150 条/秒、20 批/秒、预填 1200 条；除最后两行外均为面板钉底：

| 场景 | FPS | p95 | Script | Style | Layout | **Task** | 在屏弹幕 | 面板行 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 注入器地板（事件被丢弃） | 59.8 | 24.0 | 155.3 | 40.7 | 2.6 | **677.5** | 0 | 25 |
| 渲染层 + 面板 | 57.9 | 29.1 | 291.3 | 128.4 | 91.8 | **901.5** | 18 | 25 |
| 隐藏列表 | 58.1 | 29.5 | 299.2 | 145.7 | 98.7 | **912.1** | 22 | 25 |
| 仅渲染层（面板列 `display:none`） | 56.5 | 33.6 | 323.6 | 148.5 | 73.1 | **874.3** | 29 | 6 |
| 仅面板（渲染层隐藏） | 58.1 | 29.9 | 297.0 | 131.8 | 91.4 | **891.1** | 20 | 25 |

- **地板 677.5 ms/s 是注入器自身**：事件在 `eventBus.dispatch` 因 epoch 不匹配被丢弃，只剩 IPC 序列化与批次校验。扣除后渲染增量约 **224–250 ms/s**。
- 隐藏列表（912.1）与可见列表（901.5）无差异；把整个面板列 `display:none` 只到 874.3（约 −3%）。**面板虚拟化后列表已不是瓶颈。**
- 面板钉底稳态滚动事件在 7 轮 150 条/秒采样中为 **0–15.8 次/秒**（正反序轮均为 0，部分控制轮 1.6–15.8），量级远低于模拟器 P0 回归时的约 46 次/秒，且与 FPS/Task 无一致相关，**未见钉底滚动事件回归**。

### 卡顿由每批事件数决定

同为 150 条/秒、面板钉底，只改批次率：

| 批次率 | 每批条数 | FPS | p95 | >25ms 帧 | >33ms 帧 | Task | Script |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 批/秒 | 30 | **42.2** | **61.1** | 93 | **63** | 876.4 | 269.1 |
| 20 批/秒 | 7–8 | 57.9 | 29.1 | 60–77 | 10–16 | 901.5 | 291.3 |
| 40 批/秒 | 3–4 | 55.9 | 28.1 | 65 | 12 | 981.2 | 351.3 |

**Task 几乎不变而帧节奏显著恶化**：5 批/秒时每批要同步处理 30 条弹幕，单帧阻塞拉长到 p95 61–81 ms、`>33ms` 帧达 63–67/9 秒，FPS 掉到 42；把同一总量摊成 20–40 批后恢复 56–59 FPS、`>33ms` 帧回到 10–16。瓶颈是**单批同步处理时长**，不是每秒总工作量——这条结论只在真机获得，模拟器与桌面夹具当时都固定 20 批/秒。

注意 20 批/秒下 `>25ms` 帧本就有 60–88 个/9 秒（约 7–10 帧/秒），并非零卡顿；5 批/秒把 `>25ms` 帧推高到 89–93，并把 `>33ms` 帧从 10–16 放大到 63–67（约 4–6 倍）。`>33ms` 在 20 批/秒与 40 批/秒间无实质差别（10–16 vs 12），说明 20 批/秒已进入平台期。

### 与模拟器数据的关系

真机 aarch64 与模拟器 x86_64 的绝对数字**不可相减**：注入器成本、WebView 版本（114 vs 133）与设备性能都不同。可比的是**方向**：

- 模拟器证明虚拟化本身把「真实 VOD 隐藏列表」场景的 Task 从 583.9–599.4 降到 215.9–235.1（约 −62%），收益来自消掉那 5874 行未虚拟化列表的可见性计算。
- 真机测的是**已虚拟化后的当前实现**：再隐藏列表或整个面板列只省个位数百分比。两者不矛盾——虚拟化的收益已被当前实现吃下，剩下的成本在渲染层与 IPC。
- 真机额外排除了钉底滚动事件回归，并暴露出批次粒度这一模拟器/桌面夹具都没测到的变量。

## 本轮新发现：钉底跟随在 Android 上是回归

### 现象

`panel-pinned`（钉底自动跟随）与所有含钉底面板的组合场景，当前实现的主线程耗时高于基线；
4 轮独立采样（含反序）方向一致：Task 181.4–206.0 → 284.7–380.2 ms/s。

### 根因

两版都在钉底时写 `viewport.scrollTop`（都是约 20 次/秒，写入量不是差异点）。
差异在于**这些写入是否真的产生滚动事件**：

| 证据（钉底稳态，9 秒） | 基线 | 当前 |
| --- | ---: | ---: |
| `scrollTop` 写入 / 秒 | 20.0 | 20.1 |
| **滚动事件 / 秒** | **0** | **48.8** |
| 滚动高度波动幅度 | **0px** | **115px** |
| `scrollTop` 读取 / 秒 | 20.6 | 100.4 |
| 强制同步样式+布局 `Blink.ForcedStyleAndLayout.UpdateTime`（Tracing） | 30.6 ms/s | **108.0 ms/s** |

机制：基线的滚动高度被裁剪锁在**完全恒定**的 10 296px，钉底时写 `scrollTop` 落在同一个值上，
不产生滚动事件；当前实现用虚拟器撑到约 **40 800px**，且总高度随行测高与窗口变化
**持续波动约 115px**，同样的写入因此产生约 49 次/秒真实滚动事件。
每次滚动事件回到面板的 `updateAutoScroll`（读 `scrollHeight` / `scrollTop` /
`virtualizer.getVirtualItemForOffset`），在 React 提交路径里形成「强制样式+布局」的循环。

两条独立验证都指向「写入触发滚动事件」而不是「写入本身」：

| 对照 | 基线 | 当前 |
| --- | ---: | ---: |
| 解除钉底、两版都停止写入时的 Task | 270.1（1200 行） | **176.9** |
| 屏蔽 `scrollTop` 写入后的 Task | 188.5 → 240.4（无收益） | **283.8 → 151.7** |

即：**当前实现在不写 `scrollTop` 时确实更快**（非钉底 176.9 vs 基线 270.1），
一旦进入钉底跟随就反过来。基线在非钉底时因为要挂 1200 个真实行反而更慢。

### 交叉验证

- **抬高滚动区本身不是原因**：给基线追加 30 000px 空白尾后 Task 反而略降（193.9 → 164.0），
  当前同样不因滚动区变高而恶化（313.4 → 257.3）。变量是**高度波动 + 由此产生的滚动事件**，不是静态高度。
- **解除钉底即可消除**：同一实现停止跟随写入后，Task 从 303.8 降到 176.9，比基线非钉底的 270.1 更低。
- **桌面 Chromium 不复现**：同一夹具、同一 production 包，在 412×915（dpr 2.625 与 1 都试过）
  与 780×493 下，当前实现的 Task 全面低于基线（钉底 46.5 vs 68.5；上滚 4× 节流 134.3 vs 595.8）。
  桌面 Chromium 的滚动事件节流/合成实现与 Android WebView 不同，是差异的可能来源。
- **不是渲染层回归**：`layer` 单独场景两版一致（188.2 / 186.9）。

## 钉底跟随修复

### 改动（`DanmakuPanel`）

| 改动 | 作用 |
| --- | --- |
| `directDomUpdates: true`（`position` 模式）+ `containerRef` | 测高、滚动但可视范围不变时由虚拟器直接写容器高度与行 `top`，不再重渲染 React 子树 |
| 估高按已挂载普通行的最小实测值向下校准 | 估值与实测一致后，每批淘汰已测行、补进未测行时总高不再漂移 |
| 钉底时 `anchorTo: "start"`，阅读态才 `"end"` | 钉底时不再先做稳定键锚定补偿、再被拉回底部 |
| 钉底时禁用逐行测高补偿（`shouldAdjustScrollPositionOnItemSizeChange`），`scrollEndThreshold: -1` | 测高不再逐行写 `scrollTop`，也关闭 end 锚定的隐式回底 |
| 追加、测高、视口 resize 合并到一个可取消 rAF 回底 | 每帧最多一次读写；上滚、打开菜单时立即取消 |
| 钉底期间只有 `scrollTop` 向上移动才可能解除跟随 | 测高夹取后的回放等程序滚动事件晚于下一批到达时，不再被误判为用户上滚 |

没有使用虚拟器的 `followOnAppend`：当前版本启动的跨帧 index 追踪没有公开取消 API，
回归夹具复现了「底部打开菜单后仍被新消息推走」和「跟随中快速上滚被拉回」两种竞态。

## 归档

以下结论已定稿，不再重复展开。

| 项 | 结论 | 证据 |
| --- | --- | --- |
| `DanmakuRenderer.remove(id)` | 墓碑 + 阈值压实（`COMPACT_THRESHOLD = 512`）。6 万条移除 20 条：Chromium 131.9 → **0.1 ms**、Android 209.3 → **0.2 ms**；压实单次尖峰 146.9 → 20.4 ms | [P1 数据](../bench/danmaku-p1-2026-10-13.json) |
| `setComments` → `appendComments` | 增量合并，VOD 分段语义。12 万条后追加 6 000 条：Chromium 89.4 → **1.8 ms**、Android 129.8 → **4.7 ms** | 同上 |
| 合成层策略（P2） | **保持节点独立成层**。当年对照时合成层由 WAAPI 的 `ActiveTransformAnimation` 提升，与 `will-change` 无关（FPS 107.0 / 108.4 / 109.2，Style 239.6 / 250.8 / 249.3，均在噪声内）；自建 WAAPI 已随引擎移除，现在位移是节点上的 CSS transition，合成器自行决定图层提升，不需要再手工写 `will-change` | [P2 数据](../bench/danmaku-p2-2026-10-13.json) |
| 滚动弹幕合成器动画（旧引擎） | **旧实现已随引擎一起移除**。当年曾用自建 WAAPI 动画 + 媒体时钟分级校时把每帧位移误差 p95 从 1.1–4.3px 降到约 0.5px；现在由 `danmu` 写一次 CSS transition 在合成器推进（见下文），不再有逐帧位移误差这一项 | [VOD 数据](../bench/vod-danmaku-android-2026-10-12.json) |
| 设备在屏预算 | **已从代码移除**，回退到无设备判据的 `DANMAKU_MAX_ACTIVE_COMMENTS = 800`。历史数据显示它能把高密度 4× 节流从 25.2 提到 60.1 FPS（Chromium）、14.8 提到 78.5（WebView2），但在 Android 上「上限生效、FPS 未改善、p95 反而升高」，未解决即被回退。迁移后按车道容量重新引入（`DANMAKU_LANE_ACTIVE_COMMENTS = 5`），但那是**准入判据**而不是节流阀 | [P0 数据](../bench/danmaku-p0-2026-10-12.json) |
| 120Hz 显示节奏 | 固定 120Hz 节奏下，基线弹幕开启时掉回 60Hz 档（Task 878.7–882.1、`computeIntersections` 666.5），当前维持满帧节奏（Task 249.8–287.3、18.5）。模拟器 rAF 上限约 92–95 次/秒，**不能宣称达到 120 FPS** | [120Hz 数据](../bench/danmaku-android-120hz-2026-10-12.json) |

### 明确不建议改动的方向

- **不要用 CSS `@keyframes` 替换逐帧 `transform`**：实测 Style 308.5 vs 130.4（无引擎对照）。
- **不要为直播层引入 canvas 渲染器**：在屏约 190 条时 Canvas 逐帧 `fillText` 的 Script 是
  240.0 ms/s、离屏文字缓存 143.3 ms/s，均高于 DOM 的 62.2 ms/s；且弹幕含大量内联表情图片。
  `RecordedDanmakuCanvas` 用于离线回放是合适的，直播层不合适。

### 滚动弹幕位移：合成器 CSS transition

历史上这里曾给每条滚动弹幕建一条线性 WAAPI 动画在合成器上推进，并用「媒体时钟偏差分级校正」
（≤ 10 ms 跟回媒体倍速、> 1000 ms 硬写 `currentTime`、中间微调速率）和 `updatePlaybackRate`
处理暂停、缓冲与倍速。这一整套自建运动层已删除，现在由 `danmu` 在节点上写一次
`transition: transform linear <duration>ms`，位移在合成器上推进，**主线程不再逐帧写 `transform`**；
暂停、缓冲、倍速与 seek 由渲染器读 `currentTime` 驱动投放，库按 `actualDuration() = duration / rate`
折算在途与新建弹幕的时长。

取舍：暂停/恢复时库用 `transitionDuration` 重写剩余时长（`_getMovePercent()` 按记录器时间算），
因此恢复瞬间的位置由最后一次写入的 transform 决定，不依赖逐帧校正；主线程卡顿时弹幕速度不再跟着波动，
这是与旧路径相反的方向。倍速切换只影响新投放的弹幕，在途弹幕保持原 `duration`（库的 `setRate` 不追溯），
与旧引擎「逐帧按媒体时间算 `x`」的即时响应不同。后续若重新评估这条路径，需要在真实 VOD
中重新采样，不要直接引用移除前的数字。

## 已知限制

- **真机数据来自单台 Huawei MatePad 11（Snapdragon 865，Android 12，WebView 114）**，横屏 1024×640；其他设备、竖屏与 120Hz 未测。
- **真机注入器地板偏高（150 条/秒时约 677 ms/s）**：受控注入走 `plugin:event|emit` 的前端 IPC 路径，其成本高于原生 WS 直接投递，因此真机的**绝对 Task 不能当作生产值**，只用于同口径对照。
- **钉底回归只在模拟器 WebView 复现**，真机同场景滚动事件为 0–1.6 次/秒，未见回归；桌面 Chromium 亦不复现。
- **未测**：Android 真机 120Hz 高刷、触摸点选、SuperChat 富文本路径；Windows 真实 VOD production A/B。
  历史高密度数据（在屏 400/575 条）是 1920×1080 + 12px 字号的**构造上限探测**，
  真实房间受轨道准入限制通常只有 10–30 条在屏。
- 历史测量在 WebView2 / Chrome 133 / Chromium 151 完成；**只做同一平台内的前后对比**，
  不同平台（同场景下 WebView2 的 Style 约为 Chromium 的 2 倍）与不同夹具的数字不可相减。
