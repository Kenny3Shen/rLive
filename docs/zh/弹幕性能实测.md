# 弹幕性能实测

测试日期：2026-10-12。基线：`690c0dec`（滚动弹幕改走合成器动画），rLive `7.6.0`。
本文记录直播与 VOD 弹幕链路的压测方法、实测数据、瓶颈定位与重写建议。**只读压测，未改动源码。**

- 播放链路性能问题与已落地的优化：[性能优化](性能优化.md)
- VOD 首屏与续播的时间线测量：[Windows Debug VOD 性能实测](VOD性能实测.md)
- 代码证据与优先级清单（不含实测数字）：[代码审计与优化方向](代码审计与优化方向.md)

## 结论

**弹幕飘动本身不是瓶颈**——2026-10-12 把滚动弹幕改为合成器动画（WAAPI）之后，桌面在屏 575 条弹幕
仍保持 171 FPS，主线程 Task 只占 701 ms/s，其中飘动动画的样式重算 309 ms/s 是主要构成。

**真正的瓶颈是 `DanmakuPanel` 侧栏列表**。它每条消息挂一个 Base UI `Popover` + `useDanmakuActions`
（3 个 `useState`、3 个 `useSettingsStore` 订阅、一个 `useQuery`），单行成本是纯文本行的约 5 倍。
在 Android 上，**25 条/秒**就把主线程吃到 54%（Script 539 ms/s），FPS 掉到 45.4；上滚展开到 1200 行
窗口后 FPS 只有 16.8。

次要瓶颈：渲染层每帧对每条在屏弹幕做样式重算（与条数线性）、`remove(id)` 的 O(分组×时间轴) 扫描、
VOD `setComments` 的全量时间轴重建。

## 一、链路总览

```
Rust 站点 WS → DanmakuEventSender.try_send → dispatch_batches（50ms ticker / 512 条上限）
  → app.emit("danmaku-batch") → eventBus 单监听器校验 → 扇出到各 sink
      ├─ LiveDanmaku.renderEvents → danmakuCommentFromEvent → DanmakuRenderer.emit
      │     → 原生 danmaku 2.0.10 rAF：轨道分配 + WAAPI 位移
      └─ DanmakuPanel 订阅 → 有界队列 → rAF/定时冲刷 → React 列表
```

| 环节 | 实测 | 判定 |
| --- | --- | --- |
| Rust 批处理（50ms / 512 条 / 2048 容量 `try_send`） | 未观测到堆积 | 合理，不动 |
| `eventBus` 校验 + 扇出 | 单监听器、预校验、异常隔离 | 合理，不动 |
| `LiveDanmaku.renderEvents` | 批内 `activeScrollCount` 累加已避免 O(n²)（[LiveDanmaku.tsx](../../src/features/room/danmaku/LiveDanmaku.tsx) 第 414 行） | 合理，不动 |
| `DanmakuRenderer.emit` | **1.74 µs/条**（1200 条/秒下 10 秒共 5754 条，累计 10 ms） | 不是瓶颈 |
| `DanmakuRenderer` 每帧渲染 | 在屏 575 条时 Style **309 ms/s** | **次要瓶颈** |
| `DanmakuPanel` 列表行 | 单行约 2 ms 主线程（生产）；Android 25 条/秒即掉到 45 FPS | **首要瓶颈** |

## 二、瓶颈一：`DanmakuPanel` 列表行（首要）

### 根因

每条消息渲染的组件链（[DanmakuPanel.tsx](../../src/features/room/DanmakuPanel.tsx)）：

- 第 124 行 `SelectableDanmakuRow`：`useState` + `useDanmakuActions`
- 第 144 行 `useDanmakuActions`（[useDanmakuActions.ts](../../src/features/room/danmaku/useDanmakuActions.ts)）：`useQueryClient()`、3 个 `useState`、3 个 `useSettingsStore` 订阅、1 个 `useQuery`
- 第 169 / 178 行 `Popover` / `PopoverTrigger`：Base UI 的 `useOpenStateTransitions`、`useTriggerDataForwarding`、`useHoverReferenceInteraction`、`useRenderElement`、`mergeInto`、`useStableCallback`
- 第 617 行 `items.map()`：**全量渲染**，无虚拟化；配合第 38 行 `MAX_PER_FLUSH = 32`，每个冲刷帧最多挂 32 个新 `Popover` 子树

### 实测：行实现对照（桌面生产构建，150 条/秒，300 行窗口）

| 行实现 | Script ms/s | Style ms/s | Layout ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: |
| 真实 `DanmakuPanel` 行 | **293.7** | 15.5 | 15.4 | 391.5 |
| 精简行（纯 `div` + 文本，同 300 行、同追加节奏） | **59.8** | 43.0 | 91.8 | 281.8 |

Script 差 **4.9 倍**，折算单行约 **1.96 ms** vs **0.40 ms**。精简行 Style/Layout 反而更高（缺 `will-change`
与绝对定位），说明差距全部来自 React 协调与 Base UI 组件，**不在文本排版**。

### 实测：弹幕层 vs 面板（桌面生产构建，逐级提升事件率）

| 事件率 | 弹幕层在屏 | 层 Script ms/s | 层+面板 Script ms/s | 面板增量 |
| ---: | ---: | ---: | ---: | ---: |
| 25 条/秒 | 9 | ~12 | 167.5 | **+155** |
| 100 条/秒 | 11 | ~19 | 252.4 | **+233** |
| 400 条/秒 | 10 | ~29 | 291.8 | **+263** |
| 800 条/秒 | 11 | ~36 | 195.1 | **+159** |

弹幕层的 Script 几乎不随事件率变化（9→36 ms/s，因为在屏数被轨道准入锁在 ~10 条），而面板部分恒在
150~260 ms/s——**面板是唯一随事件率增长的项**。

### 实测：每次冲刷的提交延迟（桌面 dev React，30 行/批）

12 批连续注入，每批 30 行，批间 150 ms：中位 **154.8 ms**，全部落在 153~176 ms。即每批 30 行要花
~155 ms 主线程。**该数字含 dev React 开销**（生产折算见上表约 2 ms/行），仅用于说明提交延迟的稳定性。

### 实测：窗口放宽到 1200 行时崩塌（桌面生产构建）

| 场景 | 行数 | FPS | p95 | 卡顿帧 | Script ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 钉住底部 | 300 | 60.0 | 16.7 | 0 | 248.3 | 352.2 |
| 上滚（保留历史） | **1 200** | **36.5** | **50.1** | **86** | **904.1** | 994.2 |

`DANMAKU_LIST_MAX_SCROLLED_UP = 1_200`（[listWindow.ts](../../src/features/room/danmaku/listWindow.ts) 第 21 行）
意味着读者一上滚，React 就要在每次提交里协调 1200 个带 `Popover` 的行。

### 实测：Android 上更早崩塌

| 场景 | 事件率 | 行数 | FPS | p95 | max | 卡顿帧 | Script ms/s | Task ms/s | longtask |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 仅弹幕层 | 1 000 条/秒 | — | 59.3 | 16.7 | 16.8 | 0 | 152.3 | 430.8 | 0 |
| 层 + 面板 | 25 条/秒 | 300 | **45.4** | 49.9 | 83.3 | 89 | **538.7** | 797.5 | 2 次 / 51 ms |
| 层 + 面板 | 200 条/秒 | 300 | **34.4** | 66.7 | 100 | 117 | **640.9** | 864.4 | 74 次 / 4 371 ms |
| 层 + 面板（上滚） | 100 条/秒 | 975 | 46.3 | 50.1 | 100 | 38 | 539.7 | 792.8 | 24 次 / 1 473 ms |
| 层 + 面板（上滚） | 300 条/秒 | 1 200 | **16.8** | **233.4** | 267 | 54 | 714.6 | 942.5 | 25 次 / 3 662 ms |

对比第 1 行与第 2 行：**Android 上弹幕层 1000 条/秒完全无卡顿（59.3 FPS、0 卡顿帧）**，
但加上侧栏面板后 25 条/秒就出现 89 个卡顿帧。面板在 Android 上占主线程 54%~64%。

### 优化方向

1. **虚拟滚动**：项目已在用 `@tanstack/react-virtual`（`src/features/history/historyVirtual.ts`）。
   行高近似固定（`leading-relaxed` + `py-1`），`estimateSize` 可用常量，无需测量。
2. **把交互从行内提升到面板级单例**：列表只渲染纯文本行；点击时事件委托把 `id` 交给面板顶部的一个
   `Popover`，菜单锚定到点击坐标。这一项单独就能消掉 `SelectableDanmakuRow`、`PopoverTrigger`、
   `useDanmakuActions`、`DanmakuEmojiText` 的全部每行开销。
3. 虚拟化后 `DANMAKU_LIST_MAX_SCROLLED_UP` 与 `scrollTopAfterDanmakuListTrim` 的滚动补偿逻辑可以
   **整体删除**——虚拟滚动天然没有"移除顶部行导致位移"的问题。这是净减代码。

预期：Script 从 250~290 ms/s 降到接近精简行的 60 ms/s；1200 行窗口从 36.5 FPS 恢复到 60；
Android 从 34~45 FPS 恢复到 60。

## 三、瓶颈二：渲染层每帧样式重算（次要）

### 根因

滚动弹幕的位移由 WAAPI 合成器动画承担（方向正确），但原生 `danmaku` 引擎的 rAF 仍每帧遍历
`runningList`：调用 `allocate` / `willCollide` 做轨道准入，给每条弹幕计算 `comment.x`，并在我们的
`render` 钩子里调用 `syncMotion` 比对动画与媒体时钟。同时每条弹幕带 `will-change:transform`
（[danmakuRenderer.ts](../../src/features/room/danmaku/danmakuRenderer.ts) 第 536 行），使其成为独立合成层。

### 实测：在屏密度曲线（桌面 dev，1920×1080，14px 字号，面积 100%）

| 在屏条数 | FPS | Script ms/s | Style ms/s | Task ms/s |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 172.1 | 1.8 | 0 | 13.8 |
| 51 | 172.8 | 7.4 | 21.0 | 65.8 |
| 100 | 171.3 | 11.5 | 40.0 | 106.7 |
| 200 | 172.9 | 23.2 | 87.9 | 216.1 |
| 302 | 172.7 | 39.3 | 135.4 | 331.5 |
| 401 | 170.5 | 47.1 | **185.2** | **434.0** |

Style 与条数严格线性（约 0.46 ms/s per 条）。注意 **FPS 未下降**（动画走合成器），但主线程被占用
意味着**留给解码、IPC、React 的余量被吃掉**——一旦叠加 CPU 受限或页面上有其他工作，就会掉帧。

### 实测：CPU 节流下的崩塌（桌面 dev，在屏 ~500 条）

| 模式 | 在屏 | FPS | p95 | 卡顿帧 | Script ms/s | Style ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 无节流 | 575 | 170.8 | 6.2 | 0 | 74.2 | 309.0 | 701.2 |
| 4× CPU 节流 | 539 | **41.5** | 30.1 | 54 | 101.6 | **418.4** | **968.5** |
| 6× CPU 节流 | 468 | **28.9** | 46.7 | 232 | 92.0 | **416.2** | **981.5** |

这是**低端设备（含移动端中低端机）的真实风险模型**：`MAX_ACTIVE = 800` 允许的密度在 4× 节流下
只能跑 41 FPS。

### 实测：动画实现对照（同一批 400 个绝对定位节点）

| 实现 | 在屏 | FPS | Script ms/s | Style ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| **现状：WAAPI + `will-change`** | 431 | 171.5 | 65.7 | **239.5** | 551.3 |
| WAAPI，动画 `pause()` | 419 | 170.4 | 54.7 | **21.9** | 143.7 |
| 原生每帧写 `transform`（停用 WAAPI） | 451 | **96.9** | 81.4 | **625.6** | 906.5 |
| 纯 CSS `@keyframes`（无 DOM 引擎） | 400 | 172.5 | 2.7 | **308.5** | 552.8 |
| 纯 WAAPI（无 DOM 引擎） | 400 | 170.7 | 2.5 | **130.4** | 283.2 |

判读：

- **`pause()` 使 Style 从 239.5 掉到 21.9 ms/s** → 这 240 ms/s 完全来自"N 个运行中动画"的每帧动画样式
  计算，与 JS 无关（Script 几乎不变）。
- **回退到原生每帧写 `transform` 后 Style 飙到 625.6、FPS 掉到 96.9** → 2026-10-12 的合成器动画改造
  **方向正确，不要回退**。
- **纯 WAAPI 只有 130.4，DOM 引擎却是 239.5** → 差值 ~109 ms/s 来自引擎每帧对每条弹幕的
  `comment.x` 赋值、`allocate`/`willCollide` 计算，以及 `will-change` 的图层开销。
- **CSS `@keyframes` 比 WAAPI 更差（308.5 vs 130.4）** → 不要用 CSS 关键帧替换 WAAPI（每节点都要解析
  关键帧变量）。在普通 Chromium 上同样成立（WAAPI 54.5 vs CSS 110.0）。

### 实测：合成开销（Tracing，在屏 382 条）

| 事件 | ms/s |
| --- | ---: |
| `Paint` | 7.4 |
| `RasterTask` | 未出现在采样中（舞台只走合成） |
| `UpdateLayer` | 11.0 |
| `PrePaint` | 42.5 |
| `Layerize` | 45.0 |
| `PaintArtifactCompositor::Update` | 44.7 |
| `Commit` | 54.1 |
| `AnimationHost::TickAnimations` | 223.6 |
| `LocalFrameView::UpdateStyleAndLayout` | 326.2 |

`will-change:transform` 把每条弹幕提升为独立合成层，575 条时 `Layerize` + `PrePaint` + `Commit` 合计
约 140 ms/s，而它换来的 `Paint` 收益只有 7.4 ms/s。**但 A/B 实测去掉 `will-change` 无改善**
（Style 254.9 vs 248.8，Script 69.6 vs 74.1），说明当前 Style 成本并非来自它——**建议先做面板重写，
再回来评估图层策略**。

### 优化方向

1. **为在屏数设硬上限（配置驱动）**。`danmakuMaxActiveComments`（[danmakuAdapter.ts](../../src/features/room/danmaku/danmakuAdapter.ts)）
   给的是 `min(800, max(120, 轨道数 × 12))`；1920×1080 + 12px 字号下约 636 条，对应 Style 300+ ms/s。
   建议改为按设备分档（`hardwareConcurrency` / `deviceMemory` / 首次渲染基准）给桌面 300、移动 150
   的固定预算，或用帧间隔 EWMA 动态收敛。当前真实在屏数只有 10~30 条（轨道准入先拒绝），
   **调低上限不会改变日常观感**，但能防止异常流量下的雪崩。
2. **减少合成层数量**：在屏数超过阈值后把 `will-change` 从节点移到组容器，或只给"本帧有新弹幕上屏"
   的组加提示。收益不明确，**先做面板**。

## 四、瓶颈三：`remove(id)` 的 O(分组 × 时间轴) 扫描

### 根因

[danmakuRenderer.ts](../../src/features/room/danmaku/danmakuRenderer.ts) 第 209 行的 `remove` 对每个分组做两次
全量 `filter`，并在其中调用 `definitions.get()`；`LiveDanmaku.removeRecord` 另外用 `indexOf` 线性扫描
`recordOrderRef` 与 `superChatIdsRef`。

### 实测

| 时间轴规模 | 移除 20 条耗时 |
| ---: | ---: |
| 60 000 条 | **63.3 ms** |

一次 63 ms 的主线程阻塞。触发路径：SuperChat 到期计时器（每条一个 `setTimeout`）、屏蔽用户
（`useLayoutEffect` 里对全部记录循环）、面板的 `+1`。VOD 中调用密度低，但直播 SC 集中到期时会连续触发。

### 优化方向

维护 `Map<id, {group, index}>` 索引，`remove` 时按索引 `splice`；或 `comments` 改为"墓碑 + 周期性压实"
而非每次 `filter` 重建。预期从 63 ms 降到亚毫秒。

## 五、瓶颈四：`setComments` 全量时间轴重建（VOD）

### 根因

[VideoDanmakuLayer.tsx](../../src/features/video/VideoDanmakuLayer.tsx) 第 230 行每次 `comments` 变化都调用
`renderer.setComments()`，而 `setComments` 会重建**全部**分组的 `comments` 数组（`grouped` / `seen` /
`sort` / `lowerBound`）。VOD 分段加载的语义是**追加**，不是替换。

### 实测（单次 `setComments` 中位耗时）

| 时间轴规模 | 耗时 |
| ---: | ---: |
| 10 000 | 5.8 ms |
| 30 000 | 19.1 ms |
| 60 000 | 40.4 ms |
| 120 000 | **75.2 ms** |

分段加载累计（每次 +6 000 条）：

| 段 | 时间轴 | 耗时 |
| ---: | ---: | ---: |
| 1 | 6 000 | 3.0 ms |
| 2 | 12 000 | 4.2 ms |
| 3 | 18 000 | 5.7 ms |
| 4 | 24 000 | 7.7 ms |
| 5 | 30 000 | 10.0 ms |
| 6 | 36 000 | 17.9 ms |
| 7 | 42 000 | 13.0 ms |
| 8 | 48 000 | 16.5 ms |
| **累计** | | **78 ms** |

单次不致命，但它是纯 O(N log N) 重建，**随视频时长线性增长**——10 万条以上的长视频会变成肉眼可见的卡顿。

### 优化方向

给 renderer 加 `appendComments(comments)`，只对新条目做 `groupFor` + 有序插入（`splice` 到 `lowerBound`
位置），`comments` 数组本身改为"原地追加 + 定期压实"；同时 `VideoDanmakuLayer` 用 `useMemo` 缓存已
转换的 `DanmakuComment`（当前 `comments` 的 `useMemo` 依赖 `schedule`，`schedule` 依赖 `entries` 引用，
分段加载必然新建）。预期从 75 ms/次 降到约 5 ms/次。

## 六、已确认**不是**瓶颈的部分

| 环节 | 证据 |
| --- | --- |
| `DanmakuRenderer.emit` | 1 200 条/秒注入时 **1.74 µs/条**，10 秒共 5 754 条累计 10 ms |
| `canAttach` 的 O(n²) | 在屏 550 条时 32 条候选迭代 18 143 次，但自耗时仅 **0.1~0.2 ms/s**（插桩）；一帧 12~14 ms 基本被 `emit` 的 DOM 创建吃掉。**当前不是主因**，但迭代次数随在屏数线性增长，属已埋下的地雷 |
| 后端批处理 | 50 ms ticker / 512 条上限 / 2 048 容量 `try_send`，前端侧无堆积 |
| 轨道分配 `allocate` / `willCollide` | 600 条/秒下合计约 147 ms / 6.2 s（dev），可接受 |
| `LiveDanmaku` 事件摄入 | 批内 `activeScrollCount` 累加已避免 O(n²)；`eventBus` 单监听器 + 预校验 + 异常隔离 |

### `canAttach` 规模效应（供后续参考）

| 在屏条数 | 32 条候选的 `records` 迭代次数 | 一帧耗时 |
| ---: | ---: | ---: |
| 0 | 1 024 | 12.4 ms |
| 200 | 7 019 | 11.5 ms |
| 400 | 13 328 | 12.5 ms |
| 550 | 18 143 | 13.6 ms |

若 `MAX_ACTIVE = 800` 被真正吃满且每帧 32 条候选，就是每帧约 2.5 万次比较。

## 七、重写优先级

| 优先级 | 对象 | 方案 | 预期 |
| --- | --- | --- | --- |
| **P0** | `DanmakuPanel` 列表行 | 虚拟滚动 + 交互提升到面板级单例 | Script 250~290 → ~60 ms/s；1200 行窗口 36.5 → 60 FPS；Android 34~45 → 60 FPS |
| **P0** | 渲染层在屏预算 | 按设备分档或用帧间隔 EWMA 动态收敛 `danmakuMaxActiveComments` | 4× 节流下 41.5 FPS → 60；防止异常流量雪崩 |
| P1 | `DanmakuRenderer.remove(id)` | id 索引 + `splice`，或墓碑 + 周期压实 | 60 000 条下 63 ms → 亚毫秒 |
| P1 | `setComments` | 新增 `appendComments` 增量合并；`VideoDanmakuLayer` 缓存转换结果 | 120 000 条下 75 ms → ~5 ms |
| P2 | 合成层数量 | `will-change` 分档 / 移到组容器 | 收益不明确，**先做 P0 再回测** |

### 明确不建议改动的方向

- **不要回退合成器动画**：原生每帧写 `transform` 时 Style 625.6 ms/s、FPS 96.9，是现状（239.5 / 171.5）的 2.6 倍劣化。
- **不要用 CSS `@keyframes` 替换 WAAPI**：实测 Style 308.5 vs 130.4（无引擎对照），WebView2 与普通 Chromium 一致。
- **不要为直播层引入 canvas 渲染器**：原型实测在屏 192 条时，Canvas 逐帧 `fillText` 的 Script 是
  **240.0 ms/s**、离屏文字缓存 143.3 ms/s，**均高于现状 DOM+WAAPI 的 62.2 ms/s**（对照表见下）。
  Canvas 只在"每帧全量重绘 + 富文本极少"时划算，而本项目的弹幕有大量内联表情图片，需要额外的图片
  解码与缓存管理。`RecordedDanmakuCanvas` 用于回放（离线、无交互）是合适的，直播层不合适。

| 渲染方案（在屏约 190~560 条） | FPS | Script ms/s | Style ms/s | Task ms/s |
| --- | ---: | ---: | ---: | ---: |
| DOM + WAAPI（现状） | 171.8 | 62.2 | 240.8 | 546.2 |
| Canvas 逐帧 `fillText` | 172.1 | **240.0** | 0 | 411.8 |
| Canvas + 离屏文字缓存 | 162.7 | **143.3** | 0 | 451.9 |

## 八、可复跑采样

以下步骤复现本文数据。压测夹具为**临时文件**（`/tmp` 下，未入库）；如需长期回归，建议把渲染层部分
固化为 `tests/*.browser.js`，参照 [danmaku-performance.browser.js](../../tests/danmaku-performance.browser.js)
的写法（该夹具覆盖"空闲基线 / VOD 40 条每秒 + 固定弹幕 / 直播 60 条每秒"三档，不含侧栏面板）。

### 桌面主窗口（CDP）

```bash
bash scripts/sync-to-windows.sh
# 停掉所有 rLive 实例（共享 WebView2 数据目录），再带调试端口启动
#   WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9223 --remote-allow-origins=*"
#   bun run tauri dev
playwright-cli attach --cdp=http://127.0.0.1:9223
playwright-cli --s=default goto "http://localhost:1420/settings"   # 干净路由，避免残留监听器
```

在页面内用 `tests/browser/harness.js` 的 `setupHarness` 挂真实组件，通过事件插件的 emit 命令注入
`danmaku-batch`（`connection_epoch` 必须与 `setExpectedDanmakuConnectionEpoch` 设的值一致，否则
`eventBus` 会按围栏丢弃整批）。采样用 `page.context().newCDPSession(page)` 的
`Performance.getMetrics()` 取增量，用 `PerformanceObserver({type:"longtask"})` 取长任务。

**关键坑**：`import()` 被测模块时**不要加 `?t=` 缓存击穿参数**——`LiveDanmaku.tsx` 与
`eventBus.ts` 会因此拿到两份模块实例，`setExpectedDanmakuConnectionEpoch` 设在 A 上、`dispatch`
读的是 B，表现为"事件发出但一条也不渲染"。`DanmakuPanel` 需要 `QueryClientProvider` 包裹，
否则 `useDanmakuActions` 抛 `No QueryClient set` 并让整棵树静默卸载。

### Android 模拟器

```bash
# Windows emulator，从 WSL 用 pwsh 7 的 Start-Process 起（管道会杀进程）
# adb reverse 让 dev APK 的 localhost:1420 指到 Windows 侧 vite
adb reverse tcp:1420 tcp:1420
adb forward tcp:9222 localabstract:webview_devtools_remote_$(adb shell pidof com.shenss.rlive)
playwright-cli attach --cdp=http://localhost:9222
```

WSL 的 `adb reverse` 无法把端口接到**另一个 Windows 进程**；若 Windows 侧 1420 被占用或不可达，
在 WSL 内起 `bun run dev --port 1421`，再 `adb reverse tcp:1420 tcp:1421`。启动模拟器前必须用
WSL 的 `adb kill-server` 清理 Windows adb daemon，否则 `forward`/`reverse` 会在两个 server 之间错位。

## 九、已知限制

- **Android 数据来自 x86_64 模拟器**（4 核、Chrome 133），非真机 aarch64。绝对 FPS 偏高，但"面板占
  主线程 54%~64%"这一**相对结论**与桌面一致（桌面同为 250~290 ms/s），方向可信。
- **生产构建的弹幕层在屏数只有 10~30 条**（轨道准入先拒绝），因此生产环境没能复现 dev 高密度场景；
  400/575 条曲线是在 dev 页面用 12px 字号 + 1920×1080 构造的上限探测。
- **行成本对照表**中的"精简行"是同一页面内构造的对照组件，不是项目内既有实现；它证明的是
  "React 协调 + Base UI 组件"这一层的成本量级，不代表可直接替换的方案。
- **`canAttach` 的 O(n²) 结论是预防性的**：当前自耗时仅 0.1~0.2 ms/s，未构成当下瓶颈。
- **未测**：真机触摸点选（`useDanmakuPinInteraction`）与 SuperChat 富文本路径的渲染成本（SC 走独立
  固定组、条数上限 3，预期不构成瓶颈）；VOD 全链路（真实视频解码 + 弹幕并行），只测了 `setComments`
  的纯计算成本；`will-change` 分档策略的收益。
- 所有测量在 WebView2 154 / Chrome 133 完成；生产对照用的普通 Chromium 与项目 `chrome120` 目标同代，
  但 `Style` / `Task` 的绝对值与 WebView2 存在平台差异（同场景下 WebView2 的 Style 约为 Chromium 的 2 倍），
  **只做同一平台内的前后对比**。
