# rLive 未来路线图

> 状态：规划提案  
> 基线日期：2026-08-20  
> 当前源码版本：`2.3.1`

## 1. 路线图定位

本路线图描述工作顺序、完成条件和决策门槛，不承诺发布日期。rLive 同时依赖直播平台接口、WebView、FFmpeg、sherpa-onnx 和各操作系统打包链，未经真机与分发验证的能力不能仅凭“代码可编译”标记为完成。

路线图分为三层：

- **近期承诺**：稳定当前能力、收敛架构契约、完成可发布性工作。
- **中期方向**：提高播放 / 录制可诊断性、平台适配韧性和跨平台交付质量。
- **条件性候选**：新平台、自动更新、移动端重能力和新的内容组织能力，必须先通过决策门槛。

功能排序遵循“可靠播放 > 数据安全 > 可维护性 > 新能力数量”。

## 4. R0：基线与发布事实统一

目标：任何使用者都能从版本、文档和 Release 得到一致结论。

### R0.1 明确版本序列

- 核对 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 与 `Cargo.lock` 根包版本。
- 以 `2.0.0` 作为固定断代版本，核对 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 和 `Cargo.lock`。
- 在 Release 说明中明确旧数据库、profile、localStorage、LAN Sync、录制配置和录制 bundle 的拒绝/跳过行为；升级前由用户在旧版本自行导出或备份。
- Release 页面、README 的“当前支持平台”和 workflow 实际产物必须一致。

### R0.2 保存可复验基线

- 保存一份不含凭据的旧 profile、旧数据库、旧 FLV、旧 HLS 和缺字段 metadata fixture，仅用于确认 2.0 拒绝或跳过且不改写，不用于迁移。
- 记录 Windows / Linux 当前可用构建环境、FFmpeg 版本、Sherpa runtime 清单和 SHA-256。
- 把人工验证结果关联到具体 commit，不使用“之前测过”作为发布证据。

完成条件：

- 发布顺序有明确决策记录。
- README、发布流程、版本号和实际可下载产物无冲突。

## 5. R1：契约和依赖边界收敛

目标：降低新增字段、command 和缓存更新时的多点同步成本。

范围对应代码简化计划中的 CS-0 与 CS-1：

- 建立领域 API，禁止 feature 直接使用裸 `invokeCmd` 字符串。
- 为 `AppSettings`、`PlayUrl`、`RecordingItem`、事件 payload 和 profile 策略建立跨语言 fixture。
- 把 query key、query options、mutation 与缓存更新放回领域模块。
- 清除 `shared -> features` 反向依赖，重新归属共享播放器和弹幕纯逻辑。
- 增加静态边界检查，防止重构后再次分散。

交付物：

- `shared/api/commands` 与领域 query key factory。
- 设置默认值 / normalization / profile 字段策略测试。
- IPC command 清单和事件清单。
- 依赖方向检查。

完成条件：

- 业务 JSX 中没有 command 字符串和临时 response type。
- 新增一个设置字段时，权威修改点、UI adapter 和测试位置清晰可枚举。
- profile 不会因 schema 自动化意外包含 Cookie、发送授权、本机路径、ASR 本机配置或私有 M3U。

## 6. R2：播放与录制内核简化

目标：在不改变用户行为的前提下，让核心生命周期可局部推理和测试。

### R2.1 播放 runtime

- 完成 `shared/player/runtime`，统一直播、IPTV 和多画面的 proxy + xgplayer 生命周期。
- 保持播放恢复会话与媒体生命周期会话分离。
- 把全屏、PiP、音频、source profile 和 transport fact 分成可测试模块。
- 收缩 `useWebPlayer` 与 `PlayerPane`，页面不直接管理底层资源 generation。
- 录制回放复用媒体内核与控制基础层，但保留独立时间轴和 seek 语义。

完成条件：

- 多播放器之间的 proxy、全屏和音频所有权有完整场景测试。
- 快速切房、旧 cleanup、软切换失败、HLS fatal、Twitch token 过期和 IPTV 重连均保持有界。
- `/iptv` 发现页的“零播放器、零代理”约束有自动化 smoke。

### R2.2 录制 manager

- 按 model、storage、metadata、session、danmaku、playback server 拆分 `recording.rs`。
- 保持 FFmpeg remux、自动分段、finalizing fence、磁盘保护和 graceful shutdown 不变量。
- 让当前 v2 录制格式验证、旧 bundle 跳过测试与 manager 并发测试分属对应模块。
- 为录制目录外部变更、损坏 metadata 和 `.part` salvage 建立清晰错误分类。

完成条件：

- 录制磁盘格式未改变。
- 关键失败路径可以从测试名称定位到 owner 模块。
- manager facade 不再包含 HTTP Range、JSONL 格式和 storage transaction 细节。

### R2.3 FLV tag 感知直录（候选，未承诺）

背景：2.3.1 之前，FLV 录制在 libavformat 层开启了 `reconnect` 系列参数。FLV 是单条连续字节流，重连只在字节层续接、不认容器边界，因此上游断线后新响应的 FLV 头与 `onMetaData` 会被写进未完成的 H.264 slice 内部，产出容器结构完好但解码失败的文件（播放器报 `PIPELINE_ERROR_DECODE`）。2.3.1 已把重连参数收敛到 HLS 并加上 `+discardcorrupt`，代价是 FLV 断流即结束当前任务。

本项目标是让 FLV 断流可以在**不丢弃已录内容、也不污染码流**的前提下续录：

- 扩展现有 `run_direct_recording` 裸流路径，使其解析 FLV tag 头（type / 长度 / 时间戳 / PrevTagSize），按 tag 边界写盘。
- 重连后丢弃未写完的半个 tag，跳过新响应的 9 字节文件头、`PrevTagSize` 与重复的 `onMetaData`，并把新流时间戳平移到已写内容之后，保持单调。
- 重连策略复用弹幕侧已有的失败流式退避约定（仅有效会话重置失败计数），不新增第二套参数。
- 保留 `stream_proxy` 注入请求头的统一路径，不在录制侧复制一份 header 逻辑。

参考实现：biliLive-tools 用同样的判断把 `-reconnect` 限制在 HLS，并为 FLV 备了 B 站录播姬（`bililive-recorder downloader`）作为专用后端；DouyinLiveRecorder 则对 FLV 走 httpx 裸流直下、完全绕过 ffmpeg。两者都不在 FLV 流内做字节级续接。

进入条件：

- R2.2 录制 manager 拆分完成，session 与 storage 边界稳定。
- 有可复验的断流 fixture（含 CDN 切换、5xx、连接重置三类），能离线验证重连后码流仍可解码。

完成条件：

- 断流续录后的文件在 xgplayer 与 ffmpeg 下均可完整解码，无截断 slice。
- FLV 录制不再依赖 libavformat 的 HTTP 重连。
- 时间轴与弹幕 sidecar 在续录点保持对齐。

## 7. R3：平台适配与质量体系

目标：平台接口变化时快速定位，CI 失败时能区分代码回归与外网上游波动。

### R3.1 平台 adapter 健康

- 各站点拆出 transport、parser、playback 和 fixture tests。
- 各弹幕协议拆出 connect、frame、parser、send 和 identity matcher。
- 为公开响应保存脱敏 fixture；fixture 不含 Cookie、token、用户 ID 或可重用签名。
- 建立开发者可运行的 opt-in live smoke，输出站点、阶段和错误码，不输出请求秘密。
- 维护平台能力矩阵：浏览、分页、搜索、房间、播放、弹幕接收、发送及其账号条件。

### R3.2 CI 质量

- 前端增加 `format:check`。
- Rust 增加 `fmt` 和经过噪声治理的 `clippy`。
- 增加无外网 Playwright smoke，覆盖路由、设置、IPTV 发现页和空录制库。
- 对 release workflow 使用的版本、runtime 文件清单和 SHA-256 增加自动核验。
- 保留真实平台 smoke 为手动或定时任务，不让它阻塞普通 PR。

完成条件：

- parser 回归可以完全离线复现。
- 普通 CI 不需要私密账号、本地 ASR 模型或正在直播的房间。
- 平台上游变化能映射到一个 adapter 阶段，而不是表现为泛化“播放失败”。

## 8. R4：跨平台发布闭环

目标：把“代码支持”提升为“可下载、可安装、可运行、可复验”。

### R4.1 Windows

- 记录应用整体分发结论。FFmpeg 已改为自建裁剪版 LGPL 2.1 shared 构建，不再启用 `--enable-gpl`，原 GPLv3 审计项不再适用。
- 在未预装 FFmpeg、Sherpa 和开发工具的干净 Windows x64 环境验证 NSIS 与 MSI。
- 验证首次启用 ASR 的 runtime 下载、校验、加载和失败恢复。
- 评估 Authenticode。没有证书时，Release 必须明确 SmartScreen 预期，不伪装为已签名。

### R4.2 Linux

- 固定 FFmpeg SDK / runtime 来源、版本、校验和与许可文件。
- 验证 DEB、RPM、AppImage 的 RUNPATH 及 CPU-only 动态库清单。
- 在无开发包的 Debian / Ubuntu 与至少一个 RPM 系发行版验证 HLS / FLV 播放、录制和本地字幕。
- 验证 CPU provider；Windows CUDA 路径必须在匹配 NVIDIA driver、CUDA 和 cuDNN 的真机单独标记。

### R4.3 macOS

- 分别验证 Apple Silicon 和 Intel 构建。
- 固定 FFmpeg dylib，重写 install name，并纳入签名范围。
- 建立 Developer ID 签名、公证、staple 和首次启动验证。
- 验证 WebKit HLS、FLV / MPEG-TS MSE、录制目录权限、麦克风 / 音频采集和 ASR runtime。

### R4.4 Android

- 建立至少覆盖 API 24、一个中间版本和当前主流版本的真机矩阵。
- 验证横竖屏、系统栏、返回键、音量 / 亮度、网络切换和后台恢复。
- 核验 APK / AAB 签名、`versionCode`、arm64-v8a 和商店安装路径。
- 继续明确不支持桌面录制、多画面和本地 ASR，直到单独方案通过决策门槛。

完成条件：

- 每个宣称支持的平台都有干净环境记录和对应 Release artifact。
- `SHA256SUMS.txt`、运行库许可证、签名状态和文档与产物一致。
- 尚未完成的平台继续标记“代码支持，未验证”，不提前升级文案。

## 9. R5：可诊断性与本地媒体能力

该阶段建立在内核边界稳定之后，避免诊断功能继续耦合到大文件。

### R5.1 脱敏诊断包

提供用户显式触发的本地诊断导出，候选内容包括：

- 应用版本、操作系统、WebView、播放器协议和功能开关；
- 最近一次播放恢复状态转移和脱敏错误码；
- proxy 聚合遥测，不含 URL query、headers、Cookie 或 token；
- 录制任务状态、FFmpeg 错误分类和磁盘空间摘要；
- runtime 文件存在性与版本，不打包模型或媒体文件。

诊断包必须先定义 redact 测试，再实现导出。默认不上传，由用户决定如何提供。

### R5.2 录制库健康与数据检查工具

- 扫描 bundle 完整性、metadata、媒体可读性、sidecar 和 ASS 状态。
- 对可恢复的 `.part`、`.tmp`、`.bak` 提供预览和明确操作，不静默覆盖。
- 对旧版本、缺字段、未知字段或损坏 metadata 只输出清晰的诊断结果；2.0 不提供批量转换、补索引或旧 bundle 迁移。
- 任何未来的离线转换工具都必须是独立工具，不得重新进入 rLive 运行时读取路径。

### R5.3 性能基线

- 保存首页首屏 bundle、进入房间时间、proxy 首字节、播放器首帧、内存和 CPU 基线。
- 多画面分别记录 2 / 4 / 6 路的解码、网络和内存预算。
- 录制记录 1 / 4 路 remux、自动分段和低磁盘条件下的资源占用。
- ASR 分别记录 CPU 和 Windows CUDA 的实时率与内存。

完成条件：

- 用户报告可以在不暴露凭据的前提下定位到站点、proxy、播放器、录制或 ASR 阶段。
- 旧录制拒绝/跳过有真实 fixture 和 warning 诊断支撑；rLive 运行时不承诺旧录制兼容。
- 性能优化以对比数据验收，不以主观流畅度结论验收。

以下项目不是当前承诺，只在前置条件满足后进入版本计划。

| 自动更新 | Windows / macOS 签名、发布密钥管理、回滚和差分包验证完成 | 暂缓，不能在未签名分发上直接启用 |

继续排除礼物 / 支付、付费内容绕过、批量发送、自动回复、平台内容托管和未经授权的离线下载。

## 11. 优先级与容量建议

在团队容量未知时，不给出虚假的日期。建议以“一个高风险生命周期工作包 + 一个低风险契约 / 测试工作包”为一个迭代上限，并保持以下 WIP 规则：

- 同时最多一个播放或录制高风险重构。
- 平台接口紧急修复可以插队，但必须补回脱敏 fixture。
- 发布合规和真机阻塞由独立 owner 跟踪，不用功能 PR 掩盖。
- 简化阶段冻结新的跨平台重功能，避免旧边界尚未稳定就扩大维护面。

相对工作量用于排期比较：

| 工作项 | 估算 | 风险 | 说明 |
| --- | --- | --- | --- |
| R0 版本与演练决策 | S | 中 | 代码量小，历史产物和人工演练是关键 |
| R1 领域 API 与 query key | M | 中 | 可按领域渐进迁移 |
| R1 settings contract | M | 中 | 涉及 profile 安全策略 |
| R2 播放 runtime | L | 高 | 多平台、多实例和资源 cleanup |
| R2 录制拆分 | L | 高 | 磁盘事务和后台任务不变量多 |
| R2.3 FLV tag 感知直录 | M 到 L | 高 | 需自建 FLV 解析与续录时间轴，依赖断流 fixture |
| R3 adapter / fixture | L | 中 | 可按平台分批完成 |
| R3 CI smoke | M | 低到中 | 需稳定测试数据和运行环境 |
| R4 Windows 收口 | M | 中 | 主要是许可、干净机和签名决策 |
| R4 Linux / macOS | L | 高 | runtime、签名和真机资源决定周期 |
| R5 诊断与录制健康 | M 到 L | 中 | 必须在内核模块化后实施 |

`S`、`M`、`L` 仅表示相对量级，不映射固定周数。
## 12. 每阶段通用验收

每个阶段交付前都应回答：

1. 用户可观察行为发生了什么变化，哪些明确没有变化？
2. Windows、Linux、macOS、Android 中哪些实际验证，哪些只是编译通过？
3. 是否改变 SQLite、profile、localStorage、录制 bundle 或 IPC schema？
4. 是否新增 Cookie、token、路径、字幕或媒体内容离开设备的路径？
5. 哪些检查自动化，哪些仍依赖人工和真实平台？
6. 文档、版本和 Release artifact 是否表达同一支持范围？

## 13. 路线图更新规则

- 完成项必须附带 commit、测试和真机 / 干净机证据，不能只把表格改成“完成”。
- 上游平台变化优先更新能力矩阵和限制，再决定是否调整里程碑。
- 新功能进入近期承诺前，必须写清 owner、依赖、数据边界和退出条件。
- 版本号分配在 R0 发布序列明确后进行；路线图阶段不自动等同于 SemVer minor。
- 架构工作状态以[代码简化计划](代码简化计划.md)为准，平台与发布状态以 README、[架构说明](架构说明.md)和[发布流程](发布流程.md)为准。
