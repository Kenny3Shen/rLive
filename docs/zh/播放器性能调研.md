# 播放器性能调研

更新时间：2026-07-25。本文记录 rLive 当前 Web MSE 播放链路的性能判断与后续验证路线。

## 结论

不建议把现有 `mpegts.js` 播放器整体替换成“纯 Rust 播放器”。当前链路中，Rust 负责本机代理和请求头注入，`mpegts.js` 负责 FLV / MPEG-TS 到 fMP4 的解封装与重封装，最终视频解码仍由 WebView2 / Chromium 的 `<video>` 硬件路径承担。

换成 Rust 或 FFmpeg 不会天然提升解码性能，反而会增加 Windows 原生窗口嵌入、D3D 合成、透明控制条/Canvas 弹幕叠层、DLL 分发与编解码器许可等成本。优先顺序应是：**测量 → mpegts Worker 小范围验证 → 按协议补强代理 → 只在 CPU profile 证明必要时研究 Rust transmux PoC**。

## 当前实现与边界

```text
平台播放 URL + Referer / Cookie
  → Rust stream_proxy（localhost、持续字节流转发）
  → mpegts.js 1.8.0（FLV/TS → fMP4）
  → WebView2 MediaSource / <video>（浏览器硬件解码）
  → React 控制层 + Canvas 弹幕
```

当前 `useWebPlayer.ts` 已启用：

- `enableStashBuffer: true`、`stashInitialSize: 384`；
- `liveBufferLatencyChasing: true`，最大延迟 2.5 秒、最小保留 0.4 秒；
- `autoCleanupSourceBuffer: true`；
- 进房时重建 `<video>` 和 MediaSource，避免旧流的黑屏状态；
- Rust 代理复用一个 reqwest 客户端与连接池，连续 HTTP-FLV 不会为每个 chunk 重建 TLS。

目前 `enableWorker` 固定为 `false`，且还没有 `getVideoPlaybackQuality()`、`STATISTICS_INFO`、首帧时间或卡顿计数的运行时遥测。因此现在不能严谨断言卡顿来自 JS transmux、视频解码、网络、MSE 或 Canvas。

## 推荐路线

### 1. 先补可观测性，再调参数

每个播放会话至少采样下列指标，并按平台、清晰度、FLV/TS、WebView2 版本聚合：

| 指标 | 用途 |
|------|------|
| 进房到 `playing` 的时间 | 首帧 / 启动体验 |
| `video.getVideoPlaybackQuality()` 的总帧与丢帧 | 判断解码 / 渲染压力 |
| `buffered.end - currentTime` 与 live edge | 缓冲量和实际延迟 |
| `waiting` / `stalled` 次数与时长 | 重缓冲 |
| mpegts `STATISTICS_INFO` | 网络吞吐、解复用侧压力 |
| JS long task、Canvas 帧预算 | 主线程竞争 |

验收时不要只看“能播放”。建议至少比较首帧 P50/P95、每分钟卡顿、丢帧比例、端到端延迟和 CPU 占用；若指标没有改善，不推广实验配置。

### 2. A/B 验证 mpegts Dedicated Worker

`mpegts.js` 1.8 支持 `enableWorker`，可把 transmux 工作转移到 Dedicated Worker；支持环境还可研究 `enableWorkerForMSE`。这比重新实现播放器风险低得多，也不会替换 Chromium 硬件解码。

建议做成默认关闭的实验开关，只在 Windows WebView2 真机测试后扩大：

1. 先仅开启 `enableWorker: true`，保留主线程 fallback；
2. 分别在 1080p / 60fps、普通画质、弹幕高峰和网络抖动下测量；
3. 对网络稳定的源试验 `enableStashBuffer: false` 降低延迟；网络不稳时继续保留 stash；
4. `MediaSource.canConstructInDedicatedWorker` 不可用或首帧/错误率变差时回退当前配置。

不能把关闭 stash 设为全局默认：官方文档明确它会降低延迟，但会更容易在网络抖动时卡顿。

### 3. 先把 HLS 当作独立问题

当前本机代理适合一条连续的 FLV/TS 上游流：它固定拉起始 URL，不会按客户端路径改写 m3u8、分片、Range 或重定向。`mpegts.js` 也不是完整的 HLS 播放器，不能因为 URL 后缀是 `.m3u8` 就认为 HLS 已被支持。

若产品需要通用 HLS：

- 增加 path/query-aware playlist + segment 代理，安全重写上游 URL；
- 转发 Range、状态和必要响应头；
- 用 `hls.js` 作为 HLS 专用路径，或在经验证的 Edge 原生 HLS 环境走原生路径；
- 保持低延迟 FLV/TS 仍优先走现有 MSE 链路。

### 4. Rust 只作为有条件的 transmux 实验

可考察的 Rust 起点包括 [`transmux`](https://crates.io/crates/transmux)（MPEG-TS → CMAF/fMP4）和 [`scuffle-flv`](https://crates.io/crates/scuffle-flv)（FLV demux）。但它们不会直接把数据送进 WebView 的 SourceBuffer；完整生产链还需处理 AVC/AAC/HEVC codec config、时间戳、断流恢复、背压和 JS/Worker 到 MSE 的交接。

因此仅在 profile 明确显示 JS transmux 是 CPU 热点且 Worker 不足时，再以独立 TS 小样本进行 PoC。评估条件是实测 CPU 和卡顿改善能覆盖 IPC / localhost copy / 维护成本，而不是“Rust 理论上更快”。

### 5. 不建议近期采用原生播放器或 WebCodecs 重写

| 方案 | 结论 |
|------|------|
| FFmpeg / libmpv / GStreamer / VLC | 不作为近期方向。需要原生 DLL、许可证治理、HWND/D3D 叠层和 Tauri UI 合成，不能自然复用当前弹幕与控制层。|
| `ffmpeg-next` | 它是 FFmpeg C API 封装且项目自称 maintenance-only；不是“纯 Rust 解码器”。|
| WebCodecs | 是低层 codec API，输入前仍需 demux，且需要自建 A/V 同步、渲染和回退，适合作为未来实验而非 mpegts 直接替换。|

## 决策表

| 症状 / 目标 | 首选动作 | 不应先做的事 |
|-------------|----------|----------------|
| 高 CPU、Canvas 与播放同时卡 | 加指标，A/B `enableWorker` | 立刻引入 FFmpeg |
| 网络稳但直播延迟高 | 按平台测试关闭 stash | 全局关闭 stash |
| HLS 播放失败 | 做 HLS 专用代理 + hls.js 路径 | 继续把 m3u8 传给 mpegts |
| profile 证明 transmux 占主要 CPU | Rust transmux 小范围 PoC | 全面替换视频解码 |
| 要录制、DRM、特殊 codec | 单独评估 native sidecar | 把它伪装成性能优化 |
