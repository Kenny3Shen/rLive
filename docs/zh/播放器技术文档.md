# 播放器技术文档

更新时间：2026-08-10。本文描述 rLive 当前播放器的实际架构、播放源契约、线路记忆、故障转移、软切换、多画面并发和性能改进方法。它是实现说明，不是播放器方案选型记录。

## 1. 设计目标

播放器需要同时满足以下约束：

- Bilibili、Huya、Douyu、Douyin、Twitch 和 IPTV 共用 Web 播放链；
- 上游需要的 `Referer`、Cookie 和其他请求头只交给 Rust 代理，不暴露给媒体插件；
- FLV、HLS、MPEG-TS 和浏览器原生媒体按结构化协议选择插件；
- 多线路先探测再排序，播放成功后不因后台测速更快而无故中断；
- 同协议换源默认尝试保留播放器，任何异常都回退到完整重建；
- 桌面多画面最多并发 6 个播放器，各路代理生命周期和音量互相隔离；
- 性能数据只在设备内存中用于诊断，不上传、不持久化，也不记录播放地址和请求头。

当前仍由 WebView2 / Chromium 的 `<video>` 和 MediaSource 完成媒体解码与呈现。Rust 负责站点解析、代理和测量，不在播放主路径中进行视频解码。

## 2. 分层架构

```text
站点适配器 / M3U 解析器
  -> LivePlayQuality + PlayUrl[]
  -> usePlaybackController
       -> stream_proxy_probe_sources
       -> 智能排序、手动选择、故障转移
  -> useWebPlayer / IptvPlayer
       -> stream_proxy_start
       -> xgplayer + 协议插件
       -> HTMLVideoElement / MediaSource
  -> React 控制层、Canvas 弹幕、SC、字幕
       -> 本地播放遥测快照
```

| 层 | 主要文件 | 职责 |
|----|----------|------|
| 播放源模型 | `src-tauri/src/models/live.rs`、`src/shared/types/live.ts` | 定义结构化协议和线路元数据 |
| 站点适配 | `src-tauri/src/sites/` | 获取清晰度、播放地址、请求头和平台优先级 |
| 线路控制 | `src/features/room/playback/usePlaybackController.ts` | 记忆恢复、选择、重试和故障转移 |
| 线路记忆 | `src/features/room/playback/linePreference.ts` | 有界本地记录、来源匹配和序号回退 |
| 故障选线 | `src/features/room/playback/sourceSelection.ts` | 选择本轮尚未耗尽的下一条线路 |
| 播放生命周期 | `src/features/room/player/useWebPlayer.ts` | 代理会话、xgplayer、软切换和硬回退 |
| 多画面播放 | `src/features/multi-room/` | 3×3 槽位布局、拖拽交换、独立播放控制与设备本地状态 |
| IPTV 播放 | `src/features/iptv/IptvPlayer.tsx` | HLS、FLV、裸 MPEG-TS 和原生媒体 |
| 本机代理 | `src-tauri/src/stream_proxy.rs` | 请求头注入、HLS 改写、线路探测和代理计数 |
| 本地遥测 | `src/features/room/player/playbackTelemetry.ts` | 媒体、主线程和代理指标的内存快照 |

前后端只通过 Tauri commands 交换播放数据。前端不复制站点签名或上游业务逻辑，媒体插件也只访问 `127.0.0.1` 上当前代理会话返回的地址。

## 3. 结构化播放源

`PlayUrl` 不再只表示 URL，而是一个可排序、可展示、可测量的播放候选：

```ts
type PlayUrl = {
  source_id?: string;
  label?: string;
  protocol?: "flv" | "hls" | "mpeg_ts" | "native" | "unknown";
  priority?: number;
  url: string;
  headers: Record<string, string>;
};
```

| 字段 | 规则 |
|------|------|
| `source_id` | 在一次清晰度结果内稳定，不包含签名 URL、Cookie 或请求头 |
| `label` | 可直接展示的安全线路名称，不展示 CDN 域名 |
| `protocol` | 由站点或 M3U 解析器显式给出；旧数据为 `unknown` 时才根据 URL 回退推断 |
| `priority` | 数值越小越接近平台原始首选顺序，仅在健康状态和延迟相同时作为稳定排序依据 |
| `url` / `headers` | 仅供本机代理请求上游，不能进入遥测快照或错误展示 |

Bilibili、Huya、Douyu、Douyin 和 Twitch 的站点实现均返回结构化线路。IPTV 解析器也写入 `protocol`，前端仅对旧缓存或不透明地址使用兼容推断。

协议到播放实现的映射如下：

| 结构化协议 | xgplayer 路径 | 备注 |
|------------|---------------|------|
| `flv` | `xgplayer-mpegts.js` 兼容插件，`mediaDataSource.type = "flv"` | 连续 HTTP-FLV、低延迟 MSE；复用经过斗鱼、虎牙验证的 `mpegts.js` 解封装路径 |
| `hls` | `xgplayer-hls.js` / `hls.js` | 所有站点统一由 hls.js 解析清单、加载分片并转封装；代理改写主/子清单、密钥和分片 |
| `mpeg_ts` | `xgplayer-mpegts.js` 兼容插件 | 用于裸 MPEG-TS，不等同于 HLS 内的 `.ts` 分片 |
| `native` | xgplayer 核心 + `<video>` | MP4、WebM 等浏览器原生媒体 |
| `unknown` | URL 兼容推断，最终默认 FLV | 只为旧后端和不完整数据保留 |

播放源的语义 key 同时包含 URL、排序后的 headers、`source_id`、`label`、`protocol` 和 `priority`。等价对象不会重建播放器，任一实际路由信息变化都会被识别。该 key 只存在于当前 WebView 内存，不进入诊断快照。

## 4. 代理生命周期

`stream_proxy` 是应用级服务，但不是单活动代理。每个播放器实例生成不可复用的实例 ID，每次完整打开再增加 generation，组合为代理 `session_id`；Rust 分别在 `active: HashMap<String, ProxyInner>` 和 `pending: HashMap<String, u64>` 中保存已启动监听器与启动预留，因此多个播放器可同时持有独立的 localhost 端口。

代理启动遵循以下顺序：

1. 为当前 `session_id` 预留 generation；
2. 构造使用当前应用代理配置的 `reqwest::Client`；
3. 绑定新的 `127.0.0.1` 随机端口并准备 HLS 资源表；
4. 新监听器准备完成后，只原子替换同一 `session_id` 的旧活动监听器；
5. 将只含 localhost 的播放地址返回前端。

旧路由的异步清理只能停止自己持有的 `session_id`。同一会话较旧的 `start` 也会被 generation 栅栏拒绝，而其他会话的预留和活动监听器不受影响，因此快速切房、返回同一房间、多画面并发启动或并发 cleanup 都不会误关无关代理。应用退出时的全局 `stop` 才会清空所有预留并关闭全部活动监听器。

连续 FLV 和 MPEG-TS 按字节流转发。HLS 清单中的相对 URL、子清单、`URI` 属性、密钥和分片会改写到同一 localhost 会话；代理继续携带原始请求头，并转发 Range 与必要响应元数据。

### 4.1 多画面播放

桌面 `/multi-room` 最多挂载 6 个 `MultiRoomPlayer`。每个组件使用稳定的直播间 key 作为 React key 和 `useWebPlayer` 的 `sessionKey`；仅交换槽位时组件会移动而不会因主副角色变化创建新的播放会话。3×3 布局中槽位 0 占据左下 2×2 区域，槽位 1–5 沿上方和右侧排列；拖到已占用槽会交换，拖到空槽会移动。主副切换额外记录每个直播间的副画面槽位：直播间离开主槽时优先回到自己的记忆槽位，若该槽位被临时占用，则把占位副路转移到被提升直播间的原槽位，从而让连续切换保持稳定的位置关系。主槽不能留空，移动或移除当前主画面时会从剩余画面中提升一路。

每路复用 `usePlaybackController` 与 `useWebPlayer`；弹幕连接、Canvas/SC 叠加层、ASR 采集和弹幕发送由 `MainMultiRoomControls` 只为主画面挂载，副路不挂载这些能力，两者都不挂载房间侧栏。`useWebPlayer` 在媒体元素挂载和自动播放前应用该路的初始音量：首路为 80%，新增副路为 0% 且静音，防止副路先以单房间默认音量短暂出声。暂停、刷新、静音和音量状态均按直播间独立；主副交换时新主解除静音（0% 恢复 80%），所有副路静音，音量数值仍保留。

全屏归属于主画面单路。原生窗口全屏是窗口级状态，同一窗口内的 6 路播放器都会观察到同一结果，因此 `useWebPlayer` 增加 `fullscreenOwner` 选项：多画面只对主画面传入 `true`，副路传入 `false`。非归属播放器的 `mode` 恒为 `windowed`，既不监听 `fullscreenchange`，也不订阅原生窗口的 resize 同步，`toggleFullscreen` 直接返回，避免全部副路同时被标记为全屏。房间页与 IPTV 播放页不传该选项，默认仍为归属方。

主画面的容器同时带上 `data-player-stage` 与 `data-fullscreen`，复用 `styles.css` 中既有的舞台规则：全屏时该 `<article>` 以 fixed 全窗口图层脱离 3×3 网格，因此填满屏幕的是主画面本身，而不是整个导播矩阵和应用外壳。主画面被降级、拖走或移除时，`useWebPlayer.exitFullscreen()` 会在归属转移前退出全屏，不会留下一个包着整个网格的全屏窗口。

槽位、位置记忆、基础房间元数据和各路音量由 Zustand persist 写入设备 localStorage `rlive-multi-room`，不进入 SQLite、配置导入导出或远程同步。最多 6 路是 UI 和持久化规范化共同执行的硬上限。

### 4.2 控制层的移动端安全区约定

Android 以 `enableEdgeToEdge()` 运行，`index.html` 使用 `viewport-fit=cover`，因此 `env(safe-area-inset-*)` 会给出真实的系统 UI 遮挡高度。关键约束是：这些值描述**窗口**边缘被遮挡多少，不描述某个元素与屏幕的距离。只有当元素自身贴着窗口对应边时，才可以直接把它当作自己的 padding。

播放器控制层并不总是贴着窗口底边。竖屏房间在打开侧栏后是堆叠布局——视频在上、弹幕面板在下，控制栏浮在视频画面底边，下方是面板而非屏幕边缘；IPTV 播放页的 stage 是 `relative aspect-video`，下方还有 footer；多画面里每路只是 3×3 网格中的一格。这些情形下引用 `env(safe-area-inset-bottom)` 会凭空多出一段与实际遮挡无关的偏移（竖屏手势导航条约 17 CSS px）。

因此 `PlayerControls` 用纯函数 `playerControlsAvoidSystemGestureBar(fullscreen, stackedBelowPlayer)` 显式判定是否需要避让：全屏、或播放器铺满视口时需要；由调用方通过 `stackedBelowPlayer` 声明自己堆叠在其他内容之上时不需要。房间页传入 `portraitStackedPlayer`，IPTV 播放页与多画面固定传入该标记。

叠加在画面上的 SuperChat 与 ASR 字幕必须与控制栏共用同一基准，否则控制栏收缩后它们仍按旧偏移定位。两者不再各自引用 `env()`，而是读取 stage 上的 `--player-chrome-inset` 变量，该变量由房间页按同一条件设值。判定逻辑的回归测试在 `tests/player-controls.test.ts`。

Android 构建、ABI 与真机验证见 `docs/zh/Android开发-Windows.md`。

### 4.3 全屏顶部 HUD

全屏时 stage 是 `position: fixed; z-index: 60` 的全窗口图层，会完整覆盖 `RoomTopBar` 和房间底部操作栏，房间标题、主播身份和房间级操作因此全部消失。`src/features/room/PlayerFullscreenHud.tsx` 把这些信息重新画在画面顶部：左上角是标题、主播头像与名称、平台房间号和热度，右上角是「更多房间操作」溢出菜单。

HUD 是 stage 内与底部控制栏同级的兄弟节点（`absolute inset-x-0 top-0 z-30`），不占布局高度，只在全屏时挂载。是否渲染由纯函数 `showPlayerFullscreenHud({ fullscreen, hasRoomIdentity, hasActions })` 判定：仅全屏不足以渲染，房间既没有可用标题/主播也没有任何菜单项时不挂载，避免在画面顶部留下一条空 scrim。热度文案由 `playerHudOnlineLabel` 归一化，平台未上报时整段隐去。两个函数的回归测试在 `tests/player-controls.test.ts`。

显隐直接接入既有的命令式机制：`setControlVisibility` 同时遍历顶部 HUD 与底部控制栏两个 ref，改写 `data-visible` / `aria-hidden` / `inert`，由 CSS 完成合成层淡入淡出，两层用同一个 idle timer 同步出现和消失，全程不触发 React 重渲染，因此不会打断视频与 Canvas 弹幕。键盘可达性也按两层计算：`hasKeyboardFocusWithinControls` 与失焦处理都同时认两个 ref，Tab 在顶部 HUD 与底部控制栏之间移动不会被误判为离开 chrome 而重启倒计时；Tab 唤出 chrome 时按 DOM 顺序从顶部 HUD 开始。菜单打开期间通过新增的 `"hud"` 交互来源参与 idle 栅栏，Android 返回键先关菜单而不是退出全屏或离开房间。

顶部渐变使用 `styles.css` 中的 `player-scrim-overlay-top`，与底部 `player-scrim-overlay` 同材质、反方向，浓度略低（顶部只承载文本）。两者都坚持纯 sRGB 停止值，理由与底部一致：过旧的 Android WebView 无法解析 `in oklab` 会丢弃整条声明。

HUD 内的菜单必须 `container={player.stageRef}`：Base UI 默认 portal 到 `<body>`，会被 `:fullscreen` 的 top layer 压住。`isPlayerEdgeGestureIgnoredTarget` 也加入 `[data-player-hud]`，避免在 HUD 上按下触发亮度/音量拖动或 stage 的单击/双击。

复制链接、复制直链、关注/取消关注和加入多画面由 `RoomPage` 通过 `fullscreenRoomActions` 下传，复用已有的 `copyRoomValue` / `toggleFollow` / `openInMultiRoom`，不在播放器内新增平行实现；`PlayerPane` 自己的播放开关（静音、纯音频、弹幕、字幕、画中画）复用已发布给移动端房间操作表的同一份列表。带 `exitsFullscreen` 的项（关注、多画面）在执行前先 `exitFullscreen()`，因为它们的后续界面是对话框或路由跳转，只存在于应用层。Toast 同理：`Toaster` 的 portal 目标改为可切换，`PlayerPane` 在全屏期间通过 `setToastPortalContainer(stage)` 把通知视口移入 stage 并抬高到控制栏之上，退出全屏时还原为 `<body>`。

### 4.4 移动端亮度、音量手势与会话边界

手势开始后先经过 `12 px` 纵向意图阈值和方向锁定，再以完整画面高度映射 0–100 连续浮点值；画面左右半区分别固定为亮度与音量，不会在同一次拖动中换边。中央 HUD 显示当前手势百分比和连续进度条，只在出现与消失时用 GSAP 动画 `transform` / `opacity`，并尊重 `prefers-reduced-motion`。Android 音量最终按设备媒体音量档位取整，原生命令回读实际百分比用于控制栏展示。

Android 左侧手势通过 Tauri 命令写 `Activity.window.attributes.screenBrightness`，从不写 `Settings.System`。TypeScript、Rust 与 Kotlin 全链路保留浮点百分比，快速 pointer move 先在前端合并，再按顺序写入原生窗口。退出房间、直接切换到另一房间或页面进入后台时，清理会等待在途写入完成后再恢复进入手势前的窗口值；`MainActivity.onPause` 仍作为 WebView 生命周期之外的兜底释放点。没有原生亮度桥的 iOS/移动浏览器使用合成层黑色遮罩，只调整当前播放器画面。

Android 右侧手势、控制栏音量滑块、静音按钮和 IPTV 播放页音量统一调用原生 `AudioManager.setStreamVolume(STREAM_MUSIC, …)`。前端以 `50 ms` 窗口合并快速输入，亮度与音量写入经同一异步队列串行跨越 Tauri IPC；Kotlin 写入时关闭系统提示音与震动，再返回设备实际档位。WebView 媒体元素在 Android 保持 `100%` 增益，避免播放器音量与系统音量叠乘。系统媒体音量与硬件音量键共用且不会在离开播放页时恢复；非 Android 移动端仍直接写当前 `<video>.volume` / `.muted`，桌面多画面继续保留各路独立音量。

## 5. 线路记忆与故障转移

直播房间取得 `PlayUrl[]` 后先读取设备本地的逐房间线路记忆。键由 `site_id + room_id` 组成，值只包含安全的 `source_id`、上次序号和更新时间，不保存 URL 或 headers。恢复时优先在新列表中匹配 `source_id`；平台调整来源标识或不提供标识时，才把上次序号限制到当前列表范围内。没有记忆时使用平台原始顺序。

只有用户在播放器菜单中手动选择线路时才更新记忆，自动故障转移不会覆盖用户偏好。记录采用最近使用顺序并限制为 100 个房间；localStorage 不可用、内容损坏或容量不足时静默退回平台顺序。恢复在线路 URL 交给子播放器前完成，因此不会先启动线路 1 再切到记忆线路。

播放器故障时先由协议插件执行有界网络重连，再由控制器按平台预算重建当前播放器：斗鱼、虎牙当前线路最多完整重建一次，其他站点最多两次，随后从平台顺序中选择本轮尚未耗尽的其他线路。同一播放器 generation 在 `750 ms` 内连续上报的 `error` / `eof` 会合并，避免一次故障重复消耗预算。一次 `playing` 只表示已经重新出画面；必须连续稳定播放至少 30 秒，下一次故障才会清除旧预算并作为独立故障重新评估全部线路。

`waiting` / `stalled` 事件只更新内存中的缓冲次数和重缓冲时长，不再启动持续卡顿计时器，也不会向控制器上报故障、自动切换线路或重载播放器。B 站 HLS 的 fatal 事件仍由 hls.js 先原地恢复；重复 fatal 必须跨过 20 秒恢复窗口才升级为播放器重建，避免短暂上游波动造成频繁重载。

连续 FLV / MPEG-TS 的上游连接关闭时，播放器直接监听 `mpegts.js` 的 `loading_complete`，不再等 `<video>` 缓冲耗尽后才收到 `ended`。房间 FLV 会在最多三次的续签预算内重新获取房间详情、清晰度和线路；斗鱼因此会生成新的网页播放签名，再用新 URL 完整重建播放器。IPTV 没有站点签名，收到同一事件后复用播放页的自动重连。旧媒体节点的 `ended` 仅在其 generation 仍是当前会话时有效，避免销毁旧播放器时误触发新会话故障。

## 6. 软切换

「软切换」是正式支持且默认开启的播放能力。启用时，HLS、MPEG-TS、FLV 的同协议播放源变化会优先保留 xgplayer 和 `<video>`；关闭时任何播放源变化都会停止旧代理并完整创建新会话。HLS / MPEG-TS 继续请求 seamless 切换；FLV 使用 `seamless: false`，由 `xgplayer-mpegts.js` 在 `URL_CHANGE` 时销毁旧 core、创建新 core 并重新附着到相同媒体元素，不假设不同 CDN 时间戳连续。硬切换路径始终作为兼容性回退。

启用后的状态机：

```text
目标源变化
  |-- 房间变化 / 协议插件变化 / 无活动播放器 ------> 硬重建
  |-- 语义 key 未变化 ------------------------> 保持当前播放
  `-- 同一协议插件且 key 变化
        |-- 新代理启动失败 --------------------> 硬回退
        |-- player.switchURL 不可用 -----------> 硬回退
        |-- HLS/MPEG-TS seamless 成功 --------> 提交新活动源
        |-- FLV core 替换并 canplay ----------> 提交新活动源
        `-- switchURL 抛错 ---------------------> 硬回退
```

质量或线路查询短暂没有 URL 时，同一房间会保留当前有效源，避免元数据空窗先制造黑帧。播放器异步创建期间若目标源再次变化，活动源状态更新会重新触发资格判断，不会把较旧线路静默留在播放器中。

软切换先以同一 `session_id` 准备新代理，再调用 xgplayer `switchURL`。成功后才更新活动源 key；抛错或 12 秒内未进入可播放状态都会递增硬回退 token，触发完整重建。快速连续切换通过 sequence 取消过期操作。FLV 切换期间旧 core 销毁产生的迟到 `loading_complete` 不参与故障计数，`mpegts_error` 仍会上报，订阅会在 `urlchange` 后迁移到新 core。跨 HLS、MPEG-TS、FLV 或 native 插件的变化始终硬切换。

不同 CDN 的时间戳连续性、关键帧间隔和 MSE 状态并不一致，因此正式路径仍以自动硬回退保证兼容性。FLV 回归同时覆盖多次连续 `switchURL`、core 订阅迁移和浏览器真实 H.264/AAC FLV 交替换源；持续验收仍应比较真实平台的黑帧、首帧、错误率和重缓冲，而不是把本地样本通过等同于所有 CDN 均兼容。

## 7. 本地播放遥测

直播播放器每 2 秒生成一次内存快照，并最多保留最近 120 条。关闭或切换播放会话后旧快照不再更新，并在后续采样时从有界队列淘汰；当前没有上传、SQLite 持久化或远程聚合。

| 指标 | 来源 | 解释 |
|------|------|------|
| `startup_ms` | session 创建到首次 `playing` | 代理启动、插件初始化和首帧的组合耗时 |
| `playing_ms` | `performance.now()` | 首次播放后的会话时长 |
| `waiting_count` / `stalled_count` | `<video>` 事件 | 缓冲不足与网络停滞次数 |
| `rebuffer_ms` | waiting/stalled 到下一次 playing | 累计重缓冲时长 |
| `buffered_seconds` | `buffered.end - currentTime` | 当前前向缓冲量 |
| `live_latency_seconds` | `seekable.end - currentTime` | 浏览器时间轴上的 live edge 距离 |
| 总帧 / 丢帧 | `getVideoPlaybackQuality()` | 解码和渲染压力 |
| 分辨率 | `videoWidth` / `videoHeight` | 当前解码尺寸 |
| Long Task 次数 / 时长 | `PerformanceObserver` | React、Canvas 或其他主线程竞争 |
| 代理请求 / 失败 / 字节 | Rust 原子计数 | 上游请求活动和转发规模 |
| 首次 / 最近响应耗时 | Rust 请求计时 | 代理到上游响应头的耗时 |

快照使用安全的 `source_id`、站点、协议、清晰度和 `hard` / `soft` 模式区分会话。代理遥测接口只在请求方仍持有活动 `session_id` 时返回聚合计数，结构中不存在 URL 和 headers。

当前遥测适合本机开发诊断，还不能直接给出跨设备 P50/P95。若未来增加导出，必须让用户显式触发，并在序列化层再次建立字段白名单；不能直接导出内存对象或代理内部错误。

## 8. 当前性能参数

| 路径 | 关键参数 | 当前值 |
|------|----------|--------|
| 房间 / IPTV HLS | `manifestLoadingMaxRetry` / `levelLoadingMaxRetry` / `fragLoadingMaxRetry` | 3 / 3 / 3 |
| 房间 / IPTV HLS | `backBufferLength` / `maxBufferLength` | 30 s / 30 s |
| 房间 / IPTV HLS | `liveSyncDurationCount` / `liveMaxLatencyDurationCount` | 3 / 6 个分片 |
| 房间 FLV（桌面） | `autoCleanupMaxBackwardDuration` / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 15 s / 1 s / 5 s |
| 房间 FLV（移动） | `autoCleanupMaxBackwardDuration` / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 20 s / 1.5 s / 6 s |
| IPTV FLV | stash / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 384 KiB / 0.5 s / 3 s |
| MPEG-TS | stash / 延迟追赶 / SourceBuffer 回收 | 开启，初始 stash 384 KiB |
| 遥测 | 采样间隔 / 内存上限 | 2 s / 120 条 |
| 卡顿判定 | 普通线路 / B 站 HLS | 8 s / 20 s |

HLS 和 FLV 均使用 MSE，流媒体内核只保留 `hls.js` 与 `mpegts.js`。FLV 由 `mpegts.js` 渐进解析并转封装为 fMP4，桌面保留 1 秒追帧余量、5 秒最大延迟和 15 秒后向缓冲，移动端对应放宽到 1.5 秒、6 秒和 20 秒；同协议线路变化保留外层播放器并替换内部 core。所有 HLS 通过 `xgplayer-hls.js` 使用 `hls.js`，关闭低延迟模式并保留 30 秒前后缓冲窗口；致命错误先使用插件内恢复，重复失败再刷新短时播放元数据，B 站 HLS 会先保留 20 秒原地恢复窗口。Twitch 仍保留广告等待与解码清晰度降级策略：若 Chromium/WebView 报告 `PIPELINE_ERROR_DECODE`，播放器会销毁当前 MSE 会话并按清晰度从高到低切换到下一个视频变体，跳过 `audio_only`；没有可降级变体时才显示解码失败。

## 9. 性能改进方法

性能改动应遵循“先分层定位，再单变量实验”：

1. 用 `startup_ms` 和代理响应耗时区分上游慢、代理慢与播放器初始化慢；
2. 用缓冲量、live latency 和重缓冲时长判断延迟参数是否过于激进；
3. 用丢帧率、分辨率和 Long Task 判断解码压力与 Canvas / React 主线程竞争；
4. 分平台、协议、清晰度和硬/软切换模式比较，不把不同流混为一组；
5. 至少覆盖稳定网络、抖动网络、1080p/60fps 和高弹幕量场景；
6. 任何优化只在首帧、每分钟重缓冲、错误率、丢帧率和直播延迟没有明显退化时保留。

优先级建议：

| 优先级 | 改进 | 判断依据 |
|--------|------|----------|
| P0 | 完善真实设备遥测查看与可控导出 | 当前已有采样，但缺少本地聚合视图 |
| P0 | Windows WebView2 真机比较软/硬切换 | 验证时间戳连续性和黑帧，而非只测 API 成功 |
| P1 | 按平台实验 `liveSyncDurationCount`、`liveMaxLatencyDurationCount`、`maxBufferLength` | 稳定网络与抖动网络需要不同取舍 |
| P1 | 补充 HLS 清单、Range、短时签名回归样本 | 减少代理兼容问题被误判为播放器问题 |
| P1 | 将 Canvas 帧预算与遥测时间线关联 | 确认高弹幕量是否造成 Long Task / 丢帧 |
| P2 | Profile 证明 JS transmux 为热点后再做 Rust PoC | Rust 或 FFmpeg 不会天然改善浏览器解码 |

不建议仅因“原生实现可能更快”就切换到 FFmpeg、libmpv、GStreamer、VLC 或 WebCodecs。它们会引入原生窗口/纹理合成、编解码器分发、许可证、A/V 同步和弹幕叠层重做。只有 profile 明确证明当前 transmux 或 WebView 路径是主瓶颈，且 PoC 能量化降低 CPU、卡顿或延迟时，才值得扩大范围。

## 10. 测试与验收

当前自动化覆盖：

- 结构化协议、标签、稳定 source key 和重复 `source_id`；
- 健康、未测速、失败线路的排序和故障转移；
- 正常播放后不因较快探测结果切线；
- 软切换的同插件资格与跨协议硬回退条件；
- 本地遥测的首帧、缓冲、帧、live edge 和敏感字段边界；
- 代理会话所有权、待启动取消、替换时保留旧监听器；
- 两个真实 loopback 代理监听器并发存活、按 `session_id` 独立停止；
- 多画面主槽布局、主副交换、拖到空槽、主槽自动补位与 80% / 0% 音量默认值；
- 全屏顶部 HUD 的渲染条件与热度文案归一化；
- HLS 清单改写、媒体签名检查、HTML 拒绝和应用代理转发。

常用检查：

```bash
bun run check
bun test tests/
cd src-tauri && cargo test --lib
```

自动化不能替代真实 CDN 与 WebView2 验证。软切换、硬件解码、CPU 占用、端到端直播延迟和网络抖动仍需在目标设备上测量。
