## 1. 分层与不变量

媒体解码与呈现由 WebView2 / Chromium 的 `<video>` 和 MediaSource 完成，Rust 只做站点解析、代理与测量，不进入解码路径。

```text
站点适配器 / M3U 解析器 -> LivePlayQuality + PlayUrl[]
  -> usePlaybackController -> 排序、手动选择、故障转移
  -> useWebPlayer / IptvPlayer -> stream_proxy_start -> Video.js 媒体适配器或原生 `<video>`
  -> HTMLVideoElement / MediaSource
  -> Video.js 原生控件 + 业务扩展按钮、DanmakuRenderer 画面弹幕、字幕
```

| 层 | 主要文件 | 职责 |
|----|----------|------|
| 播放源模型 | `src-tauri/src/models/live.rs`、`src/shared/types/live.ts` | 结构化协议与线路元数据 |
| 站点适配 | `src-tauri/src/sites/` | 清晰度、播放地址、请求头、平台优先级 |
| 线路控制与记忆 | `src/features/room/playback/` 下 `usePlaybackController.ts`、`linePreference.ts`、`sourceSelection.ts` | 记忆恢复、选择、重试、故障转移与选线 |
| 播放生命周期 | `src/features/room/player/useWebPlayer.ts` | 代理会话、Video.js 适配器、软切换与硬回退 |
| 控制层 | `src/components/videojs/`、`src/shared/components/player/PlayerControls.tsx` | 原生控件与皮肤、业务扩展按钮、控制条表面 |
| 画面弹幕 | `src/features/room/danmaku/` | 统一 `DanmakuRenderer`、事件映射、富文本与操作菜单 |
| 多画面 | `src/features/multi-room/` | 2/4/6 槽位布局、主副交换、时钟同步、设备本地状态 |
| IPTV 播放 | `src/features/iptv/IptvPlayer.tsx` | HLS、FLV、裸 MPEG-TS 与原生媒体 |
| 卡片悬停预览 | `src/features/room/player/roomCardPreview.ts`、`useRoomCardPreview.ts` | 全局单例预览会话、最低画质静音低缓冲播放 |
| 本机代理 | `src-tauri/src/stream_proxy.rs` | 请求头注入、HLS 改写、代理计数 |

必须保持的不变量：

- 上游 `Referer`、Cookie 与其他请求头只交给 Rust 代理；媒体插件只访问 `127.0.0.1` 上当前代理会话返回的地址。
- 前后端只通过既有 Tauri commands 交换播放数据，前端不复制站点签名或上游业务逻辑。
- 代理遥测只在设备内存中聚合，不上传、不持久化，不记录播放地址和请求头。
- 多线路按适配器给出的优先级排序，不做运行时测速；同协议换源默认保留播放器，任何异常都回退到完整重建。

## 2. 结构化播放源契约

`PlayUrl` 是可排序、可展示、可测量的播放候选，不只是 URL：`source_id?`、`label?`、`protocol`、`priority?`、`url`、`headers`（定义见 `src/shared/types/live.ts`）。

| 字段 | 规则 |
|------|------|
| `source_id` | 在一次清晰度结果内稳定，不含签名 URL、Cookie 或请求头 |
| `label` | 可直接展示的安全线路名称，不展示 CDN 域名 |
| `protocol` | 必填；由站点或 M3U 解析器显式给出，上游无协议元数据时写 `unknown` |
| `priority` | 数值越小越接近平台原始首选顺序，仅在健康状态与延迟相同时作为稳定排序依据 |
| `url` / `headers` | 仅供本机代理请求上游，不能进入代理遥测或错误展示 |

五个站点与 IPTV 解析器都写入 `protocol`；只有值为 `unknown` 时播放器才按 URL 推断。

| 协议 | 播放路径 | 说明 |
|------|----------|------|
| `flv` | `mpegts.js`，`mediaDataSource.type = "flv"` | 连续 HTTP-FLV，低延迟 MSE |
| `hls` | Video.js HLS 适配器 / `hls.js` | 由适配器选择 MSE 引擎解析清单、加载分片并转封装 |
| `mpeg_ts` | `mpegts.js`，`mediaDataSource.type = "mpegts"` | 裸 MPEG-TS，不等同于 HLS 内的 `.ts` 分片 |
| `native` | 原生 `<video>` | MP4、WebM 等浏览器原生媒体 |
| `unknown` | 按 URL 推断 | 协议元数据不透明时仍按既有规则选择播放路径 |

播放源语义 key 由 URL、排序后的 headers、`source_id`、`label`、`protocol` 和 `priority` 组成：等价对象不重建播放器，任一路由信息变化都会被识别。该 key 只存在于当前 WebView 内存。key 的构造与还原、以及「能否原地重连」的判定集中在 `src/features/room/playback/sourceIdentity.ts`，恢复会话与媒体生命周期共用同一份，避免两处对「同一个源」得出不同结论。

### 2.1 DASH 续播与销毁顺序

B 站点播通过 MPD `#t=秒` 在首次分片调度前定位，不在 `loadedmetadata` 后重复 seek；临时分片失败先交给 dash.js 自身重试，不叠加逐片重建播放器的循环。

`DashAdapter` 10.1.0 的 `destroy()` 先调用 `attachView(null)`，随后 dash.js 清理控制器时已找不到旧媒体，遗留的 `seeking` / `seeked` / `progress` 监听会在下一会话反复访问空的 `streamInfo.id`。共享播放器因此必须先在媒体仍绑定时同步设置 DASH `source = null`，停止分片调度并解绑监听，再销毁适配器。清源失败也执行销毁和媒体清理；此顺序不适用于 HLS（HLS 清源会异步排队新加载）。

历史回归使用真实引擎和本地 DASH 样本（原夹具与样本已移除，可从 Git 历史查阅），在同一媒体上连续续播到 6 / 4 / 6 秒；断言不下载首片、单次分片 503 由引擎重试后恢复且不报告终止错误、销毁后不残留旧监听。Windows WebView2 已验证；另用真实 B 站 720P、399.7 秒稿件从 30 / 60 秒起播，两轮均达到 `readyState = 4` 并继续推进且无播放错误。不代表所有平台与真实 CDN 均已覆盖。

## 3. 代理会话生命周期

`stream_proxy` 是应用级服务但不是单活动代理。每个播放器实例生成不可复用的实例 ID，每次完整打开递增 generation，组合为 `session_id`；Rust 分别用 `active: HashMap<String, ProxyInner>` 与 `pending: HashMap<String, u64>` 保存活动监听器与启动预留，因此多个播放器可同时持有独立 localhost 端口。

启动顺序：为当前 `session_id` 预留 generation → 构造带应用代理配置的 `reqwest::Client` → 绑定新的 `127.0.0.1` 随机端口并准备 HLS 资源表 → 新监听器就绪后只原子替换同一 `session_id` 的旧监听器 → 返回只含 localhost 的播放地址。

所有权规则：异步清理只能停止自己持有的 `session_id`；同一会话较旧的 `start` 被 generation 栅栏拒绝；其他会话的预留与监听器不受影响。只有应用退出时的全局 `stop` 会清空全部预留与监听器。

转发规则：FLV 与 MPEG-TS 按字节流转发；HLS 清单中的相对 URL、子清单、`URI` 属性、密钥与分片都改写到同一 localhost 会话，代理继续携带原始请求头并转发 Range 与必要响应元数据。

主清单 302 钉扎：HLS 会话的 `/live` 重载会重放首个成功应答的最终 URL，而不是每次重新进入原始入口。一些 IPTV 入口按请求 302 轮换到 MEDIA-SEQUENCE 基数与分片路径完全不同的后端，hls.js 依赖清单重载之间的序列连续性，重进入口会在轮换瞬间被甩上另一条时间轴，表现为播放一段时间后必然断流重连。钉扎地址失效（签名过期或后端下线）时回退原始入口重新解析并重新钉扎；FLV/MPEG-TS 与 Twitch 续期路径不参与钉扎。

## 4. 多画面

桌面 `/multi-room` 支持 2、4、6 画面，最多挂载 6 个 `MultiRoomPlayer`，6 路是持久化规范化的硬上限。

- 布局：2 画面 `grid-cols-2 grid-rows-1`；4 画面左主右副用 3×3 网格（槽位 0 跨左侧 3×2），均分用 2×2；6 画面 3×3，槽位 0 占左下 2×2。已有路数超过目标容量时拒绝切换。
- 组件 key 与 `useWebPlayer` 的 `sessionKey` 都用稳定的直播间 key，交换主副或切换排列不创建新会话。状态只保存槽位，不维护平行位置元数据；移除后紧凑排列。
- 主画面（槽位 0）独占音频、弹幕连接、DanmakuRenderer 画面弹幕与 SC、ASR 采集、弹幕发送和全屏；副路不挂载这些能力，两者都不挂载房间侧栏。多画面画面弹幕默认关闭（`osdOn` 初始 `false`）。
- 音量在媒体元素挂载和自动播放前应用：首路 80%，新增副路 0% 且静音。暂停、刷新、静音、音量按直播间独立；主副交换时新主从 0% 恢复 80%，其余静音。多画面按槽位各存一份音量，不参与跨播放页的共享音量记忆（见第 7.1 节）。
- 全屏归属由 `useWebPlayer` 的 `fullscreenOwner` 决定，多画面只对主画面传 `true`。非归属播放器 `mode` 恒为 `windowed`，不监听 `fullscreenchange`、不订阅原生窗口 resize，`toggleFullscreen` 直接返回。房间页与 IPTV 播放页不传该选项，默认为归属方。主画面被降级、拖走或移除前会先 `exitFullscreen()`。主画面全屏时其顶部 HUD 最左侧出现返回箭头（`OverlayIconButton`，tooltip portal 进 stage），点击 `exitFullscreen()` 退出；它随 HUD 一起受空闲计时器淡入淡出。
- 容量与排列、槽位、基础房间元数据、各路音量、`syncMode` 与 `syncOffsets` 由 Zustand persist 写入 localStorage `rlive-multi-room-v2`，不进 SQLite、配置导入导出或远程同步；旧 `v1` key 不读取、不迁移。

### 4.1 直播时钟同步

目标是各路展示同一时刻内容，只做秒级、不做帧级。只能把画面往后延（seek 回已缓冲内容），不能超过已接收的 live edge。

时钟来源两档：

| 档位 | 来源 | 推导 |
|------|------|------|
| `program-date` | HLS `EXT-X-PROGRAM-DATE-TIME`，`getVideoJsHlsCore().programDateMs()` 读 `hls.playingDate` | `epochAtMediaZero = playingDate - currentTime` |
| `stream-anchor` | `stream_proxy` 每会话锁存一次的 `first_media_at_ms`，配对首次观测的 `buffered.start(0)` | `epochAtMediaZero = first_media_at_ms - mediaTimeOrigin` |
| `none` | 抽不到时钟 | 只能按自己的 live edge 延后 |

`stream-anchor` 含 CDN 边缘 burst，只在各路之间可比，不是真正采集时刻；硬切换、软切换和更换 `<video>` 都会作废锚点，且只在缓冲跳度不超过 20 s 时采信，否则该路降为 `none`。

内置追帧必须先解除：`mpegts.js` 的 `liveBufferLatencyChasing` 与 hls.js 的 `liveMaxLatencyDurationCount` 都会强行跳回 live edge 抹除对齐，而两个插件只在创建时读这些选项。因此 `useWebPlayer` 的 `liveSyncHold` 计入 `hardStreamKey`，开关同步会重建一次传输，而不是改插件私有配置。同步档参数见第 11 节。

控制环在 `src/features/multi-room/liveSync.ts` 中是纯函数，`MultiRoomLiveSyncProvider` 每秒采样，`liveSyncRegistry` 汇总各路 `player.sync.readTimeline()`，`planLiveSync()` 每路返回一个动作：

- `manual`：目标 `mediaTime = bufferEnd - (1.2 + offset)`，不依赖时钟；
- `auto`：`targetLatency = max(主画面贴住自己 live edge 后 1.2 s 时的延迟, 各路可达延迟下界 + 0.3 s)`，各路按 `mediaTime + (latency - (targetLatency + offset))` 对齐；无时钟的路回退到 `manual`。

主画面是基准，因为它是唯一有声、不能变速的一路；基准取「贴住自己 live edge 时的延迟」而非当前位置，否则每次重缓冲都会把整组永久拉后。目标延迟变大立即生效，变小每秒最多释放 0.35 s。每路修正三档：偏差 ≤ 0.35 s 不动；≥ 1.5 s 直接 seek（FLV 走 `mpegts.js` 自己的 seek 路径，避免被当成 unbuffered seek 而 flush MSE）；中间区间用 ±3% 变速平滑靠拢，且只对静音副画面使用。每次 seek 后冷却 2.2 s，目标位置夹在 `[bufferStart + 0.4, bufferEnd - 0.6]`，被夹断时标记 `limited` 并提示缓冲不足。

状态发布走 `useSyncExternalStore` 的每路订阅，四舍五入到 0.1 s 后才视为变化。主画面弹幕使用 `DanmakuRenderer` 接收延后后的直播事件；本地字幕取自该路 `<video>` 音频，天然对齐。各路偏移滑杆（-5 s … +20 s，步长 0.5 s）是设计的一部分而非降级方案：`EXT-X-PROGRAM-DATE-TIME` 记录的是平台接收/转码时刻，各主播上行延迟不同，`stream-anchor` 又含 CDN burst，固有偏差无法消除。

## 5. 控制层：Video.js 原生组件

当前使用 Video.js **10.1.0** 稳定版，`@videojs/react`、`@videojs/core`、`@videojs/hlsjs-video`、`@videojs/dash-video` 固定同一版本。升级时以已安装包的 `docs/llms.txt` 和 `.agents/skills/videojs/SKILL.md`（本机技能目录，不入库）为准；不要把仍属于 v8 的 `video.js` npm 包或旧 `videojs()` API 引入项目。

控制层不是应用自绘的按钮行。`src/components/videojs/` 是从官方 shadcn registry（`components.json` 的 `@videojs` → `https://shadcn.videojs.org/r/react/{name}.json`）取下并纳入版本管理的组件源码：行为、可访问性、状态订阅与国际化由 `@videojs/react` 提供，rLive 只改类名与组合方式。

| 目录 | 职责 |
|------|------|
| `src/components/videojs/ui/` | 当前播放器使用的原生控件包装：播放、音量、进度、全屏、画中画、缓冲、错误、封面、跳转提示、音量提示与状态播报 |
| `src/components/videojs/skins/live-video/`、`skins/video/` | 直播与点播各自的原生快捷键和状态提示 |
| `src/components/videojs/skins/shared/` | `skin-surface.tsx`（统一媒体表面）、`controls-surface.tsx`（唯一控制条表面）与直播 / 点播共用的快捷键集合 |
| `src/components/videojs/styles/theme.css`、`src/styles.css` | 统一播放器使用的 `--media-*` token、`media-root` 容器断点与 `.r-live-player-skin` 项目覆盖 |
| `src/features/room/player/videoJsControls.tsx` | 唯一 `createPlayer` store（`videoFeatures` + `liveFeature`）、`I18nProvider locale="zh-CN"`，以及按 `variant="live" \| "vod"` 注入快捷键和状态提示的 `VideoJsContainer` |
| `src/shared/components/player/PlayerControls.tsx` | 只剩业务扩展按钮（刷新、章节槽位、播放设置、弹幕、字幕来源与本地字幕设置、侧栏、网页全屏、信息显隐、页内全屏、Android 系统音量）与中央槽位，作为 children 交给皮肤的控制条 |

必须保持的约束：

- **术语约定**：如无特殊说明「顶部」或「底部」，「控制栏」包括顶部控制栏（HUD）与底部控制栏；通用尺寸、显隐及交互规范同时适用于两者。

- 播放 / 暂停、静音与音量、进度与预览、直播边缘、画质、音轨、倍速、字幕、投屏、AirPlay、画中画与浏览器原生全屏一律用原生组件，应用侧不再保留等价实现；业务只补 Video.js 没有的能力（站点画质与线路、弹幕、ASR、网页全屏、页内全屏层）。
- 全应用复用同一个 `createPlayer` 工厂，每个 `VideoJsPlayerProvider` 创建独立 store；同一播放器的媒体与控制层共享状态，多画面之间不共享 store。`<video controls>` 始终关闭。
- PiP 使用稳定版的 `isPictureInPicture`、`pictureInPictureAvailability` 与 `requestPictureInPicture()` / `exitPictureInPicture()`。业务入口订阅 `selectPiP`，仅在 `available` 时显示；`useVideoJsPiP` 统一捕获拒绝并提示，不把浏览器策略失败当作媒体故障。原生 `PiPButton` 的渲染状态仍名为 `pip`，不要与 player store 字段混淆。
- 控制条表面唯一：`ControlsSurface` 用 `Controls.Root visibility="always"` + `Controls.Backdrop` + `Controls.Content`，显隐仍由各播放页既有的 chrome 管线（`data-visible` + 指针 / 焦点计时器，见第 6.1 节）命令式驱动。让 Video.js 自己收起会与业务淡出管线互相打架，因此刻意关掉它的自动隐藏。
- 窄容器降级与原生控件共用同一套 `media-root` 容器断点（`media-max-sm:hidden` 等），不用视口媒体查询，也不靠 `overflow-hidden` 截断业务按钮行。
- 文案走 `@videojs/react/i18n` 的 `zh-CN` 包并在入口静态注册，避免首帧英文；不为原生控件另写中文标签。
- **画面点按/双击仍由播放页自己的舞台管线拥有动作，但识别统一复用 Video.js 官方 `useTapGesture` / `useDoubleTapGesture`**（封装于 `usePlayerStageTapGestures`）。两套皮肤不再额外挂声明式 `<Gesture action="…">`：声明式 action 只会改 Video.js store，无法更新业务的 chrome `data-visible`、Android / 桌面 Tauri 全屏路径与 `userPausedRef` 暂停记账；同时挂两份识别还会让一次点按执行两次。长按倍速、上下换片、边缘亮度音量继续由业务手势处理，并以抑制 ref 阻止点按回调。键盘快捷键则由皮肤的原生 `Hotkey` 拥有，页面 keydown 见 `defaultPrevented` 即让位。动作按指针类型分叉，与直播页一致：**移动端触摸**单击切换 HUD（隐藏时唤出、已可见时收起，两条路径都不碰播放状态），双击播放/暂停；**桌面鼠标**仍是单击暂停/继续、双击全屏。验证需确认移动端单击切换 HUD 各一次且播放状态不动、双击恰好切换一次播放且不泄漏成单击、滑动后的抑制标志否决延迟回调。
- **桌面方向键跳转不唤醒控制栏**：`VideoPlayerPage` 在 `onKeyDownCapture` 记录 `←` / `→`（含 `Shift` 与重复按键）的跳转意图，不抢占原生 `Hotkey` 的动作；该次 seek 的 `waiting` 仍显示缓冲反馈、参与恢复判定，但不触发 chrome 的 `keepVisible`。`seeked` / `playing` 仅在媒体已不处于 `seeking` 时清除意图，避免上一跳迟到的完成事件清掉新一跳；新媒体会话同样清除，鼠标活动及非 seek 卡顿恢复正常显隐。暂停、错误、弹层与控制区键盘焦点的可见性守卫不变；页面兜底方向键和录制回放方向键也不调用 `revealControls`，录制页对 `defaultPrevented` 让位以免重复执行。实机在桌面主窗口监测两层 `data-visible`，验证原生快捷键、`Shift` 兜底、长按连跳、上一跳完成事件迟到、鼠标唤醒与暂停态跳转。
- 全屏按钮归属由 `showFullscreenButton` 决定：浏览器原生全屏用原生 `FullscreenButton`，两个 Tauri 端的页内全屏层（见第 6 节）由 `PlayerControls` 自己渲染。
- 音量入口唯一，由 `showPlayerVolumeControl(compact, portrait, fullscreen)` 决定是否出现：Web/桌面用原生 `VolumePopover`；Android 原生音量桥可用时（`androidPlayerControls.supported`）换成 `PlayerControls` 里绑定 `externalAudioControls` 的同形弹出滑杆——真实音量是系统媒体音量，原生组件只能写 `<video>.volume`。移动端全屏两者都不出现，交给边缘滑动手势。
- 控制栏三个弹层（音量、播放设置、字幕）手感统一：悬停 `200ms` 展开、移开 `100ms` 收起。音量走原生 `VolumePopover` 的 `openOnHover`；播放设置与字幕用 `Menu.Root` / Base UI `Popover`，由 `useHoverOpen`（`src/components/videojs/lib/use-hover-open.ts`）补同一套时序。**悬停展开后点触发器本身不收回**：两套原语都会在触发器 click 时再请求一次关合（Video.js `reason: "click"`，Base UI `reason: "trigger-press"`），`ignoresTriggerPressClose` 只挡这一条——按 `event.detail > 0` 区分真指针点按与键盘合成 click，菜单项选择（不带 event）、`Esc`、点空白照旧收起，无 hover 能力的触屏仍按点击开合。悬停需用真实鼠标验证，纯判定另见 `tests/hover-open.test.ts`。
- **字幕来源菜单在紧凑视口改走抽屉**：`PlayerControls` 的字幕按钮（直播、IPTV、多画面三处共用）与点播页的 `captionsSlot` 都以 `compact` 为判据，在紧凑视口渲染 `Drawer` 而非锚定弹层（竖屏从底部、横屏从右侧；`container` 分别取各页的 `portalContainer` / 舞台，非全屏且侧栏可见时经 `DrawerScope` 挂进 `DrawerViewport`）；宽视口仍是悬停弹层。两种形态共用同一份触发器与正文，抽屉形态点击只切换开合（触摸端没有悬停）。判据、侧别与相邻的播放设置抽屉、点播章节菜单完全一致。正文里的「原文语言 / 译文语言」是 Base UI `Select`，已实机确认在 scoped 与舞台 portal 两种抽屉下都能展开、命中并写回（抽屉本身不被 `Select` 的浮层关掉）。
- 移动端（`isMobileClient()`）上下控制栏统一缩小一档：`PlayerSurface` 标记 `data-player-density="dense"`，顶部 HUD 与 `ControlsSurface` 的 `data-density="dense"` 共用 `--media-control-size: 1.75rem`（28px）、`--media-icon-size: 1.25rem`（20px）。标题字号与独立全屏锁定按钮不缩小；桌面窄窗口不缩。
- **移动端 VOD 非全屏竖屏**：`progressPlacement="center"` 将原生 `TimeSlider` 放在底部控制栏中央，保留章节、缓冲、预览和键盘定位；弹幕发送框移到「弹幕」页签固定底部。桌面、横屏、画面全屏及窗口全屏仍为上方独立进度行 + 主行中央弹幕输入，录制回放不变。
  时间与滑杆**同排一行**（当前时间在前、剩余时间在后），两种位置共用同一条横向 flex 行，不用上下分栏。这一行一旦改成列向（`flex-col`），纵向主轴上的 `flex-basis: 0%` 会把滑杆高度压成 0，进度条不可见也不可命中 —— 两者不再分叉后这类错配不可能再出现。横向主轴下宽度是唯一竞争维度，因此中央布局额外做两件事：把滑杆的 `min-w-18`（64.8px）覆写为 `min-w-0` 让它可让位，并在容器宽度 < 24rem（`media-max-sm`，media 容器宽度即舞台宽度）时收起剩余时间，保证滑杆仍有可用拖动长度、整行不溢出到右侧按钮。上方布局保留原生最小宽度与两个时间标签。实机在 320px/401px 上检查同排关系、溢出、宽度与命中区。
- **控制栏按钮上下贴边、全屏发送框不高于按钮**：上下两条栏的垂直内边距收紧到约为原来一半（顶部 HUD `pt/pb`、底部 `ControlsSurface` 与主行/进度行 `py`），按钮更贴近屏幕上下两侧。底部主行中央的弹幕发送框高度改为无条件对齐同排原生媒体按钮（`height/min-height: var(--media-control-size)`，并覆盖粗指针下 Input / InputGroup 自带的 `min-h-11` 44px 下限），因此**全屏时它也不会高于两侧按钮**，与按钮等高；紧凑视口仍额外收窄两端小按钮与图标。顶部四处 HUD（`PlayerFullscreenHud`、视频、IPTV、多画面）共用同一档减半后的上下留白。
- **直播间侧栏的堆叠判据**：`usesStackedRoomSidePanel(compactViewport, compactLandscapeViewport, stackedDetailsViewport)`（`PlayerPane.tsx`）决定侧栏是列在舞台**下方**还是并排在右侧。判据是「矮横屏除外，紧凑视口**或**窄于 `64rem`」——`stackedDetailsViewport` 与点播、IPTV 播放页的 `@media (width < 64rem)`（`STACKED_DETAILS_QUERY`）同源。平板竖屏（≥768px 且窄于 1024px，典型 800×1280）只落在后一项上：旧判据只看 `max-width: 767px`，平板因此走桌面并排，800 宽的列里 16:9 画面只占中间 450px、上下近 800px 全是黑边，右侧栏还吃掉 40% 宽度 —— 同一台设备上的点播与 IPTV 早就按 `64rem` 堆叠了。`RoomStageSkeleton` 与真实布局共用这一个纯函数，加载态与落定后不会换形态。
- **直播间紧凑视口**（侧栏列在舞台下方，或矮横屏收进浮层抽屉）：侧栏可见且非原生全屏时，弹幕发送框固定在侧栏「弹幕」页签最下方，控制栏只剩按钮，与点播控制栏同高；侧栏收起、网页全屏或原生全屏时发送框回到控制栏中央；侧栏并排在右侧的宽窗口保持原样（那里控制栏就在聊天旁边）。留在控制栏中的输入框同样由 `styles.css` 中 `[data-slot="player-extension-controls"] [data-slot="player-center-slot"]` 规则压到按钮高度，与原生媒体按钮对齐，不按全局 44px 触摸下限撑高整行。
- **仅播声音统一在顶部 HUD**（`PlayerAudioOnlyButton`，`src/shared/components/player/PlayerAudioOnlyButton.tsx`）：直播、视频、IPTV 与多画面四处共用一枚常驻图标，摆在 HUD 右侧、溢出菜单左侧（直播与 IPTV 在录制槽之后）。它原先只对点播如此（`4afbb653` 为章节菜单腾出控制栏左组），其余页面留在底部控制栏；统一后底部控制栏不再有这枚开关，左组只剩暂停、刷新与音量（点播另有章节）。组件内部只做两件事：用 `audioOnlyControlPresentation` 取文案与图标，渲染 `MediaButton` + `PLAYER_HUD_BUTTON_CLASS`/`PLAYER_HUD_ICON_CLASS`——**新增 HUD 按钮必须走这两个配方**，否则尺寸与配色会与整排对不上。`PlayerControls` 的 `audioOnly`/`onToggleAudioOnly` 两个 prop 随之删除（`audioOnlyControlPresentation` 保留导出，供 HUD 组件与各页判断）。四处接线各有前提：直播与 IPTV 的 HUD 窗口化也挂载（`showPlayerFullscreenHud` 在直播恒传 `fullscreen: true`，流内顶栏已全端删除），按钮直接摆在 HUD 行里；IPTV 的 HUD 只在 `channel && controlsAvailable` 时渲染，因此按钮无需再套条件。多画面把这段上移到 `MultiRoomPlayerContent`：`toggleAudioOnly`（含「进入仅音频前先退画中画」）与状态同处一层，按钮只在 `main` 格渲染（副画面无业务意义），HUD 的 `data-visible` 由主画面的空闲计时器驱动。点播页的 `VideoPlayerPage` 也改用本组件，不再内联画一遍。注意直播间的 HUD 溢出菜单（`mobileRoomActions`）原先另有一枚同功能的 `audio-only` 磁贴，现已删除——它曾是移动端竖屏的唯一入口（`showSecondaryPlayerControls` 会在「紧凑 + 竖屏」时隐藏底部控制栏的次级控件），提到 HUD 后移动端与桌面同为一枚常驻图标，不再依赖抽屉。
- **当前直播时长**（`LiveDurationClock`，`src/shared/components/player/LiveDurationClock.tsx`）挂在底部控制栏左组的最右端（音量/章节之后，贴着中央槽位），显示 `mm:ss`、满一小时起 `hh:mm:ss`。它只在平台给出开播时间时出现：`PlayerPane` 收 `liveStartedAt`，`RoomPage` 按 `detail.status ? detail.live_started_at : null` 传入（未开播时平台可能留着上一场的时间戳）。IPTV、点播、录制回放与多画面不传该 prop，因此那几处不渲染任何内容。文案与判定统一在 `src/shared/liveDuration.ts`：`formatLiveDurationText` 是关注列表与房间侧栏用的中文长文案（`formatFollowLiveDuration` 现为该函数的**再导出**，导出名保留以免两处调用点跟着改），`formatLiveDurationClock` 是控制栏的秒级时钟，`formatLiveDurationLabel` 是悬停提示（中文时长 + 本地开播时刻）。**心跳留在叶子组件里**：1Hz 状态若提到 `PlayerControls`，每秒会连带重渲染中央的弹幕发送框（已实机验证相邻输入框节点不被替换）；每拍用 `liveDurationTickDelayMs` 对齐真实秒边界并重算「现在 − 开播时间」，不累加，因此后台节流后回到前台的第一拍就把秒数补齐。秒表是只读读数，用 `role="timer"`（隐性 live 语义为 off，屏幕阅读器不会每秒播报）并把完整说法放进 `aria-label` 与 `title`。窄于 `24rem`（`media-max-sm`，与进度行收起剩余时间同一档）时让位给中央输入框。**尺寸不取固定 px**：`src/styles.css` 里 `[data-slot="player-live-duration"]` 用 `font-size: calc(var(--media-control-size) * 0.45)`、`line-height: var(--media-control-size)`，即字号与行高都由控制栏按钮尺寸推导——桌面 14.6px / 32.4px 行高（按钮 32.4px、图标 24px），移动端 dense 档 12.6px / 28px（按钮 28px、图标 20px）。固定的 `text-xs`（12px）在桌面明显小于按钮的视觉重量，而 `--text-media` 那档（11.7px）同样偏小；乘系数还能让读数在整条控制栏换档时自动跟着换，不需要第二处断点。行高取整行控件高度，是为了让读数与相邻按钮的中心线对齐不靠基线凑。注意控制栏在 rLive 里**不随窗口或全屏放大**：`--media-scale` 的媒体查询要求原生 CSS `:fullscreen`，而本项目的全屏是 `[data-player-stage][data-fullscreen="true"]` 页面级固定层（`src/styles.css`），因此全屏下按钮仍是 32.4px，读数天然同步。
- 控制栏的底色只表示两种状态：**悬停**（`--media-muted`）与**菜单展开**（`mediaPopupTriggerOpenClass`，同为中性填充）。开关类按钮（弹幕、网页全屏、侧栏）的「已开启」不铺底色，只靠图标区分（`MessageSquareText`/`MessageSquareOff`、`Shrink`/`Expand`、`PanelRightClose`/`PanelRightOpen`）——曾用 `glassOptionSelectedClass`（白 18%）表示开启，但它与悬停的白 15% 几乎无法分辨，点开开关后移开指针看上去仍像停在悬停态。展开态触发器一律显式带 `mediaPopupTriggerOpenClass` 盖掉 `MediaButton` 对 `aria-expanded` 画的 accent 蓝（HUD `⋮` 溢出菜单、录制入口与音量、播放设置、字幕同一条配方），否则指针移进弹层后会点亮蓝底。

### 5.1 进度条缩略图（storyboard）

点播进度条的悬停预览由原生 `TimeSlider` 的 `Slider.Thumbnail.*` 渲染，应用只负责喂给它一条符合规范的 WebVTT 轨：`<track kind="metadata" label="thumbnails" default>`，cue 载荷为 `雪碧图URL#xywh=x,y,w,h`。数据链是 `video_get_storyboard`（Rust，`x/player/videoshot`）→ `storyboardToVtt`（前端转 VTT，Blob URL）→ 媒体元素上的 metadata 轨。

- 上游规格随稿件类型变化，不能写死：UGC 一般是单张 10×10 拼版、单帧 160×90（`i0.hdslb.com/bfs/videoshot/<cid>.jpg`），PGC 是多张 10×10 拼版、单帧 480×270（`bimp.hdslb.com/videoshotpvhdboss/...`）。换页按 `img_x_len * img_y_len` 计算，坐标一律取上游给的 `img_x_size` / `img_y_size`。
- `index` 首项恒为哑元 0，第 1 项起才是各帧秒数，因此前端丢掉首项后帧号与拼版格号一一对应（格 0 即 0 秒那帧）。长视频 JSON 不返回 `index` 时回退 `pvdata`（`.bin`，大端 `u16`）；同一稿件两种来源逐项等价，含同样的前导哑元。
- **雪碧图必须经本机图片代理**（`src/shared/api/imageProxy.ts` 的 `proxyImageUrl` → `/img?url=`）。videoshot CDN 对带非 bilibili `Referer` 的请求直接回 403，而 WebView 无法为 `<img>` 去掉 `Referer`；代理补平台请求头，并回 `Access-Control-Allow-Origin: *`，满足缩略图 `<img>` 从媒体元素继承来的 `crossOrigin="anonymous"`。代理端口是异步取回的，VTT 又只在快照数据变化时重算，所以 storyboard 查询先 `await preloadImageProxy()` 再取数据，避免把直连 URL 烧进轨道。
- 无快照（命令返回 `null`）或雪碧图加载失败时不做兜底绘制：没有轨道时 `Slider.Thumbnail.Root` 带 `data-hidden`（`time-slider.tsx` 的 `data-hidden:hidden` 使其 `display: none`），加载失败时带 `data-error`，两种情况悬停都只剩时间标签，不出现空预览框。
- 字幕轨与缩略图轨各自独立清理：字幕按 `track[kind="subtitles"]` 移除，缩略图按 `track[data-track-kind="thumbnails"]` 移除（它的 `kind` 是 `metadata`），互不误删。

## 6. 全屏的三条平台实现

| 平台 | 铺满屏幕的方式 | 系统 UI |
| --- | --- | --- |
| 移动端浏览器 | HTML Fullscreen API，`:fullscreen` 由浏览器提升到 top layer | 浏览器自己收起 chrome |
| Tauri 桌面端 | 原生窗口全屏 + stage 的 `data-fullscreen="true"` 页内 fixed 图层 | 原生窗口覆盖任务栏 |
| Tauri Android | 同一套 `data-fullscreen="true"` 页内 fixed 图层 | `android_player_controls_set_immersive` 隐藏系统栏 |

两个 Tauri 端刻意不用 HTML Fullscreen API：桌面端 WebView2 在窗口最大化时 `:fullscreen` 元素按屏幕高度渲染而视口仍是工作区高度，底部留黑边；Android 的 `WebChromeClient.onShowCustomView` 会把内容移交给新建 View，这次渲染表面交接必然黑屏数帧，同帧 CSS 无法补救。

配套约束：

- 页内图层依赖「没有 transformed ancestor」，由 `Shell` 沉浸式分支渲染裸容器与 `PageZoom` 入场后 `clearProps` 共同保证。
- 两个 Tauri 端自己拥有 `mode`，跳过 `fullscreenchange` 同步分支；桌面端另有原生窗口 resize 对账。原生命令缺失（旧 APK）时 invoke 被吞掉，页内图层照常工作，只是系统栏不隐藏。
- 返回键沿用 `rlive:android-back` 链，不新增原生拦截。直播由 `PlayerPane` 消费，视频与录制回放由 `useRecordingPlayerFullscreen` 消费，退出时恢复系统栏并撤下图层。视频的锁定判定在适配器的退出入口完成：事件直接派发到 `window` 时监听器按注册顺序执行，不能依赖另一个捕获监听器抢先拦截。展开的 base-ui 弹窗排在这条链之前（`dismissTopmostPopup`），一次返回只关菜单，再按一次才退出全屏。
- 沉浸态属于全屏播放器而非 Activity：`useWebPlayer` 在卸载和失去 `fullscreenOwner` 时恢复系统栏，`MainActivity.onResume` 在插件仍记录沉浸态时跳过恢复，`onCreate` 先清除静态标记。
- 安全区冻结由 `useFullscreenInsetFreeze` 共享，底层为 `src/shared/fullscreenTransition.ts`：把 `.app-shell` 的 `padding-top` 钉在进入全屏时的值，避免图层背后的 chrome 在系统栏动画期间回流；全屏事件、失败、超时和卸载均释放冻结。

### 6.1 顶部 HUD

直播、视频与 IPTV 播放页都已删除流内顶栏（所有端、所有模式统一）：房间/频道身份、返回与低频工具由 `src/features/room/PlayerFullscreenHud.tsx`（直播）或各页自己的顶栏 HUD 画在画面顶部。全屏 stage 是 `position: fixed; z-index: 60` 的全窗口图层，会覆盖房间底部操作栏，HUD 因此始终挂在舞台内。

- 播放页底部的应用外壳栏（直播间的「复制链接 / 复制直链」、IPTV 的来源与状态徽标）在触摸客户端不渲染：直播间按 `!isMobileClient()`（与点播播放页同一条判据），IPTV 按 `touch-wide:hidden`（≥48rem 粗指针）。平板宽度虽已越过 `md`，那两条 37~57px 的横杠只是重复 HUD 里已有的动作与中央浮层的播放状态，却按应用外壳画法占了画面下方的整条边。手机（窄屏）保持原样 —— IPTV 那条栏是手机上看播放状态的唯一常驻位置；点播的底部栏本来就只在桌面渲染。

- HUD 是 stage 内与底部控制栏同级的兄弟节点（`absolute inset-x-0 top-0 z-30`），不占布局高度。直播页渲染条件由 `showPlayerFullscreenHud` 判定（恒传 `fullscreen: true`，只要有房间身份或菜单条目就挂载）；视频与 IPTV 页同画法全模式挂载。录制回放仍保留流内顶栏，仅全屏时由 `showPlayerFullscreenHud` 挂 HUD。
- 最左侧返回箭头（`onBack` / `backLabel`）按层退出全屏：`nextFullscreenLayerToExit(fullscreen, webFullscreen)` 与 Escape 的分层习惯一致，画面全屏优先，网页全屏留给下一次；移动端窗口化没有全屏层时返回来源页面。
- 直播 HUD 的信息区在移动端竖屏非全屏时只保留直播间标题，不渲染主播头像、名称、平台房间号及热度；返回、录制、仅播声音和更多操作不变。`PlayerPane` 用 `playerHudTitleOnly(mobileClient, roomPortraitOrientation, fullscreen || webFullscreen)` 判定，经 `PlayerFullscreenHud` 的 `titleOnly` 传给 `RoomIdentityLine`，保留原有标题字号、空标题兜底及溢出平移；切换模式会重新测量并清理旧平移动画。桌面端（包括窄窗口）、移动端横屏、原生全屏和网页全屏都保持完整信息，多画面默认不受影响。
- HUD 标题（房间名、视频名、频道名）的字号只有一处定义：`PLAYER_HUD_TITLE_SIZE_CLASS`（16px，比应用顶栏标题大一档，画面上的标题要在明暗画面与小屏上都一眼可读）。直播与多画面经 `RoomIdentityLine` 使用它，视频页与 IPTV 页直接用；新增 HUD 标题的字号必须走它，否则同一位置的标题会像之前那样在四个页面之间出现 `text-base` / `text-sm` / `text-xs` 三种字号。它只管字号，字重、配色、底色与投影仍归各调用点（IPTV 频道名带胶囊底色，直播与视频标题靠投影）。
- HUD 图标按钮的画法只有一处来源：`PlayerControls.tsx` 导出的 `PLAYER_HUD_BUTTON_CLASS`（按钮骨架与 hover 配色）与 `PLAYER_HUD_ICON_CLASS`（`size-6`，移动端被共享 `--media-icon-size` 覆盖为 20px）。返回箭头、录制、溢出菜单触发器、IPTV 的关注入口与四处共用的 `PlayerAudioOnlyButton` 都走这两个 recipe；**新增 HUD 按钮必须复用它们**，否则尺寸与配色会与整排对不上（录制按钮就曾自行画一个）。
- 多画面分格 HUD 的图标按钮只有一处画法：`MultiRoomPlayer.tsx` 导出的 `OverlayIconButton`（36px `MediaButton` + 药丸圆角 + `PLAYER_HUD_BUTTON_CLASS` 的 hover 配色）。退出全屏、拖拽把手、设为主画面、刷新、仅播声音与移除共用它 —— 拖拽把手曾自己用 shadcn `Button size="icon-sm"`，在同一行里矮了 8px、圆角也不一样。它透传 `button` 属性，dnd-kit 的 `setActivatorNodeRef`、`attributes` 与 `listeners` 直接挂上去即可；`label` 同时作 tooltip 文案与默认 `aria-label`，需要更具体的读屏文案（如带房间名）时再传一个 `aria-label` 覆盖。
- 加载态不出现流内顶栏，也不绘制控制栏、身份行、进度条或假按钮骨架。`src/shared/components/player/PlayerStageSkeleton.tsx` 只保留纯黑画面与调用方传入的真实返回按钮；`RoomStageSkeleton` 保留侧栏信息占位，并只在桌面（`!isMobileClient()`，与真实页底部同一判据）保留底部操作行的空间，`ShortsStageSkeleton` / `ShortsInfoSkeleton` 只保留左下信息占位。`Shell` 的沉浸路由 Suspense 继续复用轻量舞台占位，不 import `PlayerControls`，不把播放器重依赖带入外壳首屏。
  - 黑底信息骨架通过 `StageSkeletonBlock` 覆盖 `Skeleton` 默认的 `bg-muted`，不在画面中央铺大块灰色。
  - 返回必须是真按钮；`Shell` 的路由占位除外，此时没有可用的返回目标。加载文案挂在 `role="status"` 上，信息骨架只作装饰。保留左下信息占位，顶部与底部控制栏区域没有骨架。
- **首轮取流未出画前不显示控制栏**（顶部 HUD 与底部控制栏一起隐藏），只保留退出当前播放层的真实返回按钮：直播由 `PlayerPane` 按 `player.ready`（`canplay` / `playing` 置位，换源或重建复位）判定，VOD 由 `VideoPlayerPage` 的 `transportReady`、IPTV / 录制回放由各自的生命周期 `ready` 判定，多画面主/副画面同样只在 `ready` 或错误后挂载控制栏（单格的 HUD 不隐藏：刷新与移除是卡住时的唯一出口）。暂停、播放中缓冲不隐藏；失败态立即恢复完整 chrome，重试入口不会一起消失。`usePlayerStartupGate` 与辅助内容共用同一次「首次可播」信号。
- 显隐复用命令式机制：`setControlVisibility` 同时改写各层的 `data-visible` / `aria-hidden` / `inert`，共用同一 idle timer，不触发 React 重渲染（锁定期间两层 chrome 被强制留在收起态，见 5.2）。`hasKeyboardFocusWithinControls` 与失焦处理认全部三层 ref（controls / hud / lock）；菜单打开期间以 `"hud"` 交互来源参与 idle 栅栏。
- 鼠标移出播放器区域（stage 的 `pointerleave`，`pointerType === "mouse"`）时两层 chrome 立即收起，不等空闲倒计时；守卫与空闲隐藏一致（暂停、缓冲、失败、弹层打开或键盘焦点在 chrome 内时保持可见）。**移动端触摸不走指针活动与 `pointerleave` 这两条路径**：舞台的 `pointerenter` / `pointermove` 与抬手的 `pointerleave` 对触摸一律提前返回，chrome 可见性完全交给点按识别器（`handleStagePointerActivity` / `handleStagePointerLeave` 里的 `mobileClient && isTouchLikePointer(...)` 守卫）。两条都是真机实测的缺陷，缺一条就出问题：(1) 指针活动若顺带 `revealControls()`，按下时 chrome 已可见，而单击回调要等满双击窗口（约 200 ms）才跑，那时 `controlsVisibleRef` 已是 `true`，切换语义便按「已可见」把它收掉——表现为单击后 HUD 闪一下即灭；(2) 抬手排隐藏会先撞上 `scheduleControlsHide` 的 `keepVisible` 守卫，暂停/缓冲/失败时它把 chrome 置为可见，紧随其后的单击回调同样只会收起——暂停态永远点不出 HUD。单击的收起走 `hideControls`，它刻意越过 `keepVisible`：暂停、缓冲、失败正是「chrome 最可能正显示、用户最想收掉」的三种状态，沿用被动守卫会让「再点一下收起」恰好在最常见的场景里失效；只保留键盘焦点守卫（`:focus-visible`，触摸点按不会命中），因为隐藏会写 `aria-hidden`，把焦点留在隐藏子树里是无障碍缺陷。验证需同时覆盖鼠标与触摸回落路径。
- 桌面直播间的 HUD 宿主使用 `pointer-events: none`，只在 `data-visible="true"` 时为其中未禁用的 `button` 恢复指针命中；标题、头像、渐变与留白因此不再拦截下方弹幕及其操作菜单。隐藏态不会留下透明按钮热区，移动端不启用该穿透规则；按钮区域仍以 HUD 操作为先。
- 顶部渐变用 `styles.css` 的 `player-scrim-overlay-top`，与底部同材质反方向，只用纯 sRGB 停止值（旧 Android WebView 无法解析 `in oklab` 会丢弃整条声明）。
- **原生全屏**下 HUD 内菜单必须 `container={player.stageRef}`，否则 Base UI 默认 portal 到 `<body>` 会被 top layer 压住；`isPlayerEdgeGestureIgnoredTarget` 也要包含 `[data-player-hud]`。原生全屏期间 `setToastPortalContainer(stage)` 把通知视口移入 stage，退出时还原。网页全屏没有 top layer，刻意改回默认 portal —— 塞进 stage 反而会被它的 `overflow-hidden` 裁掉。
- 房间级动作由 `RoomPage` 通过 `fullscreenRoomActions` 下传，复用 `copyRoomValue` / `toggleFollow` / `openInMultiRoom`；带 `exitsFullscreen` 的项先 `exitFullscreen()`。

### 首屏加载优先级

- 直播保留必要的「房间详情 → 清晰度 → 线路」链路，`RoomPage` / `PlayerPane` 在媒体可播（`canplay`）或开始播放后才连接弹幕、刷新关注列表、挂载辅助面板及弹幕输入框；未开播、取流失败或恢复耗尽时也开放辅助内容。用户主动切到关注或设置页签时立即响应，不必等待首帧。
- 普通视频保留取流键解析和本地观看历史续播依赖，播放器适配器与取流并行准备。`loadeddata` / `playing` 后才请求字幕与章节元数据、进度预览图和弹幕，并懒加载 `VideoSidebar`（相关视频、评论等）；播放或详情失败也显示侧栏。自动播放被拦截时，`loadeddata` 仍可放行，不要求用户先点播放。
- `usePlayerStartupGate` 按内容身份记忆首次就绪：暂停、缓冲和同内容重连不卸载辅助内容；换房/换片立即关闭，旧回调不能干扰新内容。
- **加载间隙不得撤销全屏**（移动端实测缺陷：网络卡顿后「先掉出全屏、加载完再切回去」）。两条独立成因都已按「加载不是状态变更」处理：
  - **详情刷新失败不换掉播放器**。`RoomPage` 只在 `detailQuery.isError && !detailQuery.data`（首屏就没拿到）时整页报错；刷新失败时 TanStack 保留 `data` 只把 `status` 置为 `error`，此时换页会卸载 `useWebPlayer`，正在全屏的舞台被拆掉（`mode` 复位为窗口化并恢复系统栏）。那条失败仍可见：`refreshPlaybackDetail` 抛错后由恢复会话发布 `loadError`，`PlayerPane` 照常渲染错误态与重试入口。
  - **画幅跨媒体重建保留**。换线路、故障转移与元数据续期在无法原地重连时会重建 `<video>`，新节点在首个元数据前报告 0×0；那不是「画幅未知」而是「还没量」。当成 `null` 会经 `fullscreenPlayerOrientation` 把方向锁退回 `auto`，全屏播放器被释放方向锁、随物理方向转回竖屏，全屏也跟着旋转联动一起退出。`retainMeasuredAspectRatio` 同内容期间沿用上一次实测值（`useWebPlayer` 按 `sessionKey`、`VideoPlayerPage` 按 `videoKey` 判断身份），实测值永远优先，因此自适应阶梯在流中换分辨率仍照常更新。
  - 判定本身是纯函数（`tests/player-fullscreen.test.ts`），但「加载态不再引起卸载」要在真机复现：全屏播放中切断网络数秒，画面应留在全屏内显示加载态，恢复后不出现模式切换。
- B 站短视频的活动槽位在推荐/取流仍在途时预加载所需播放器适配器，复用模块缓存。弹幕从活动媒体的首次有效进度开始加载，重新开启时从当前进度补取，不抢首轮取流，也不固定从 0 秒开始请求弹幕。抖音短视频已于 2026-10-21 下线，专用适配器 `DOUYIN_SHORTS_SOURCE` 已删除；共享舞台的 native 分支仍保留，但当前没有短视频平台使用。
- 实机验证视频请求顺序、暂停时就绪、辅助内容不重建播放器、换片与迟到回调隔离、短视频弹幕按进度补取，以及首帧前隐藏控制栏、重试/换流后重新隐藏；直播、IPTV、录制还需检查请求顺序、失败放行、控制栏骨架与平台页文案。

**播放错误的来源分层**：`VideoPlayerPage` 把「当前媒体真的坏了」和「刷新或辅助请求失败」分开，避免正在播放时被一张错误卡盖住。

- `playbackError` 只由播放器**致命**错误写入；引擎可恢复错误（dash.js code 15/16/17/18/21/22/26/27/33，或带 `fatal: false` 的 hls.js 错误）走 `recoverableError`，渲染为顶部非阻塞提示，真实 `playing` 到达即清除。分类函数是 `videoJsPlaybackErrorSeverity`，纯函数有单测。
- 取流查询用 TanStack 的 `keepPreviousData`：同 key 刷新失败时 `status = error` 但 `data` 仍保留，此时只显示一条可重试的底部提示（`retainedSourceFailure`），不卸载播放器、不停止播放；只有「当前内容键还没有任何可用 source」的首次失败才显示整页错误卡。
- 错误卡 `ErrorState` 复用 `Empty` 与 `Button`：一句可读说明 + 明确操作（重试/返回/授权），原始 code 与 message 收进可展开的技术详情；HTML、URL、HTTP 状态行、堆栈与超长文本都只出现在详情里，长串用 `break-all` 不撑破卡片。`role="alert"` 保留。

回归见 `tests/playback-errors.test.ts`（分级、可恢复文案、错误呈现与短视频错误遮罩）。

**移动端竖画幅点播分流**：`videoRoute.ts` 的 `shouldAutoEnterVideoShorts` 仅接受当前内容匹配的单 P UGC（`archive.pages` 为空）与可靠的 `0 < frameAspectRatio < 1`；桌面、仅音频、PGC、多 P 和未知/方形/横画幅不分流。`VideoPlayerPage` 等媒体尺寸就绪后退全屏，以 `replace` 进入已有 `shortsPath(bvid)`，不承诺精确进度接续。`ShortsPage` 的「视频详情」与手动短视频入口按 `videoKey` 保留该历史条目的详情意图，手动入口仍 `push`，Back 不循环；等待退全屏期间换片、离页或历史条目变化会取消旧导航。回归见 `tests/video-shorts-entry.test.ts`，入口与返回语义详见[短视频功能](短视频功能.md#从播放页带种子进入)。

### 6.2 网页全屏与全屏交互锁定

两者都不进入原生全屏，各自解决一端的问题，判定函数都是纯函数并有单测。

**网页全屏（桌面端）** 让画面占满应用窗口：隐藏房间底部操作栏与右侧栏，保留 `AppTitleBar`（`decorations: false` 使它是唯一的最小化/关闭入口；顶栏已在所有模式下交给画面内 HUD）。

- 状态由 `RoomPage` 持有并下传 `webFullscreen` / `onWebFullscreenChange`，因为让位的上下两条栏属于该层；`PlayerPane` 只负责隐藏右侧栏与提供开关。
- 控制条上它取代了原来的「收起右侧栏」：`showPlayerSidePanelControl` 现在只在移动端窗口化返回 `true`，桌面改由 `showPlayerWebFullscreenControl(compact, fullscreen)` 判定（原生全屏时两者都不显示，此时舞台已独占窗口）。
- 右侧栏用 `showRoomSidePanel(sidePanelOpen, webFullscreen)` 判定可见性，**只隐藏不卸载**（挂载仍由 `shouldRetainRoomSidePanel` 控制），因此退出后弹幕队列与滚动位置都还在。同一个值必须传给 `DanmakuPanel` 的 `visible`：该 prop 同时门控缓冲 flush 与 `ResizeObserver`，否则会去测量一个 `display: none` 的零尺寸元素。
- 刻意不把原生全屏并入该判定：原生全屏下 stage 已在 top layer 盖住侧栏，再加 `hidden` 反而会干扰弹幕列表的高度测量与钉住判定。
- `Esc` 退出由 `PlayerPane` 监听，并在 `mode === "fullscreen"` 时跳过 —— `useWebPlayer` 已为原生全屏注册了 Escape，两个监听器同时响应会让一次按键连退两层。
- 顶部 HUD 在所有模式挂载（流内顶栏已删除，`stageOwnsRoomTopBar` 随之移除）。两处差异：
  - 录制按钮经 `hudToolsSlot` 补进 HUD，在所有窗口化模式可用。`RecordingControl` 的 popover 没有 `container`，默认 portal 到 `<body>`，因此画面全屏时仍不挂载它。
  - `portalContainer` 也只在原生全屏传 `stageRef`；网页全屏走默认 portal，否则菜单会被 stage 的 `overflow-hidden` 裁掉。
- 带 `exitsFullscreen` 的 HUD 动作（关注、多画面）经 `handleExitAnyFullscreen` 同时退出两种全屏：它们要靠应用层 chrome 应答，只退其中一种会让确认框继续被另一种盖住。

**全屏交互锁定** 供桌面端与移动端全屏观看时防误触，由 `showPlayerFullscreenLock(fullscreen)` 判定（任一平台只要舞台进入全屏即挂载）。锁定期间 `playerStageGesturesEnabled` 返回 `false`，单击/双击与边缘滑动全部短路；桌面鼠标点按同样不会触发播放或全屏动作，Android Back 被消费但不退出全屏。

- 锁定按钮同样会休眠：三层共用同一个 idle timer，锁定只是把两层 chrome 强制留在收起态（`playerChromeVisible(visible, locked)`），锁定按钮仍在 `CONTROLS_HIDE_DELAY_MS` 后淡出，避免长期遮挡画面。它是全屏画面上的独立浮动操作，不沿用控制栏的紧凑尺寸：桌面命中框为 `48×48px`、图标 `28px`，粗指针设备为 `56×56px`、图标 `30px`；圆形半透明底、描边与轻量模糊保证在明暗画面上都可辨，同时满足至少 `44px` 的触控目标。
- 休眠后它是被 `pointer-events: none` 让开的，因此锁定期间的舞台触摸专门用来唤回它：`handleStagePointerDown` 在按下时就 `revealControls()`，`handleStagePointerUp` 在 `playerStageGesturesEnabled === false` 时再从抬手时刻重排倒计时，两者都不切换 chrome、不进双击全屏；弹幕层等子级浮层已 `preventDefault` 的点按也放行唤醒，否则落在弹幕上的一次点按会静默丢失。Android Back 在锁定时同样只唤回按钮，告知解锁入口在哪。
- 上锁与解锁都走 `revealControls()`：锁定态先写入 `fullscreenLockedRef`，chrome 因此立即收起，而按钮先保持唤醒并重新排定倒计时——手刚离开按钮它就消失会让人以为点错了。
- 锁定属于全屏会话：离开全屏与切换房间都会复位。这两条路径只改 state，因此 `fullscreenLocked` 的同步 effect 在解锁时补一次 `revealControls()`，否则 chrome 会停在锁定期间的收起态。Back 监听器注册在 effect 内，因此读 `fullscreenLockedRef` 而不是 state，避免闭包过期。
- 按钮层随进入全屏挂载，而双击进入全屏不经过 `revealControls`：`data-visible` 在渲染时取 `controlsVisibleRef.current`，挂载后再由 effect 调 `applyFullscreenLockVisibility` 同步一次 `inert`，否则它会以可见态孤立常驻。
- 三层的 JSX 渲染值必须与命令式写入的目标值一致：两层 chrome 渲染 `playerChromeVisible(controlsVisibleRef.current, fullscreenLocked)`，锁定按钮渲染唤醒态。React 只在渲染值变化时改写属性，一旦分叉，锁定期间任意一次重渲染（旋屏、字幕、定时器 tick）都会把 chrome patch 回可见。
- 唤醒路径刻意排在 `showHost` 判定之前，并在 `pointerdown` 就触发（`pointerup` 再按点按重排倒计时）：加载/报错态下按钮仍然挂载，慢按一下也必须立刻有反应。`hasKeyboardFocusWithinControls` 与 `handleChromeBlurCapture` 同样认 `lockRef`，否则键盘焦点停在按钮上时会被 `inert` 强制 blur。
- 视频普通画面全屏复用 `PlayerFullscreenLock`，由 `usePlayerChromeIdle` 同步上下控制层与锁按钮的唤醒态；退出全屏或换视频复位。
- 直播与普通视频共用 `usePlayerEdgeGesture`、`PlayerBrightnessShade` 与 `PlayerEdgeGestureFeedback`：左半区纵滑调亮度、右半区调音量，拖动中命令式更新，松手提交；原生桥与兜底路径复用同一套阈值。旋屏、失焦、多指、会话切换和锁定会取消旧手势。

### 6.3 控制层的移动端安全区

`env(safe-area-inset-*)` 描述**窗口**边缘被遮挡多少，不描述元素与屏幕的距离；只有元素自身贴着窗口对应边时才能当作自己的 padding。播放器控制层并不总是贴底（竖屏堆叠布局、IPTV `relative aspect-video` stage、多画面单格），此时引用它会多出与实际遮挡无关的偏移。

普通播放（包括移动端直播与视频页）由 `.app-shell` 统一预留顶部安全区，画面从状态栏下方开始；画面内 HUD、加载舞台与失败态的兜底顶栏都不再重复叠加安全区。Android 优先使用原生注入的 `--android-safe-area-top`，旧 APK 与浏览器回退到 `env(safe-area-inset-top)`。

短视频推荐流（`/shorts/bilibili`，沉浸路由）遵守同一条约定：顶部控制栏与画面区从视口顶边（即状态栏下沿）开始，不再自带顶部安全区；底部相反，沉浸路由不渲染底部导航，手势条让位必须由那一页自己做（`SHORTS_SAFE_AREA_BOTTOM`，见 `docs/zh/短视频功能.md`）。抖音短视频已于 2026-10-21 下线，旧 `/shorts/douyin` 退回 `/shorts`，不再进入沉浸路由。

顶部 HUD 统一读取舞台的 `--player-safe-area-top`：普通舞台为 `0px`；一般画面全屏在 `:fullscreen`、`:-webkit-full-screen` 或 `data-fullscreen="true"` 生效后切为原生 inset / `env()`。安全区由 `--android-safe-area-top` / `--android-safe-area-bottom` 提供，旧 APK 与浏览器回退到 `env()`。普通全屏退出后恢复外壳占位。

因此 `PlayerControls`（`src/shared/components/player/PlayerControls.tsx`）用纯函数 `playerControlsAvoidSystemGestureBar(fullscreen, stackedBelowPlayer)` 判定：全屏或播放器铺满视口时避让，调用方声明 `stackedBelowPlayer` 时不避让。房间页传 `portraitStackedPlayer`，IPTV 播放页与多画面固定传该标记。画面内叠加层必须跟着控制栏的同一份判定：SuperChat 与房间页的 ASR 字幕读 stage 上的 `--player-chrome-inset`，不各自引用 `env()`；控制栏不避让手势栏的表面（IPTV、多画面、点播）则用叠加层默认的 `bottom-[4.5rem]`，不叠该变量。

Android 画面全屏上 `env(safe-area-inset-bottom)` 会塌缩为 0，底部按钮贴死屏幕底边时会被临时滑出的系统手势栏压住。因此避让分支叠加 `GESTURE_NAV_CLEARANCE_CLASS`：粗指针设备保底 `max(0.75rem, env(safe-area-inset-bottom))`，指针设备维持原紧凑内边距。

### 6.4 Android 方向与全屏联动

`useAndroidFullscreenOrientation`（`src/features/room/player/androidOrientation.ts`）把设备方向和画面全屏绑在一起，直播（`PlayerPane`）、点播（`VideoPlayerPage`）与 IPTV 播放页（`IptvPlayer`）共用同一个 hook，方向由共享的 `usePortraitOrientation()` 提供。三件事必须同居一个 hook，因为它们共享「这次全屏是不是旋转带起来的」这一份来路：

- **转到横屏自动进入全屏**：`shouldAutoEnterFullscreenOnLandscape`。
- **转回竖屏自动退出**：`shouldAutoExitFullscreenOnPortrait`，只撤销自动进来的那次。
- **全屏期间的方向锁**：`fullscreenPlayerOrientation`。

约束与取舍：

- **只认跳变，不按当前方向持续纠正**。基线 `wasLandscape` 从 `null` 起步，首屏就是横屏（横屏启动或从别的横屏页面过来）不算跳变，否则一进页面就自动全屏。持续纠正还会让用户在横屏下的手动退出变成不可拒绝——effect 会立刻把他拽回全屏。
- **方向锁按来路分叉，这是本节最容易踩的一环**。`landscape` 走 `SCREEN_ORIENTATION_SENSOR_LANDSCAPE`（见 `RlivePlayerControlsPlugin`），一上锁 Activity 就被钉在横屏，系统再也不上报竖屏，自动退出便永远等不到那次跳变。所以旋转进来的全屏不上锁：它本来就已经横屏了，不需要锁去转它，不锁才留得住回竖屏的观测。手动在竖屏下点开的全屏仍要上锁，否则 16:9 只能在竖屏里占一条。
- **画幅判定与方向锁同源**，只认宽高比 > 1 的横屏画面：竖屏直播间转横屏不该铺满全屏。比例来自解码后的 `videoWidth/videoHeight`（`videoAspectRatio`），未知时不猜，等元数据到了再说。
- **画幅在媒体重建期间保留**（`retainMeasuredAspectRatio`）。重建出来的 `<video>` 在首个元数据前报告 0×0，那是「还没量」而不是「未知」，当成未知会撤销方向锁并连带把全屏交给旋转联动退出。内容身份不变（同 `sessionKey` / 同 `videoKey`）时沿用上一次实测值，换房换片才丢弃。
- **自动退出只撤销自动进入**。手动点开的全屏由用户自己关闭：那种全屏还上着 `landscape` 锁本就观测不到竖屏，即便观测到了，替用户关掉他亲手打开的全屏也是越权。
- **来路作废只认全屏的下降沿**（`shouldClearFullscreenRotationProvenance`）。只看当前 `!fullscreen` 会误伤刚请求进入全屏的那一帧：来路已记下、播放器还没报告全屏，来路就被擦掉，方向锁于是按「手动」上 `landscape` 把 Activity 钉在横屏，自动退出再也等不到竖屏。反过来不清也不行，下一次在竖屏手动点开的全屏会继承「旋转进来」而不上方向锁。
- `MainActivity` 在 `configChanges` 声明了 `orientation|screenSize`，旋转既不重建 Activity 也不重启媒体会话。

四个判定都是纯函数并有单测（`tests/player-fullscreen.test.ts`），画幅保留（`retainMeasuredAspectRatio`）同样如此；仓库没有 React 测试环境，逻辑必须留在 `useEffect` 外面才测得到。

## 7. 线路记忆与故障转移

线路记忆键为 `site_id + room_id`，值只含安全的 `source_id`、上次序号与更新时间，不保存 URL 或 headers。恢复时优先匹配 `source_id`，平台不提供稳定标识时才把上次序号夹到当前列表范围内；没有记忆时用平台原始顺序。恢复在线路 URL 交给子播放器前完成。

- 只有用户在播放器菜单手动选择线路才更新记忆，自动故障转移不覆盖用户偏好。记录按最近使用顺序保留 100 个房间；localStorage 不可用或损坏时静默退回平台顺序。
- 故障时先由协议插件做有界网络重连，再由控制器按平台预算重建：斗鱼、虎牙当前线路最多完整重建一次，其他站点最多两次，随后换用本轮尚未耗尽的其他线路。
- 同一 generation 在 `750 ms` 内连续上报的 `error` / `eof` 合并计数。一次 `playing` 只表示重新出画面；必须连续稳定播放至少 30 秒，下一次故障才清除旧预算并重新评估全部线路。
- `waiting` / `stalled` 只更新内存中的缓冲次数与重缓冲时长，不上报故障、不切线、不重载。B 站 HLS 的 fatal 先由 hls.js 原地恢复，重复 fatal 需跨过 20 秒恢复窗口才升级为重建。
- FLV / MPEG-TS 上游关闭直接监听 `mpegts.js` 的 `loading_complete`，不等 `<video>` 缓冲耗尽的 `ended`。房间 FLV 在最多三次续签预算内重取房间详情、清晰度与线路（斗鱼因此生成新的网页播放签名）再原地重连；IPTV 无站点签名，复用播放页自动重连。旧媒体节点的 `ended` 仅在其 generation 仍为当前会话时有效。
- **自动恢复不再整窗重载**（`renewToken`）：续期与同线路重试只要求「重新打开传输」，不再递增 `reloadToken`；换到另一条线路时来源 key 变化，本来就走软切换。播放器因此在同一媒体元素与适配器上重开本机代理并重连（HLS 重设 `src`，FLV/MPEG-TS 重建 `mpegts.js` 传输层），画面不重建、`<video>` 不换节点、音量不变。只有协议变化（例如 FLV→HLS）、软切换关闭、或原地重连失败（抛错 / 12 秒内未就绪）才自增 `softFallbackToken` / 走 `reloadToken` 完整重建。手动点「刷新」仍按用户意图完整重建。签名地址常常原样返回，因此续期信号必须独立于 `playUrlKey`：同一条 `playUrl` 也允许强制重连。续期发生在用户已暂停时只重建传输，不自动起播。

### 7.1 音量记忆

音量与静音是设备本地记忆，键为 localStorage `rlive-player-volume`，值只有 `{ volume: 0-100 整数, muted: boolean }`，纯函数与读写封装在 `src/shared/playerVolume.ts`。

- 直播页（`PlayerPane`）、IPTV 播放页、视频播放页与录制回放共享同一份：初值取 `readPlayerVolume()`（无记录或记录损坏时回落 `DEFAULT_PLAYER_VOLUME = 80` 且不静音），音量/静音状态变化写 `rememberPlayerVolume()`。同值不触发重渲染，一次拖动最多写它经过的档位数，不需要节流。
- 存 localStorage 而不是 SQLite `settings_kv`：拖一次滑块会经过多个档位，每档都读改写单键 JSON 太重；与线路记忆同一条设备本地约定。
- 不参与的两处：多画面按槽位各存一份（副画面默认静音是角色语义，见第 4 节）；Android 的真实音量是系统媒体音量（`AudioManager.STREAM_MUSIC`，由 OS 记住），网页层固定 100 且既不读也不写这份记忆，否则会把 100 写进桌面端的记忆。
- 越界、非数值或坏 JSON 一律回落默认值：坏记录不该把播放器锁在静音或爆音上。localStorage 不可用（隐私模式、配额耗尽）时静默失败。

### 7.2 自动播放策略

直播、IPTV、视频、短视频与卡片预览共用 `requestPlayerAutoplay`，不在代理生命周期队列中等待 `play()`：

- 首次按现有音量/静音状态起播；只有 `NotAllowedError` 且尚未静音时降级为静音，立即同步 UI，成功后也保持静音，等用户手动恢复声音。不再用定时器自动解除静音，避免再次被浏览器暂停。
- 适配器初始化的 `load()` 可能中断首次 `play()`；`AbortError` 最多按原音量重试一次。网络、解码和不支持的来源不触发静音重试，继续由媒体错误管线处理。
- Android 系统音量桥启用时，界面同时反映 WebView 的静音降级；用户点取消静音或调整音量后恢复 WebView 单位增益，再由系统音量决定声音，避免系统有音量但媒体仍静音。
- 每次尝试及异步完成都核对会话与用户暂停意图，离开页面或已暂停后不重试、不调用旧回调。即使静音也可能被浏览器拦截，手动播放入口必须保留。

回归：`tests/player-autoplay.test.ts`；Windows 主窗口验证真实 HLS 经 Rust 代理出帧、软切源、PiP 拒绝处理及卸载清理。DASH 槽位的同 URL / 同缓冲模式更新是空操作，避免重复 `sourcechange` 或误清暂停调度状态；见 `tests/shorts-dash-buffer.test.ts`。

## 8. 软切换

软切换是正式支持且默认开启的能力：HLS、MPEG-TS、FLV 的同协议播放源变化优先保留 Video.js 媒体适配器与 `<video>`；关闭时任何变化都停止旧代理并完整重建。HLS 由适配器重新加载源，MPEG-TS / FLV 重建 `mpegts.js` 传输层并复用同一媒体元素；硬切换始终作为兼容性回退。

```text
目标源变化 / 续期信号
  |-- 房间变化 / 协议插件变化 / 无活动播放器 ------> 硬重建
  |-- 语义 key 未变化且无续期信号 -----------------> 保持当前播放
  `-- 同一协议插件且（key 变化或收到续期信号）
        |-- 新代理启动失败 --------------------> 硬回退
  |-- Video.js `switchSource` 不可用 ----------> 硬回退
  |-- HLS/MPEG-TS 适配器切源成功 -------------> 提交新活动源
  |-- FLV `mpegts.js` 传输层重建并就绪 --------> 提交新活动源
  `-- `switchSource` 抛错 ---------------------> 硬回退
```

- 先以同一 `session_id` 准备新代理，再调用 `switchSource`；成功后才更新活动源 key。抛错或 12 秒内未进入可播放状态都递增硬回退 token，触发完整重建。快速连续切换用 sequence 取消过期操作。
- 续期信号（`renewToken`）与来源 key 解耦：同一 `session_id` 下代理会以新端口重建，媒体元素不动，因此「签名没变但连接已失效」也能原地恢复。续期序号在处理时立即记账，避免重渲染或重复发布把同一次续期重放成多次重连。
- 质量或线路查询短暂没有 URL 时，同一房间保留当前有效源，避免元数据空窗制造黑帧。异步创建期间目标源再变化会重新触发资格判断。
 - FLV 切换期间旧 `mpegts.js` 实例销毁产生的迟到 `loading_complete` 不计入故障，传输错误仍上报。跨适配器变化始终硬切换。

不同 CDN 的时间戳连续性、关键帧间隔和 MSE 状态并不一致，因此正式路径仍以自动硬回退保证兼容性；本地样本通过不等于所有 CDN 兼容，持续验收要比较真实平台的黑帧、首帧、错误率与重缓冲。

### 8.1 卡片悬停预览

浏览页卡片走独立轻量路径，不复用房间播放器的 hook，只共享取流契约（同一批 `site_get_room_detail` / `site_get_play_qualities` / `site_get_play_urls` 查询键与缓存策略、同一 `stream_proxy` 会话协议、Video.js 适配器的惰性加载与销毁封装）。`roomCardPreview.ts` 只导出纯策略函数与一个会话工厂：

- 画质固定 `pickDefaultQualityIndex(length, "low")`，线路取 `rankPlaybackSourceIndices` 首位；不探测、不写线路记忆、不参与故障转移。
- 全局最多一个会话，创建与释放共用同一条 `createSerialTaskQueue()`；会话 id 前缀 `room-card-preview:<serial>`，与房间播放器代理会话隔离。
- 缓冲刻意收紧：禁用 stash、`autoCleanup` 窗口 3–6 秒、HLS 开启 `capLevelToPlayerSize` 且 `startLevel: 0`。起播复用 `requestPlayerAutoplay`，预览始终静音，初始化中断重试也不解除静音。
- 任何失败（未开播、无画质、无线路、代理不可用、插件错误、首帧 12 秒未到）都静默回到封面并停止代理，不提示、不重试。
- `useRoomCardPreview.ts` 只在 `pointerType === "mouse"`、非移动端、`(hover: hover) and (pointer: fine)`、系统未开启减少动态效果时起用，并要求停留 600 ms。`<video>` 挂在封面内 `pointer-events: none` 的绝对定位节点里、位于渐变遮罩之下，因此命中区不变。

## 9. 画面弹幕与手势的播放侧契约

`DanmakuRenderer` 是直播与 VOD 共用的画面弹幕渲染器，底层是 `danmu`（imtaotao）的 DOM 引擎：直播由事件流调用 `emit` 直接投放，VOD 由渲染器自己的 `requestAnimationFrame` 读 `currentTime` 推进时间轴与游标（`danmu` 不绑定媒体）。渲染器提供 `setComments`、`appendComments`、`pin`、`unpin`、`clear`、`resize`、`setSpeed`、`setArea`、`setLaneHeight` 和 `destroy` 等公共方法；`danmu` 负责轨道分配、每条弹幕自己的 CSS transition 位移（在合成器上推进，主线程不再逐帧写 `transform`）、暂停/缓冲冻结与到期销毁。应用不另建动画时间轴、不做漂移校时。平台内容不写入 `innerHTML`，富文本只用 `createTextNode` 与白名单校验的 B 站 HTTPS 图片构造。

**分工原则：能用原生 API 就用原生 API，只有原生确实做不到的才自建。** `danmu` 负责两层 `Manager`（滚动层限制在用户设置的显示区域内，固定层占满舞台）、轨道分配与 `adaptive` 碰撞预测、`push`/`pushFlexibleDanmaku`/`freeze`/`unfreeze`/`clear`/`format`/`setSpeed`/`setRate`/`setArea`/`setTrackHeight`、生命周期钩子（`$createNode`/`$appendNode`/`$moved`/`$destroyed`/`limitWarning`）。下列能力原生没有，由渲染器补齐；每条都有明确边界，改前先看「原生为何做不到」一栏，不要当成重复实现删掉。碰撞检测档位不再开放：库的 `mode` 固定为 `strict`、`distribution` 固定为 `random`，两者都在 `danmakuRenderer.ts` 里写成常量：

| 自建能力 | 原生为何做不到 |
| --- | --- |
| 时间轴与游标（`setComments`/`appendComments`） | `danmu` 不绑定媒体，没有「按 `currentTime` 投放到第几条」的概念；媒体时间推进、暂停/缓冲/seek 与倍速都由本文件驱动 |
| 车道占用表（`LanePool`） | 原生轨道只能表达「整条车道空闲/占用」，无法表达固定弹幕（不参与轨道调度）与占两条车道的大表情滚动弹幕；大表情还要 `lock()` 对应轨道，让同层普通弹幕避开。`lock()` 只拦后来者，车道里已在途的普通弹幕尾部可能还在舞台外，因此大表情先锁住等待最短的一段车道，等其中普通弹幕尾部全部进屏（`laneEntryWaitMs`，与库 `_getTrack` 同一判据）再投放，等待超过 5 秒即丢弃 |
| 固定弹幕几何 | 固定弹幕走 `pushFlexibleDanmaku` + `direction: 'none'`，居中 x 与车道 y 由 `position` 回调给出，原生不提供「顶部/底部固定」这一档 |
| 样式应用与清理 | 原生的 `setStyle` 写的是库自己的包裹节点（`danmaku.node`）且只有全局一份，而业务样式要逐条落在 `render()` 产出的子元素上（SC 六档配色、普通弹幕取 `event.color`、大表情按 `trackSpan` 改高度），因此逐条应用必须自建。清理靠约定而非 `removeProperty`：样式构造器总是给出完整键集，条件键（`WebkitTextStroke`/`paintOrder`）在无描边时取空串，按 CSSOM 语义等同删除 |
| 直播待投队列（`pendingQueue.ts`） | 原生没有「舞台不可用先暂存」的概念：零尺寸时容器没有轨道（`_getTrack` 在 `rows === 0` 时返回 `null`），事件只能被丢弃；库自身的 `limits.stash` 也接不住这段窗口，因为渲染器实例尚未建立（`loadDanmakuRenderer()` 异步加载引擎），没有可投的 `Manager`。且库的 stash 只有条数上限、没有时间语义，尺寸恢复后会把堆积的陈旧弹幕一次性倒出，因此「超过 5 秒即弃」由本模块表达 |
| 录制回放 canvas（`RecordedDanmakuCanvas`） | 需要与 ASS 导出器同规则、整段预排轨、双向 seek 稳定、按「已发生」计数的重复合并；原生是在线贪心分配，轨道结果依赖播放路径 |

关闭弹幕走 CSS 而不调 `renderer.clear()`：清屏会连同在途弹幕一起销毁，与「关掉再打开看到的还是同一批在途弹幕」的语义不符。直播与 VOD 一致：容器切 `data-visible` 到 `opacity: 0` 并禁用全部后代命中，渲染器实例、事件订阅与在途弹幕照常运行；因此直播侧的挂载条件不含「关闭弹幕」开关（`PlayerPane` 只按 `showHost && !audioOnly` 挂载），关弹幕后恢复看到的是隐藏期间仍在飘动的那批弹幕，而不是从恢复时刻重新开始。

**SC 不走自建路径。** 醒目留言就是一条普通的顶部固定弹幕：`mode: "top"`、`duration` 取平台下发的持续时长，到期、钉住顺延、缓冲冻结全部由库的 `moveTimer` 负责，同屏条数由固定层车道数自然限制（不再有「最多 3 条」的自建上限）。应用侧只保留重连去重（`superChatDedupeKey` + 有界键集合）与展示层差异（金额分档配色、`【SC】` 前缀、整颗节点可点选）。**因此渲染器不提供单条移除**：原生只有整屏 `clear()` 与实例级 `destroy()`，而删掉「SC 到期」「SC 超限淘汰」「屏蔽用户追溯移除」这三个调用点后已无调用方。将来若 VOD 需要按 id 撤下未投放的条目，得重新实现（含「已受理未上屏」的墓碑记账）。

渲染器补齐的边界行为（`danmakuRenderer.ts`）：

- **单条钉住**：`pin` 调用原生 `danmaku.pause()`（`paused` 为 true 才算成功），DOM 与当前位置原样保留；`unpin` 走 `resume()`，按剩余时长继续（固定弹幕的 `moveTimer` 同时顺延），不会立即消失。`seeking` 照常清掉钉住的弹幕。
- **固定弹幕**：`direction: 'none'` 由原生 `setTimeout(actualDuration())` 到期，暂停/释放自动顺延。因此 SC 与用户自己发送的弹幕在**暂停播放、缓冲、被钉住**时都不会继续倒计时，恢复后按剩余时长退出。
- **改速/改区域/改尺寸**：`setSpeed` 只改后续新弹幕（原生 `setSpeed` 不追溯在途弹幕）；`setArea`/`setLaneHeight` 触发 `format()` 重建轨道，大表情（含等待进入的）按原车道重占，占不到即丢弃，固定弹幕按新几何重新落位，滚动弹幕位置由 transition 推进、不回写。
- **倍速**：`setRate(playbackRate)` 交给原生 `actualDuration() = duration / rate`，在途与新建弹幕共用同一倍速语义，不需要逐条改写。
- **投放摊帧**：单帧最多投放 `MAX_PUSH_PER_FRAME` 条，批量注入不会在单帧建上百个节点。
- **饱和时延后不叠放**：应用侧不再按车道容量卡住新弹幕（原 `scrollCapacity` 已移除），碰撞检测档位也已固定为库的 `strict`：车道不满足准入时由库留在待投队列等空位，上界 `limits.stash`（`MAX_STASHED = 256`），高密度房间表现为延迟而不是叠字。轨道分配固定 `random`，同屏弹幕在可用轨道间散开。
- **结算唯一**：`live` 集合保证每条受理过的弹幕恰好回调一次 `onDetach`（库丢弃、清屏、`destroy` 都经过 `onDestroyed`），调用方的记录表才不会泄漏。屏蔽用户与关闭「显示醒目留言」都只过滤新到达的事件，不追溯撤下已上屏的弹幕，因此调用方没有「主动移除」这条路径。


实机验证方式见[开发指南](开发指南.md#真实主窗口验证)。原 JS 弹幕夹具已移除；本节行为契约仍需覆盖暂停/缓冲、改速不清屏、seek、单条 pin 与到期清理。性能历史数据见[弹幕性能实测](弹幕性能实测.md)，不作为当前性能保证。

移动端手势：`12 px` 纵向意图阈值加方向锁定，左右半区分别固定为亮度与音量，按完整画面高度映射 0–100 连续浮点值。Android 亮度经 Tauri 命令写 `Activity.window.attributes.screenBrightness`，从不写 `Settings.System`，离开房间或进入后台时等在途写入完成后恢复原值；没有原生桥的 iOS / 移动浏览器改用合成层黑色遮罩。Android 音量统一走原生 `AudioManager.setStreamVolume(STREAM_MUSIC, …)`，前端以 `50 ms` 窗口合并输入并与亮度共用同一异步串行队列，WebView 媒体元素保持 `100%` 增益避免叠乘；非 Android 移动端直接写 `<video>.volume` / `.muted`，桌面多画面保留各路独立音量。

**点播侧栏横滑与占比拖动**（移动端）复用同一套 `useHorizontalSwipe({ layout: "track" })`：页签内容常驻同一条带，条带按选中项整体平移，`items` 传实际可见页签而非全集（PGC、单 P、无弹幕数据下多传一项就整体错位）。这里有三条已由真机缺陷换来的不变量：

1. **`touch-pan-y` 必须写在滚动容器自己身上**，不能只靠 `Tabs` 外壳那一层。Chromium 用命中元素所在的**最近滚动容器**决定手势归属，容器为默认 `touch-action: auto` 时横向拖动被合成器当作滚动接走，第一次 `pointermove` 之后就派发 `pointercancel`，手势永远攒不到 `12 px` 锁定阈值——表现为「侧栏怎么滑都不切页签」。侧栏内每个纵向滚动容器（评论回复、分集、合集、选集、弹幕列表、页签面板）因此都自己声明它。合成 `PointerEvent` 不经合成器，这类问题需在真实触摸环境验证。
2. **条带视口用 `overflow-clip` 而不是 `overflow-hidden`**。`hidden` 仍是滚动容器（只是不给滚动条），`scrollIntoView` 照样能滚它：条带宽 `n × 100%`，非活动面板横向偏出视口，面板里任何 `scrollIntoView`（合集/选集定位当前项）都会让浏览器横向滚动视口去「露出」那个偏移过的面板，条带停在页签之间，**显示的面板与选中的页签脱同步**。`clip` 不建立滚动容器，这条不变量由布局本身保证，不依赖每个面板记得自我约束。
3. **面板内的定位滚动必须受 `active` 把关，并只滚自己的列表**。合集、选集和分集移到「相关视频」的信息卡下后，使用有界的独立滚动列表，当前项定位只写列表的 `scrollTop`，不调用会连带移动信息卡、页签或舞台祖先的 `scrollIntoView`。后台页签不做定位。弹幕列表同样只写自己的 `viewport.scrollTop`（目标位置夹紧到可滚区间后回读，见 `videoDanmakuFollow.ts`）。

**点播侧栏自适应占比**（移动端，`useDetailsResize` + `detailsResize.ts`）：仅已知非 16:9 视频启用（容忍 1% 编码取整误差），未知画幅、16:9 与仅音频保持默认布局。Tab 栏不再是抓手，只有页签内容视口绑定调整手势。契约：

- **上滑先扩大侧栏，下滑先回顶部**：`detailsContentScrollStep` 分配占比与滚动位移；上滑到侧栏上限后余量滚动命中内容，下滑先消耗滚动链的 `scrollTop`，到顶部才缩小侧栏。边界反向立即响应，短内容也可调整。原生非 passive `touchmove` 仅在需要改变占比时阻止默认行为；已进入原生滚动的不可取消事件不抢回，保留惯性，下一次在顶部下滑可恢复画面空间。横向锁定仍交给 `useHorizontalSwipe`，Tab 栏只切换页签；输入框、滑块、开关、弹层不参与，多指输入结束本轮调整。
- **布局只由一个自定义属性表达**：`--vod-details-share` 是侧栏占主区域高度的百分比，以 `@property` 注册为 **不继承的 `<percentage>`**。拖动后由主容器的两行网格消费：舞台占 `calc(100% - var(--vod-details-share))`，侧栏填满余量，因此总和始终为 100%，变量也不会逐帧传播到播放器、评论和所有后台页签，引发整棵子树重算样式。舞台封顶与画幅比只在**拖动开始后**让位（`data-vod-details-resizing` / `data-vod-details-share`）：未拖动时舞台仍按画幅比撑高、最高 70%；宽屏并排或网页全屏移除侧栏时仍走原有 flex 布局。不支持 `@property` 的旧 WebView 可继续拖动，但没有非继承带来的样式隔离收益。
- **拖动逐帧只写 CSS 变量与 `data-*`，不进 React 状态**。会触发布局的占比预览用单个 `requestAnimationFrame` 合并同帧指针事件，只消费最新位置；值或标记未变化时不重复写 DOM。释放/取消时撤掉待执行帧，最终位置同步落位，再交给 React 状态保存；禁用/卸载通过回调 ref 清理监听器与预览，不留下实时标记；已存占比在全屏、宽屏或 16:9 下不应用，切视频或分 P 按 `videoKey` 隔离。横向翻页仍直接写 transform，不套这层合帧。`data-vod-details-resizing` 只由手势写、`clearDetailsResizing` 清；`--vod-details-share` 拖动期间由手势写，松手提交后由 React 接管，避免播放进度触发的普通重渲染干扰跟手。
- **零滚动位移不触碰滚动位置**：`scrollDetailsContent`（`src/shared/gestures/detailsScroll.ts`）在 `|delta| < 1e-9`（含浮点尾差）时直接返回 `0`，不读写 `scrollTop`，避免纯占比布局帧因无效滚动操作额外结算布局。非零位移仍按内外滚动链消费并返回实际滚动量，惯性 `stalled` 判定复用该返回值，去掉滚动后的重复全链回读；分配前所需的边界读取、嵌套滚动余量与 RAF 合帧保持不变。回归见 `tests/details-scroll.test.ts`。
- **动态双向边界**：下限由 `detailsShareMinPercent(width, height, aspectRatio)` 按原始舞台高度 `min(width / aspectRatio, height × 70%)` 的补集计算，不再固定为 `20%`。下滑恢复原始画幅布局后硬停，重复滑动也不能继续扩大舞台。上限仍由保留满宽 16:9 窗口解出（401×757 约 `70.2%`），放不下时回退 `85%`；上限不得低于原始布局下限。21:9 等宽画幅的区间可以收为原始占比一个点；极宽画幅的合法原始占比即使超过 `85%` 也保留，CSS 序列化与提交只做 `[0,100]` 物理收口，不再次套兜底界限。起点按侧栏真实高度量取，首次拖动不跳变；只在本页有效、不落盘。
- **手势中按下时快照边界**：上限保住 `max(起点, 原始布局下限, 16:9 约束)`，防止默认宽画幅在第一帧突变；下限必须由源画幅推导，不能采用每次手势起点，否则上滑松手后无法完整恢复。
- **容器尺寸或画幅改变要重算上下限**：`ResizeObserver` 监听旋转、分屏和浏览器栏变化，画幅变化同步重算；已调整过的占比经 `onClamp` 收回新范围。变化发生在手势中时，立即结束旧手势再收口，旧触摸后续事件不能按旧尺寸覆盖新布局；没有调整过的默认布局交给 CSS。
- **监听器不按 `enabled` 绑定，是否接管逐帧看**：首次进入播放页时画幅要等媒体报出 `videoWidth/videoHeight` 才可知，而手指可能先于它按下。从前 `bindContent` 在 `enabled` 为假时直接返回，这一整次拖动会在启用那一刻被丢掉 —— 正是「首次进入视频页，侧栏自适应高度有时不触发」的根因。现在按压与调整分成两份状态：`ResizePress` 只记与布局无关的东西（触摸身份、起点、滚动链），`ResizeState` 在真正接管时才现场量布局。接管那一帧的位移取「当前减上一次已派发位置」的增量，不追溯按下以来的总位移（那段跨过了画幅到位引起的布局变化，算进来会让第一帧跳一下）。禁用时只丢调整状态、保留未接管的按压，因此一次按住跨越「禁用→启用」还能接着用。
- **锁定距离内必须先 `preventDefault` 才能赢得手势归属**：合成器按**第一个 `touchmove` 是否被阻止默认行为**决定这次触摸归谁。锁定距离是 `10px`，与合成器的触摸 slop 同量级（真机实测首帧 9px 就已判给原生滚动），而手指逐帧位移常常只有 3~4px —— 等攒够 `10px` 时后续事件早已被标成 `cancelable === false`，`!event.cancelable` 把整次拖动当成原生滚动丢掉。真机表现为「切换侧栏页签或点开信息卡标题后，第一次滑动不改变侧栏高度」，只有首帧位移就 ≥10px 的大跨度滑动才正常，这也解释了为什么该缺陷只在这两个入口后稳定复现（页签切换与信息卡展开都会让上一次布局变更落在首帧前）。修复在 `claimPendingMove`：意图仍为 `pending` 时，只要纵向占优、已启用调整、且这一步按 `detailsContentScrollStep` **真能**改变布局，就当场 `preventDefault`；既不预览也不提交，激活仍在 `10px` 轴锁处。到边界、下滑要先滚回内容顶部、未启用（画幅未知、16:9、全屏、并排）时照旧不拦，保留原生滚动与惯性。`preventDefault` 只作用于 `touchmove`，不吞 click，也不影响页签横滑用的 PointerEvent。
- **认领门槛用像素而不是百分比**（`detailsResizeStepIsVisible`）：占比由侧栏真实高度反算，而容器高度只有 `clientHeight` 的整数精度，边界处会留下约 `0.04%` 的测量偏差。在上限处直接比较百分比会把这个偏差读成「还能再拖」，于是每次到达上限都恰好抢走原生滚动与惯性（真机实测上限处首个 `touchmove` 仍被 `preventDefault`）。因此「这一步是否值得认领」按 `|Δ占比| / 100 × 容器高 ≥ 1px` 判定，未接管的手势也套用同一门槛。
- **松手后的惯性**（`detailsResizeVelocity` + `detailsMomentumStep`）：快速甩动侧栏后继续推进一段再停下，不会硬停在抬手位置。速度取最近 `100ms` 内采样的位移（px/ms，向上为负），跨度不足 `16ms` 或采样少于两条时读作 `0`（1px 的坐标取整会放大成极大速度，宁可少接一次）。启动阈值 `0.3px/ms`（约 300px/s），低于它视为「停下来」；速度按 `τ = 325ms` 的指数衰减，单帧参与衰减的时长夹在 `64ms`（后台页签恢复、长任务后的 `dt` 可上百毫秒，不夹住会一帧走完），低于 `0.02px/ms` 停下。位移是速度在该段时间上的积分（`v₀·τ·(1 - e^(-dt/τ))`，总位移收敛于 `v₀·τ`），因此渐停而不是硬停。惯性复用 `detailsContentScrollStep` 的同一套分配规则（先滚内容、到顶再缩侧栏），不会绕开边界；只有真正拖过占比的手势接惯性，只滚了一段内容、刚认领就抬起、慢速松手以及 `touchcancel` 都不接。惯性期间再次按下立即停住并把当时的位置提交出去（新手势从该位置接着走，不会弹回甩出前的起点），同时重新拉长点击抑制 `420ms`，避免抬起后的第一下点按落在刚被甩过去的内容上。几何变化（旋转、分屏、画幅变化）与禁用、卸载只清状态不提交 —— 那些情况下宿主自己会按新边界收口。惯性刻意留在手势模块里，不进 `src/shared/motion/`：它写的是布局占比而不是可交给合成器的位移，也要与拖动共用同一套位移分配。
- 自适应手势只在侧栏列在舞台**下方**时启用（`STACKED_DETAILS_QUERY`，与样式表那条 `@media (width < 64rem)` 同源）。宽屏两者并排，上下拖动不改任何布局；若改用 `compact` 判定，1024px 以上的平板横屏会「手势开着但拖不动」。

交互验证包括惯性（快速上滑后逐帧推进并渐停提交、慢速松手不接惯性、惯性期间再按下立即停住并从该位置继续），并逐帧模拟「按下 → 画幅到位 → 继续移动 → 抬起」，断言启用后的首个 `touchmove` 当场接管、接管帧不追溯总位移、跨越启用的手势正常提交；同时验证锁定距离内的认领契约（能改占比时返回 `defaultPrevented`、横向占优与下滑回顶部时不拦、不预览不提交）。合成事件不经合成器，`cancelable` 那条路径只能在真机验证：Android WebView 上以 3px 步长在「评论」页签与信息卡标题后各滑一次，均应改变占比（修复前两次都完全不动）。
回归：`tests/details-resize.test.ts` 验证画幅资格、位移分配、锁轴、边界与反向响应、认领门槛的像素换算，以及速度采样窗口、惯性积分与衰减（总位移收敛到 `v₀·τ`、单帧时长夹紧、启动/停止阈值的滞回）。滚动容器的 `touch-pan-y`、条带的 `overflow-clip` 和 Tab 抓手移除仍是布局约束。真实 Shell/播放页需验证未知/16:9 禁用、非 16:9 内容调整、原始画幅硬停（含 4:3、21:9 和极宽画幅）、Tab 不调整、在线人数位置与会话重置。

侧栏与控制栏布局验证：在真实主窗口检查信息卡下的选集/合集/分集、局部定位滚动、队列导航、固定发送区，以及可见 Tab 增减后选中值不变但索引改变的重新停靠。320px/401px 竖屏下检查上下按钮与图标尺寸、主行进度条不越界且高度与命中区可用，以及进入/退出全屏时发送框位置恢复。

性能验证：真实主窗口检查同帧合并、变量不继承、总高度守恒、释放/取消/禁用/卸载清理；对真实 VOD 记录帧间隔、样式重算与布局耗时，固定评论规模和采样帧数，结束后恢复视口和内联布局。耗时依赖设备与当前页面，不写死 FPS 门槛。帧间隔还受系统刷新率影响，模拟器结果不能代表真机；上述优化描述实现边界，不作为已达成某一帧率的结论。

## 10. 代理遥测边界

前端不做周期性播放采样；唯一的遥测是 Rust 本机代理按会话聚合的计数，通过 `stream_proxy_telemetry` 按需读取。当前没有上传、SQLite 持久化或远程聚合。

| 指标 | 来源 |
|------|------|
| 代理请求 / 失败 / 字节、首次与最近响应耗时 | Rust 原子计数与请求计时 |
| `first_media_at_ms` | Rust 锁存首个媒体字节，供 FLV/TS 时钟同步做壁钟锚点 |

代理遥测接口只在请求方仍持有活动 `session_id` 时返回聚合计数，结构中不存在 URL 与 headers。若未来增加导出，必须由用户显式触发并在序列化层再次建立字段白名单。

Linux 桌面端和 WSL2 下 WebKitGTK 通过 GStreamer 提供 MSE 的 H.264/AAC 解码。出现「当前环境不支持 MSE 直播播放」时先安装完整 GStreamer 插件集（`gstreamer1.0-plugins-base` / `-good` / `-bad` / `-ugly`、`gstreamer1.0-libav`、`gstreamer1.0-tools`），再用 `gst-inspect-1.0 avdec_h264`（以及 `openh264dec`、`avdec_aac`）确认解码器已注册，然后重启 rLive；仍未识别时删除 `~/.cache/gstreamer-1.0/registry.x86_64.bin` 重建缓存。AppImage 还要确保 `GST_PLUGIN_SYSTEM_PATH_1_0` 指向的目录包含对应插件。其他环境准备见 [开发指南](开发指南.md)。

性能改动遵循先分层定位、再单变量实验：用 `startup_ms` 与代理响应耗时区分上游慢 / 代理慢 / 播放器初始化慢；用缓冲量、live latency 与重缓冲时长判断延迟参数是否过于激进；用丢帧率、分辨率与 Long Task 判断解码压力和主线程竞争。比较必须分平台、协议、清晰度与硬/软切换模式，覆盖稳定网络、抖动网络、1080p/60fps 与高弹幕量，且只在首帧、每分钟重缓冲、错误率、丢帧率和直播延迟都没有明显退化时保留优化。不建议仅因「原生实现可能更快」就切换到 FFmpeg、libmpv、GStreamer、VLC 或 WebCodecs：它们会引入原生窗口/纹理合成、编解码器分发、许可证、A/V 同步和弹幕叠层重做，只有 profile 证明当前 transmux 或 WebView 路径是主瓶颈时才值得扩大范围。
