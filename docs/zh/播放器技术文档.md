# 播放器技术文档

更新时间：2026-08-07。本文描述 rLive 当前播放器的实际架构、播放源契约、线路探测、故障转移、软切换和性能改进方法。它是实现说明，不是播放器方案选型记录。

## 1. 设计目标

播放器需要同时满足以下约束：

- Bilibili、Huya、Douyu、Douyin、Twitch 和 IPTV 共用 Web 播放链；
- 上游需要的 `Referer`、Cookie 和其他请求头只交给 Rust 代理，不暴露给媒体插件；
- FLV、HLS、MPEG-TS 和浏览器原生媒体按结构化协议选择插件；
- 多线路先探测再排序，播放成功后不因后台测速更快而无故中断；
- 同协议换源默认尝试保留播放器，任何异常都回退到完整重建；
- 性能数据只在设备内存中用于诊断，不上传、不持久化，也不记录播放地址和请求头。

当前仍由 WebView2 / Chromium 的 `<video>` 和 MediaSource 完成媒体解码与呈现。Rust 负责站点解析、代理和测量，不在播放主路径中进行视频解码。

## 2. 分层架构

```text
站点适配器 / M3U 解析器
  -> LivePlayQuality + PlayUrl[]
  -> usePlaybackController
       -> stream_proxy_probe_sources
       -> 智能排序、手动选择、故障转移
  -> useWebPlayer / IptvPlayer
       -> stream_proxy_start
       -> xgplayer + 协议插件
       -> HTMLVideoElement / MediaSource
  -> React 控制层、Canvas 弹幕、SC、字幕
       -> 本地播放遥测快照
```

| 层 | 主要文件 | 职责 |
|----|----------|------|
| 播放源模型 | `src-tauri/src/models/live.rs`、`src/shared/types/live.ts` | 定义结构化协议和线路元数据 |
| 站点适配 | `src-tauri/src/sites/` | 获取清晰度、播放地址、请求头和平台优先级 |
| 线路控制 | `src/features/room/playback/usePlaybackController.ts` | 探测、排序、选择、重试和故障转移 |
| 选线策略 | `src/features/room/playback/sourceSelection.ts` | 可测试的纯排序与选线函数 |
| 播放生命周期 | `src/features/room/player/useWebPlayer.ts` | 代理会话、xgplayer、软切换和硬回退 |
| IPTV 播放 | `src/features/iptv/IptvPlayer.tsx` | HLS、FLV、裸 MPEG-TS 和原生媒体 |
| 本机代理 | `src-tauri/src/stream_proxy.rs` | 请求头注入、HLS 改写、线路探测和代理计数 |
| 本地遥测 | `src/features/room/player/playbackTelemetry.ts` | 媒体、主线程和代理指标的内存快照 |

前后端只通过 Tauri commands 交换播放数据。前端不复制站点签名或上游业务逻辑，媒体插件也只访问 `127.0.0.1` 上当前代理会话返回的地址。

## 3. 结构化播放源

`PlayUrl` 不再只表示 URL，而是一个可排序、可展示、可测量的播放候选：

```ts
type PlayUrl = {
  source_id?: string;
  label?: string;
  protocol?: "flv" | "hls" | "mpeg_ts" | "native" | "unknown";
  priority?: number;
  url: string;
  headers: Record<string, string>;
};
```

| 字段 | 规则 |
|------|------|
| `source_id` | 在一次清晰度结果内稳定，不包含签名 URL、Cookie 或请求头 |
| `label` | 可直接展示的安全线路名称，不展示 CDN 域名 |
| `protocol` | 由站点或 M3U 解析器显式给出；旧数据为 `unknown` 时才根据 URL 回退推断 |
| `priority` | 数值越小越接近平台原始首选顺序，仅在健康状态和延迟相同时作为稳定排序依据 |
| `url` / `headers` | 仅供本机代理请求上游，不能进入遥测快照或错误展示 |

Bilibili、Huya、Douyu、Douyin 和 Twitch 的站点实现均返回结构化线路。IPTV 解析器也写入 `protocol`，前端仅对旧缓存或不透明地址使用兼容推断。

协议到播放实现的映射如下：

| 结构化协议 | xgplayer 路径 | 备注 |
|------------|---------------|------|
| `flv` | `xgplayer-mpegts.js` 兼容插件，`mediaDataSource.type = "flv"` | 连续 HTTP-FLV、低延迟 MSE；复用经过斗鱼、虎牙验证的 `mpegts.js` 解封装路径 |
| `hls` | `xgplayer-hls.js` / `hls.js` | 所有站点统一由 hls.js 解析清单、加载分片并转封装；代理改写主/子清单、密钥和分片 |
| `mpeg_ts` | `xgplayer-mpegts.js` 兼容插件 | 用于裸 MPEG-TS，不等同于 HLS 内的 `.ts` 分片 |
| `native` | xgplayer 核心 + `<video>` | MP4、WebM 等浏览器原生媒体 |
| `unknown` | URL 兼容推断，最终默认 FLV | 只为旧后端和不完整数据保留 |

播放源的语义 key 同时包含 URL、排序后的 headers、`source_id`、`label`、`protocol` 和 `priority`。等价对象不会重建播放器，任一实际路由信息变化都会被识别。该 key 只存在于当前 WebView 内存，不进入诊断快照。

## 4. 代理生命周期

`stream_proxy` 是应用级单活动代理。每个播放器实例生成不可复用的实例 ID，每次完整打开再增加 generation，组合为代理 `session_id`。

代理启动遵循以下顺序：

1. 为新请求预留 generation；
2. 构造使用当前应用代理配置的 `reqwest::Client`；
3. 绑定新的 `127.0.0.1` 随机端口并准备 HLS 资源表；
4. 新监听器准备完成后，原子替换旧活动监听器；
5. 将只含 localhost 的播放地址返回前端。

旧路由的异步清理只能停止自己持有的 `session_id`。较旧的 `start` 也会被 generation 栅栏拒绝，因此快速切房、返回同一房间或并发 cleanup 不会误关新代理。

连续 FLV 和 MPEG-TS 按字节流转发。HLS 清单中的相对 URL、子清单、`URI` 属性、密钥和分片会改写到同一 localhost 会话；代理继续携带原始请求头，并转发 Range 与必要响应元数据。

## 5. 线路探测与智能选择

开启「智能线路选择」后，直播房间在取得多条 `PlayUrl` 时调用 `stream_proxy_probe_sources`。该设置默认开启。

探测边界：

- 使用与真实媒体代理相同的应用代理配置和播放请求头；
- 最多接收前 12 路，最多 4 路并发；
- 单路总超时 5 秒，连接超时 3 秒；
- 最多读取首个响应 chunk 的 64 KiB，不下载完整直播；
- 记录 HTTP 状态、媒体首字节耗时、规范化 Content-Type 和采样字节数；
- HLS 必须通过 `#EXTM3U` 检查，FLV 必须以 `FLV` 开头，MPEG-TS 必须符合同步字节；
- HTTP 错误、空响应、HTML 登录/验证页和协议签名不匹配均视为不可用。

探测结果只返回 `source_id`、输入索引、状态和脱敏错误码，不返回 URL、Cookie、Referer、重定向地址或原始网络错误。前端按输入索引关联结果，避免平台重复 `source_id` 导致线路错配。

排序使用稳定的四级比较：

1. 已测可用线路，按 TTFB 从低到高；
2. 未测速线路；
3. 已测不可用线路；
4. 同组再按平台 `priority` 和原始索引。

在首帧出现前可以采用测速胜者。当前线路一旦进入 `playing`，后台地址刷新和更快的测速结果不会单独触发切线；只有当前探测明确失败或播放器报告故障才进入故障转移。线路菜单显示「测速中」「未测速」「可用 / xx ms」或「不可用」。探测 command 不可用时保留平台原始顺序，正常播放不依赖测速成功。

播放器故障时先由协议插件执行有界网络重连，再由控制器按平台预算完整重建播放器：斗鱼、虎牙当前线路最多完整重建一次，其他站点最多两次，随后按健康排序选择尚未耗尽的下一路。同一播放器 generation 在 `750 ms` 内连续上报的 `error` / `eof` 会合并，避免一次故障重复消耗预算。一次 `playing` 只表示已经重新出画面；必须连续稳定播放至少 30 秒，下一次故障才会清除旧预算并作为独立故障重新评估全部线路。

「卡顿自动换线」默认开启并由播放器控制条即时调整。`waiting` / `stalled` 只负责开始观察；当前播放时间连续 8 秒没有推进，且媒体没有暂停、结束、换房或换源时，才向控制器报告持续卡顿。控制器还要求当前线路已经成功出帧且至少存在两条线路，再将当前线路标记为本轮耗尽，并按测速排序选择下一条。任何时间推进、恢复 `playing`、用户暂停或会话清理都会取消计时，因此首帧等待和短暂重缓冲不会误触发。稳定播放达到 30 秒后会重新允许评估先前线路。

连续 FLV / MPEG-TS 的上游连接关闭时，播放器直接监听 `mpegts.js` 的 `loading_complete`，不再等 `<video>` 缓冲耗尽后才收到 `ended`。房间 FLV 会在最多三次的续签预算内重新获取房间详情、清晰度和线路；斗鱼因此会生成新的网页播放签名，再用新 URL 完整重建播放器。IPTV 没有站点签名，收到同一事件后复用播放页的自动重连。旧媒体节点的 `ended` 仅在其 generation 仍是当前会话时有效，避免销毁旧播放器时误触发新会话故障。

## 6. 软切换

「软切换」是正式支持且默认开启的播放能力。启用时，HLS、MPEG-TS 的同协议播放源变化会优先保留 xgplayer、MediaSource 和 `<video>`；关闭时任何播放源变化都会停止旧代理并完整创建新会话。FLV 不参与软切换，不同 CDN 线路和重连始终完整重建播放器，避免复用不连续的时间戳与旧 MediaSource 状态。硬切换路径始终作为兼容性回退。

启用后的状态机：

```text
目标源变化
  |-- 房间变化 / FLV / 协议插件变化 / 无活动播放器 --> 硬重建
  |-- 语义 key 未变化 ------------------------> 保持当前播放
  `-- 同一协议插件且 key 变化
        |-- 新代理启动失败 --------------------> 硬回退
        |-- player.switchURL 不可用 -----------> 硬回退
        |-- switchURL({ seamless: true }) 成功 -> 提交新活动源
        `-- switchURL 抛错 ---------------------> 硬回退
```

质量或线路查询短暂没有 URL 时，同一房间会保留当前有效源，避免元数据空窗先制造黑帧。播放器异步创建期间若目标源再次变化，活动源状态更新会重新触发资格判断，不会把较旧线路静默留在播放器中。

软切换先以同一 `session_id` 准备新代理，再调用 xgplayer `switchURL`。成功后才更新活动源 key；任何失败都会递增硬回退 token，触发完整重建。快速连续切换通过 sequence 取消过期操作。FLV 源变化以及跨 HLS、MPEG-TS 或 native 插件的变化始终硬切换，因为 FLV CDN 时间戳和不同插件的 MSE 状态不可安全复用。

不同 CDN 的时间戳连续性、关键帧间隔和 MSE 状态并不一致，因此正式路径仍以自动硬回退保证兼容性。持续卡顿触发的线路变化也遵循同一资格判断：HLS、MPEG-TS 可尝试软切换，FLV 完整重建。持续验收应比较软切换与硬切换的黑帧、首帧、错误率和重缓冲，而不是只观察一次 `switchURL` 是否成功。

## 7. 本地播放遥测

直播播放器每 2 秒生成一次内存快照，并最多保留最近 120 条。关闭或切换播放会话后旧快照不再更新，并在后续采样时从有界队列淘汰；当前没有上传、SQLite 持久化或远程聚合。

| 指标 | 来源 | 解释 |
|------|------|------|
| `startup_ms` | session 创建到首次 `playing` | 代理启动、插件初始化和首帧的组合耗时 |
| `playing_ms` | `performance.now()` | 首次播放后的会话时长 |
| `waiting_count` / `stalled_count` | `<video>` 事件 | 缓冲不足与网络停滞次数 |
| `rebuffer_ms` | waiting/stalled 到下一次 playing | 累计重缓冲时长 |
| `buffered_seconds` | `buffered.end - currentTime` | 当前前向缓冲量 |
| `live_latency_seconds` | `seekable.end - currentTime` | 浏览器时间轴上的 live edge 距离 |
| 总帧 / 丢帧 | `getVideoPlaybackQuality()` | 解码和渲染压力 |
| 分辨率 | `videoWidth` / `videoHeight` | 当前解码尺寸 |
| Long Task 次数 / 时长 | `PerformanceObserver` | React、Canvas 或其他主线程竞争 |
| 代理请求 / 失败 / 字节 | Rust 原子计数 | 上游请求活动和转发规模 |
| 首次 / 最近响应耗时 | Rust 请求计时 | 代理到上游响应头的耗时 |

快照使用安全的 `source_id`、站点、协议、清晰度和 `hard` / `soft` 模式区分会话。代理遥测接口只在请求方仍持有活动 `session_id` 时返回聚合计数，结构中不存在 URL 和 headers。

当前遥测适合本机开发诊断，还不能直接给出跨设备 P50/P95。若未来增加导出，必须让用户显式触发，并在序列化层再次建立字段白名单；不能直接导出内存对象或代理内部错误。

## 8. 当前性能参数

| 路径 | 关键参数 | 当前值 |
|------|----------|--------|
| 房间 / IPTV HLS | `manifestLoadingMaxRetry` / `levelLoadingMaxRetry` / `fragLoadingMaxRetry` | 3 / 3 / 3 |
| 房间 / IPTV HLS | `backBufferLength` / `maxBufferLength` | 30 s / 30 s |
| 房间 / IPTV HLS | `liveSyncDurationCount` / `liveMaxLatencyDurationCount` | 3 / 6 个分片 |
| 房间 FLV（桌面） | `autoCleanupMaxBackwardDuration` / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 15 s / 1 s / 5 s |
| 房间 FLV（移动） | `autoCleanupMaxBackwardDuration` / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 20 s / 1.5 s / 6 s |
| IPTV FLV | stash / `liveBufferLatencyMinRemain` / `liveBufferLatencyMaxLatency` | 384 KiB / 0.5 s / 3 s |
| MPEG-TS | stash / 延迟追赶 / SourceBuffer 回收 | 开启，初始 stash 384 KiB |
| 遥测 | 采样间隔 / 内存上限 | 2 s / 120 条 |
| 线路探测 | 并发 / 单路上限 / 样本 | 4 / 5 s / 64 KiB |

HLS 和 FLV 均使用 MSE，流媒体内核只保留 `hls.js` 与 `mpegts.js`。FLV 由 `mpegts.js` 渐进解析并转封装为 fMP4，桌面保留 1 秒追帧余量、5 秒最大延迟和 15 秒后向缓冲，移动端对应放宽到 1.5 秒、6 秒和 20 秒；线路变化仍完整重建播放器，避免跨 CDN 时间戳污染 MediaSource。所有 HLS 通过 `xgplayer-hls.js` 使用 `hls.js`，关闭低延迟模式并保留 30 秒前后缓冲窗口；致命错误先使用插件内恢复，重复失败再刷新短时播放元数据，避免无限重放过期 URL。Twitch 仍保留广告等待与解码清晰度降级策略：若 Chromium/WebView 报告 `PIPELINE_ERROR_DECODE`，播放器会销毁当前 MSE 会话并按清晰度从高到低切换到下一个视频变体，跳过 `audio_only`；没有可降级变体时才显示解码失败。

## 9. 性能改进方法

性能改动应遵循“先分层定位，再单变量实验”：

1. 用 `startup_ms` 和代理响应耗时区分上游慢、代理慢与播放器初始化慢；
2. 用缓冲量、live latency 和重缓冲时长判断延迟参数是否过于激进；
3. 用丢帧率、分辨率和 Long Task 判断解码压力与 Canvas / React 主线程竞争；
4. 分平台、协议、清晰度和硬/软切换模式比较，不把不同流混为一组；
5. 至少覆盖稳定网络、抖动网络、1080p/60fps 和高弹幕量场景；
6. 任何优化只在首帧、每分钟重缓冲、错误率、丢帧率和直播延迟没有明显退化时保留。

优先级建议：

| 优先级 | 改进 | 判断依据 |
|--------|------|----------|
| P0 | 完善真实设备遥测查看与可控导出 | 当前已有采样，但缺少本地聚合视图 |
| P0 | Windows WebView2 真机比较软/硬切换 | 验证时间戳连续性和黑帧，而非只测 API 成功 |
| P1 | 按平台实验 `liveSyncDurationCount`、`liveMaxLatencyDurationCount`、`maxBufferLength` | 稳定网络与抖动网络需要不同取舍 |
| P1 | 补充 HLS 清单、Range、短时签名回归样本 | 减少代理兼容问题被误判为播放器问题 |
| P1 | 将 Canvas 帧预算与遥测时间线关联 | 确认高弹幕量是否造成 Long Task / 丢帧 |
| P2 | Profile 证明 JS transmux 为热点后再做 Rust PoC | Rust 或 FFmpeg 不会天然改善浏览器解码 |

不建议仅因“原生实现可能更快”就切换到 FFmpeg、libmpv、GStreamer、VLC 或 WebCodecs。它们会引入原生窗口/纹理合成、编解码器分发、许可证、A/V 同步和弹幕叠层重做。只有 profile 明确证明当前 transmux 或 WebView 路径是主瓶颈，且 PoC 能量化降低 CPU、卡顿或延迟时，才值得扩大范围。

## 10. 测试与验收

当前自动化覆盖：

- 结构化协议、标签、稳定 source key 和重复 `source_id`；
- 健康、未测速、失败线路的排序和故障转移；
- 正常播放后不因较快探测结果切线；
- 软切换的同插件资格与跨协议硬回退条件；
- 本地遥测的首帧、缓冲、帧、live edge 和敏感字段边界；
- 代理会话所有权、待启动取消、替换时保留旧监听器；
- HLS 清单改写、媒体签名检查、HTML 拒绝和应用代理转发。

常用检查：

```bash
bun run check
bun test tests/
cd src-tauri && cargo test --lib
```

自动化不能替代真实 CDN 与 WebView2 验证。软切换、硬件解码、CPU 占用、端到端直播延迟和网络抖动仍需在目标设备上测量。
